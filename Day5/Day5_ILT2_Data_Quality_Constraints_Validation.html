The DQ Scan Pattern

Build one _dq_issue column with a chain of when() conditions in priority order — the first matching rule wins. One pass gives the complete picture of every problem before any fix is applied.

dq_scan_df = bronze_customers.withColumn("_dq_issue",
  when(col("CustomerID").isNull(), lit("NULL_CUSTOMER_ID"))
  .when(~col("Email").rlike(EMAIL_REGEX), lit("INVALID_EMAIL_FORMAT"))
  .when(age_at_registration < 18, lit("REGISTERED_UNDER_18"))
  .otherwise(None)
)

The Real Decision: Fix, Flag, or Quarantine?

OutcomeWhen to use itGlobalMart example
FixCorrect value is knowable/recoverableEmail with a stray space — remove it, customer is real
FlagRow is usable, one field is suspectDelivery-before-ship timezone artifact (below)
QuarantineGenuine rule violation, value not safely guessableCustomer registered under 18

Case study — REGISTERED_UNDER_18 (clean quarantine)

77 customers show age-at-registration under 18 — GlobalMart requires 18+. We can't assume which field is wrong (DOB typo vs. genuinely underage at an unvalidated form), so the row can't be safely fixed. Kept out of Silver; business team decides next steps.

Case study — DELIVERY_BEFORE_SHIP (why over-quarantining is a bug)

First pass compares raw timestamps: 725 orders flagged as "delivered before shipped." Re-running at the date level (stripping the time-of-day noise) drops that to 114 — and every one of those 114 shows exactly a 1-day gap. That consistency is the signal of a systemic cause, not random error.

# Supabase stores UTC; GlobalMart's delivery scanners record IST (UTC+5:30)
Delivered : June 14, 23:45 IST -> stored as June 14
Shipped : June 15, 00:30 IST -> stored as June 15
# Physically shipped before delivered -- only the date LABEL flips
What went wrong the first time: all 114 orders were quarantined outright. Building silver.order_items downstream then orphaned 352 line items whose parent order no longer existed in Silver — silently hiding real revenue/quantity from Gold reports. The defect was confined to two date columns; customer_id, order_channel, and the line items were never in question. The cost of over-quarantining showed up two tables later — that's what makes it dangerous.
Corrected decision: keep all orders, add _data_note = 'POSSIBLE_TIMEZONE_OFFSET_1DAY' on the 114 rows. Fully joinable for revenue; filterable for SLA analysis.

Enforcing Quality at Write Time — Delta Constraints

A DQ scan is a check you remember to run. A Delta constraint is enforced by the table itself — nobody can write a violating row, ever, from any notebook.

TypeSyntaxGlobalMart example
NOT NULLALTER TABLE t ALTER COLUMN c SET NOT NULLcustomer_id, order_id, product_id
CHECKADD CONSTRAINT name CHECK (condition)actual_price_inr > 0, rating BETWEEN 0 AND 5
ALTER TABLE gbmart.silver.products
ADD CONSTRAINT valid_price CHECK (actual_price_inr > 0);

ALTER TABLE gbmart.silver.products
ADD CONSTRAINT valid_rating CHECK (rating BETWEEN 0 AND 5);
A constraint is a backstop, not a replacement for the scan. The scan runs before the write and routes bad rows to quarantine gracefully; a constraint just fails the whole write if violated.

The Quarantine Table Pattern

clean_df = dq_scan_df.filter(col("_dq_issue").isNull())
quarantine_df = dq_scan_df.filter(col("_dq_issue").isNotNull())

clean_df.write.saveAsTable("gbmart.silver.customers")
quarantine_df.write.saveAsTable("gbmart.silver.customers_quarantine")

Nothing is ever silently dropped — a rejected row is always findable in the quarantine table, tagged with exactly why it was rejected.

Decision Checklist

1Is the correct value knowable/recoverable from elsewhere in the row? → Fix
2Row still usable, but one field is suspect? → Flag with a _data_note-style column
3Genuine rule violation, can't safely guess the value? → Quarantine
4Before quarantining: what depends on this row downstream? (This is the step the DELIVERY_BEFORE_SHIP story skipped.)
