The DQ Scan Pattern

Think of it like a hospital triage nurse. Every patient gets looked at in priority order and tagged with their one most urgent issue before anyone starts treatment — nobody tries to fix things mid-triage.

Same idea, one Bronze table

Build one _dq_issue column with a chain of when() conditions, checked in priority order — the first matching rule wins.

Why one pass matters: this gives a complete picture of every problem in the table before any fix is applied — and a row with two problems still gets exactly one tag (the highest-priority one), so counts never double-book a single bad row.

Real Example — The bronze.customers DQ Scan

The pattern used across every GlobalMart Silver notebook is the same chain of priority checks. Order matters: a row that's both null and underage still gets tagged with whichever rule comes first.

dq_scan_df = bronze_customers.withColumn("_dq_issue",
    when(col("CustomerID").isNull(),        lit("NULL_CUSTOMER_ID"))
    .when(col("FirstName").isNull(),        lit("NULL_FIRST_NAME"))
    .when(col("Email").isNull(),            lit("NULL_EMAIL"))
    .when(~col("Email").rlike(EMAIL_REGEX), lit("INVALID_EMAIL_FORMAT"))
    .when(age_at_registration < 18,           lit("REGISTERED_UNDER_18"))
    .otherwise(lit(None))
)

The Real Decision: Fix, Flag, or Quarantine?

Every flagged row needs one of three outcomes — and picking the wrong one is a quality bug in itself.

OutcomeWhen to Use ItGlobalMart Example
FixCorrect value is knowable or recoverableEmail with a stray space — remove it, the customer is real
FlagRow is usable, but a specific field is suspectDelivery date appearing before shipping date
QuarantineGenuine rule violation, value not safely guessableCustomer registered under 18

The next three slides are the most important story in this session — a case where the obvious answer (quarantine) turned out to be the wrong one.

Case Study — REGISTERED_UNDER_18: A Clean Quarantine Decision

77 customers in bronze.customers show an age-at-registration under 18. GlobalMart requires 18+ to register — legal compliance and payment authorization.

Why this one IS a quarantine: unlike the email-space issue, we cannot assume which field is wrong — the DOB could be a typo, or the customer really was underage when the (unvalidated, at the time) form let them through. We can't safely fix it, and letting it into Silver as a valid customer would be actively wrong.

Silver will not include these 77 records — the business team decides next steps.

Case Study — DELIVERY_BEFORE_SHIP: The Investigation

bronze.orders has an early DQ scan that flags 725 orders where the delivery timestamp is before the shipping timestamp — physically impossible. Before fixing anything: look closer.

date_level_flag = bronze_orders.withColumn(
    "_delivery_before_ship",
    col("actualdeliverydate").cast(DateType()) <
    col("shippingdate").cast(DateType())
)
flagged = date_level_flag.filter(col("_delivery_before_ship"))
print(f"Flagged at date level: {flagged.count():,}")

Timestamp level: 725 orders flagged.
Re-run at the date level (stripping time-of-day noise): only 114 remain.

Every one of those 114 shows exactly a 1-day gap. That consistency is the signal of a systemic cause — not random error.

Root Cause — A Timezone Artifact, Not a Data Error

Supabase stores timestamps in UTC. GlobalMart's delivery scanners record in IST (UTC+5:30). Near midnight, the same real-world moment can land on different calendar dates once cast down to a plain date.

# Supabase stores UTC; delivery scanners record IST
Delivered : June 14, 23:45 IST  ->  stored as June 14
Shipped   : June 15, 00:30 IST  ->  stored as June 15
# Physically shipped before delivered -- only the date LABEL flips

The order physically shipped before it was delivered. Only the calendar-date label flips near midnight — the data isn't wrong, the comparison was too coarse.

The Cost of Getting This Wrong — and the Corrected Decision

What happened the first time: all 114 orders were quarantined outright. Building silver.order_items downstream then orphaned 352 line items whose parent order no longer existed in Silver — silently hiding real revenue and quantity from every Gold report. The defect was confined to two date columns; customer_id, order_channel, and the line items were never in question.

Corrected decision: keep all 114 orders, and add _data_note = 'POSSIBLE_TIMEZONE_OFFSET_1DAY'. They stay fully joinable for revenue and quantity; analysts can still filter them in or out for SLA analysis specifically.

The lesson: the cost of over-quarantining showed up two tables later — that's exactly what makes it dangerous. It fails silently, downstream, somewhere else.

Section 3

Enforcing Quality at Write Time

A DQ scan is a security guard checking bags at the door — reliable, but only if someone remembers to staff the checkpoint every time. A Delta constraint is the locked turnstile itself: it can't be bypassed, forgotten, or skipped — by any notebook, this year or next.

Delta Constraints — NOT NULL & CHECK

A DQ scan is a check you remember to run. A Delta constraint is enforced by the table itself — nobody can write a violating row, ever, from any notebook.

TypeSyntaxGlobalMart Example
NOT NULLALTER TABLE t ALTER COLUMN c SET NOT NULLcustomer_id, order_id, product_id
CHECKADD CONSTRAINT name CHECK (condition)actual_price_inr > 0, rating BETWEEN 0 AND 5

Real Example — From the silver.products DQ Rules

ALTER TABLE gbmart.silver.products
ADD CONSTRAINT valid_price
  CHECK (actual_price_inr > 0);

ALTER TABLE gbmart.silver.products
ADD CONSTRAINT valid_rating
  CHECK (rating BETWEEN 0 AND 5);

The products DQ scan already checks NULL_PRODUCT_ID, INVALID_PRICE, DISCOUNT_EXCEEDS_PRICE, and INVALID_RATING. These are exactly the rules that belong as table constraints once Silver is stable — turning a scan you have to remember into a guarantee the table enforces on its own.

A constraint is a backstop, not a replacement for the scan. The scan runs before the write and routes bad rows to quarantine gracefully; a constraint just fails the whole write if violated.

The Quarantine Table Pattern

Every table that needs one follows the same shape: split the DQ-scanned DataFrame into clean_df (no issue) and quarantine_df (issue present), then write both.

Nothing is ever silently dropped — a rejected row is always findable in the quarantine table, tagged with exactly why it was rejected.

clean_df      = dq_scan_df.filter(col("_dq_issue").isNull())
quarantine_df = dq_scan_df.filter(col("_dq_issue").isNotNull())

clean_df.write.saveAsTable(
    "gbmart.silver.customers")
quarantine_df.write.saveAsTable(
    "gbmart.silver.customers_quarantine")

Decision Checklist — Fix, Flag, or Quarantine?

  1. Is the correct value knowable or recoverable from elsewhere in the row? (e.g. a PIN code duplicated inside an address line) → Fix.
  2. Is the row still usable, but I shouldn't hide that one field is suspect? → Flag with a _data_note-style column; keep the row.
  3. Does keeping the row violate an actual business rule, and I can't safely guess the correct value? → Quarantine.
  4. Before quarantining anything: what depends on this row downstream? The DELIVERY_BEFORE_SHIP story exists because this step was skipped the first time.
