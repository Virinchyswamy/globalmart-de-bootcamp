Why Bronze Isn't Enough On Its Own

Bronze does exactly one job well: land the data exactly as the source gave it to us, with zero loss. Think of it like a grocery delivery dropped at the door in whatever bags it arrived in — nothing is missing or spoiled, but you can't serve dinner straight out of the delivery bags.

The Real Complication

GlobalMart's Bronze layer fills up two different ways, and each one spells column names differently:

  • Autoloader (ADLS files) keeps each source file's original casing
  • Lakeflow Connect (Postgres CDC) lowercases every column
SourceIngestion ToolCasing landed in Bronze
orders, order_items
(Postgres/Supabase)		Lakeflow Connect (CDC)OrderID → orderid
customers, products, address, payments
(ADLS files)		AutoloaderCustomerID stays CustomerID

Why it matters: if Gold tries to join bronze.orders.customerid to bronze.customers.CustomerID directly, every query becomes a guessing game about casing. That's exactly what conform fixes — one of the three problems this session solves, alongside standardize and enrich.

Section 2

Three Ways Bronze Becomes Silver

Think of Bronze data like laundry straight out of the hamper. Some items are stained or torn — fix those first (standardize). Everything needs folding into the same labeled drawers no matter which store it came from (conform). Only once it's clean and organized does it make sense to sew on a nametag with information that didn't exist before (enrich).

STEP 1  Standardize — Fix the Values, Not Just the Shape

The row is in the right table, right column — but the value itself is malformed: wrong type, extra characters, inconsistent format.

Real example — PhoneNumber in bronze.customers

Every phone number in Bronze is 12 digits. GlobalMart's registration form auto-prepends the 91 India country code but drops the + — so +91-7584314890 lands in Bronze as 917584314890. Not wrong data — an unstandardized format.

bronze_customers = spark.table("gbmart.bronze.customers")

# PhoneNumber is BIGINT in Bronze (Autoloader inferred it as a
# number) -- cast to string first, or leading digits get read as math.
standardized_phone = (
    bronze_customers
    .withColumn("PhoneNumber", col("PhoneNumber").cast("string"))
    .withColumn("PhoneNumber",
        when(
            (length(col("PhoneNumber")) == 12) & col("PhoneNumber").startswith("91"),
            concat(lit("+91-"), col("PhoneNumber").substr(3, 10))
        ).otherwise(col("PhoneNumber"))
    )
)

STEP 1  Standardize — Email Formatting Errors

Two distinct, recoverable patterns show up in bronze.customers.Email:

PatternExampleRoot Cause
Accidental spaceswaminathaninaaya 482@outlook.comMobile autocorrect inserts a space after a long name
Apostrophe in surnametaran.d'alia307@hotmail.comD'Souza/D'Silva-style surnames; most providers strip d', this form didn't

Standardize, don't discard. Both are recoverable format issues — quarantining these customers would lose real people over a keyboard quirk. (More on that fix/flag/quarantine split in ILT 2.)

standardized_email = bronze_customers.withColumn("Email",
    regexp_replace(
        regexp_replace(
            trim(lower(col("Email"))),
            " ", ""                  # remove stray space
        ),
        "d['’‘]", ""    # remove d + apostrophe variant
    )
)

STEP 2  Conform — One Vocabulary Across Every Source

Conforming means making data from different sources speak the same structural language — same naming convention, same casing — so Gold can join across them without translation logic scattered everywhere. GlobalMart's rule: every Silver table uses lowercase snake_case, no matter what casing the source or ingestion tool used.

Lakeflow source (small rename)

bronze_orders = spark.table("gbmart.bronze.orders")
conformed_orders = (
    bronze_orders
    .withColumnRenamed("orderid", "order_id")
    .withColumnRenamed("customerid", "customer_id")
)

Autoloader source (bigger rename)

conformed_customers = (
    bronze_customers
    .withColumnRenamed("CustomerID", "customer_id")
    .withColumnRenamed("FirstName", "first_name")
)

Conforming a Value, Not Just a Name

bronze.address has the same underscore-for-space corruption in both State and AddressType (Tamil_Nadu instead of Tamil Nadu). This is still conform — it's not correcting a wrong value, it's aligning representation with every other Silver text field.

bronze_address = spark.table("gbmart.bronze.addresses")

conformed_address = bronze_address \
    .withColumn("State",
        regexp_replace(col("State"), "_", " ")) \
    .withColumn("AddressType",
        regexp_replace(col("AddressType"), "_", " "))

The distinction that matters: standardize fixes a value that's wrong or malformed; conform fixes a value that's already correct but written inconsistently with the rest of Silver. Tamil_Nadu isn't incorrect — it's just not how every other Silver text field writes a space.

STEP 3  Enrich — Add Business Value That Doesn't Exist Yet

The rule: if multiple Gold tables or reports need the same derived value, compute it once — in Silver.

Gold, BI dashboards, and Genie will all eventually ask for customer segments like New (<90 days), Regular (90–365), Loyal (>365). Computing tenure once in Silver means nobody repeats datediff(current_date(), registration_date) five different ways — five chances to get it subtly wrong.

enriched_customers = (
    bronze_customers
    .withColumn("age",
        floor(datediff(current_date(), col("DateOfBirth")) / 365.25)
        .cast("int"))
    .withColumn("customer_tenure_days",
        datediff(current_date(), col("RegistrationDate"))
        .cast("int"))
)

Real Example — Order Fulfillment KPIs

bronze.orders has four raw date columns. None of them is itself a business metric — but the gaps between them are exactly what Operations' delivery-SLA dashboard needs every day.

Derived ColumnFormulaBusiness Need
order_to_ship_daysdatediff(shippingdate, orderdate)Fulfillment SLA KPI
is_lateactualdeliverydate > expecteddeliverydateSLA breach reporting
order_statusDerived from which dates are populatedSingle readable status for Genie/BI

Same rule as tenure: derive it once in Silver — order_status (Delivered / Shipped / Pending) means Genie and BI tools never have to infer status from raw date columns themselves.

Putting It Together — The Order Matters

  1. Standardize first — fix values while they're still easy to reason about, before renames make the logic harder to read
  2. Conform next — once values are trustworthy, align naming/casing so joins across sources are simple
  3. Enrich last — derive new columns on data that's already standardized and conformed, so the logic doesn't fight messy inputs
