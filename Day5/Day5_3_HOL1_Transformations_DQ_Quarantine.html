PHASE B · INVESTIGATE BEFORE FIXING

Look Before You Fix

Look at the actual INVALID_EMAIL_FORMAT rows before writing a fix. Guessing without looking at real examples is how you "fix" data that wasn't broken.

Two real patterns you'll see

  • A stray space inserted mid-email (mobile autocorrect)
  • A d' prefix from surnames like D'Souza/D'Silva that most providers strip, but this form accepted

Business decision: fix, don't quarantine. Both are recoverable formatting errors — quarantining them would mean losing real customers over a keyboard quirk.

PHASE D · THE QUARANTINE DECISION

REGISTERED_UNDER_18

Look at the actual flagged rows before deciding anything. Unlike the email fix, these rows can't be "corrected" — we don't know if the DOB is wrong or the customer genuinely registered underage (the form had no age check at the time).

GlobalMart requires 18+ (legal compliance, payment authorization) — these rows must not reach Silver as valid customers. You justify this call yourself in the notebook; ILT 2 walked through the identical reasoning.

PHASE F.5 · ENFORCE WITH DELTA CONSTRAINTS

Lock In the Guarantee

The DQ scan already guarantees every row in clean_df has a non-null customer_id and a valid, non-null email — that's exactly why those rows are in clean_df, not quarantine_df. Turning that guarantee into a table constraint is safe and permanent.

ALTER TABLE gbmart.silver.customers
ALTER COLUMN customer_id SET NOT NULL;
ALTER TABLE gbmart.silver.customers
ALTER COLUMN email SET NOT NULL;

ALTER TABLE gbmart.silver.customers
ADD CONSTRAINT valid_email_shape
  CHECK (email LIKE '%@%.%');

Add constraints for rules you've already proven true via the DQ scan — never one you haven't tested. A CHECK that fails on existing data turns the ALTER TABLE itself into a hard error.

PHASE G · VERIFY

Confirm It Actually Worked

Checks to run

Non-negotiable check: clean rows + quarantine rows = Bronze total. If it doesn't add up, something was silently dropped or double-counted.
