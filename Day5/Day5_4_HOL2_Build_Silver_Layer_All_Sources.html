Before You Start

The Pattern, Once

Every notebook in this lab (Day5_4_HOL2_Silver_02_Orders_DQ.ipynb through ...08_Returns_DQ.ipynb) follows the same shape. Run them in order — order_items, payments, and returns all check referential integrity against Silver tables built earlier in this same sequence, so don't skip ahead.

3Investigate flagged rows — don't fix blind

5Transform — standardize, conform, enrich
6Write to Silver (SCD1 overwrite/MERGE, or SCD2 initial load)

Think of bronze.products like a shipping manifest: most fields are plain text, but specs and supplier_info are folders-within-the-folder (structs), and tags/color_options are lists taped to the box (arrays). Inspect the real shape before assuming anything.

bronze_products.printSchema()

SOURCE 3 · RECOVER A CORRUPTED VALUE · 30,000 ROWS

Address — Recovering PinCode

Autoloader inferred PinCode as numeric — any PIN starting with 0 already lost that digit before Spark showed it to us. 2,861 of 30,000 rows are affected. Like a torn label rewritten elsewhere on the package: AddressLine1 embeds the same PIN as plain text (e.g. Hajipur_051580), and text never strips leading zeros.

recovered_address = bronze_address.withColumn(
    "PinCode",
    when(pincode_len < 6,
        regexp_extract(col("AddressLine1"),
            r"(\d{5,6})\s*$", 1))
    .otherwise(col("PinCode")
        .cast("long").cast("string"))
)
# 0 extraction failures, 0 mismatches across all 2,861 rows

Recovered PINs starting with 0 are kept, even though real India Post zones never start at 0. Silver's job here is source fidelity — cross-validated against an independent copy of the value — not India Post zone validation, which would need its own reference table and is out of scope.

SOURCE 3 · REMOVE DUPLICATION, THEN WRITE

Address — Clean AddressLine1, Write Silver

AddressLine1 embeds a duplicate of City/PinCode at the end (19,088 rows via newline, the rest via comma). Since City/PinCode already exist as clean columns, remove everything after the last comma or line break, then normalize State/AddressType's underscore-for-space.

cleaned_address = recovered_address \
    .withColumn("AddressLine1",
        regexp_replace(col("AddressLine1"),
            r"[,\n][^,\n]*$", "")) \
    .withColumn("State",
        regexp_replace(col("State"), "_", " "))

Naming note: the Silver table is singular — silver.address, not silver.addresses — matching the real gbmart workspace convention. 0 DQ issues found; no quarantine table for this source either. No surrogate key generated here — that happens later in Gold.

SOURCE 4 · SCD1 VIA MERGE · 126,036 ROWS

Orders — One Current Truth

Lakeflow Connect lowercases every Postgres column (OrderID → orderid). An order has one current truth at any moment, so this is SCD1: matched rows get overwritten, unmatched rows get inserted — unlike customers/products, no history kept. A confirmed 0 duplicate orderid values means no dedup step is needed either.

deltaTable.alias("tgt").merge(

) \
 .whenMatchedUpdateAll() \
 .whenNotMatchedInsertAll() \
 .execute()
SOURCE 4 · APPLYING ILT 2'S LESSON

DELIVERY_BEFORE_SHIP — Flagged, Not Quarantined

Do not quarantine these rows. The full ILT 2 investigation found 725 timestamp-level flags collapse to 114 at the date level — all a timezone-cast artifact (UTC vs. IST), not real data errors. Quarantining them (the earlier version of this notebook) orphaned 352 downstream order_items.

Keep every one of the 126,036 orders. Add a _data_note = 'POSSIBLE_TIMEZONE_OFFSET_1DAY' column to the 114 affected rows instead — fully joinable for revenue, still filterable for SLA analysis.

SOURCE 5 · REFERENTIAL INTEGRITY · 126,036 ROWS

Order Items — The Grain of fact_sales

No derived columns needed — pricing and totals get computed when joined with products at Gold. The important step: every order_id/product_id here must exist in the Silver tables you already built. A left_anti join against each confirms 0 orphans on both.

orphan_orders = bronze_order_items.join(
    orders_df,
    bronze_order_items["OrderID"] == orders_df["order_id"],
    "left_anti"
)
print(f"Missing OrderID references: {orphan_orders.count():,}")
# 0

Real debugging artifact worth reading: the notebook's first join attempt (bronze_df.order_id) throws PySparkAttributeError — dot-notation column access only works if the name exists exactly as spelled (case-sensitive), and Bronze still has OrderID. The fix is bracket notation: bronze_df["OrderID"]. This confirms the 352-orphan cascade from Slide 10 is gone — 0 orphans on the rebuilt silver.orders.

SOURCE 6 · A BUSINESS RULE, NOT A DQ GAP · 126,036 ROWS

Payments — Conditional-Null Columns

GiftCardAmount/CouponAmount are only populated when the matching *Usage flag is "Yes". Before assuming that's a data gap, confirm it's actually a clean, consistent rule — 0 violations in either direction.

bronze_payments.groupBy("GiftCardUsage").agg(
    count(when(col("GiftCardAmount").isNull(), 1))
        .alias("amount_null"),
    count(when(col("GiftCardAmount").isNotNull(), 1))
        .alias("amount_populated")
).show()

Silver derives one new column from this: used_any_discount = (gift_card_usage == "Yes") | (coupon_usage == "Yes"). Referential integrity vs. silver.orders also confirms 0 orphans. No quarantine table needed.

SOURCE 7 · SMALL REFERENCE TABLE · 5 ROWS

Payment Methods — A Lookup Table

A small reference table (PaymentMethodID → MethodName) — exactly what a Gold dim_payment_method needs, and what silver.payments joins against to display "Credit Card" instead of PM-001.

This lab reads the existing <your-catalog>.bronze.payment_methods (already ingested via Autoloader, same as every other flat source) — it does not build Bronze here. DQ is minimal for a table this size: nulls, PaymentMethodID uniqueness (0 duplicates), and the standing _rescued_data check. Rename to snake_case, overwrite Silver.
