A First DQ Scan

Tag every row with its first failing rule, in priority order. Observe only — no fixes yet.

dq_scan_df = bronze_df.withColumn("_dq_issue",
  when(col("CustomerID").isNull(), lit("NULL_CUSTOMER_ID"))
  .when(col("Email").isNull(), lit("NULL_EMAIL"))
  .when(~col("Email").rlike(EMAIL_REGEX), lit("INVALID_EMAIL_FORMAT"))
  .when(age_at_reg < 18, lit("REGISTERED_UNDER_18"))
  .otherwise(None)
)

B Investigate Before Fixing

Look at real INVALID_EMAIL_FORMAT rows before guessing a fix. Two real patterns: a stray space from mobile autocorrect, and a d' prefix from surnames like D'Souza/D'Silva.

Decision: fix, don't quarantine. Both are recoverable formatting errors — losing these customers over a keyboard quirk would be wrong.

C Standardize: Phone Number

Every number is 12 digits — GlobalMart's form prepends 91 without a +. Reformat to +91-XXXXXXXXXX only for numbers matching that exact shape.

when(
  (length(col("PhoneNumber")) == 12) & col("PhoneNumber").startswith("91"),
  concat(lit("+91-"), col("PhoneNumber").substr(3, 10))
).otherwise(col("PhoneNumber"))

D The Quarantine Decision

REGISTERED_UNDER_18 rows can't be "corrected" like the email issue — we don't know if the DOB is wrong or the customer genuinely registered underage (the form had no age check at the time). GlobalMart requires 18+, so these rows must not reach Silver as valid.

F.5 Enforce With Delta Constraints

The DQ scan already guarantees every row in clean_df has a non-null customer_id and a valid-shaped, non-null email — that's exactly why those rows are in clean_df, not quarantine_df. Turning that guarantee into a table constraint is safe (it can't fail) and means no future notebook can ever silently reintroduce a null.

ALTER TABLE gbmart.silver.customers ALTER COLUMN customer_id SET NOT NULL;
ALTER TABLE gbmart.silver.customers ALTER COLUMN email SET NOT NULL;

ALTER TABLE gbmart.silver.customers
ADD CONSTRAINT valid_email_shape CHECK (email LIKE '%@%.%');
Add constraints for rules you've already proven true via the DQ scan — never one you haven't tested. A CHECK that fails on existing data turns the ALTER TABLE itself into a hard error.
