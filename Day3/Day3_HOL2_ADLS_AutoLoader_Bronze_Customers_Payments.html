What Makes Autoloader Special

Without Autoloader (manual approach):
You read all files every time → expensive
Or you manually track which files are new → complex code

With Autoloader:
Run 1: ADLS has customers_010626.csv → Autoloader reads it, saves checkpoint
Run 2: ADLS has customers_020626.csv → Autoloader reads ONLY the new file
Run 3: No new files → Autoloader does nothing (very fast)

Key Autoloader Concepts

TermWhat It Means
cloudFilesThe Autoloader format — like format("delta") but for reading files incrementally
cloudFiles.formatWhat kind of files you're reading — csv, json, parquet
cloudFiles.schemaLocationWhere Autoloader stores the inferred schema — consistent across runs
checkpointLocationWhere Autoloader tracks which files have been processed — the "memory"
trigger(availableNow=True)Process all available new files and stop — like a batch job
.toTable(...)Registers the stream's output as a real Unity Catalog managed table
Pre-requisites: make sure raw-data/customers/ and raw-data/payments/ exist under the GlobalMart external location. Autoloader needs no JDBC driver and no storage key — Unity Catalog's External Location (set up in Day 2 HOL 1) already grants this cluster read access.

Setup — No Storage Keys Needed

# ─── Setup: Unity Catalog External Location — NO storage keys needed ──────────
EXTERNAL_LOCATION = "abfss://ecom-gbmart-data@ecomadlsdata.dfs.core.windows.net/raw-data"
CATALOG = "gbmart"
SCHEMA = "bronze"

spark.sql(f"CREATE CATALOG IF NOT EXISTS {CATALOG}")
spark.sql(f"CREATE SCHEMA IF NOT EXISTS {CATALOG}.{SCHEMA}")

Part 1 Ingest customers with Autoloader

# ─── Step 1: Read customers/ using Autoloader (cloudFiles) ────────────────────
customers_source_path = f"{EXTERNAL_LOCATION}/customers/"
customers_schema_path = f"{EXTERNAL_LOCATION}/_schemas/customers/"
customers_checkpoint_path = f"{EXTERNAL_LOCATION}/_checkpoints/customers/"
customers_target_table = f"{CATALOG}.{SCHEMA}.customers"

customers_stream = (
    spark.readStream
    .format("cloudFiles")
    .option("cloudFiles.format", "csv")
    .option("cloudFiles.schemaLocation", customers_schema_path)
    .option("cloudFiles.inferColumnTypes", "true")
    .load(customers_source_path)
    .withColumn("_source_file", col("_metadata.file_path"))
    .withColumn("_ingested_at", current_timestamp())
)
# ─── Step 2: Write to Bronze as a managed Delta table (.toTable, not a path) ───
customers_stream.writeStream \
    .format("delta") \
    .option("checkpointLocation", customers_checkpoint_path) \
    .option("mergeSchema", "true") \
    .trigger(availableNow=True) \
    .toTable(customers_target_table)
.toTable() registers the output as a real Unity Catalog table — gbmart.bronze.customers. Anyone with catalog access can query it by name, no ADLS path needed.

# Re-run the SAME stream — same schema/checkpoint paths

Checkpoint Folder ContentsWhat It Tracks
commits/List of completed micro-batches
offsets/Tracks progress through the source
sources/Tracks which exact files have been read
metadataQuery metadata

This is why Autoloader never re-reads the same file: every file's path and size is recorded in the checkpoint after processing.

Summary — Autoloader vs Manual CSV Read

Manual spark.read.csvAutoloader (cloudFiles)
Tracks processed filesNo — reads everything every timeYes — checkpoint remembers every file
Handles new filesMust add code to detect themAutomatic — detects on next run
Schema inferenceOnce per runInferred once, stored, reused
Schema evolutionBreaks on new columnaddNewColumns handles it
Duplicates riskHigh (re-reads every run)Zero (checkpoint prevents re-reads)
When to useQuick one-off readProduction ingestion pipeline
