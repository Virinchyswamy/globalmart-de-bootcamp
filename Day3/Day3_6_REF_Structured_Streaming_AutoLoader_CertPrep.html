Batch vs Streaming Data

BATCH Data:
  Arrives on a schedule — weekly, daily, hourly
  Delays are ACCEPTABLE
  Example: weekly sales report — 2 hours late is fine

STREAMING Data:
  Arrives continuously — every second
  Delays of even 5 minutes are NOT acceptable
  Example: live cricket score, cab ETA

The critical rule: Streaming vs Batch = HOW you PROCESS, not how data arrives. If Kafka sends data every second but you process it once a week — that's still BATCH.

Business example — Amazon vs Flipkart

You browse a laptop on Amazon, don't buy immediately. Amazon processes your clickstream within 1 minute and sends a discount offer. If they waited 5 minutes, you'd have already bought it on Flipkart. That 1-minute window is near real-time processing.

Why ADLS between Event Hub and Databricks? (1) Databricks processes in-memory — a network glitch loses everything; ADLS gives durable persistence. (2) Event Hub retention is short (Basic: 1 day, Standard: 7 days) — after that, data is gone forever. ADLS preserves it.

Micro-Batch Concept and the Stateful Processing Problem

A trigger fires every N seconds (e.g., 10 sec)
All data in those 10 sec = one micro-batch
Resources are shared, not monopolised
Micro-batch 1: CUST-00123 placed 100 orders
Micro-batch 2: CUST-00123 placed 70 more

Q: How does Spark know the previous count was 100?
→ It needs to store STATE

Old Spark Streaming:  manual updateStateByKey() — error-prone
Structured Streaming: checkpoint stores state automatically

Spark Streaming vs Structured Streaming

FeatureSpark Streaming (Old)Structured Streaming (New)
APILow-level RDDHigh-level DataFrame / SQL
State managementManual (updateStateByKey)Automatic (checkpoint)
Late dataNo built-in handlingWatermarking
Recommended?No — deprecatedYes — current standard

Save-game analogy for checkpointing: you save at checkpoint 2, the game crashes at level 3 — you restart from checkpoint 2, not from the beginning. Structured Streaming does the same: if micro-batch 3 fails, Spark resumes from the last checkpoint and only reprocesses batch 3.

Chapter 4

Structured Streaming — Live Code Demo

Note on this reference's sample data: in the real GlobalMart pipeline, orders/order_items arrive via Postgres CDC (Day 2), not as a file drop — there is no real orders/ folder under raw-data/. This chapter is self-study: upload any sample orders CSV to the sandbox path before running.

Step 1 — The WRONG Approach

spark.read = BATCH, NOT STREAMING
batch_df = spark.read \
    .format("csv") \
    .option("header", "true") \
    .load(f"{raw_path}/orders.csv")

print(f"Is streaming? {batch_df.isStreaming}")
# Output: Is streaming? False — reads everything at once and stops

Step 2 — Attempt readStream With inferSchema (Fails)

SCHEMA INFERENCE DOES NOT WORK ON A STREAM
try:
    stream_df = spark.readStream \
        .format("csv") \
        .option("header", "true") \
        .option("inferSchema", "true") \
        .load(f"{raw_path}/")
except Exception as e:
    print(f"ERROR: {e}")

Why it fails: Structured Streaming cannot infer schema from streaming data. It processes data in micro-batches — it never scans ALL files upfront. Solution: define the schema manually.

Step 3 — Correct: Extract Schema First, Then Stream

THE FIX
# Load one file as batch, purely to extract the schema
sample_df     = spark.read.format("csv").option("header", "true") \
                     .option("inferSchema", "true").load(f"{raw_path}/orders.csv")
orders_schema = sample_df.schema

# Reuse that schema in the streaming read
orders_stream = spark.readStream.format("csv").option("header", "true") \
                     .schema(orders_schema).load(f"{raw_path}/")

print(f"Is streaming? {orders_stream.isStreaming}")  # True

Aggregations, Schema Evolution Limits, and Key Rules

orders_by_channel = orders_stream.groupBy("OrderChannel") \
    .agg(count("*").alias("order_count"))
# display(orders_by_channel) triggers the live stream

Schema evolution limitation: a new CSV with an extra column (e.g. promo_code) is silently ignored by Structured Streaming — no error, the column's data is just missing. Fix: manually update the schema and restart. Auto Loader (next chapter) solves this automatically.

Schema MUST be manualinferSchema does not work
display() triggers the streamWon't run without an action
Cluster must stay runningStream stops when cluster stops
Chapter 5

Auto Loader (cloudFiles)

Built to fix Structured Streaming's two biggest gaps: no schema inference, and no schema evolution.

Required Parameters and Schema Evolution Modes

ParameterWhat It Does
format("cloudFiles")Activates Auto Loader
cloudFiles.formatFile type: csv, json, parquet
cloudFiles.schemaLocationWhere inferred schema is stored — separate from data
checkpointLocationTracks which files were already processed
ModeWhat Happens on a New Column
addNewColumns (default)Adds the new column to schema automatically
rescueNew column data stored in _rescued_data JSON column
failOnNewColumnsPipeline FAILS — strict schema enforcement

Auto Loader in Code

SCHEMA INFERENCE + RESCUE MODE
orders_autoloader_stream = spark.readStream \
    .format("cloudFiles") \
    .option("cloudFiles.format", "csv") \
    .option("cloudFiles.schemaLocation",
            f"{autoloader_base}/schemas/orders") \
    .option("header", "true") \
    .option("inferSchema", "true") \
    .load(f"{raw_path}/")
# No schema needed — Auto Loader infers and stores it
orders_rescue_stream = spark.readStream \
    .format("cloudFiles") \
    .option("cloudFiles.schemaEvolutionMode", "rescue") \
    ...
    .load(f"{raw_path}/")

# A new PromoCode column shows up as:
# _rescued_data = {"PromoCode": "SAVE10", ...}

Write to Bronze, and File Notification vs Directory Listing

query = orders_with_meta.writeStream \
    .format("delta").outputMode("append") \
    .option("checkpointLocation", f"{stream_checkpoint}/orders_autoloader") \
    .option("mergeSchema", "true") \
    .trigger(availableNow=True) \
    .start(f"{bronze_path}/orders_stream")

query.awaitTermination()  # self-stopping, one-shot batch

File Notification (cloud sends an event on new file) scales to billions of files without a full folder scan; Directory Listing (default) scans the folder each trigger — fine up to millions of files.

Chapter 6 — Triggers & Output Modes

TriggerBehavior
processingTime='10 seconds'Fires every 10 sec — continuous
availableNow=TrueProcess all pending, then stop
continuous='1 second'No batching — ultra-low latency
Default (none)500ms micro-batch — not recommended, costly
Output ModeBehavior
appendInsert new rows only, never updates
completeOverwrite entire output with fresh result
updateWrite only rows that changed

Databricks recommendation: always specify an explicit trigger to control cost — the default 500ms keeps the cluster constantly processing.

Trigger Examples — Safe Patterns Only

BOTH EXAMPLES FULLY STOP THEMSELVES — SAFE TO RUN ALL
# Example 1: processingTime — started, proven alive
# for one interval, then stopped programmatically
q1 = orders_stream.writeStream.format("delta") \
    .outputMode("append") \
    .trigger(processingTime="10 seconds") \
    .option("checkpointLocation", f"{stream_checkpoint}/orders_10sec") \
    .start(f"{bronze_path}/orders_trigger_demo")

time.sleep(12)  # let one 10-sec micro-batch fire
q1.stop()
# the line you must never skip with processingTime triggers
# Example 2: availableNow — processes everything
# pending, then terminates on its own
q2 = orders_stream.writeStream.format("delta") \
    .outputMode("append") \
    .trigger(availableNow=True) \
    .option("checkpointLocation", f"{stream_checkpoint}/orders_available") \
    .start(f"{bronze_path}/orders_available_demo")

q2.awaitTermination()  # no manual .stop() ever needed

A processingTime trigger runs FOREVER until something calls .stop(), and blocks cluster auto-termination the whole time — exactly the kind of thing that quietly runs up cost if left unattended. Always pair it with an explicit stop, as shown here.

Chapter 7

Fault Tolerance: Checkpointing & WAL

Two mechanisms combine to give Structured Streaming its exactly-once guarantee.

Checkpoint Folder Structure = Memory for Spark Streaming

_checkpoints/orders_autoloader/
  metadata   ← stream query ID and configuration
  sources/   ← which files/offsets read per micro-batch
  offsets/   ← current stream position (a bookmark)
  commits/   ← log of completed micro-batch transactions
  state/     ← ONLY when GROUP BY / window functions used
Micro-batch 1: CUST-00123 → 100 orders → checkpoint saved
Micro-batch 2: CUST-00123 → 70 more    → checkpoint saved
Total count: 170

Micro-batch 3 FAILS:
  Spark reads checkpoint → resumes from count 170
  Only reprocesses batch 3 → no data loss

WAL (Write-Ahead Log) = Idempotency

WAL = a log entry created for EACH record
      BEFORE it is processed

Before processing a record:
  Spark checks: does a WAL entry exist?
  YES → skip (already processed)
  NO  → process and create WAL entry

Result: running the pipeline 100 times =
        same output, no duplicates

Attendance register analogy: a teacher checks the register before letting a student in — already marked, skip; not marked, mark and let them in. WAL does the same for every record.

CheckpointWAL
StoresSTATE (aggregated counts)LOG per record
EnablesRecovery + stateful processingIdempotency (no duplicates)

Together: Exactly-Once Processing guarantee.

Certification Summary

  1. Auto Loader vs COPY INTO — scale + notification difference
  2. Output modes: complete = overwrite, append = insert only
  3. Fault tolerance = Checkpointing + WAL
  4. Triggers: always specify explicit trigger; default = 500ms
  5. Medallion: raw→Bronze (Auto Loader/COPY INTO), Bronze→Silver (MERGE), Silver→Gold (GROUP BY)
  6. stream.isStreaming = True only with readStream
  7. Schema must be manually defined in Structured Streaming (not with Auto Loader)
