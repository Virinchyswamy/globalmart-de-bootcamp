1. What Is Schema Evolution?

Schema = the structure of your data: column names, data types, nullability. Schema evolution = the schema changes over time as the business changes.

DAY 1: orders.csv has 8 columns
OrderID, CustomerID, OrderDate, ShippingDate, ...

DAY 90: Supplier adds a new column → PremiumFlag
DAY 180: Marketing renames a column → OrderChannel → SalesChannel
DAY 270: Finance changes a data type → TotalAmount (string → decimal)
ScenarioWithout Schema HandlingWith Schema Handling
New column addedPipeline crashesNew column added automatically
Column removedPipeline crashesMissing column shows as null
Type changesSilent data corruptionError caught early
Column renamedWrong data in wrong columnHandled via column mapping

2. The 4 Types of Schema Change

Type 1 — Additive 🟢 Low RiskNew column added. Existing rows get null. Safest, most common in production — Autoloader + Delta handle it automatically.
Type 2 — Subtractive 🟡 Medium RiskColumn removed. Bronze should KEEP the column (fill null) — never drop Bronze columns. Silver/Gold can drop it intentionally.
Type 3 — Rename 🔴 High RiskLooks like remove+add — double impact. Requires columnMapping mode=name to track the rename in Delta metadata.
Type 4 — Type Change 🔴 High RiskWidening (int→long) is usually safe. Narrowing (decimal→string) risks data loss. Never rely on inferSchema for critical type changes — pin the schema explicitly.
Golden ruleBronze absorbs every change without crashing. Silver is where you decide what to do about it.
Most common in practiceType 1 (additive) — by far. This is exactly what addNewColumns mode was built for.

3. How Auto Loader Handles Schema Changes

Auto Loader has a dedicated option: cloudFiles.schemaEvolutionMode

ModeBehaviourUse When
addNewColumnsAdds new columns automatically, updates schema locationDefault — use this in production
rescueKeeps existing schema strict, stores unexpected data in _rescued_dataStrict pipelines that must audit unexpected fields
failOnNewColumnsStream fails if a new column appearsCompliance pipelines where any change must be reviewed
noneIgnores new columns — silently droppedLegacy pipelines with externally-controlled schema

Mode: addNewColumns (what we use)

raw_stream = (
    spark.readStream
    .format("cloudFiles")
    .option("cloudFiles.format", "csv")
    .option("cloudFiles.schemaLocation", schema_path)  # schema stored here
    .option("cloudFiles.schemaEvolutionMode", "addNewColumns")  # ← key option
    .option("header", "true")
    .load(raw_path)
)
1Auto Loader detects PremiumFlag in the new file
2Updates the schema stored at schema_path
3Stream restarts automatically with the new schema
4New column is written to Bronze Delta table
5Historical rows get null for PremiumFlag

4. The _rescued_data Column

When schemaEvolutionMode = rescue, Auto Loader adds a special column: _rescued_data

Incoming row: OrderID=001 | CustomerID=C01 | NewUnexpectedColumn=XYZ
Schema says: OrderID, CustomerID (does NOT know about NewUnexpectedColumn)

Result:
OrderID = 001
CustomerID = C01
_rescued_data = {"NewUnexpectedColumn": "XYZ"} ← stored as JSON string
Use case: audit pipelines that want to capture ALL incoming data without breaking the schema, then review _rescued_data later to decide whether to add the column officially. Think of it as a safety net — nothing is lost.

5. How Delta Lake Handles Schema Changes

Even after Auto Loader handles the incoming schema, the Delta table also needs to accept the change.

Option 1 — mergeSchema=true (Additive Only)

raw_stream.writeStream
  .format("delta")
  .option("mergeSchema", "true")  # new cols added
  .option("checkpointLocation", checkpoint_path)
  .start(output_path)

New columns added, historical rows get null. This is what we use in the Auto Loader demo.

Option 2 — overwriteSchema=true (Destructive)

df.write.format("delta") \
  .option("overwriteSchema", "true") \
  .mode("overwrite") \
  .save(output_path)

Replaces the ENTIRE schema — dangerous on production tables. Batch-only, dev/full-reload use only.

Option 3 — Delta Column Mapping (Rename Support)

ALTER TABLE delta.`/path/to/table`
SET TBLPROPERTIES (
    'delta.columnMapping.mode' = 'name',
    'delta.minReaderVersion'   = '2',
    'delta.minWriterVersion'   = '5'
);

ALTER TABLE delta.`/path/to/table`
RENAME COLUMN OrderChannel TO SalesChannel;

No data rewrite — just updates Delta metadata. Historical data is instantly accessible under the new name.

6. GlobalMart Scenario — Schema Evolution in Practice

WeekWhat HappensPipeline Response
Week 1Supplier sends orders.csv with 8 columnsAutoloader ingests → Bronze has 8 cols + _ingested_at + _source_file
Week 4Supplier adds PremiumFlagaddNewColumns detects it, mergeSchema adds it to Bronze. Weeks 1–3 rows: null
Week 8Marketing renames OrderChannel → SalesChannelBoth columns exist in Bronze (historical preserved). Needs a manual RENAME COLUMN to merge cleanly
The key insight: Auto Loader + mergeSchema handles additive changes automatically. Renames require a manual ALTER TABLE RENAME COLUMN step.

7. Decision Framework

Change TypeAction
New column addedaddNewColumns + mergeSchema=true — handled automatically
Column removed from sourceKeep column in Bronze (fill null); drop intentionally in Silver
Column renamedShort term: two columns co-exist; long term: RENAME COLUMN with column mapping
Data type changedCast explicitly in Silver — never rely on inferSchema for type changes

Key Takeaways

✓Schemas always evolve — build your pipeline to expect it, not avoid it
✓addNewColumns is right for ~95% of production cases
✓mergeSchema=true on every writeStream — no reason not to
✓Never drop Bronze columns — absorb the change, decide in Silver
✓_rescued_data is your audit safety net for strict pipelines
✓Type changes are the sneakiest — always cast explicitly in Silver
