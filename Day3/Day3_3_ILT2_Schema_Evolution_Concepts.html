What Is Schema Evolution?

Schema = the structure of your data: column names, data types, nullability. Schema evolution = that structure changes over time as the business changes — a new column, a rename, a data type swap.

In the real world, schemas always evolve. Your pipeline must handle it gracefully — or it will crash.

DAY 1:   orders.csv has 8 columns
         OrderID, CustomerID, OrderDate, ...

DAY 90:  Supplier adds a new column
         → PremiumFlag

DAY 180: Marketing renames a column
         → OrderChannel becomes SalesChannel

DAY 270: Finance changes a data type
         → TotalAmount: string becomes decimal

The 4 Types of Schema Change

Not all schema changes carry the same risk. Two are usually safe to automate; two need a human decision.

Types 1 & 2 — Additive and Subtractive

Type 1 — Additive 🟢 Low Risk

BEFORE: OrderID | CustomerID | OrderDate
AFTER:  OrderID | CustomerID | OrderDate | PremiumFlag ← new
  • Safest change — backward compatible
  • Existing rows get null for the new column
  • Most common in production

Type 2 — Subtractive 🟡 Medium Risk

BEFORE: OrderID | CustomerID | OrderDate | LegacyCode
AFTER:  OrderID | CustomerID | OrderDate     ← LegacyCode gone
  • Downstream dashboards referencing LegacyCode will break
  • Bronze layer should KEEP the column (fill null) — never drop Bronze columns
  • Silver/Gold can drop it intentionally

Types 3 & 4 — Rename and Type Change

Type 3 — Rename 🔴 High Risk

BEFORE: OrderID | OrderChannel
AFTER:  OrderID | SalesChannel  ← renamed from OrderChannel
  • Looks like remove + add — double impact
  • Without column mapping: historical data appears to vanish
  • Requires careful source/pipeline coordination

Type 4 — Type Change 🔴 High Risk

BEFORE: TotalAmount STRING  → "1234.56"
AFTER:  TotalAmount DECIMAL → 1234.56
  • Widening (int → long): usually safe
  • Narrowing (decimal → string): data loss risk
  • Best practice: pin your schema explicitly for critical columns

How Auto Loader Handles Schema Changes

Auto Loader has a dedicated option: cloudFiles.schemaEvolutionMode

ModeBehaviourUse When
addNewColumnsAdds new columns automatically, updates schema locationDefault — use this in production
rescueKeeps existing schema strict, stores unexpected data in _rescued_dataStrict pipelines that must audit unexpected fields
failOnNewColumnsStream fails if a new column appearsCompliance pipelines where any change must be reviewed
noneIgnores new columns — silently droppedLegacy pipelines with externally-controlled schema

Mode: addNewColumns (What We Use)

raw_stream = (
    spark.readStream
    .format("cloudFiles")
    .option("cloudFiles.format", "csv")
    .option("cloudFiles.schemaLocation", schema_path)
    .option("cloudFiles.schemaEvolutionMode",
            "addNewColumns")  # ← key option
    .option("header", "true")
    .load(raw_path)
)

What happens when a new column appears:

  1. Auto Loader detects PremiumFlag in the new file
  2. Updates the schema stored at schema_path
  3. Stream restarts automatically with the new schema
  4. New column is written to the Bronze Delta table
  5. Historical rows get null for PremiumFlag

The Schema Location — Why It Matters

_autoloader/schemas/orders_demo/
    schema   ← current inferred schema (JSON)
  • Auto Loader stores the schema here between runs
  • On restart, it loads from this location — it does not re-infer from scratch
  • Deleting this folder (Clean Start) forces a fresh re-infer
  • Keeps schema consistent across restarts — prevents silent drift

The _rescued_data Column

When schemaEvolutionMode = rescue, Auto Loader adds a special safety-net column:

Incoming row:  OrderID=001 | CustomerID=C01 | NewUnexpectedColumn=XYZ
Schema says:   OrderID, CustomerID  (knows nothing about NewUnexpectedColumn)

Result:
  OrderID       = 001
  CustomerID    = C01
  _rescued_data = {"NewUnexpectedColumn": "XYZ"}  ← stored as JSON string

Use case: audit pipelines that want to capture ALL incoming data without breaking the schema, then review _rescued_data later to decide whether to add the column officially.

Think of _rescued_data as a safety net — nothing is lost, you just decide later what to do with it.

How Delta Lake Handles Schema Changes

Even after Auto Loader handles the incoming schema, the Delta table also needs to accept the change.

Option 1 — mergeSchema=true (Additive Only)

raw_stream.writeStream
  .format("delta")
  .option("mergeSchema", "true")  # new cols added
  .option("checkpointLocation", checkpoint_path)
  .start(output_path)

New columns added, historical rows get null. This is what we use in the Auto Loader demo.

Option 2 — overwriteSchema=true (Destructive)

df.write.format("delta") \
  .option("overwriteSchema", "true") \
  .mode("overwrite") \
  .save(output_path)

Replaces the ENTIRE schema — dangerous on production tables. Batch-only; development or full-reload use only.

Option 3 — Delta Column Mapping (Rename Support)

ALTER TABLE delta.`/path/to/table`
SET TBLPROPERTIES (
    'delta.columnMapping.mode' = 'name',
    'delta.minReaderVersion'   = '2',
    'delta.minWriterVersion'   = '5'
);

ALTER TABLE delta.`/path/to/table`
RENAME COLUMN OrderChannel TO SalesChannel;

No data rewrite — just updates Delta metadata. Historical data is instantly accessible under the new name, because Delta stores a mapping: SalesChannel → physical_col_id_7. Requires minReaderVersion=2, minWriterVersion=5.

GlobalMart Scenario — Schema Evolution in Practice

WeekWhat HappensPipeline Response
Week 1Supplier sends orders.csv with 8 columnsAutoloader ingests → Bronze has 8 cols + _ingested_at + _source_file
Week 4Supplier adds PremiumFlagaddNewColumns detects it, mergeSchema adds it to Bronze. Weeks 1–3 rows: null
Week 8Marketing renames OrderChannel → SalesChannelBoth columns exist in Bronze (historical preserved). Needs a manual RENAME COLUMN to merge cleanly

The key insight: Auto Loader + mergeSchema handles additive changes automatically. Renames require a manual ALTER TABLE RENAME COLUMN step.

Summary — Decision Framework

Change TypeAction
New column addedaddNewColumns + mergeSchema=true — handled automatically ✅
Column removed from sourceKeep column in Bronze (fill null); drop intentionally in Silver ✅
Column renamedShort term: two columns co-exist. Long term: ALTER TABLE RENAME COLUMN with column mapping ✅
Data type changedCast explicitly in Silver — never rely on inferSchema for type changes ✅

Key Takeaways

  1. Schemas always evolve — build your pipeline to expect it, not avoid it
  2. addNewColumns is the right Auto Loader mode for ~95% of production cases
  3. mergeSchema=true on every writeStream — no reason not to have it
  4. Never drop Bronze columns — absorb the change, decide in Silver
  5. _rescued_data is your audit safety net for strict pipelines
  6. Type changes are the sneakiest — always cast explicitly in Silver
