Scope: What This Demo Is (and Isn't)

This demo ingests every CSV in a private sandbox _demo/raw/ folder, including a stand-in orders.csv — purely to get a large-enough file set and a stable ID column (OrderID) to prove exactly-once processing, live.

Output location

Written to a throwaway path: raw-data/_demo/bronze/orders_demo_v2/ — never the real gbmart.bronze.orders.

In the real GlobalMart architecture, orders/order_items arrive via Postgres CDC through Lakeflow Connect (Day 2) — not Autoloader. The genuinely Autoloader-sourced entities are products, customers, address, and payments (see HOL 2).

What We Are Proving

Auto Loader does NOT re-read files it has already processed. When a NEW file lands in ADLS, Auto Loader detects it automatically — zero manual intervention.

Setup — Unity Catalog External Location

# No storage key needed — same auth as HOL 2
EXTERNAL_LOCATION = "abfss://ecom-gbmart-data@ecomadlsdata.dfs.core.windows.net/raw-data"

raw_path        = f"{EXTERNAL_LOCATION}/_demo/raw"            # this demo's private "raw/" folder
staging_path    = f"{EXTERNAL_LOCATION}/_demo/staging"        # holding area, not watched
checkpoint_path = f"{EXTERNAL_LOCATION}/_checkpoints/orders_demo_v2"
output_path     = f"{EXTERNAL_LOCATION}/_demo/bronze/orders_demo_v2"  # throwaway path
schema_path     = f"{EXTERNAL_LOCATION}/_schemas/orders_demo_v2"

How Auto Loader Tracks Files — The Checkpoint

ADLS _demo/raw/ folder:
  orders.csv       ← Phase 1: processed  (checkpoint remembers this)
  orders_new.csv   ← Phase 4: we drop this (not yet seen)

What happens every trigger (30 seconds):

  1. List all files in raw/
  2. Compare against checkpoint sources/
  3. orders.csv → already in checkpoint → SKIP
  4. orders_new.csv → NOT in checkpoint → PROCESS ← this is the moment
  5. Write 5 new rows to Bronze Delta, update checkpoint

Phase 1 — Load Everything, Rename Bad Columns

LIVE CODE · availableNow=True (ONE-SHOT BATCH)
raw_stream = (
    spark.readStream
    .format("cloudFiles")
    .option("cloudFiles.schemaLocation", schema_path)
    .option("cloudFiles.schemaEvolutionMode", "addNewColumns")
    .option("header", "true")
    .load(raw_path)
    .withColumn("_ingested_at", current_timestamp())
    .withColumn("_source_file", input_file_name())
)
# shipping_tier.csv has "Cost (Rs)" — clean special characters before writing
for c in raw_stream.columns:
    clean = c.replace(" ", "_").replace("(", "").replace(")", "")
    if clean != c:
        raw_stream = raw_stream.withColumnRenamed(c, clean)

phase1_query = (
    raw_stream.writeStream.format("delta").outputMode("append")
    .option("checkpointLocation", checkpoint_path)
    .option("mergeSchema", "true")
    .trigger(availableNow=True)
    .start(output_path)
)
phase1_query.awaitTermination()  # one-shot: processes everything, then stops itself

Why Rename Columns Before Writing?

"Cost (Rs)" → "Cost_Rs" avoids the DELTA_INVALID_CHARACTERS_IN_COLUMN_NAMES error — Delta rejects spaces, parentheses, and other special characters in column names.

Phase 1 and Phase 3 must use the exact same renaming logic, or the Bronze table schema won't match between the two writes.

Phase 2 — Prepare the New File (Staging)

LIVE CODE · WRITE TO A HOLDING AREA
orders_new_content = """OrderID,CustomerID,OrderDate,...
ORD-NEW-2026-001,CUST-08966,2026-06-15,...
... 5 fresh GlobalMart orders total ..."""

staged_csv = f"{staging_path}/orders_new.csv"
dbutils.fs.put(staged_csv, orders_new_content, overwrite=True)

Staging = holding area. The file is written with 5 fresh orders but is not in raw/ yet — Auto Loader cannot see it. We control exactly when Auto Loader sees the file by copying it into raw/ in Phase 4.

Phase 3 — Start the Continuous Stream

LIVE CODE · SAME CHECKPOINT AS PHASE 1
continuous_query = (
    continuous_stream.writeStream
    .format("delta").outputMode("append")
    .option("checkpointLocation", checkpoint_path)
    .option("mergeSchema", "true")
    .trigger(processingTime="30 seconds")
    .start(output_path)
)
Phase 1 checkpoint state:  all CSVs → DONE
Phase 3 first trigger:     all files → SKIP, nothing new → IDLE
Phase 4 (file dropped):    orders_new.csv → NEW → PROCESS

The stream runs in the background — you can run subsequent cells while it is active.

Phase 4 — The Demo Moment

LIVE CODE · DROP THE FILE INTO raw/
dbutils.fs.cp(
    f"{staging_path}/orders_new.csv",
    f"{raw_path}/orders_new.csv"
)

Trigger fires within 30 seconds → count jumps by 5 → _source_file shows orders_new.csv → _ingested_at is LATER than the Phase 1 rows. No manual retrigger.

Stop the Stream + Final Summary

if continuous_query.isActive:
    continuous_query.stop()
    print("Continuous stream stopped.")
else:
    print("Stream already stopped.")

Always stop a continuously-triggered stream once its purpose is demonstrated. The demo explicitly checks isActive and calls .stop() before printing the final summary — never leave a processingTime stream running untethered.

  orders.csv + 9 other CSVs  → Phase 1: ingested (checkpoint records all)

        ▼  cloudFiles (Auto Loader)

        │
        ▼  writeStream → Delta

    All rows from all files

    _ingested_at  = when Auto Loader ingested it
