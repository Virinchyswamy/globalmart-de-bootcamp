Two Ways to Reach the Same Storage Account

Other Bronze notebooks in this course use an External Location. This session deliberately uses a different, older pattern instead — worth knowing as a real alternative, not a downgrade.

Why bother, if Day 2 called mounting a legacy anti-pattern? Day 2 was right that nobody sets up a new mount for a governed, ongoing pipeline anymore — External Locations exist precisely to replace it. But plenty of real workspaces still have old mounts sitting around from before that shift, and you'll be expected to recognize the pattern, know its trade-offs, and migrate off it when asked. That's why it's still worth building once, hands-on, even though it's not where you'd start a brand-new pipeline today.

Why wasbs:// and Not abfss:// Here

Think of it like two doors into the same warehouse: one door (abfss://) only opens if the building has a specific newer lock installed (Hierarchical Namespace). The other door (wasbs://) is the older lock — works everywhere, just less feature-rich.

The real constraint: abfss:// only works for mounting/reading against a storage account with Hierarchical Namespace (ADLS Gen2) enabled. If the storage account doesn't have that enabled, or the workspace's mount setup doesn't support abfss:// mounting, wasbs:// against the .blob.core.windows.net endpoint is the working alternative — same underlying data, older Blob Storage protocol.

Why This Is Worth Knowing, Not Just a Workaround

Not every storage account you'll meet on a real project has HNS turned on. Knowing the mounting fallback means you're never blocked by that — you have a second working path.

STORAGE_ACCOUNT = "ecomdata"

    f"fs.azure.account.key.{STORAGE_ACCOUNT}.blob.core.windows.net": STORAGE_ACCOUNT_KEY
}

# Check if already mounted
if any(m.mountPoint == MOUNT_POINT for m in dbutils.fs.mounts()):
    print(f"✅ {MOUNT_POINT} is already mounted.")
else:
    dbutils.fs.mount(
        source=f"wasbs://{CONTAINER}@{STORAGE_ACCOUNT}.blob.core.windows.net/",
        mount_point=MOUNT_POINT,
        extra_configs=configs
    )

This Isn't the Same Catalog as the External Location Version — and That's Expected

The External Location Bronze notebooks write to your one shared catalog. This mounting-based build writes to a separate practice catalog instead — a real, distinct catalog name in the actual run, kept intentionally different.

This is a genuinely different setup, not a typo — mounting with a storage key doesn't go through Unity Catalog's External Location machinery at all, so there's no reason it would land in the same catalog.

The Checkpoint Layout — Trust the Code, Not Just the Comment

CHECKPOINT_PATH =
  f"{MOUNT_BASE}/_checkpoints/{SOURCE_FOLDER}/"

# resolves to:

The notebook's own Step 1 markdown claims checkpoint/schema state is nested inside each table's folder (customers/_checkpoints/). The actual code disagrees: CHECKPOINT_PATH is built from MOUNT_BASE, making _checkpoints/ a sibling of customers/ — the same shared-root layout used elsewhere in the course.

The Addresses and Remaining-Sources notebooks confirm shared-root is the real, standardized layout — one of them even cleans up leftover nested clutter from an earlier iteration. Lesson: when a comment and the code it's attached to disagree, trace the actual variable — the code is always the ground truth.

multiLine Fix #1 — Embedded Newlines in AddressLine1

A CSV reader normally assumes one record per line. Real address data breaks that assumption the moment a field itself contains a line break — e.g. a multi-line street address typed with an Enter in the middle.

OptionValueWhy
multiLinetruelets a single CSV record span multiple physical lines
escape'"'handles quoted fields correctly alongside the embedded newline

Without both options together, rows silently split mid-address — you'd see more rows than source records, with garbage in the extra ones, not a clean error.

multiLine Fix #2 — the products JSON Story

Auto Loader's default JSON reader assumes NDJSON — one object per line. The real products_010626.json file is a pretty-printed array instead. That mismatch surfaced as a real, specific error: CF_FAILED_TO_INFER_SCHEMA.

How It Was Actually Diagnosed

Santosh's approach: don't guess — read the raw bytes. dbutils.fs.head(path, 500) printed the file's first 500 characters. It started with [, not { — confirming a JSON array, not NDJSON, and pointing straight at the fix: cloudFiles.multiLine = "true".

The debugging habit worth keeping: when a schema-inference error is confusing, look at the raw file before touching the reader options. The file's shape usually tells you the fix directly.

Live in the Workspace — Preview, Then Fix

The Format-Aware Pre-Flight Check

dbutils.fs.ls() returning entries doesn't mean Auto Loader can actually see files to ingest — Auto Loader's own file discovery filters for the expected format. A folder that looks non-empty to ls() can still look empty to Auto Loader if nothing inside actually matches.

That mismatch is exactly what causes CF_EMPTY_DIR_FOR_SCHEMA_INFERENCE — a genuinely confusing error if you haven't seen it before, since the folder clearly isn't empty.

The Fix — source_has_files()

Checks for files matching the expected extension before Auto Loader ever starts. A missing folder, an empty folder, or a folder with only non-matching files is reported and skipped — never a notebook-stopping exception.

Live in the Workspace — the Pre-Flight Function

From Notebook 3, Step 3b
def source_has_files(source_folder, source_path, file_format):
    entries = dbutils.fs.ls(source_path)  # wrapped in try/except upstream

    if len(entries) == 0:
        print(f"  Skipping {source_folder} because the folder is empty.")
        return False

    extension = f".{file_format}"
    matching_files = [
        e for e in entries
        if not e.isDir() and e.name.lower().endswith(extension)
    ]

    if not matching_files:
        print(f"  Skipping {source_folder}: no files ending in '{extension}'")
        return False

    print(f"  {source_folder}: {len(matching_files)} matching file(s) — OK to ingest.")
    return True

reset_bronze_table() — Clean Re-Runs on Demand

What It Does

  • Removes the table's checkpoint folder
  • Removes the table's schema folder
  • Drops the Bronze table itself

Every step is wrapped so a folder that can't be deleted (common on Blob Storage) doesn't stop the notebook — it logs a warning and moves on.

Why It Exists

Rehearsing or re-teaching this build shouldn't require manually hunting down stale checkpoint/schema folders. It's also used automatically at the start of Notebook 3 to clean up a known stale checkpoint on addresses before re-ingesting products after fixing the JSON schema-inference failure.

Closing Step — Change Data Feed on Every Bronze Table

Notebook 3 ends by enabling Change Data Feed (CDF) on all 6 Bronze tables — customers, addresses, payments, payment_methods, products, returns.

Why this matters downstream: without CDF, Silver would have to re-scan and re-diff the entire Bronze table on every run to find what changed. With CDF on, Silver can read only the row-level changes since its last run — MERGE-based incremental loads instead of full rebuilds.

Set It Once, at the End of Bronze — Not Later

CDF only captures changes from the point it's enabled forward. Turning it on as the last step of the Bronze build (rather than an afterthought in Silver) means no history is missed.

Live in the Workspace — Enabling CDF

From Notebook 3, final cell
CATALOG = "harsh_kumar01_npmentorskool_onmicrosoft_com"
SCHEMA  = "bronze"

BRONZE_TABLES = [
    "customers", "addresses", "payments", "payment_methods",
    "products", "returns"

for table in BRONZE_TABLES:
    full_name = f"{CATALOG}.{SCHEMA}.{table}"
    spark.sql(f"""
        ALTER TABLE {full_name}
        SET TBLPROPERTIES (delta.enableChangeDataFeed = true)
    """)
    print(f"CDF enabled: {full_name}")
