Bronze in the Medallion Architecture

Think of a restaurant kitchen: raw ingredients arrive at the receiving dock exactly as the supplier sent them. Nobody chops or seasons anything there — that happens later, in prep.

The Three Stations

  • Receiving dock (Bronze) — land it raw, ask questions later
  • Prep station (Silver) — wash, chop, standardise — "make it trustworthy"
  • Plated dish (Gold) — ready to serve — "make it useful"; this is where fact_sales lives
Sources → BRONZE → SILVER → GOLD → Consumers

BRONZE  = Raw ingestion layer
          "Land first, ask questions later"

SILVER  = Cleaned, conformed, enriched
          "Make it trustworthy"

GOLD    = Business-ready aggregates
          "Make it useful"

Bronze Is NOT a Staging Area

Common misconception: Bronze is a temporary holding area you delete once Silver is built. Wrong — Bronze is permanent.

Staging Area (wrong mental model)Bronze Layer (correct)
Temporary — deleted after processingPermanent — kept forever
No audit trailFull audit trail (when + from where)
No time travelDelta time travel across all historical loads
Can't reprocessCan always reprocess Silver from Bronze

Bronze is your insurance policy. If Silver has a bug, you don't go back to the source — you reprocess from Bronze. Faster, cheaper, and the source may have already changed.

Why Keep Bronze Forever? A Real Example

❌ Without Bronze

Silver job has a timezone bug → orders from 11 PM to 1 AM get the wrong date. Fix requires re-extracting from Postgres and re-requesting ADLS file history — painful, and the files may no longer be there.

✅ With Bronze

Correct the transformation, rerun Silver from Bronze. Problem solved — no re-extraction, no missing files, no dependency on the source system still having the data.

This is why every GlobalMart Bronze table is kept forever, regardless of pathway.

Section 2

The 3 Golden Rules of Bronze

Every table GlobalMart writes to Bronze — CDC or Autoloader — follows the exact same three rules.

Rule 1 — Land Raw, Transform Never

✅ Bronze DOES

  • Land incoming data
  • Add audit columns
  • Preserve source column names
  • Handle schema evolution

❌ Bronze DOES NOT

  • Rename columns
  • Cast data types
  • Join with other tables
  • Filter rows
  • Aggregate or apply business rules

The only columns Bronze adds are audit columns — everything from the source lands exactly as it arrived.

Rule 2 — Idempotent Writes

Idempotent means running the ingestion multiple times produces the same result — no duplicates, no matter how many times a job reruns.

Run 1: products.csv → 12,000 rows in Bronze
Run 2: products.csv → same 12,000 rows (not re-processed)
Run 3: products_v2.csv → 12,040 rows (only 40 new rows added)

ADLS Autoloader

Achieved via checkpoint — tracks every file already processed.

Postgres Lakeflow Connect

Achieved via the cursor's last-seen value — Lakeflow Connect re-queries WHERE updated_at > last_seen_value each run and only touches rows that actually changed.

Read the code, not just the comment, when tracing a checkpoint path. HOL 1's mounting-based notebooks (dbutils.fs.mount() + wasbs://) have a markdown cell claiming the checkpoint/schema state is nested inside each table's own source folder (e.g. customers/_checkpoints/) — but the actual path variable, f"{MOUNT_BASE}/_checkpoints/{SOURCE_FOLDER}/", builds a shared root instead: _checkpoints/<table>/, a sibling of the data folder, same as the standard pattern above. When a notebook's prose and its code disagree, the code is the ground truth — worth the habit of double-checking.

Rule 3 — Bronze Never Manually Deletes a Row

Both Pathways Honor This, Differently

  • Autoloader (products, customers, address, payments): literally append-only — every file's rows land as new rows, nothing overwritten or removed
  • Lakeflow Connect (orders, order_items): upserts the latest row per key — but still never issues a manual DELETE
  • If an order is hard-deleted in Postgres, Bronze doesn't remove it either — it simply stops being updated and goes stale
  • Nothing tells the pipeline to delete a stale row, and nothing does

Neither pathway ever overwrites Bronze wholesale. There is no "full snapshot, overwrite daily" source in GlobalMart's real pipeline.

Why Keep Audit Columns This Minimal?

A common instinct is to add _source_system, _batch_id, _load_type, and similar "just in case" columns to every table. GlobalMart's real build doesn't.

Every extra column is one more thing to keep correct across every ingestion script, forever. Add a column only when a real query will filter or group by it.

Why Each "Obvious" Extra Column Is Redundant Here

  • _source_file already answers "which pathway, which file, when" for Autoloader — the path itself encodes the source folder
  • Lakeflow Connect needs no manual audit columns at all — Databricks already governs lineage and history for the managed table

Table Naming — the Real, Live Unity Catalog Pattern

-- Fully qualified: CATALOG.SCHEMA.TABLE
<your-catalog>.bronze.orders
<your-catalog>.bronze.products
<your-catalog>.silver.orders    -- cleaned
<your-catalog>.gold.fact_sales  -- business-ready

Why No Source Prefix?

A common instinct coming from path-based storage is to encode layer and source into the table name itself (bronze_adls_products). In Unity Catalog, don't — the three-level namespace already carries that information.

<your-catalog>.bronze.bronze_adls_products is redundant. Just <your-catalog>.bronze.products — the schema already says "bronze," the catalog already says which project.

Honest note on catalog names: the real run of this course used gbmart as the shared catalog for the Gold layer, but the mounting-based Bronze/Silver build in HOL 1 writes to a different, personal catalog (harsh_kumar01_npmentorskool_onmicrosoft_com in the real run) — because mounting with a storage key never goes through Unity Catalog's External Location path that gbmart is set up under. Your own catalog name will differ from both — what matters is the pattern: catalog.schema.table, used consistently within your own chain.

Write Modes — Append vs Upsert vs Overwrite

Append — Autoloader (4 of 6 tables)

Use append when the source produces a new batch of rows with nothing to reconcile against — every Auto Loader file's rows land as new rows.

Upsert — Lakeflow Connect (orders, order_items)

GlobalMart's real pipeline does not append — it upserts. Each run re-queries the cursor column and merges the result: new keys inserted, existing keys updated in place (history tracking Off / SCD1). Databricks manages this write for you.

Overwrite would only apply to a full-state snapshot source with no way to identify just the changed rows — GlobalMart has none today. Know the pattern anyway; you'll meet it on other projects.

❌ Wrong: overwriting Bronze products daily
   Day 1: 12,000 rows → Bronze = 12,000
   Day 2: 12,040 rows → Bronze overwritten
   Day 3: Day 1 bug found → CANNOT go back

✅ Correct: appending every day (Autoloader)
   Day 1: 12,000 rows appended
   Day 2: 40 new rows appended
   Day 3: time travel back to Day 1 state

✅ Correct: upserting every run (Lakeflow Connect)
   Run 1: ~126,000 orders upserted (full snapshot)
   Run 2: 40 changed orders upserted in place
          — row count grows only for genuinely new orders
Section 6

Lakeflow Connect Bronze Design

GlobalMart's real pipeline (query/cursor-based, history tracking Off) lands current state — not an event log. Worth being precise about which one you're building.

What Bronze Actually Looks Like

<your-catalog>.bronze.orders (upserted, one row per order_id):

order_id  | customer_id | order_channel | ...   (no _cdc_op column)
----------|-------------|----------------|----
ORD-001   | CUST-001    | Shipped        | ...
ORD-002   | CUST-002    | Delivered      | ...

When ORD-001's status later changes Shipped → Delivered:
  the SAME row updates in place — still exactly one row for ORD-001.

This is NOT an event log. There's no MERGE in Silver to collapse multiple rows into one, because Bronze never had multiple rows for the same order_id — Lakeflow Connect already upserted it for you. Silver just reads the current state and applies its own transformations.

The One Real Gap: Hard Deletes

What Happens When an Order Is Deleted

  1. It stops matching the cursor query (WHERE updated_at > last_seen_value)
  2. Lakeflow Connect never sees a "this row is gone" event — there isn't one
  3. The row stays in Bronze exactly as it last was, silently going stale
  4. No downstream layer is told about the deletion

Why Use It Anyway?

No manual scheduling code, a governed Unity Catalog table with lineage and access control out of the box, and far less to maintain than a hand-rolled JDBC script — the same blind spot as a watermark either way, but someone else maintains the pipeline.

This is the real, named limitation of query/cursor-based capture — see Day 2 for the full explanation and what a log-based (WAL) connector would do differently.

GlobalMart's 6 Bronze Table Designs

<your-catalog>.bronze.orders:  (upserted — no manual audit columns to add)
  order_id         STRING
  customer_id      STRING
  order_date       STRING  ← kept STRING, Silver casts
  ... (all source columns)
<your-catalog>.bronze.products:
  _ingested_at     TIMESTAMP
  _source_file     STRING
  product_id       STRING
  product_name     STRING
  category         STRING
  ... (all CSV columns)

Lakeflow Connect pathway (orders, order_items) carries no manual audit columns at all — upserted, governed by Databricks. Autoloader pathway (products, customers, addresses, payments) carries _source_file + _ingested_at. Everything else is the entity's own source columns, untouched.

Recap

Key Takeaways

Permanent, Not Staging

Bronze is kept forever — your insurance policy if Silver ever needs to be rebuilt.

3 Golden Rules

Land raw, idempotent writes, never manually delete a row — Lakeflow Connect's upserted tables just go stale, never explicitly delete.

Minimal Audit Columns

_ingested_at + _source_file on Autoloader tables — Lakeflow Connect tables need none, Databricks governs them for you.
