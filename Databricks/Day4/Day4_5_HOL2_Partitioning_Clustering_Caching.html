Overview

What We're Building

A small, disposable practice table modeled on gbmart.bronze.customers, deliberately written as many tiny files — then we apply each performance lever from ILT 3 and measure the before/after ourselves.

Why Bronze, not Gold? By Day 4, only Bronze exists — Silver, dimension tables, and fact_sales haven't been built yet. You'll repeat these exact levers against Gold tables once they exist.

Before You Start — Cost & Safety

Everything here runs against a personal practice table in your own schema — never against shared gbmart.bronze / silver / gold tables. OPTIMIZE, ZORDER, and especially VACUUM rewrite or delete real files.

Replace YOUR_SCHEMA with a schema that is actually yours (e.g. main.your_name) before running anything. Never run VACUUM ... RETAIN 0 HOURS — it permanently deletes file history. Nothing here starts a cluster, job, or pipeline.

Setup — Your Own Practice Schema

Notebook cell · replace YOUR_SCHEMA before running
PRACTICE_SCHEMA = "main.YOUR_SCHEMA"   # ← e.g. "main.virinchy_practice"
spark.sql(f"CREATE SCHEMA IF NOT EXISTS {PRACTICE_SCHEMA}")

PRACTICE_TABLE = f"{PRACTICE_SCHEMA}.orders_partitioning_practice"

Phase 1 — Create the Small-File Problem on Purpose

Read-only source, safe to run

It's like taking one organised book and ripping it into 200 loose sticky notes on purpose — then seeing how much longer it takes to find one page.

source_df = spark.table("gbmart.bronze.customers")

(source_df
    .repartition(200)
    .write.format("delta").mode("overwrite")
    .saveAsTable(PRACTICE_TABLE))
# repartition(200) forces 200 tiny files —
# simulates months of small streaming writes

Phase 2 — Measure the Baseline

This number is what every later phase compares against
CUSTOMER_ID_HERE = spark.table(PRACTICE_TABLE).select("CustomerID").first()[0]

start = time.time()
result = spark.table(PRACTICE_TABLE).filter(col("CustomerID") == CUSTOMER_ID_HERE).count()
baseline_seconds = time.time() - start

file_count = spark.sql(f"DESCRIBE DETAIL {PRACTICE_TABLE}").select("numFiles").collect()[0][0]

Record both numbers — file count and query time — before touching anything.

Phase 3 — OPTIMIZE + Z-ORDER

Compact the small files, then co-locate by the filter column
spark.sql(f"OPTIMIZE {PRACTICE_TABLE} ZORDER BY (CustomerID)")

file_count_after = spark.sql(f"DESCRIBE DETAIL {PRACTICE_TABLE}") \
    .select("numFiles").collect()[0][0]

# Re-run the exact same filtered query and compare the timing

Phase 4 — Liquid Clustering as an Alternative

A new table, clustered incrementally instead of Z-ORDERed
LIQUID_TABLE = f"{PRACTICE_SCHEMA}.orders_liquid_practice"

spark.sql(f"""
    CREATE TABLE {LIQUID_TABLE}
    CLUSTER BY (CustomerID)
    AS SELECT * FROM {PRACTICE_TABLE}
""")
spark.sql(f"OPTIMIZE {LIQUID_TABLE}")  # no ZORDER BY needed

Liquid Clustering's incremental approach means future OPTIMIZE calls stay cheap even as new data arrives, without re-specifying ZORDER columns each time.

Phase 5 — Caching

A small dimension-shaped table read repeatedly — the textbook caching case
dim_df = spark.table("gbmart.bronze.payment_methods").cache()
dim_df.count()          # first access materializes the cache

start = time.time()
for _ in range(5):
    dim_df.count()       # subsequent access reads from memory
dim_df.unpersist()       # always free cache memory when done

Recap

Key Takeaways

Easy to Create, Easy to Fix

The small-file problem happens by accident in production; OPTIMIZE fixes it on purpose, same as we just did.

Two Ways to Co-Locate

Z-ORDER and Liquid Clustering both improve filtered queries. Liquid Clustering is the modern default — it clusters incrementally.

Real Tables, Real Risk

These same commands against shared gbmart.* tables would affect the whole cohort — that's why production runs are scheduled jobs, not ad-hoc cells.
