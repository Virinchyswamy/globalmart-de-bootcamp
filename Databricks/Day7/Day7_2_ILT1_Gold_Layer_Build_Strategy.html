1. Why Order Matters: Dimensions Before Facts

It's like a cashier trying to ring up a shopper's cart before the store has priced any of its products — there's no tag to scan, no price to charge. A fact table's entire job is to look up context by joining out to dimensions.

If dim_product doesn't exist yet, there's nothing for fact_sales to join against when it needs Actual_price / Discounted_price. A star schema can only be assembled in one direction: dimensions first, fact second.

This is why Day 6 explicitly stopped before building fact_sales — it wasn't a scheduling accident, it's the only order that works.

2. The Join Chain, Table by Table

fact_sales's grain is order_items (one row per order line). Everything else is a lookup from that grain — this is the exact chain GlobalMart's real Gold build uses:

StepJoinBrings in
1silver.order_items (the grain itself)order_item_id, order_id, product_id, quantity
2+ silver.orders on order_idcustomer_id, order_date
3+ silver.products (is_current = true) on product_idActual_price, Discounted_price
4+ gold.dim_date on order_date = dateTime_ID (= date_key)
5+ silver.address (one row per customer) on customer_idAddress_ID
6+ silver.payments on order_idPayment_ID

Why filter is_current = true on products? dim_product is SCD2 — a product can have more than one row (one per price version) in Silver. Filtering to the current version keeps this a clean many-to-one join instead of fanning out order lines.

3. The One-to-Many Trap: Address

Live demo · the fan-out and its fix

If you mail one parcel to a customer who has three addresses on file and you don't pick one, you don't get one delivery — you get three, one to each address. silver.address links to customer_id, not to a specific order, so a plain join would do exactly that: silently fan out every order line for any customer with 2+ addresses.

The fix: pick exactly one address per customer before joining, ranked so a Shipping address wins if one exists, otherwise take whatever's first.

# Rank addresses per customer, Shipping wins, take rank 1 only
address_window = Window.partitionBy("customer_id").orderBy(
    when(col("address_type").contains("Shipping"), 0).otherwise(1)
)
address_primary = (
    spark.table("gbmart.silver.address")
    .withColumn("_rank", row_number().over(address_window))
    .filter("_rank = 1")
)
# rows after ranking == distinct customers -- exactly 1 address each

4. The Big Decision: Natural Keys or Surrogate Keys?

Imagine mailing a birthday card using the address on file from the exact day the person was born, versus mailing it to wherever they live right now — regardless of how long ago that birthday was. Those can be two different addresses.

Same idea, applied to fact_sales

Every dimension built on Day 6 has a proper surrogate key (customer_sk, product_sk, ...). Textbook Kimball: join by surrogate key — that's what makes SCD2 history queryable ("what did this order look like using the customer's address at the time").

GlobalMart's real, running build makes a different, deliberate choice: fact_sales stores Customer_ID, Product_ID, Order_ID, Address_ID, Payment_ID — natural keys, not surrogate keys. Only fact_sales_sk itself (the fact's own row identifier) is generated.

The Tradeoff, Side by Side

Surrogate-key fact (textbook)Natural-key fact (GlobalMart's real build)
Point-in-time accuracyYes — lands on the exact SCD2 version active at order timeNo — always resolves to whatever is "current" when you query
Join complexityHigher — needs effective-date range logic at load timeLower — plain equi-join on IDs you already know
Build/debug speed for trainingSlowerFaster — the reason it was chosen here
Production-grade for a real BI teamPreferredAcceptable as a documented simplification

Not a mistake to "fix" in HOL 2 — build it exactly this way. Understanding why a real team would make this tradeoff, and being able to say what it costs you, is the actual lesson. You'll build fact_sales with natural keys next, faithfully matching the real system.

5. Write Strategy: Overwrite Today, Incremental Later

Today (HOL 2)

mode("overwrite") — same as every dimension in Day 6. At GlobalMart's current data volume this is simple and always correct: re-run the notebook, get a fresh, fully-accurate fact_sales.

This does not scale forever. Recomputing the entire fact table from scratch every time new orders land becomes wasteful as volume grows. Day 9–10 replaces this with an incremental MERGE-based refresh that only touches the new/changed order lines — you're seeing the simple version first on purpose.
