1. Why Fact Tables Have Different Performance Needs Than Bronze

Reading a Bronze table is like flipping through one inbox looking for messages from a single sender — scan the whole thing, or filter on one column. Reading a fact table is a different motion entirely: it's cross-referencing a big ledger against a thin reference booklet, where the filter you actually care about is written in the booklet, not the ledger.

The columns that matter for fact_sales's performance aren't arbitrary — they're exactly the join keys used to reach the dimensions that carry the filters.

SELECT ... FROM fact_sales f
JOIN dim_product p ON f.Product_ID = p.product_id   -- join column
JOIN dim_date d    ON f.Time_ID = d.date_key         -- join column
WHERE p.category = 'Electronics'                     -- filter lands on the DIMENSION,
                                                    -- not the fact

Look at the Real Query Plan

Live demo · .explain() shows what Spark actually decided
query_df = spark.sql("""
    SELECT p.category, SUM(f.Sales_amount) AS revenue
    FROM gbmart.gold.fact_sales f
    JOIN gbmart.gold.dim_product p ON f.Product_ID = p.product_id AND p.is_current = true
    JOIN gbmart.gold.dim_date d    ON f.Time_ID = d.date_key
    WHERE p.category = 'Electronics'
    GROUP BY p.category
""")

query_df.explain(mode="formatted")

Look for a BroadcastHashJoin or a SortMergeJoin in the output — this is what shows what Spark actually decided to do, not what we assume.

2. Broadcast Joins vs Sort-Merge Joins

Handing every attendee in a lecture hall a photocopy of a one-page handout is fast — print it once, everyone has their own copy instantly. That's a broadcast.

Now imagine two entire stadiums of people who need to pair up by matching ticket numbers — everyone has to line up in order and walk past each other to find their match. That's the shuffle cost of a sort-merge join.

Spark picks automatically, based on table size — no manual hint needed.

3. Choosing Z-ORDER Columns — Not a Guess

A library that shelves books by subject lets you scan one shelf instead of walking the entire building for one topic. Z-ORDER does the same thing to the files inside a Delta table — it co-locates rows with similar column values into the same files, so a filter on that column can skip most files entirely.

The right choice comes directly from real query patterns, not intuition.

Z-ORDER Candidates for fact_sales

Real query pattern (from HOL 2's views)Column filtered/joined onZ-ORDER candidate?
vw_monthly_category_sales — join to dim_product, group by monthProduct_ID, Time_IDYes — both, if query volume justifies 2 columns
vw_regional_sales — join to dim_addressAddress_IDYes, if regional queries dominate
Ad-hoc "find this one customer's orders"Customer_IDOnly if this pattern is actually common

Z-ORDER isn't free. More columns means more file-rewrite cost every time OPTIMIZE runs, for diminishing returns per additional column (2–3 columns is the practical ceiling). Pick the columns your actual dashboards and views hit most — not every column that theoretically could be filtered on.

4. Partition Pruning and Predicate Pushdown, Made Visible

Predicate pushdown

A filter like p.category = 'Electronics' is pushed down to file-scan level for dim_product — Spark never reads rows for other categories into memory.

Partition pruning

If a table is partitioned by a column that appears in the WHERE clause, entire partition folders are skipped without opening a single file inside them.

fact_sales itself isn't partitioned — per Day 4's guidance, it relies on Z-ORDER + file statistics (data skipping) instead. Partition pruning matters more for the large, append-heavy Bronze tables from Day 3–4.
