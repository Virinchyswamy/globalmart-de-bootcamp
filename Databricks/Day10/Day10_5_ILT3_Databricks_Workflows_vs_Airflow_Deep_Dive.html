Part 1

Databricks Workflows vs. Apache Airflow

Both are orchestrators. The real question isn't "which one is better" — it's "which one fits the org actually doing the orchestrating."

Something Has to Call Bronze, Then Silver, Then Gold

What every orchestrator does

Runs things in the right order, on a schedule, and tells you when it breaks — whether that's Databricks Workflows, Apache Airflow, or Dagster.

The real decision

Not "which tool is objectively better," but "which tool fits the shape of the organization doing the orchestrating" — a Databricks-only shop has different needs than one coordinating five different systems.

Head to Head — Scope, Tasks, Compute, Authoring

Databricks WorkflowsApache Airflow
ScopeNative to Databricks — built specifically to orchestrate Databricks-native workGeneral-purpose — orchestrates anything an operator exists for: Databricks, Snowflake, S3, dbt, Kubernetes, on-prem systems, plain APIs
Task typesNotebook, Python script, SQL, dbt, Lakeflow/DLT pipeline, JAR, "Run Job" — all first-class, zero extra installWhatever a provider package supplies — 90+ provider packages. Databricks awareness is an add-on, not native
Cluster / computeSpins up a job cluster automatically per run, sized per task, terminates it when the run endsDoesn't manage compute at all — an operator calls the Databricks Jobs REST API; Databricks still starts/stops the cluster
AuthoringPoint-and-click UI, JSON, Databricks Asset Bundles (YAML), or TerraformPython DAG files — "configuration as code," everything is a DAG() object in a .py file

Head to Head — Scheduling, Observability, Governance, Cost

Databricks WorkflowsApache Airflow
Scheduling engineBuilt into the Databricks control plane — nothing extra to runA separate service you operate yourself: scheduler, webserver, metadata database, workers
UI / observabilityPer-task Gantt-style run view — one click from a failed task straight into its Spark UI / driver logsDAG graph and grid views in the Airflow webserver — reaching a Spark UI means leaving Airflow entirely
Governance / lineageUnity Catalog lineage is automatic for every Databricks task — no extra wiringNo native Unity Catalog awareness — lineage has to be stitched together separately
Cost modelJob-compute pricing, billed only while a run is actually executingAirflow itself needs infrastructure running continuously, independent of the compute the tasks it triggers cost

When You'd Actually Choose One Over the Other

A Databricks-only shop — like GlobalMart today

Every source lands in gbmart and every transformation is a Databricks notebook or pipeline. Workflows wins: no separate infrastructure to run, faster to author, Unity Catalog lineage comes for free.

An org already standardized on Airflow

If Databricks is one stop among many — a nightly DAG that also refreshes a Snowflake mart, calls a Salesforce API, and drops a file over SFTP — Airflow wins, because it can express the whole company DAG, not just the Databricks slice.

The common hybrid in practice: Airflow as the company-wide orchestrator, where one Airflow task's entire job is "kick off this one Databricks Workflow and wait for it to finish." Each tool does the part it's actually good at — Airflow coordinates across systems, Workflows coordinates inside Databricks.

Grounding This in GlobalMart's Real Sources — 2, Not 4

Day 3 ILT 1 and Day 4 ILT 1 already established this, explicitly: GlobalMart's production pipeline has exactly two real ingestion pathways.

The 2 real pathways

  • Postgres/Supabase CDC via Lakeflow Connect (orders_data_ingestion_cdc)
  • ADLS Autoloader

The REST API and Neo4j/GraphDB patterns from Day 3 are deliberate side-explorations that land in a sandbox/ path — they never touch a real gbmart.bronze table, so they don't get a task_key here or on Day 11.

Both real pathways feed one Databricks-only pipeline, so Workflows is the right default — and exactly what Day 11's hands-on builds.

Hypothetically: if GlobalMart's Postgres source were ever owned by a different team running its own Airflow instance for reasons that have nothing to do with Databricks, that's the moment a cross-tool Airflow DAG — with GlobalMart's entire Bronze→Silver→Gold Workflow as a single task inside it — would start to make sense.

What Happens When an Upstream Task Fails?

By default, every task's implicit condition is run_if = ALL_SUCCESS. If any task in depends_on did not succeed, the downstream task is not run at all — Databricks marks it SKIPPED, not failed, not run-with-partial-data.

This cascades: if ingest_bronze_autoloader fails, build_silver is skipped, and since build_gold_fact_sales depends on build_silver, it's skipped too — one failure quietly skips the rest of the chain, unless you deliberately design around it.

Retries

Every task in the notebook's task list carries three retry fields — real Databricks Jobs API fields, not simplified stand-ins.

Databricks JobsAirflow

Retries, Simulated in Plain Python

for attempt in range(1, max_retries + 2):
    try:
        result = simulate_flaky_call(task_key, attempt, fail_until)
        return "SUCCEEDED"
    except ConnectionError:
        delay = base_delay * attempt   # increasing delay each retry

Databricks' min_retry_interval_millis does not grow on its own — it's the same minimum wait every time. A truly increasing delay is something you implement yourself inside the task's own code, which is exactly what this simulation does.

Part 4

Failure Handling

In the matching notebook, ingest_bronze_autoloader deliberately exhausts its retries and fails for real. What does a well-designed Workflow do because of that?

Notifications and run_if

Databricks Jobs supports email_notifications and webhook_notifications, configurable per task or per job — fired automatically the moment a task's run finishes, no polling required.

run_if ValueRuns When...
ALL_SUCCESS (default)Every task in depends_on succeeded
AT_LEAST_ONE_SUCCESSAt least one upstream task succeeded
NONE_FAILEDNo upstream task failed (skips still allowed)
ALL_DONEEvery upstream task finished, regardless of outcome
AT_LEAST_ONE_FAILEDAt least one upstream task failed
ALL_FAILEDEvery upstream task failed

The Dedicated On-Failure Task Pattern

Live Demo · Running Python, No Spark Session
{
  "task_key": "on_failure_alert",
  "depends_on": [ ... all 4 tasks above ... ],
  "run_if": "AT_LEAST_ONE_FAILED"   # opposite of the default ALL_SUCCESS
}

on_failure_alert lists every task as a dependency and inverts the default logic — it's designed to stay SKIPPED when everything goes fine, and to fire (send the Slack/email/PagerDuty alert, kick off a cleanup job) exactly when something didn't.

Failure Handling — Contrast With Airflow

Databricks JobsAirflow
Conditional run based on outcomerun_if on the tasktrigger_rule on the task (all_success default, one_failed, all_done...)
Automatic notification on failureemail_notifications / webhook_notificationson_failure_callback, or a dedicated Slack/PagerDuty/email operator
Dedicated "if anything failed" taskdepends_on everything + run_if: AT_LEAST_ONE_FAILEDtrigger_rule="one_failed" downstream of everything it watches

One real failure (ingest_bronze_autoloader, after exhausting its retries) quietly skips 2 downstream tasks — and is the only reason the 5th task runs at all. This is the entire point of designing failure handling deliberately instead of assuming "it'll just retry and be fine."

Key Takeaways

  • ✓ Workflows and Airflow solve the same problem for different scopes. GlobalMart is Databricks-only today, so Workflows is the right default; that changes the moment orchestration needs to reach outside Databricks.
  • ✓ depends_on is how fan-out and fan-in are expressed — GlobalMart's 2 real ingestion pathways fan out from the start of the run, then fan back in at build_silver.
  • ✓ A task with an unsatisfied depends_on isn't retried and isn't failed — it's SKIPPED, and that skip cascades downstream by default.
  • ✓ max_retries / min_retry_interval_millis / retry_on_timeout give a task its own retry policy — Databricks' interval is a flat minimum, not automatic exponential backoff.
  • ✓ run_if: AT_LEAST_ONE_FAILED is what turns a normal task into a dedicated on-failure/alert task.
  • ✓ Every simulation today ran in plain Python — the real Workflow gets built for real next, on Day 11.
