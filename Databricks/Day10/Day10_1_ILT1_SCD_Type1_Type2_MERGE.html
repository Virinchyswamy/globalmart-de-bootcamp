Two Ways to Fix a Mistake

Imagine a customer's address label is wrong, and separately, a customer's email changes. Do you fix both the same way?

Correcting a typo

You cross it out and write the right word. Nobody needs to know what the typo used to say — it's just wrong, now it's right. That's SCD Type 1.

Keeping a diary

You don't erase yesterday's entry when today's happens — you date-stamp it "closed" and add a new entry. Anyone can still ask "what did it say last Tuesday?" That's SCD Type 2.

The real question this ILT answers: how do you actually implement either one, incrementally, without reprocessing the whole table every time?

Why Not Just Two Separate Statements?

Before MERGE existed, you'd write this as two separate statements:

UPDATE dim_table SET ... WHERE key IN (existing_changed_keys);
INSERT INTO dim_table SELECT ... WHERE key NOT IN (existing_keys);

The race condition: between the UPDATE and the INSERT, another process could write to the same table — a row that should have been updated could get inserted as a duplicate instead.

Think of two people editing one spreadsheet cell

Person A reads the cell to decide "update or insert?" Before A finishes writing, Person B changes the same row. A's decision is now stale — and the result is a duplicate, not an update.

MERGE INTO ... WHEN MATCHED ... WHEN NOT MATCHED ... does both in one atomic transaction — Delta Lake guarantees it either fully succeeds or fully rolls back.

The One Operation Behind Both SCD Types

This is the one operation that makes incremental dimension loading — and, in HOL 2, incremental fact loading — safe to run repeatedly without duplicate or half-applied rows.

SCD1 uses MERGE with...

One branch only — whenMatchedUpdate. No history columns, no second branch needed.

SCD2 uses MERGE with...

A whenMatchedUpdate to close out the old row, plus a separate append to insert the new version.

Where this demo writes: everything below runs against a scratch schema (main.scd_demo), cloned via SHALLOW CLONE from the real gbmart tables — never against gbmart directly. An SCD-MERGE demo consumes its pending change the first time it runs; cloning keeps this repeatable for every cohort.

Part 1

SCD Type 1 in Action — dim_address

The simpler case: when an address's address_type label changes, we don't need to know what it used to say — we just overwrite it.

SCD1 MERGE — One Branch, No History Columns

Live Demo · Instructor Notebook
# SCD1 MERGE — one branch, no history columns
(dim_address_tbl.alias("tgt")
    .merge(incoming_change_df.alias("src"), "tgt.address_id = src.address_id")
    .whenMatchedUpdate(set={"address_type": "src.address_type"})
    .execute()
)

One MERGE, one branch (whenMatchedUpdate) — the old value is simply gone afterward. That's correct: nobody needs to ask what an address label used to say.

Part 2

SCD Type 2 in Action — dim_customer

The real pattern GlobalMart uses in production. A customer's email changes — and fact_sales needs to know which email was current at the time of each sale.

The 6-Step SCD2 Flow

  1. Read the current full state of Bronze
  2. Find the version right before the change — CDF reads everything after it
  3. Take only the changed rows via CDF, not a full re-scan
  4. Process just those rows (same cleaning logic as the full load, scoped down)
  5. MERGE — close out the old version (is_current=false, stamp effective_end_date)
  6. Append the new version (is_current=true, fresh customer_sk), then verify — each changed customer shows exactly 2 rows

Step 3 — Read Only What Changed

Live Demo · Instructor Notebook
# Step 3 — CDF read: only what changed since LAST_PROCESSED_VERSION
cdf_changes_df = (
    spark.read.format("delta")
        .option("readChangeFeed", "true")
        .option("startingVersion", LAST_PROCESSED_VERSION + 1)
        .table(BRONZE_TABLE)
        .filter("_change_type != 'update_preimage'")
)

Reading from LAST_PROCESSED_VERSION + 1 onward means Spark never re-scans rows it already processed — however large Bronze grows.

Step 5 — Close Out the Old, Append the New

Live Demo · Instructor Notebook
# 5a — close out old versions where email changed
(silver_table.alias("tgt")
    .merge(processed_df.alias("src"),
        "tgt.customer_id = src.customer_id AND
         tgt.is_current = true AND
         tgt.email <> src.email")
    .whenMatchedUpdate(set={
        "is_current": "false",
        "effective_end_date": "current_date()"})
    .execute()
)

5b is a plain append, not a MERGE — every processed row becomes a brand-new Silver row with a fresh customer_sk = sha2(customer_id + effective_start_date). 5a already closed out the old row, so there's nothing to "match" for the new version.
