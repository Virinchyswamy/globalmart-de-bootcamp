DAY 11 · ILT 4
Without a bouncer

A Data Party With No One At the Door

😵 No map

Nobody knows what tables exist, so people rebuild the same "customer lifetime value" three different (wrong) ways.

🙈 No logbook

A record got viewed by... someone? No idea. No way to ever find out.

🧵 No thread

Nobody knows what feeds a dashboard — one schema change and four reports silently go blank.

🪪 No single badge

Every tool keeps its own guest list. An employee leaves, and IT forgets to remove them from 3 out of 5 systems.

🚪 One door, no rooms

The only options are "see the whole table" or "see nothing." No way to share 90% and protect one column.

The pattern

Every single one of these is a governance problem — none of them are "just get a better tool" problems. That's what a bouncer actually does: give the party structure, not just a velvet rope.

The bouncer's job description

Five Jobs, One Bouncer — Unity Catalog

🔍 Discovery

Knows the venue by heart. Catalog Explorer — search "customer," find every matching table in seconds, comments and all.

📋 Audit

Keeps a logbook. Every query, every grant, is auto-logged in system.access.audit — nobody writes logging code.

🧬 Lineage

Remembers who invited whom. Automatic upstream/downstream map — see what feeds a table before you touch it.

🪪 Identity

One badge, every door. Users & groups defined once, synced from Azure AD/Okta — not re-typed per tool.

🔑 Access

Decides who's on the list. GRANT/REVOKE at catalog, schema, table — down to a row or column.

Real example

New hire at a 200-analyst bank types "risk score" into Catalog Explorer, finds the real table in seconds — no week of Slack archaeology first.

Managed vs. External

Managed = the bouncer owns the furniture — DROP TABLE deletes the data too. External = the bouncer just has the keys to a room you own — DROP TABLE only removes the sign on the door.

Storage Credential + External Location

The keycard system: a Storage Credential (ecomprojectscredentials) authenticates to the cloud account — no raw key ever pasted into a notebook. An External Location (gbmart-ext-loc) says exactly which path it can reach.

Getting in the door

The Guest List — RBAC

RBAC answers one question: "Can this group reach this table at all?" — a yes/no gate. Grant once at the schema level, and it covers every table added later too.

GRANT USE CATALOG ON CATALOG gbmart TO `analysts`;
GRANT SELECT ON SCHEMA gbmart.gold TO `analysts`;
REVOKE SELECT ON SCHEMA gbmart.gold FROM `analysts`;
But

RBAC can't say "only this analyst's own region" or "every column except email." For that, the bouncer needs a wristband system — Fine-Grained Access Control, next.

Once you're already inside

The VIP Wristband — Fine-Grained Access Control

Same table, same door — the wristband decides which rows/columns you actually see once you're through it.

CREATE FUNCTION region_filter(region STRING)
RETURNS BOOLEAN RETURN region = 'US';

ALTER TABLE your_table
SET ROW FILTER region_filter ON (region);

Attach once — every reader, every tool, is filtered automatically. Column masks work the same way, just on values instead of rows (next slide).

The fake-ID trick, but legal

Data Masking

Same mechanism as a row filter, but it swaps the value instead of hiding the row — the table stays queryable, the sensitive bit doesn't.
