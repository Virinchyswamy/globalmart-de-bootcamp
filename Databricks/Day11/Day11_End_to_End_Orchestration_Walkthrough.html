    First Load — Bronze ⏱ any order, all 3 independent

    3 Notebooks, Same Autoloader Pattern

    Every Bronze notebook here uses cloudFiles Autoloader with trigger(availableNow=True) — the same mechanism as every other Bronze table this course has built, not COPY INTO. Its own checkpoint tracks which files it's already ingested, which is what makes the incremental section later work with zero code changes.

    1

    Bronze — Customers

    bronze/01_bronze_customers.ipynb → target: {catalog}.bronze.customers
    Step 1 — Setup

    Sets 5 widgets: catalog, schema (default bronze), mount_point, source_folder (default orchestration-lab/customers), batch_id. Builds SOURCE_PATH, CHECKPOINT_PATH, and SCHEMA_PATH from those.

    Verifies the mount exists — raise RuntimeError if not, rather than silently re-mounting. Lists the files actually sitting in the source folder. Creates the catalog and bronze schema if they don't exist yet.

    Step 2 — Ingest with Autoloader

    Reads CSV via cloudFiles, infers column types, adds 3 tracking columns: _source_file, _batch_id, _ingested_at. Columns arriving: customer_id, first_name, last_name, email, city, state, created_at — already snake_case, no rename needed later. Writes with trigger(availableNow=True) — processes what's there right now, then stops.

    Step 3 — Verify

    Prints total row count and displays rows ordered by _ingested_at. A second cell groups by _source_file — confirms exactly which file(s) landed. Expect 13 rows after this first run.

    First Load — Silver ⏱ order matters: customers → orders → transactions

    Dedup → DQ Scan → Decide → Transform → SCD1 MERGE

    Every Silver notebook follows the same investigate-then-decide shape from Day 5: tag every row with its DQ issue first, decide Fix/Flag/Quarantine per issue type, then MERGE. Orders and Transactions add a referential-integrity check against the Silver table one level up — which is exactly why the run order isn't optional here.

    4

    Silver — Customers (SCD1)

    silver/04_silver_customers.ipynb → target: {catalog}.silver.customers · depends on: Bronze Customers only
    Step 1-2 — Setup, Read & Dedup

    Widgets: catalog, source_schema, target_schema. Reads all of bronze.customers, dedupes by customer_id keeping the row with the latest _ingested_at — this is what makes a second run correctly pick up only the newest profile per customer.

    Step 3-4 — DQ Scan & Decision

    Tags NULL_CUSTOMER_ID, MISSING_EMAIL, INVALID_EMAIL_FORMAT. Decision: NULL_CUSTOMER_ID → Quarantine (no usable key). Missing/invalid email → Flag, keep the row (email is one field, not the whole record).

    Step 5 — Transform

    Builds full_name from first+last, casts created_at to a real date, stamps _silver_updated_at.

    Step 6-7 — Create Table & MERGE

    CREATE TABLE IF NOT EXISTS with columns customer_id, full_name, first_name, last_name, email, city, state, created_at, _dq_issue, _silver_updated_at. SCD1 MERGE on customer_id — this exact statement is what picks up batch 2's email change later, unchanged.

    5

    Silver — Orders (SCD1)

    silver/05_silver_orders.ipynb → target: {catalog}.silver.orders · depends on: Bronze Orders and Silver Customers
    Step 1-2 — Setup, Read & Dedup

    Dedupes by order_id, latest _ingested_at wins.

    Step 3-4 — DQ Scan & Decision

    status gets initcap()'d (source mixes casing: delivered, PLACED, Shipped). A left join against silver.customers checks referential integrity. Decision: NULL_ORDER_ID → Quarantine. ORPHANED_CUSTOMER_ID (no match in Silver customers) → Quarantine — the missing customer might just not have loaded yet.

    Step 5-6 — Create Table & MERGE

    Columns: order_id, customer_id, order_date, status, created_at, _silver_updated_at. SCD1 MERGE on order_id.

    6

    Silver — Transactions (SCD1)

    silver/06_silver_transactions.ipynb → target: {catalog}.silver.transactions · depends on: Bronze Transactions and Silver Orders
    Step 1-2 — Setup, Read & Dedup

    Dedupes by transaction_id. Casts quantity/unit_price/total_amount explicitly — a contract Silver guarantees regardless of what Autoloader happened to infer.

    Step 3-4 — DQ Scan & Decision

    Referential check against silver.orders. Decision: NULL_TRANSACTION_ID → Quarantine. ORPHANED_ORDER_ID → Quarantine. NEGATIVE_TOTAL_AMOUNT → Quarantine for this lab's data (flagged as a real-refund exception worth investigating in a live system, not assumed).

    Step 5-6 — Create Table & MERGE

    Columns: transaction_id, order_id, quantity, unit_price, total_amount, payment_mode, created_at, _silver_updated_at. SCD1 MERGE on transaction_id.

    Why does the customers → orders → transactions order actually matter?

    05 and 06 don't just clean their own table — they verify every row's foreign key exists in the Silver table one level up, before merging. Run 06 before 05 and the transaction RI check runs against an empty or stale silver.orders, incorrectly flagging valid rows as orphaned. This exact dependency chain is what gets wired as depends_on in the Workflow section below, so Databricks enforces the order instead of you having to remember it by hand.

    ✓ Silver Checkpoint

    All three Silver tables exist and are populated, in the order customers → orders → transactions. If any RI check flagged unexpected quarantines, it's almost always an ordering mistake — re-run in the correct sequence before moving on.

    First Load — Gold ⏱ run last, after all 3 Silver tables exist

    Join Chain → Surrogate Key → MERGE

    7

    Gold — fact_sales

    gold/07_gold_fact_sales.ipynb → target: {catalog}.gold.fact_sales · depends on: all 3 Silver tables
    Step 1-2 — Setup, Read Silver Tables

    silver.transactions drives the grain — one fact row per transaction. Orders and customers get joined in to enrich, not to drive row count.

    Step 3 — Build Fact Rows

    transactions → orders on order_id (inner — every transaction must have a real order; Silver already quarantined anything that didn't). orders → customers on customer_id (left, defensive re-check — Silver orders already verified this customer existed at ingestion time; this join catches only the rare case it's since been removed, without dropping the transaction). A sanity-check cell counts rows where that defensive join didn't match — expected 0.

    Step 4 — Surrogate Key

    fact_sales_sk = sha2(transaction_id, 256) — same shape as Day 7's sha2(order_item_id, 256).

    Step 5-6 — Create Table & MERGE

    Columns: fact_sales_sk, transaction_id, order_id, customer_id, order_date, status, payment_mode, quantity, unit_price, total_amount. MERGE on fact_sales_sk — deliberately MERGE, not Day 7's overwrite, since this table needs to support the incremental second run without reprocessing everything.

    Step 7 — Verify

    Total row count, revenue-by-status breakdown, and DESCRIBE HISTORY limited to the last 4 versions — confirms this run actually wrote a new MERGE commit.

    ✓ Gold Checkpoint — First Load Complete

    gold.fact_sales should have one row per valid first-load transaction. This is the end of the manual first-load walkthrough — everything from here on is about wiring these same 7 notebooks into a real, automated Workflow.

    • What Changes in Each Layer

    Bronze

    Each Autoloader stream now writes non-zero new rows — only from the second-load file. customers +6, orders +6, transactions +5.

    Silver Customers

    CUST-002's email should now show the new domain from customers_02.csv — proof the SCD1 MERGE updated an existing row, not inserted a duplicate.

    Silver Orders / Transactions

    Row counts grow by exactly the second-load file's new row count. Verify the RI checks didn't flag any new orders/transactions as orphaned — they shouldn't, since the new customers/orders they depend on landed in the same run, earlier in the dependency chain.

    Gold fact_sales

    Row count grows by the new transaction count. Revenue-by-status breakdown reflects the new orders' statuses.

    This is the actual payoff: the exact same 7 notebooks, the exact same Job, no code changed anywhere — and it correctly picked up only what was new, updated the one customer whose data actually changed, and left everything else untouched. Bronze uses Autoloader's own checkpoint to know what it already saw; Silver and Gold use SCD1 MERGE keyed on the natural/surrogate key to know what to update vs. insert. Neither mechanism needed to be told "this is run 2" — they just are what they are, every time.
