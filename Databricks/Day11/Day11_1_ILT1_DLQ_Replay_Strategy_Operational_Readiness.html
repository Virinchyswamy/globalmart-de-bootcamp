Part 1

What a DLQ Is, and Why

Every pipeline eventually meets a row it cannot process. What you do with that row next says a lot about how production-ready the pipeline is.

Three Ways to Handle a Row That Fails

Malformed JSON, a schema mismatch, a business-rule violation, a null where a downstream step assumes a value — every pipeline hits rows like this eventually. There are three ways to react, in ascending order of how much a production team should tolerate them.

A Dead-Letter Queue (DLQ) is a Delta table that exists purely to catch anything that fails processing, for any reason, anywhere in the pipeline. It's called a "queue" because the intent is to drain it — every row is expected to eventually be replayed or explicitly written off, not to live there forever.

ApproachWhat happensThe problem
Crash the batchOne bad row raises an exception; the whole job failsEvery other good row is blocked too
Silently drop itFiltered out, never written anywhereDisappears with no record it existed
Route it to a DLQWritten as-is, tagged with why and whenGood rows keep flowing; bad row is inspectable

DLQ vs. Day 5's Quarantine — Same Mechanism, Different Scope

You already built something structurally identical to a DLQ in Day 5: gbmart.silver.customers_quarantine. The write pattern — split clean vs. rejected, tag the rejected rows, write both — is the same. What differs is scope.

Day 5's QuarantineThis Session's DLQ
TriggerRows failing one DQ scan's rulesAnything that fails any step
Framing"Is this row valid data?""Did this row survive processing?"
What's nextMostly stays for human reviewDesigned to be replayed

Quarantine is a DLQ used for exactly one purpose — a DQ scan. A DLQ is the general pattern quarantine is one instance of. This session builds the general version, plus the piece Day 5 didn't need: a working replay function.

Part 2

Replay Strategy: Getting Rows Back Out Safely

A DLQ that never drains is just an expensive way to lose data slowly. The dangerous part is how you get rows back out.

The Double-Processing Trap

Think of a DLQ like a returns bin at a warehouse. If a worker "reprocesses" the bin by just re-shipping every item back onto the outgoing truck — without checking whether that item was already re-shipped an hour ago — a customer can end up with two of the same package.

That's exactly the risk with replay. If replay re-runs the transformation and blindly appends the result, and it accidentally runs twice — or retries after a partial failure — the row gets written twice. A fact_sales-style downstream aggregate quietly becomes wrong, and nobody notices until someone asks why revenue doubled for one customer.

Why this matters more than it sounds

  • Nothing crashes when this happens — the job reports success
  • The error only shows up two or three tables downstream, as a number that "looks a little high"
  • By the time someone notices, the duplicate has been aggregated into a report already

The Fix: Key-Based MERGE, Not Blind Append

This is the exact idempotency principle Day 9/Day 10 already established for incremental loading — replay is really just another incremental load, sourced from the DLQ table instead of a change feed.

StepWhat it doesWhy it's safe to re-run
1Read all rows currently in the DLQ tableReading never has side effects
2Apply the fix (default value, corrected business rule)Deterministic — same input, same output
3MERGE the fixed rows into the processed table by natural keyRe-running the same MERGE with the same key can't create a second row
4Remove the replayed rows from the DLQ (MERGE ... WHEN MATCHED THEN DELETE)Once gone from the DLQ, a second replay call finds nothing left to do

Step 3 makes replay safe; step 4 makes it idempotent end-to-end — call the replay function once, or ten times in a row, and the outcome is identical to calling it once.

Not Every DLQ Row Is Auto-Replayable

Some failures need a human decision first — is this actually bad data, or a business rule that needs to be written? And some can't be fixed at all — a row with no usable key can't be written back anywhere meaningfully.

A mature replay strategy separates two buckets

  • Auto-fixable — safe to replay on a schedule, no human needed
  • Needs a human to look at it — don't build a replay function that blindly "fixes" everything just because it's sitting in the DLQ
Part 3

Runbooks: Turning Tribal Knowledge Into a Checklist

A runbook is a written, step-by-step "if this breaks, do this" document — so whoever is on call, not just the person who built the pipeline, can follow it under pressure.

Runbook: orders_data_ingestion_cdc Failed Overnight

Symptom: gbmart.bronze.orders/order_items row counts haven't moved, or the Lakeflow Connect pipeline shows a failed/skipped run.

  1. Detect — check run history in the Jobs/Pipelines UI; run Day 9 HOL 2-style verification (row counts, MAX(updated_at), DESCRIBE HISTORY)
  2. Triage, cheapest checks first — credential/auth expiry (ecomprojectscredentials) → source connectivity → schema drift (Day 3) → cursor (updated_at) nulls/clock-skew → compute/warehouse startup issue
  3. Fix — apply the fix for whichever root cause step 2 found; manually trigger a re-run from the Databricks UI (a real click in the workspace, not automated by this notebook)
  4. Confirm recovery — re-run step 1's checks; this session's SLA check against the real last-write timestamp should now show MET; check whether any rows need replay as a side effect
  5. Close out — log the incident (what broke, root cause, fix, downtime); if it's a new failure mode, add it to step 2

The Pattern Generalizes

Every pipeline in this course deserves the same shape of runbook — the ADLS Autoloader sources, the Silver MERGE jobs, a Gold refresh: symptom, detect, triage (cheapest checks first), fix, confirm, close out.

Write the shell once

Then fill in pipeline-specific checks for step 2. A runbook that doesn't grow after every real incident stops being useful — treat it as a living document, versioned next to the pipeline code.

Part 4

SLAs: Defining and Measuring "Fresh Enough"

A pipeline SLA here means one thing: how stale is too stale? Without a stated number, "is the pipeline healthy" has no answer.

Two Ingestion Patterns, Two Freshness Targets

SourceIngestion patternReasonable SLAHow you'd measure it
orders / order_itemsQuery-based CDC on updated_atWithin 2 hourscurrent_timestamp() vs. MAX(updated_at)
customers, products, addresses, payments, payment_methodsADLS Autoloader — daily file dropWithin 24 hoursDESCRIBE HISTORY — most recent Bronze commit

These numbers are a starting point for class discussion, not a figure handed down from GlobalMart itself — in a real team, the target comes from asking downstream consumers how stale a number they can tolerate, then working backward to a pipeline schedule that can hit it.

Freshness SLA ≠ "Did the Pipeline Succeed"

A pipeline can run green — no errors, exit code 0 — and still breach its freshness SLA. No new file arrived at all, so there was nothing to fail on, but the data is now a day older than the SLA allows.

Measuring freshness directly catches that; watching only for job failures does not. The SLA check built today is intentionally print/log only — no email, Slack, or PagerDuty call. Wiring a real alert on top is an orchestration-layer concern (Databricks Workflows' own notification settings) — out of scope here.

Fix by reason, upsert by key, drain the queue — never a blind append

        .merge(fixed_df.alias("src"), "tgt.customer_id = src.customer_id")
        .whenMatchedUpdateAll()
        .whenNotMatchedInsertAll()
        .execute())

    # Drain the DLQ -- merge-delete exactly the rows just replayed.
    (dlq_tbl.alias("tgt")
        .merge(fixed_df.select("customer_id").alias("src"), "tgt.customer_id = src.customer_id")
        .whenMatchedDelete()
        .execute())

Steps 8–9 — check_sla(): Print-Only Freshness Check

Compares a last-success timestamp against a freshness target — no real alert is ever sent
def check_sla(source_name, last_success_ts, freshness_target_hours):
    hours_since = (datetime.now() - last_success_ts) \
                    .total_seconds() / 3600
    status = "MET" if hours_since <= freshness_target_hours else "BREACHED"
    print(f"SLA status: {status}")
    return status

Key Takeaways

✅ DLQ & Replay

Route, don't crash or drop. Replay must be idempotent — key-based MERGE plus draining the DLQ makes "replay twice" match "replay once."

📋 Runbooks & SLAs

Runbooks turn tribal knowledge into a checklist. SLAs measure freshness, not success — a pipeline can exit cleanly and still be stale.
