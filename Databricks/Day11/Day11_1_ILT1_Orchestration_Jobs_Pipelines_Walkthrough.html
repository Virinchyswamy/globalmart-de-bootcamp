Section 3

Compute: "Add New Cluster"

The single most important cost decision on this whole screen

Why a New Cluster, Not Your Existing One

All-purpose clusterJob cluster ("Add new cluster")
LifetimeRuns until you stop it, or it idles outStarts with the job, terminates automatically when it ends
Shared withAnyone attached, any timeNobody — exclusive to this run
DBU rateHigher — interactive pricingLower — jobs-compute pricing
Right forDevelopment, exploring data liveScheduled, unattended production runs

A nightly scheduled job should never point at your personal all-purpose cluster — more expensive per DBU, and if you're mid-edit on it, you've just contended for compute with your own pipeline.

Live: Deselecting Photon Acceleration

Screen: New cluster config

Photon is Databricks' vectorized query engine — dramatically faster for SQL/DataFrame-shaped work, at a higher DBU rate.

Deselect it when —

The workload is light (today's demo), dominated by UDFs/ML training, or the job isn't cost-critical.

Select it when —

Genuinely SQL/join-heavy at real volume — exactly the shape of GlobalMart's own Bronze→Silver→Gold builds. Day 7 ILT 2 already measured Photon's real speed impact on fact_sales.

Node Type — Standard_DS3_v2

What it is

An Azure VM family. DS3_v2 is general-purpose.

The spec

14 GB RAM, 4 cores — comfortably enough for a demo job touching a handful of small tables.

Sizing rule

Match node memory to your largest single-task working set, not your whole warehouse.

1 worker, no autoscaling, is fine here. Autoscaling matters once volume varies run to run — a monthly job that's 10x bigger at month-end, for example.

Section 4

Dependent Libraries

Anything Not Already on the Runtime

The Runtime ships with pyspark, pandas, numpy, delta-spark pre-installed. A dependent library is anything your notebook imports that isn't on that list — missing it means ModuleNotFoundError, every run, since a job cluster starts fresh.

LibraryReal GlobalMart reason you'd need itSource
openpyxlReading .xlsx directly — e.g. the supply chain assessment's Data Dictionary workbookPyPI
Postgres JDBC driverHand-rolling a JDBC connection to Supabase, bypassing the managed Lakeflow Connect pipelineMaven
azure-storage-blobDirect SDK access to ADLS, bypassing Spark's abfss:// readerPyPI

Notice: nothing in the real Bronze/Silver/Gold pipeline built across this course needs an extra library. That's the platform's native tools doing the job — reach for a dependent library only with a specific, named reason, and always pin the version.

Section 5

Parameters

The one rule in this whole session that matters most

Live: A Good Parameter — catalog_name

Screen: Task → Parameters tab
# Key:   catalog_name
# Value: harsh_kumar01_npmentorskool_onmicrosoft_com

CATALOG = dbutils.widgets.get("catalog_name")
df = spark.table(f"{CATALOG}.silver.orders")

Run the exact same job against a _dev catalog by changing one value — no code edit. This is why parameters exist: it identifies where, it isn't secret, and it genuinely differs across dev/test/prod (Day 11 ILT 2's environment strategy).

Never Do This: storage_account_key as a Parameter

The mistake, shown deliberately
# Key:   storage_account_key
# Value: <a real 88-character Azure storage key>   ❌ NEVER

Why this is a real mistake: parameters are stored in plaintext in the job config and every run's history — anyone with permission to view the job, not even run it, can read it straight off the Run Details screen. It shows up in audit logs. There's no rotation without editing every job that references it.

This is the exact class of mistake this cohort's own real pipeline hit once — a hardcoded storage key sitting in a committed notebook, caught only because GitHub's push protection blocked it.

The Correct Way: a Secret Scope

storage_key = dbutils.secrets.get(scope="globalmart-storage", key="account-key")
print(storage_key)  # prints [REDACTED] -- automatically, everywhere
Job parameterSecret Scope
Right forAnything non-sensitive that varies by run — catalog, date, thresholdAnything that grants access — key, password, token, connection string
Visible toAnyone who can view the jobRedacted from output everywhere, even for code that calls it

Notifications, In Detail

The Event Types

EventFires whenGlobalMart example
On startRun beginsRarely used — mostly noise
On successEvery task completes cleanOff for routine nightly runs; on for a rare one-time backfill
On failureAny task failsAlways on, every production job
On duration warningExceeds a threshold, even on successThe Gold fact_sales refresh — 10 min normally, 40 min means investigate now
On backlog exceededStreaming task falls behindBronze Autoloader/streaming tasks specifically

A Concrete GlobalMart Notification Plan

Bronze ingestion job     → On failure only               → #data-eng-alerts
Silver transform job     → On failure + duration warning → #data-eng-alerts
Gold fact_sales refresh  → On failure + duration warning → #data-eng-alerts + owner email
One-time backfill job    → On start/success/failure     → email to whoever's running it

Routine, frequent jobs stay quiet unless something's wrong. Rare, high-stakes runs get chattier — there's a human specifically watching that one.

Section 7

Retries, In Detail

The Settings, and When They Help

Retries help for —

Transient failures: a network blip to Supabase, a cluster still spinning up, a momentary API rate limit. True now, false a minute later, no code change needed. 2-3 retries, 1-2 min interval is standard.

Settings

Retries — how many attempts. Min retry interval — wait time between. Retry on timeout — whether a too-slow (not errored) task also retries.

The Idempotency Trap

A retry is only safe if running the same task twice produces the same result as running it once.

This is exactly the bug this cohort actually hit: orders_incremental_scd1_merge's CDF read could hand MERGE two rows for the same order_id, and separately, a customers SCD2 notebook had an insert block accidentally tripled. With retries on, a partial failure wouldn't just fail loudly again — it could succeed on attempt two while having already written duplicate data on attempt one.

Ask before enabling retries: "if this task succeeds twice in a row on the same input, is that safe?" A MERGE keyed on a real primary key — yes. A blind append with no key — no.

Section 8

Metric Thresholds, In Detail

Catching a Job That's Quietly Getting Worse

A threshold rule — if RUN_DURATION_SECONDS > X — doesn't stop the job. It triggers whichever notification you attached to "duration warning" back in Section 6.

Without one, a job that goes from 10 minutes to 55 minutes still shows a plain green success — nothing visibly wrong, because nothing failed. A threshold turns a silent, slow-motion degradation into an active alert while the job is still succeeding, when you have the most time to investigate calmly.

A Concrete GlobalMart Threshold Plan

Bronze Autoloader task      → RUN_DURATION_SECONDS > 300   (normally ~2 min)
Silver SCD2 merge tasks     → RUN_DURATION_SECONDS > 600   (normally ~5-8 min)
Gold fact_sales refresh     → RUN_DURATION_SECONDS > 900   (normally ~10 min; feeds live dashboards)

Set thresholds from the last 10-20 runs' real durations, at roughly 2-3x the normal ceiling. Too tight → alert fatigue from normal variance. Too loose → it never fires before something's badly wrong.

The Full Live-Demo Script, End to End
