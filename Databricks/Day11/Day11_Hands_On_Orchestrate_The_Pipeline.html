Before You Open Databricks

How This Works

Three phases, in order. Don't skip ahead to Phase 2 before Phase 1 is genuinely done — Phase 2 only makes sense once you've felt, by hand, what each of the 7 notebooks actually does.

1By Hand

Get the first batch of data into ADLS, mount it, and run all 7 notebooks yourself, one at a time, in the right order. This is where you actually learn what Bronze/Silver/Gold do for these 3 tables — no orchestration yet.

2Build the Job

Take those same 7 notebooks and wire them into a real Databricks Workflow — one task per notebook, dependencies matching the DAG you just ran by hand, parameters matching each notebook's widgets exactly.

3Second Load

Drop a second batch of files into the same ADLS folders — no notebook edits. Run the Job and watch it pick up only the new data, on its own.

Why do Phase 1 manually at all, if we're just going to automate it in Phase 2? Because a Job that runs notebooks you don't understand is a black box you can't debug when it fails at 2 AM. Phase 1 is where you build the mental model; Phase 2 is where you stop needing to click "Run" yourself every time.

Phase 1 ⏱ do this first, no shortcuts

Run the First Load by Hand

Step A — New ADLS Folder

Create a new folder for this lab — don't drop these files into the main GlobalMart raw-data/ folder you've used all course. Keeping this lab's practice data separate means nothing here can collide with the real pipeline you already built.

  • In your ADLS container, create a new folder — e.g. orchestration-lab/ — and inside it, three subfolders: customers/, orders/, transactions/.
  • Upload the 3 first-load CSVs from datasets-first-load/, one file into its matching subfolder (customers_01.csv → orchestration-lab/customers/, and so on).

    • Step B — Mount It

    Same mounting pattern from Day 4 — a new mount point dedicated to this lab, not reusing your existing GlobalMart mount.

    MOUNT_POINT = "/mnt/<yourname>_orchestration_lab"
STORAGE_ACCOUNT = "YOUR_STORAGE_ACCOUNT_NAME"
CONTAINER = "YOUR_CONTAINER_NAME"
# mount as taught in Day 4 -- same dbutils.fs.mount() pattern, new mount point

    Step C — Run Bronze (any order — all 3 are independent)

  • Open notebooks/bronze/01_bronze_customers.ipynb. Update the source_path widget default to your new mount/ADLS path, then run every cell top to bottom.
  • Do the same for 02_bronze_orders.ipynb and 03_bronze_transactions.ipynb.
  • Each notebook's Step 3 prints a row count — confirm you see 13 customers, 12 orders, 12 transactions in Bronze before moving on.

    • Notice the ingestion pattern: Bronze uses COPY INTO, not a plain file read — it tracks which files it's already ingested. That's the mechanism that makes Phase 3 work later: re-run the same notebook after dropping new files, and only the new files get picked up.

    Step D — Run Silver order matters here

  • 04_silver_customers.ipynb first — it only depends on Bronze Customers.
  • 05_silver_orders.ipynb second — it does a referential-integrity check against silver.customers, so that table must exist and be populated first.
  • 06_silver_transactions.ipynb third — same reason, it checks against silver.orders.
    • Why does this order actually matter?

    Each Silver notebook doesn't just clean its own table — 05 and 06 also verify that every row's foreign key actually exists in the Silver table it depends on, before merging. Run 06 before 05 and every transaction's referential-integrity check runs against an empty or stale silver.orders — you'd see rows incorrectly flagged as orphaned that aren't really orphaned at all.

    This exact dependency chain — customers → orders → transactions — is what you'll wire up explicitly as depends_on in Phase 2's Workflow, so Databricks enforces the order for you instead of you having to remember it.

    Step E — Run Gold

  • 07_gold_fact_sales.ipynb — joins all three Silver tables and MERGEs into gold.fact_sales. Run it last, after all three Silver notebooks have completed.
  • Its Step 5 verify cell prints a revenue-by-status breakdown — sanity-check the row count matches your transaction count.
    • ✓ Phase 1 Checkpoint

    Before moving to Phase 2, confirm: bronze.customers/orders/transactions each have their expected first-load row count, silver.customers/orders/transactions exist and are populated, and gold.fact_sales has one row per transaction. If any of these is missing, don't build the Workflow yet — fix it by hand first.

    Build Steps

  • Jobs & Pipelines → Create Job. Name the job something you'll recognize, e.g. globalmart_orchestration_lab.
  • Create all 7 tasks — one per notebook, task names matching the table names above (bronze_customers, silver_orders, etc.) so your depends_on references read cleanly.
  • For each task: Type Notebook, Source Workspace, path pointing at the matching notebook under Databricks/Day11/orchestration/notebooks/.
  • Set depends_on for each task exactly per the table above — this is what makes Databricks run the 3 Bronze tasks in parallel, then wait, then run Silver in the right order, then Gold last.
  • Compute: one shared job cluster for the whole job (Add new cluster, same settings as ILT 1 — Standard_DS3_v2, Photon deselected) is enough for a dataset this size.
  • Parameters — match each notebook's widget names exactly. See the table below.

    • Parameters, Per Notebook

    NotebookWidget nameWhat to set it to

    Bronze (all 3)schemabronze
    Bronze (all 3)source_pathyour mounted path's matching subfolder, e.g. /mnt/<yourname>_orchestration_lab/customers/
    Bronze (all 3)batch_ida label for this run, e.g. batch_001 — free text, used only for your own tracking

    Remember ILT 1's rule: catalog, schema, source_path are all fine as parameters — none of them are secret. Nothing in this lab needs a credential parameter at all, since ADLS access goes through your existing mount, not a raw key typed into a Job.

    ✓ Phase 2 Checkpoint

    Run the Job now, once, even though it's the same data you already loaded by hand. Every Bronze task's COPY INTO should report 0 files copied (already ingested in Phase 1), and every Silver/Gold MERGE should be a no-op — same row counts as Phase 1 ended with. This proves the Job is correctly wired before you introduce new data in Phase 3.

    Phase 3 ⏱ the payoff

    Second Load, Fully Orchestrated

    No notebook edits, no manual runs. This is the moment the whole lab has been building toward.

  • Upload the 3 files from datasets-second-load/ into the same ADLS subfolders you used in Phase 1 — customers_02.csv alongside customers_01.csv, and so on. Same folders, don't create new ones.
  • Go to your Job and click Run now — or, if you set up a schedule, just wait for it.
  • Watch the run's task graph live. Confirm the 3 Bronze tasks start together, then Silver runs in order, then Gold runs last — exactly the dependency graph from Phase 2, enforced automatically this time.

    • What to Actually Look For

    In Bronze

    Each COPY INTO result should now show non-zero num_files_copied/num_rows_inserted — only the second-load file, not the first-load file again.

    In Silver customers

    CUST-002's email should now show the new domain from customers_02.csv — proof the SCD1 MERGE updated an existing row instead of inserting a duplicate.

    In Silver orders/transactions

    Row counts should grow by exactly the second-load file's new row count — verify the referential-integrity checks didn't flag any of the new orders/transactions as orphaned.

    In Gold fact_sales

    Row count should grow by the new transaction count, and the revenue-by-status breakdown should reflect the new orders' statuses.

    This is the whole point: the exact same 7 notebooks, the exact same Job, no code changed anywhere — and it correctly picked up only what was new, updated the one customer whose data actually changed, and left everything else untouched. That's what "orchestrated" means in practice, not just in theory.
