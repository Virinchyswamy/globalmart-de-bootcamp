Recap: From Watermarks to a Managed Pipeline

In ILT 1 we saw why a simple WHERE updated_at > last_run watermark falls apart:

  • It misses DELETEs entirely — the row is just gone, nothing to filter on
  • It only catches an UPDATE if the source table actually has an updated_at column
  • At scale, re-scanning even the changed slice on a timer is wasteful

The gold-standard fix — reading the Write-Ahead Log (WAL) directly through a replication slot — is what we did by hand with raw JDBC in ILT 1 (and go deeper in HOL 2), so the mechanics aren't a mystery.

Today's question: Lakeflow Connect can run either strategy as a managed pipeline. Which one does GlobalMart actually use?

Lakeflow Connect Has Two Connector Modes

ModeHow It Detects ChangesCatches DELETEs?
Log-based (WAL / logical replication)Reads the database's write-ahead log directly, via a Postgres publicationYes — a DELETE is a WAL event like any other, as long as REPLICA IDENTITY FULL is set
Query-based (cursor column)Runs WHERE cursor_col > last_value on a schedule — same idea as a watermarkNo — same blind spot as manual watermarking

GlobalMart's real, running pipeline actually uses query-based / cursor capture — not log-based WAL streaming. The cursor column is updated_at, and history tracking is Off (SCD1). On each run, Lakeflow Connect queries WHERE updated_at > last_seen_value and upserts whatever comes back. Two things were set up on the Supabase side first: REPLICA IDENTITY FULL on both tables, and a publication naming them — real, correct setup for logical replication in general, but this pipeline doesn't use them to stream the WAL. Because it's cursor-based, it captures every INSERT and UPDATE but cannot detect hard DELETEs — a deleted row simply stops matching the query.

What Changes With a Managed Pipeline

Manual JDBC + WAL (ILT 1 / HOL 2)Lakeflow Connect — query-based (GlobalMart's real pipeline)
You open the JDBC connectionDatabricks manages the connection
You create the replication slotNot used by this pipeline — no replication slot here
You call pg_logical_slot_get_changes()Databricks re-queries WHERE updated_at > last_seen_value
You parse INSERT/UPDATE/DELETE textDatabricks applies INSERT/UPDATE for you (not DELETE)
You write to Bronze yourselfLands as a governed, managed Unity Catalog table
Captures DELETEs, more code to maintainMisses DELETEs, but far less code to maintain
Section 2

How Lakeflow Connect Works End to End

Five steps, from a stored connection to a governed table in Unity Catalog.

Connection → Pipeline → Snapshot → Sync → Destination

  1. Connection — a Unity Catalog object storing host/port/credentials. Created once, reused by any number of pipelines.
  2. Ingestion Pipeline — pick a Connection, pick tables, pick a connector mode, pick a destination catalog/schema.
  3. First Run — Full Snapshot — reads every row currently in the source table(s) as the initial state.
  4. Every Run After — Incremental Sync — reads only what changed since the last run.
  5. Destination — lands as a Delta Streaming Table in Unity Catalog: full lineage, access control, audit — the table type Lakeflow Connect always creates, whether the connector mode is log-based or query-based.

Why This Matters for orders & order_items

These two GlobalMart tables are live, continuously changing — order status moves pending → shipped → delivered, line items get added or corrected.

Re-reading the whole table on a timer (Autoloader-style) would either miss changes or waste enormous compute at GlobalMart's volume (~126,000 orders, ~377,000 order_items). On every run, Lakeflow Connect queries WHERE updated_at > last_seen_value and upserts just the changed rows, without a hand-rolled watermark script, while Databricks manages the connection, scheduling, retries, and schema evolution for you. This query-based/cursor mode captures every insert and update — but, like any cursor-based watermark, it does not catch hard deletes.

Section 3

Worked Example: The Real Pipeline

This is the actual, currently-running Lakeflow Connect pipeline behind GlobalMart's Bronze orders/order_items tables — not a hypothetical. In HOL 1 you'll build your own, named after yourself.

Step 0 — Supabase-Side Setup (Before the Connection Existed)

Run step by step in the Supabase SQL Editor — verify each step's output before running the next.

-- updated_at column + trigger to refresh it
CREATE TRIGGER trg_orders_updated_at
BEFORE INSERT OR UPDATE ON orders
FOR EACH ROW EXECUTE FUNCTION set_updated_at();
-- (same pattern on order_items)

-- REPLICA IDENTITY FULL — required for CDC to capture
-- full row images on UPDATE/DELETE, not just the PK
ALTER TABLE orders REPLICA IDENTITY FULL;
ALTER TABLE order_items REPLICA IDENTITY FULL;

-- Publication — exposes both tables to Lakeflow Connect
CREATE PUBLICATION gbmart_pub
  FOR TABLE orders, order_items;

Data loaded via CSV import, not INSERTs

At GlobalMart's real volume — ~126,000 orders rows, ~377,000 order_items rows — row-by-row INSERTs aren't practical.

Supabase → Table Editor → orders
  → Insert → Import data from CSV

Supabase → Table Editor → order_items
  → Insert → Import data from CSV

Real, correct setup — but not what this pipeline actually uses: REPLICA IDENTITY FULL and the publication are what make reliable Postgres logical replication possible in general. As the next slide shows, though, GlobalMart's real pipeline runs in query/cursor mode, not log-based mode — so it doesn't end up using this setup to stream the WAL.

Step 1 — The Connection (Already Created)

Databricks → Catalog → Connections → ecom_gbmart_conn

  Connection name : ecom_gbmart_conn
  Type            : PostgreSQL
  Host            : aws-0-ap-south-1.pooler.supabase.com
  Port            : 5432

This is a Unity Catalog Connection object — host/port/credentials are stored once, centrally, and referenced by name.

No password ever appears in the pipeline definition itself. That's the whole governance win in one sentence. Once created, orders/order_items are browsable directly under the connection in Catalog Explorer — how you confirm both tables and the Step 0 publication are visible before building the pipeline.

Step 2 — The Ingestion Pipeline (Real Spec)

Pipeline name : orders_data_ingestion_cdc
Compute       : serverless          ← no cluster to size or manage
Connection    : ecom_gbmart_conn
Source type   : POSTGRESQL

  Source                                  Destination (Unity Catalog)
  ─────────────────────────────────       ──────────────────────────────
  postgres.globalmart.orders         →    gbmart.bronze.orders
  postgres.globalmart.order_items    →    gbmart.bronze.order_items

  Table configuration:
    primary_keys      : orderid           ← real source column, NO underscore
                         orderitemid       ← order_id gets the underscore later, in Silver
    cursor_column      : updated_at       ← query/cursor mode: WHERE updated_at > last_seen_value
    history_tracking   : Off (SCD Type 1) ← latest value per row only
    schedule           : none             ← skipped, triggered manually

Notice: the source column is orderid, not order_id. Bronze lands data exactly as the source names it — the clean, underscored name is a Silver-layer standardization.

Why updated_at and not OrderDate? OrderDate is set once, when the order is placed, and never changes again — a later status update gives the pipeline no signal. updated_at is refreshed by the Step 0 trigger on every INSERT and UPDATE, so it correctly sequences every change. It has no way to represent a DELETE — a deleted row has no updated_at left to query for.

Why no schedule? The real pipeline was left without one — skip it, don't add one, and trigger runs manually via Start. A production rollout would add a periodic schedule (e.g. hourly) later — a separate decision from what's being taught here.

First Run vs. Every Run After

First Run — Full Snapshot

Status     : Completed
orders     : Upserted ~126,000 rows
order_items: Upserted ~377,000 rows
Catalog    : gbmart.bronze

Every Run After — Insert & Update Sync; Delete Does Not

Order O-10021 gets updated → updated_at = now()
  → Pipeline triggered manually (no schedule is set)
  → Upserted: 1  ← only that row, not the full table

Someone DELETEs a row entirely in Supabase
  → The row simply stops appearing in WHERE updated_at > last_seen_value
  → Lakeflow Connect has no event to react to — nothing signals a DELETE happened
  → The row is NOT removed from Bronze — it silently goes stale

This is the real limitation of cursor-based capture — REPLICA IDENTITY FULL and the Step 0 publication are correct setup for logical replication in general, but this pipeline's cursor/query mode doesn't use them to catch deletes.

GlobalMart's Full Ingestion Tool Assignment

Not every table needs Lakeflow Connect — match the tool to the source's shape:

TableSourceToolWhy
orders, order_itemsPostgres (Supabase)Lakeflow Connect (query/cursor-based)Continuously updated — INSERT and UPDATE captured every run; DELETEs are not
customers, addresses, payments, returnsADLS file dropAutoloader — IncrementalGrows over time — append + watermark
products, payment_methodsADLS file dropAutoloader — Full loadSmall / periodically refreshed — overwrite is safe

Decision rule: live database with continuous INSERT/UPDATE/DELETE → Lakeflow Connect. File that lands in ADLS and grows over time → Autoloader + Incremental. Small file, fully refreshed each time → Autoloader + Full load.

Section 4

The Other Half of Today

The old way to reach ADLS (mounting), why hardcoded storage keys are a problem — and the two Unity Catalog building blocks that replace both.

Old Approach: Mounting ADLS with dbutils.fs.mount()

Before Unity Catalog, teams gave a whole ADLS container a permanent path in the workspace, once, using a key or service principal:

configs = {"fs.azure.account.key.STORAGE_ACCT.dfs.core.windows.net": "STORAGE_KEY"}

dbutils.fs.mount(
    source       = "abfss://container@STORAGE_ACCT.dfs.core.windows.net/",
    mount_point  = "/mnt/globalmart",
    extra_configs= configs
)

# From then on, every notebook in the workspace just does:
spark.read.csv("/mnt/globalmart/raw/customers.csv")
ProblemWhat It Means
Credentials baked inThe key/service-principal secret is baked into the mount's cluster config — a security risk
Workspace-level, not UC-governedA mount point is visible and usable by anyone in the whole workspace — Unity Catalog has no say over it
No fine-grained accessNo way to grant one team read-only and another read-write per user or role
Bypasses governance entirelyMounts sit outside Unity Catalog's audit log, lineage, and permission model completely

This is why nobody sets up new mounts anymore — Storage Credentials + External Locations (this session) solve every one of these problems.

Since Day 1, Every Notebook Has Started Like This

storage_account_name = "YOUR_STORAGE_ACCOUNT_NAME"
storage_account_key  = "YOUR_STORAGE_ACCOUNT_KEY"  # ← 88-char secret

spark.conf.set(
    f"fs.azure.account.key.{storage_account_name}.dfs.core.windows.net",
    storage_account_key
)
ProblemWhat It Means
Security riskAnyone who opens the notebook sees a key with full read/write access
Git exposureA committed key stays in git history even after being deleted from the file
Key rotationRotating the key breaks every notebook that hardcodes it, all at once
No audit trailAzure sees "the key was used" — not which user, from which notebook
All-or-nothingEveryone with the key has full read/write — no read-only option

Current Flow vs. What We Want

CURRENT FLOW (key-based):
  Notebook → spark.conf.set(key) → Spark driver → ADLS
                    ↑
              secret lives in plain text in the notebook cell

WHAT WE WANT:
  Notebook → abfss://... → Unity Catalog checks permission → ADLS
                                        ↑
                              no key anywhere — auth handled centrally

The fix is two Unity Catalog objects, created once by an admin, then reused by every notebook.

The Two Unity Catalog Building Blocks

Think of it like an office building: an employee badge proves who you are, and a specific door only opens for badges that are allowed through it.

Storage Credential = the badge

Databricks' identity card for Azure. It wraps an Azure Managed Identity (the Databricks Access Connector) — an Azure resource granted "Storage Blob Data Contributor" on your ADLS account. No password, no key, nothing that can leak.

External Location = the door it unlocks

A registered ADLS path + which Storage Credential is allowed to use it.

External Location: gbmart-ext-loc
  URL:                abfss://ecom-gbmart-data
                       @ecomadlsdata.dfs.core.windows.net/
  Storage Credential: ecomprojectscredentials

The Full Auth Chain

Notebook uses abfss://ecom-gbmart-data@ecomadlsdata.dfs.core.windows.net/raw-data/
       ↓
Unity Catalog: "This path is covered by External Location 'gbmart-ext-loc'"
       ↓
Storage Credential: "Use managed identity 'ecomprojectscredentials'"
       ↓
Azure RBAC: "That managed identity has Storage Blob Data Contributor on ecomadlsdata"
       ↓
ADLS Gen2: access granted — data returned

At no point does a key appear anywhere in the notebook.

Worked Example — Real External Location, Before vs. After

BEFORE (key-based auth):

storage_account_name = "YOUR_STORAGE_ACCOUNT_NAME"
storage_account_key  = "YOUR_STORAGE_ACCOUNT_KEY"  # ← secret

spark.conf.set(...)

AFTER (Unity Catalog external location):

# No setup cell needed — External Location handles auth.
base_path = "abfss://ecom-gbmart-data@ecomadlsdata
              .dfs.core.windows.net/raw-data"

In HOL 1 you'll create your own Access Connector–backed Storage Credential and External Location against your own Day-1 storage account, and run dbutils.fs.ls() with zero keys in the notebook. gbmart-ext-loc stays the shared, real location the rest of the course's pipeline reads from.
