Why This Matters

Why CDF, Not Just "Read the Whole Table Again"

Like a bank statement that lists only this month's transactions, instead of reprinting your entire life-savings history every single time. CDF gives Silver the same shortcut.

📖 Without CDF

Silver reads all 126,000+ orders every single run, just to find the handful that actually changed. Slower and pricier every month, as the table keeps growing.

⚡ With CDF

Silver reads only the ~800 rows that changed since last run. Fast, cheap, and the cost stays roughly constant — it doesn't grow just because the table did.

CDF is a Delta Lake table property. Once you turn it on, every INSERT / UPDATE / DELETE against that table is automatically recorded as a row-level event — Delta does this as part of the write itself. No separate logging code, nothing extra to remember to call.

What CDF Actually Records

ColumnWhat it tells you
_change_typeinsert, update_preimage, update_postimage, or delete
_commit_versionWhich Delta table version the change happened in
_commit_timestampWhen the change was committed

An UPDATE produces two CDF rows — the row's old values (update_preimage) and its new values (update_postimage). When you only care what a row looks like right now, always filter out update_preimage — you'll see this exact filter used for real below.

Rollout, Step 1 · Real Code, Runs For Real

Enabling CDF on Bronze

A single, idempotent metadata change — safe to run more than once, no extra compute cost. This is the exact loop GlobalMart's real pipeline notebook (01_bronze_enable_cdf.py) runs. 

# Attempts ALL 8 Bronze tables -- does NOT pre-filter orders/order_items out
# of the list before trying. try/except records what actually happens.
CATALOG = "gbmart"
SCHEMA  = "bronze"

BRONZE_TABLES = [
    "customers", "orders", "order_items", "products",
    "addresses", "payments", "payment_methods", "returns"
]

for table in BRONZE_TABLES:
    full_name = f"{CATALOG}.{SCHEMA}.{table}"
    try:
        spark.sql(f"ALTER TABLE {full_name} SET TBLPROPERTIES (delta.enableChangeDataFeed = true)")
        print(f"  CDF enabled : {full_name}")
    except Exception as e:
        print(f"  SKIPPED     : {full_name} — {str(e)[:80]}")

🔎 Notice: addresses is plural here

That's the real Bronze table name. Keep it exactly as written — Silver's version of this table is spelled differently, on purpose (see the next section).

👀 The code finds out, it doesn't guess

The real notebook's own markdown predicts orders/order_items will get skipped — Lakeflow Connect owns them as Streaming Tables. But the code never assumes that ahead of time. It attempts all 8, and try/except records the real outcome.

Santosh Kumar ran this exact loop against real gbmart and watched orders and order_items print SKIPPED — exactly what the real pipeline notebook's markdown expected, just confirmed live instead of assumed in advance.

Rollout, Step 2

Enabling CDF on Silver Too

Turn it on now, before Silver has any incremental readers. Turning CDF on late means missing whatever changed in the gap between "table exists" and "CDF enabled." 

SILVER_TABLES = [
    "customers", "orders", "order_items", "products",
    "address", "payments", "payment_methods", "returns"
]

for table in SILVER_TABLES:
    full_name = f"gbmart.silver.{table}"
    try:
        spark.sql(f"ALTER TABLE {full_name} SET TBLPROPERTIES (delta.enableChangeDataFeed = true)")
        print(f"  CDF enabled : {full_name}")
    except Exception as e:
        print(f"  SKIPPED     : {full_name} — {str(e)[:80]}")

Look closely: address, singular — versus addresses, plural, in Bronze a section ago. Not a typo to "fix." It's the real, verbatim table name in GlobalMart's actual Silver schema. Enabling CDF on Silver now isn't because today's Gold build needs it. It's so the option is already open, at zero cost, for later. Same Batch API, One New Option Pair

Reading a Change Feed

No separate API to learn. Reading changes since a version is one option pair on a completely normal batch read.

Live check — run against real gbmart, read-only
cdf_df = (
    spark.read.format("delta")
        .option("readChangeFeed", "true")
        .option("startingVersion", 0)
        .table("gbmart.bronze.products")
)

cdf_df.groupBy("_change_type").count().show()
cdf_df.select("product_id", "discounted_price_inr", "_change_type", "_commit_version").show(10, truncate=False)

This one is safe to run in class exactly as written — it's a plain SELECT-shaped read. It doesn't write anything. In HOL 2 you'll do this same read starting from a real "last processed" version instead of 0, the way a production incremental job actually would.

Putting It Together

The Real Bronze → Silver MERGE Pattern — A Walkthrough, Not a Live Run

Everything above is real code, safe to rerun forever — ALTER TABLE ... SET TBLPROPERTIES and read-only SELECTs never create duplicate rows, no matter how many times you run them.

What comes next is different. This is a verbatim walkthrough of GlobalMart's actual 10_products_incremental_scd2_merge.py — the real Bronze → Silver SCD2 MERGE that keeps gbmart.silver.products in sync using CDF. We read it, line by line — but we do not run it in this ILT. A MERGE + append pair is not idempotent the way ALTER TABLE is: running it twice would insert a second batch of "new version" rows into a Silver table the whole cohort shares.

🧠 The habit this walkthrough builds

S R Sneha is the kind of engineer who reads a MERGE twice, end to end, before ever running it once. That's exactly the habit this session is practicing — understand it fully before you touch "run."

➡️ Where you actually build this yourself

The filing-cabinet picture, before any code: think of dim_product like a filing cabinet that keeps every past address a person ever had, not just the current one. When someone moves, the clerk doesn't erase the old card — they stamp it "moved out" with today's date and file a brand-new card marked "current." SCD2 does exactly that to a price change: the old price row gets stamped closed, a new row gets filed as current. Nothing is ever deleted — you can always answer "what was this product's price last month," not just "what is it now."

Reading The Real Notebook, Steps 1–4

Where This Starts: All of Bronze, Then Just What Changed

BRONZE_TABLE = "gbmart.bronze.products"
SILVER_TABLE = "gbmart.silver.products"

bronze_df = spark.table(BRONZE_TABLE)
print(f"Total rows currently in Bronze: {bronze_df.count():,}")

Step 2 is DESCRIBE HISTORY again — the exact command you already ran for real, just pointed at bronze.products, to find the version right before the incremental file landed. 

LAST_PROCESSED_VERSION = 0   # set this from the history output above

A real, worth-naming shortcut in this exact demo script: LAST_PROCESSED_VERSION is a number someone read off the DESCRIBE HISTORY output and typed in by hand — not a value pulled from a stored checkpoint table. Fine for a one-time demo run with a human watching. Not fine unattended: run this notebook twice with the same hardcoded 0, and CDF would happily hand back "everything since version 1" a second time. A production version would read LAST_PROCESSED_VERSION from a control table at the start and write the new value back at the end — the same "advance the marker" step ILT 2's watermark loader did with a timestamp instead of a version number.

Step 3 — Take Only the Changes

cdf_changes_df = (
    spark.read.format("delta")
        .option("readChangeFeed", "true")
        .option("startingVersion", LAST_PROCESSED_VERSION + 1)
        .table(BRONZE_TABLE)
        .filter("_change_type != 'update_preimage'")
)

Real demo scenario this notebook was built around: 2 price changes (PRD-00001, PRD-00002) + 1 new product (PRD-00501) — 3 changed rows total, regardless of how large bronze.products eventually grows. That's the entire point of CDF: cost tracks what changed, not how big the table is.

Step 4 — Process Only Those Rows

processed_df = cdf_changes_df.select(
    "product_id", "product_name", "category", "sub_category",
    "actual_price_inr", "discounted_price_inr", "rating", "num_ratings",
    col("specs.power_source").alias("power_source"),
    col("specs.country_of_origin").alias("country_of_origin"),
    col("specs.color_options").alias("color_options"),
    col("specs.is_returnable").alias("is_returnable"),
    col("specs.return_window_days").alias("return_window_days"),
    col("specs.material").alias("material"),
    col("specs.warranty_months").alias("warranty_months"),
    col("specs.weight_kg").alias("weight_kg"),
    col("supplier_info.supplier_id").alias("supplier_id"),
    col("supplier_info.name").alias("supplier_name"),
    col("supplier_info.city").alias("supplier_city"),

Exactly the same flatten logic Day 5's full-load notebook used on specs.* and supplier_info.* — just scoped down to 3 changed rows instead of the full 500+-row table.

Reading The Real Notebook, Step 5

Load Into Silver: Close the Old Row, Append the New One

Two parts, always in this order: close out the old version first, then append the new one.

5a — Close Out the Old Version (Update-Only)

silver_table = DeltaTable.forName(spark, SILVER_TABLE)

(silver_table.alias("tgt")
    .merge(
        processed_df.alias("src"),
        "tgt.product_id = src.product_id AND tgt.is_current = true "
        "AND tgt.discounted_price_inr <> src.discounted_price_inr"
    )
    .whenMatchedUpdate(set={
        "is_current": "false",
        "effective_end_date": "current_date()"
    })
    .execute()
)

Match key is a plain natural key, product_id. Notice there's no whenNotMatched clause at all — this MERGE only ever updates existing rows, it never inserts.

5b — Append the New Version, Unconditionally

new_versions_df = processed_df \
    .withColumn("effective_start_date", current_date()) \
    .withColumn("effective_end_date", lit(None).cast("date")) \
    .withColumn("is_current", lit(True)) \
    .withColumn("product_sk",
        sha2(concat_ws("|", col("product_id"), col("effective_start_date").cast("string")), 256)
    ) \
    .withColumn("discount_pct",
        round((col("actual_price_inr") - col("discounted_price_inr")) / col("actual_price_inr") * 100, 2)
    ) \
    .withColumn("_silver_updated_at", current_timestamp()) \
    .select(
        "product_sk", "product_id", "product_name", "category", "sub_category",
        "actual_price_inr", "discounted_price_inr", "discount_pct",
        "rating", "num_ratings",
        "power_source", "country_of_origin", "color_options", "is_returnable",
        "return_window_days", "material", "warranty_months", "weight_kg",
        "supplier_id", "supplier_name", "supplier_city", "tags",
        "is_current", "effective_start_date", "effective_end_date",
        "last_updated", "_silver_updated_at"
    )

new_versions_df.write.format("delta").mode("append").saveAsTable(SILVER_TABLE)

The surrogate key formula — sha2(concat_ws("|", product_id, effective_start_date), 256) — is the exact same dim_product SCD2 key formula already taught in Day 6/7. Every row in processed_df gets appended as a fresh, is_current = true row. This single append covers both cases at once: a changed product (a new price version) and a genuinely new product (5a simply never matched it, so this append is the only row it gets).

A Real Rough Edge — Named, Not Hidden

The Double-Current-Row Limitation

Look closely at what each half of Step 5 actually checks — the two conditions don't match.

5a checks one specific thing

It only closes out the old row when tgt.discounted_price_inr <> src.discounted_price_inr — the price, specifically, and nothing else.

5b checks nothing at all

It appends every row in processed_df, unconditionally — price change or not, any attribute change or not.

The real, latent bug this creates: if a CDF change touched category, rating, tags, or anything other than discounted_price_inr, 5a finds nothing to close out — the price didn't change, so its merge condition never matches. But 5b still appends that row as a brand-new is_current = true version anyway. Result: two is_current = true rows for the same product_id, and neither one was ever closed.

Proving It Generalizes

The Same Pattern, a Second Time: dim_customer

GlobalMart's real 11_customers_incremental_scd2_merge.py applies the identical six-step shape to dim_customer — worth seeing once, briefly, to prove this is a reusable pattern, not a one-off products quirk.

  1. Step 3, CDF read — same shape exactly: readChangeFeed, startingVersion, drop update_preimage.
  2. Step 4, real cleanup — filters CustomerID IS NOT NULL AND Email IS NOT NULL first. Not defensive boilerplate: a real cross-file interaction. A customer_consent_*.csv file lands in the same Bronze source folder, and its rows would otherwise show up in this same CDF read even though they're a completely different entity. Remalli Kamal Kumar is the one who'd trace an unexpected null-heavy row back to that consent file rather than assuming it's bad customer data. The same cell also computes age and customer_tenure_days, and renames PascalCase source columns to snake_case.
  3. Step 5a, close-out condition — tgt.email <> src.email. Same shape as the products price check, same limitation: an attribute change that isn't email (say, phone_number) would append a new row without closing the old one, for exactly the same reason as products above.
  4. Step 5b, append — identical pattern: sha2(concat_ws("|", customer_id, effective_start_date), 256) as the surrogate key, unconditional append of every CDF row.

The real takeaway: this MERGE shape is GlobalMart's actual reusable pattern for CDF-driven SCD2 — and the double-current-row limitation isn't a products-specific mistake, it's a property of the pattern itself, wherever it gets copy-pasted without the close-out and insert conditions kept in sync.

Quick-Fire Concept Check

Click to reveal each answer. If any of these surprise you, re-read the section above.

Why does CDF close the delete blind spot that watermark loading couldn't?
Watermark loading depends on a business column like updated_at changing. A hard delete never produces a newer updated_at — the row just vanishes, unnoticed. CDF doesn't depend on any business column at all; a DELETE is recorded as its own _change_type, automatically, by Delta itself.
Why is addresses plural in Bronze but address singular in Silver?
That's a real, intentional asymmetry in GlobalMart's actual schema, not a typo. Both names are the real, verbatim table names in their respective layers — keep them exactly as they are rather than "fixing" one to match the other.
Why does this ILT walk through the real MERGE code instead of having you run it?
ALTER TABLE ... SET TBLPROPERTIES is idempotent — running it five times leaves the table exactly the same as running it once. A MERGE + append pair is not: running it twice would insert a second batch of "new version" rows into a Silver table the whole cohort shares. Day 10 is where you get to run and fix a corrected version yourself, safely, against your own practice schema.
What exactly causes the double-current-row limitation, and where would you fix it?
Step 5a's close-out condition only fires on a specific attribute change (price for products, email for customers). Step 5b's append fires on every CDF row, unconditionally. Any change that isn't the one 5a is watching for slips through as an appended row with nothing closed out. Day 10 is where the corrected, hands-on version keeps both conditions honestly in sync.
