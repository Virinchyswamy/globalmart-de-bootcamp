Part 1 — Setting Up

Why payments, of All Tables?

Very simple version first: payments is a good first CDF target because a payment record only ever needs to show its current value. Nobody needs to know what a payment record looked like three versions ago — they just need to know what it says right now.

1:1 with orders, no history needed

payments is 1:1 with orders, and — unlike customers/products — doesn't need SCD2 history. When a payment record changes, Silver just needs the current value, not every past version.

The simplest form of the pattern

That makes this a plain upsert MERGE — the simplest version of the CDF pattern from ILT 3. Update matched rows, insert new ones, done.

Before You Touch Anything

Why a Practice Clone, Not the Real Table?

Think of it like a shared whiteboard with one eraser. The first person to test "erase then redraw" gets to see the real before/after. Everyone after them just sees a blank board — the interesting part already happened. That's exactly the trap of running a MERGE demo against a shared table.

This exercise's whole point is watching a MERGE consume a batch of pending changes, then run again and find nothing left. Against the real shared harsh_kumar01_npmentorskool_onmicrosoft_com.silver.payments, only the first person to run this in the whole cohort would ever see a non-zero merge — everyone after (including you, rehearsing before class) would see "0 changed rows," and the exercise would look broken. 

CREATE OR REPLACE TABLE bronze_payments_practice
  SHALLOW CLONE harsh_kumar01_npmentorskool_onmicrosoft_com.bronze.payments;

CREATE OR REPLACE TABLE silver_payments_practice
  SHALLOW CLONE harsh_kumar01_npmentorskool_onmicrosoft_com.silver.payments;

ALTER TABLE bronze_payments_practice
  SET TBLPROPERTIES (delta.enableChangeDataFeed = true);

A SHALLOW CLONE in your own schema gives you the same real data and the same real CDF mechanics, but a version history that's entirely yours — repeatable every time, for every student, forever. Everything you write in Part 1 stays inside main.YOUR_SCHEMA — never a direct write against shared harsh_kumar01_npmentorskool_onmicrosoft_com.* tables.

A control table tracks progress for real — main.YOUR_SCHEMA._incremental_control stores one row per source, with last_bronze_version. This isn't a hardcoded number anywhere in the code; every run reads the real stored value, so the exercise is genuinely safe to re-run as many times as you like.

The Function You'll Run

The 6-Step Refresh Pattern, in refresh_silver_payments()

Same shape as every incremental loader in this course, whether it's watermark-based (ILT 2) or CDF-based (ILT 3): read the marker, pull only what's new, process it, write it, move the marker forward.

  1. Read last_bronze_version from the control table — a real stored value, not a hardcoded number.
  2. Read Bronze's CDF since last_version + 1.
  3. Drop _change_type == 'update_preimage' rows — keep only each row's current state.
  4. Rename columns to match Silver's shape: OrderID → order_id, PaymentID → payment_id.
  5. MERGE into silver_payments_practice — whenMatchedUpdateAll() / whenNotMatchedInsertAll(). A plain upsert, nothing more.
  6. Advance the control table to the newest Bronze version just processed.

Running it — twice

Sukrit Ghosh's first run reprocesses every payments row ever written — expected, because his control table starts at -1, same as everyone's does. His second run, immediately after, is the real proof:

# Run 1 (first ever run, last_bronze_version = -1): reprocesses all history — expected.
refresh_silver_payments()

# Run 2 (immediately after, nothing changed): expect "Changed rows since last run: 0"
refresh_silver_payments()

Run 2 finding zero changes — not run 1 — is what actually proves this is incremental.

Scope Check

This Is a Plain Upsert. On Purpose.

Very simple version: an upsert answers "what does this row look like right now?" SCD2 answers "show me every version this row has ever had." Those are genuinely different jobs — Part 1 only does the first one.

Not a preview of SCD2. ILT 3 walked through the real CDF-driven SCD2 MERGE pattern for dim_product/dim_customer — read-only, watching history rows accumulate. That's a different, harder pattern (keep every past version) built for a different reason (dimension history). Full hands-on SCD2 with history-tracking is Day 10's job. This lab's Part 1 build is a plain upsert on purpose — do not extend it into SCD2 here.

On-Call Verification

Part 2 — Verify the Watermark Pipeline

Unlike Part 1, you don't build the ingestion yourself here — the real orders_data_ingestion_cdc Lakeflow Connect pipeline (Day 2) already owns it, reading straight from Postgres via CDC. Your job is to confirm it actually picked up a change — five real, read-only checks, nothing you run here writes anything.

The real scenario behind these checks

At authoring time, the instructor made a real change in source Postgres — an UPDATE on order OR-000478 (delivery date + status), and two new orders inserted, OR-900001 and OR-900002 — then re-triggered the pipeline. If your instructor repeats this live during class, run the checks below after that happens; you may see this exact pattern, or a fresh one your instructor set up. If not, run them anyway to see the current state — the counts just won't have moved.

#CheckConfirms

4Top 5 rows by updated_at DESCWhich rows the most recent pipeline run actually touched

About those row-count numbers: at authoring time, the stated baseline was 126,036 orders (126,038 once the 2 new orders land) and 377,866 order_items (unchanged, or 377,868 if the matching order_items insert was also run). order_items is not 1:1 with orders — it's one row per line item, and orders average ~3 line items each, hence the ~3x row count. Those are the pipeline's reference numbers from when this lab was written — not something to hardcode or assert against. The real cohort table keeps growing as other students and instructor demos run against it, so always verify live with COUNT(*), exactly the way Check 3 does it.

Callback, Not New Teaching

Remember Day 3's Schema Evolution Modes?

Day 3 ILT 2 already taught addNewColumns vs. rescue in full — this section does not re-teach that. It's a short, real receipt that it actually happened at GlobalMart, not just on a slide.

↩ Callback to Day 3 ILT 2 — Schema Evolution Concepts

A real practice file, customers_schema_evolution_exp.py, ran Autoloader against customers source files twice — first with cloudFiles.schemaEvolutionMode = "addNewColumns", then again with schemaEvolutionMode = "rescue" — each time against a source file that had genuinely gained one new column, third_party_data_sharing. Everything ran against harsh_kumar01_npmentorskool_onmicrosoft_com.bronze_practice.customers_exp, an isolated practice schema — production harsh_kumar01_npmentorskool_onmicrosoft_com.bronze.customers was never touched.

Pass 1 — addNewColumns

T Nikshitha's read of this pass is the simple case: the new column just shows up as a normal column, no code change needed to see it.

customers_df = spark.readStream \
    .format("cloudFiles") \
    .option("cloudFiles.schemaEvolutionMode", "addNewColumns") \
    .load(SOURCE_PATH)

Pass 2 — rescue

Same source, same target table, only the mode changes. Unexpected/new columns get captured into a side _rescued_data column instead of being added outright.

customers_df = spark.readStream \
    .format("cloudFiles") \
    .option("cloudFiles.schemaEvolutionMode", "rescue") \
    .load(SOURCE_PATH)

Sujit Kumar's proof query is the simplest possible check that this happened: SELECT * FROM harsh_kumar01_npmentorskool_onmicrosoft_com.bronze_practice.customers_exp WHERE third_party_data_sharing IS NOT NULL — rows with a value there arrived after the new column existed. That one file, run twice, is the receipt: schema evolution isn't just a Day 3 slide, it's something this course's own practice pipeline actually did, safely, in a schema built only for practicing it. Nothing to build here — just something to recognize.
