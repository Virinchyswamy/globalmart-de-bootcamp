Why Do We Need Three Layers?

Imagine handing your finance team a shoebox of crumpled receipts — some dates written 12/1/24, others 2024-01-12, a few duplicated, a few with coffee stains. Nobody would trust a revenue report built straight from that shoebox.

GlobalMart's raw data from Postgres CDC and ADLS file drops has exactly this problem: nulls, duplicate rows, inconsistent date formats, trailing spaces in names, columns named differently across files.

The Medallion Architecture fixes this

Data passes through three quality layers — each one making it more trustworthy and more useful than the last. Raw data enters at Bronze; only business-ready data leaves at Gold.

Instructor question: "We have 10 raw CSV files in ADLS — can we just query them directly for business reports?" Technically yes. In practice, the numbers would be wrong.

🥉 Bronze — Raw, Exactly as Received

The Rules

  • Never modified after landing — append-only
  • Adds _ingestion_ts and _source_file metadata columns
  • Format: Delta, converted from CSV/CDC on arrival
  • Retains ALL columns — even bad ones
  • Retains duplicates — dedup happens in Silver

Think of Bronze as: a photocopy of the original. You always have the original to refer back to if something downstream breaks.

GlobalMart examples

<your-catalog>.bronze.orders — raw CDC-upserted rows
<your-catalog>.bronze.customers — raw file-drop rows
<your-catalog>.bronze.order_items — line items

🥈 Silver — Clean, Validated & Standardised

The Rules

  • Delta format only — never CSV
  • Nulls filled or flagged; all dates → YYYY-MM-DD
  • Strings trimmed; deduplication applied
  • Schema enforced — no surprise columns
  • SCD Type 1 / Type 2 for slowly-changing dimensions

Think of Silver as: clean, trustworthy data. An analyst could query this directly and get the right answer.

GlobalMart examples

<your-catalog>.silver.customers
<your-catalog>.silver.products
<your-catalog>.silver.orders

🥇 Gold — Business-Ready, the Deliverable

The Rules

  • Delta format only — star schema (facts + dimensions)
  • Column names in plain business language
  • Calculated metrics, ready to use
  • OPTIMIZE + ZORDER applied for fast queries
  • Governed — Unity Catalog access rules apply

Think of Gold as: the final answer. A manager can query this without knowing SQL deeply.

GlobalMart output

<your-catalog>.gold.fact_sales — the whole point
plus dim_date, dim_address, and 4 more dimensions

Section 2

Delta Lake — What Makes It Different

Delta Lake is NOT a separate database. It's a storage layer that lives on top of Parquet files in ADLS — and it changes everything about how reliable that data is.

The Bank Account Analogy

Imagine a bank with no transaction history:

  • Someone credits your account — the system crashes halfway. Did the money arrive?
  • Two people withdraw at the same time — does the balance go negative?
  • An error was made last week — can you go back and see the old balance?

Without Delta Lake = a bank with no transaction log. Chaos: no ACID, no schema enforcement, no updates or deletes, no audit trail, partial writes.

With Delta Lake = every write, update, and delete is logged. You can roll back. You can see history. Nothing is lost.

The Secret Ingredient: _delta_log

customers/                            ← a Delta table's storage location
    _delta_log/                       ← Delta's brain
        00000000000000000000.json     (version 0 — initial write: 6,666 rows)
        00000000000000000001.json     (version 1 — append: 200 new rows)
        00000000000000000002.json     (version 2 — MERGE: 5 updated, 1 deleted)
    part-00000-a1b2c3.parquet         ← actual data, columnar format
    part-00001-d4e5f6.parquet

Every change → a new JSON entry

This log is what gives Delta its superpowers: ACID transactions, schema enforcement, time travel, full audit history, and MERGE (upsert) support.

Key Delta Commands

-- See all versions of a Delta table
DESCRIBE HISTORY customers;

-- Query a previous version (time travel)
SELECT * FROM customers VERSION AS OF 1;

-- Restore to a previous version
RESTORE TABLE customers TO VERSION AS OF 1;

-- Compact small files (run periodically for performance)
OPTIMIZE customers ZORDER BY (registration_date);

-- Remove old data files no longer referenced (default: 7-day retention)
VACUUM customers RETAIN 168 HOURS;

ACID — What It Means in Plain English

Without ACID, two jobs writing at once could corrupt your data — or a failed job could leave partial results behind.

A — Atomicity

All-or-nothing. If writing 6,666 rows fails halfway, zero rows are visible.

C — Consistency

Data always moves from one valid state to another — schema rules are enforced.

I — Isolation

Two jobs writing at the same time cannot corrupt each other.

D — Durability

Once written and confirmed, data is never lost — even if the cluster crashes.

Delta Write Modes — When to Use Which

overwrite

Deletes existing data, writes fresh. Safe to re-run. Small reference tables refreshed daily.

append

Adds new rows, never deletes. Growing tables — daily order batches.

merge (UPSERT)

Matches by key — UPDATE existing, INSERT new. SCD Type 1, CDC processing.

ignore

Does nothing if data already exists there. Rare in production pipelines.

Delta Table vs CSV vs Parquet

In one sentence: Delta = Parquet files + a transaction log. That log changes everything.

Section 3

fact_sales — The Gold Deliverable

A star schema separates measures (numbers you sum or average) from dimensions (attributes you slice and filter by). fact_sales is the fact table — it holds the numbers and a foreign key to each dimension.

fact_sales — Grain & Measures

            dim_customer      dim_product
                    \            /
     dim_payment_method — fact_sales — dim_date
                    /            \
             dim_orders      dim_address

"Grain" in plain words: it just means "what does ONE row represent?" Here, one row = one item inside one order (order_item_id) — not one order, not one customer.

fact_sales — the 4 numbers it tracks (measures)

  • Quantity_purchased — how many units
  • Actual_price — the sticker price
  • Discounted_price — what the customer actually paid per unit
  • Sales_amount — quantity × discounted price = real revenue

This table answers the question every business team has: "What sold, when, to whom, for how much?"

fact_sales — The 6 Dimensions It Connects To

Slice and filter by any of these 6

  • dim_customer — who bought it
  • dim_product — what was sold
  • dim_date — when
  • dim_address — where it shipped
  • dim_payment_method — how it was paid
  • dim_orders — which order it belongs to

Business questions it answers

  • Revenue by product category this month
  • Top 10 customers by total spend
  • Payment method breakdown
  • Regional sales trends by city
  • Average order value by loyalty tier
