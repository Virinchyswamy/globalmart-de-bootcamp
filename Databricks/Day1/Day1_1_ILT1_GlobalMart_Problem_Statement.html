GlobalMart's Three Pain Points

  1. Data Silos — transaction data and reference files live in separate systems with no automatic connection
  2. No Single Source of Truth — different teams pull numbers differently; reports don't match
  3. Slow Decision Making — business users wait hours or days for reports that should be instant

Why Is This Actually a Problem? A Simple Analogy

Imagine you have money in two different banks, and neither bank can see the other's balance.

To answer "How much money do I have?"

  • You'd have to log into Bank A, write down the number
  • Log into Bank B, write down that number
  • Add them together yourself, by hand
  • Do this every single time someone asks

That is exactly GlobalMart's situation today:

"Bank A" = Postgres (orders). "Bank B" = ADLS CSV files (products, customers, payments...). Every business question means manually combining both — by hand, every time, with room for a different person to get a different answer.

What we're building instead: one combined, always-up-to-date "balance" — the fact_sales table — so nobody has to do that manual math again.

The Solution: An Azure Databricks Lakehouse

In plain terms: we build one automated pipeline that pulls data out of both "banks," cleans it up, combines it, and keeps it always current — so every question above becomes a 5-second query instead of an hour of manual work. Concretely, that pipeline has 8 steps:

  1. Ingest orders continuously from Postgres using Lakeflow Connect (CDC)
  2. Ingest reference files automatically from ADLS using Autoloader
  3. Store all raw data in Bronze — Delta tables, never modified
  4. Clean and standardize in Silver — validated, de-duplicated
  5. Build fact_sales in Gold — one trusted table for all revenue questions
  6. Refresh pipelines automatically with Databricks Workflows
  7. Let stakeholders query directly through Genie (self-serve Q&A)
  8. Govern access and lineage through Unity Catalog

Section 3

The Two Ingestion Tools

We have 2 real sources, handled by 2 different Databricks tools. Everything upstream — Bronze, Silver, Gold — exists to make fact_sales correct and current.

Source 1 — Supabase (PostgreSQL) via Lakeflow Connect

Supabase is GlobalMart's primary transactional database. Every order and line item is stored here and updated continuously all day.

Lakeflow Connect is Databricks' managed CDC (Change Data Capture) connector. It can detect changes two ways — reading the Postgres Write-Ahead Log directly (log-based), or polling a cursor column on a schedule (query-based). GlobalMart's real pipeline uses query-based, with updated_at as the cursor.

-- Query-based mode, in plain terms:
Runs: WHERE updated_at > last_run_time
INSERT → new row appears, gets picked up next run
UPDATE → updated_at changes, gets picked up next run
DELETE → row just vanishes — nothing to trigger on, MISSED
-- Same blind spot as a hand-rolled watermark. A deliberate, documented trade-off.

Source 2 — ADLS File Drops via Autoloader

Reference and enrichment files land in an ADLS folder (raw-data/), inside 6 source subfolders — one per table. These are file drops, not live database connections — they arrive periodically.

Autoloader (cloudFiles) is Databricks' incremental file ingestion tool. It watches a folder and picks up new files automatically — without re-reading files it already processed.

New file lands in raw-data/  → Autoloader detects it
                        → Reads the new file only (checkpoint)
                        → Writes to Bronze as Delta
                        → Updates checkpoint

"Grain" in plain words: it just means "what does ONE row represent?" Here, one row = one item inside one order (order_item_id) — not one order, not one customer.

fact_sales — the 4 numbers it tracks (measures)

  • Quantity_purchased — how many units
  • Actual_price — the sticker price
  • Discounted_price — what the customer actually paid per unit
  • Sales_amount — quantity × discounted price = real revenue

This table answers the question every business team has: "What sold, when, to whom, for how much?"
