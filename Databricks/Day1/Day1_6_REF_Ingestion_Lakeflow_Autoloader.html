Ingestion Deep-Dive: Lakeflow Connect vs Autoloader

Why GlobalMart uses two different ingestion tools, how each one actually works, and which GlobalMart table uses which

Day 1  ·  Reference Material  ·  Self-Paced
This is reference material, not a live trainer-led session — read it whenever you want the deep-dive on the two ingestion tools.

Why Two Different Tools?

GlobalMart's data comes from two fundamentally different places. One is a live PostgreSQL database where orders are being inserted and updated right now. The other is a storage folder where CSV files land periodically. These two situations need two different approaches.

The core question: is the data changing under you right now (a live database), or does it arrive as a finished file that never changes again (a file drop)?

Two Sources, Two Tools

Lakeflow Connect

For: Live Databases (Postgres)

  • Rows are inserted, updated, and deleted in real time
  • You can't JDBC-query a large table every few minutes without hurting performance
  • Reads the database's Write-Ahead Log (WAL) continuously
  • Delivers change events to Bronze as a streaming table

GlobalMart tables: orders, order_items

Autoloader

For: File Drops in ADLS

  • CSV/JSON/Parquet files land in raw/ on a schedule
  • Once landed, files do not change
  • Uses a checkpoint to track which files are already processed
  • Never re-reads a file it has already ingested

GlobalMart tables: customers, payments, products, addresses, returns, payment_methods, shipping_tier, suppliers

How Both Feed Bronze

Supabase PostgreSQL (live orders DB)
    → Lakeflow Connect (reads WAL, continuous CDC)
    → Bronze streaming table (bronze/orders/, bronze/order_items/)

ADLS raw/ (file drops — CSVs from upstream systems)
    → Autoloader / cloudFiles (checkpoint-based incremental scan)
    → Bronze Delta tables (bronze/customers/, bronze/products/, …)

Both Bronze layers
    → Silver (clean, deduped, SCD)
    → Gold (fact_sales + dimensions)
    → Genie (self-serve Q&A for business)
Deep Dive 1

Lakeflow Connect — CDC from PostgreSQL

Databricks' native Change Data Capture connector — it reads changes directly from the Postgres transaction log, continuously, with no manual scheduling.

How CDC Works, via the PostgreSQL WAL

  1. An order is updated in Supabase: UPDATE orders SET status = 'shipped' WHERE order_id = 'O1001'
  2. PostgreSQL writes this change to the Write-Ahead Log (WAL) before applying it to the table — this is how Postgres guarantees durability
  3. Lakeflow Connect holds a replication slot in Postgres. It tails the WAL continuously and sees this UPDATE event
  4. Lakeflow Connect delivers a row to the Bronze streaming table with the operation type, the changed values, and a CDC timestamp
  5. Bronze now has a complete history of every INSERT, UPDATE, DELETE — Silver can replay this to get the current state

You configure Lakeflow Connect as a pipeline in Databricks. There's no manual code to read Postgres — Databricks handles the WAL connection, retries, and checkpointing.

Deep Dive 2

Autoloader — Incremental File Ingestion

Databricks' incremental file ingestion tool — it watches a folder in ADLS and picks up new files automatically, without ever re-reading a file it already processed.

How Autoloader Works

  1. A new file customers_2024-06-02.csv lands in raw/
  2. Autoloader detects the new file automatically
  3. It checks its checkpoint folder — has this file been processed before? No → process it
  4. Reads the CSV, applies the schema, appends rows to the Bronze Delta table
  5. Writes the file name to the checkpoint — the next run skips it
  6. When another file lands tomorrow, only that new file is read — never the whole folder

Autoloader Code Pattern

# Autoloader reads new files from raw/ and appends to Bronze
df = (
    spark.readStream
    .format("cloudFiles")
    .option("cloudFiles.format", "csv")
    .option("cloudFiles.schemaLocation", checkpoint_path + "schema")
    .option("header", "true")
    .load(raw_path + "customers_*.csv")
)

(
    df.writeStream
    .format("delta")
    .option("checkpointLocation", checkpoint_path)
    .trigger(availableNow=True)
    .toTable("bronze.customers")
)

Two Trigger Modes

availableNow=True (batch-like)

Processes all new files waiting in the folder, then stops. Run this on a schedule — for example, every hour via Workflows. Good for most GlobalMart ADLS tables.

continuous=True (streaming)

Stays running and picks up files the moment they land. Uses more cluster time. Good for near-real-time needs, like payments that must appear in Bronze within minutes.

The Rule of Thumb

One Question Decides the Tool

Is the source a live database with INSERT / UPDATE / DELETE? → Lakeflow Connect

Is the source a file that lands in ADLS and never changes?

— Grows over time? → Autoloader + Incremental Load (append + watermark)

— Small and fully refreshed each time? → Autoloader + Full Load (overwrite)
