Part 1

Introduction to Data Governance

Before any tool — what governance actually means, and why it stops being optional past a certain size

What Is Data Governance?

The set of policies, processes, and controls that decide three things for every piece of data an organization holds:

Who can access it
→
What they're allowed to do with it
→
How you prove that, after the fact

It's a discipline, not a product

Governance existed long before Unity Catalog — it's the rules. Unity Catalog is Databricks' way of implementing those rules directly on your tables, so the rule and the enforcement are the same thing, not a policy document nobody checks against reality.

Why Organizations Need It

⚖️ Compliance

GDPR, HIPAA, PCI-DSS, SOX don't just recommend access control and audit trails — they legally require them, with real fines for failing to produce one on demand.

🎯 Trust

One number, one version of the truth. Without governance, Finance and Sales can query "the same" table and get different answers because nobody controls which copy is authoritative.

🔒 Security

Every person with unnecessary access to sensitive data is one more way a breach — accidental or malicious — can happen.

The scale problem: tribal trust ("just ask Priya before touching that table") works for 3 people. It collapses at 300 — nobody knows who to ask, what exists, or who touched what last.

Challenges Without a Centralized Framework

Without governance...What actually happens
No single source of truthThe same table gets copied into 4 tools, each drifting out of sync the moment one copy is refreshed and the others aren't
No audit trailAfter a breach or a compliance ask, "who accessed this customer's record last month" has no answer
Permissions scattered per-toolAccess is managed separately in the warehouse, the BI tool, and the file store — revoking someone takes as many steps as there are systems
No lineage"Why does this dashboard number look wrong" becomes forensic archaeology through old notebooks and Slack threads
All-or-nothing accessThe only lever is "give this person the whole table or nothing" — no way to share 90% of a table while protecting one sensitive column
Part 2

The Five Pillars of Data Governance

Tool-agnostic for now — these are the problems any platform has to solve, before we look at how Unity Catalog specifically solves them

The Five Pillars, at a Glance

🔍 Discovery

Can people find data that already exists, or do they recreate it from scratch because they didn't know it was there?

📝 Audit

Is there a record of who accessed or changed what, and when?

🧬 Lineage

Do you know what feeds a table, and what breaks if you change it?

👤 Identity Management

Is "who is this person, and what groups are they in" managed in one place?

🔑 Access Control

Can you grant exactly the right level of access — not more, not less?

Part 3 takes each of these five, one at a time, and shows the concrete problem it solves, live in Databricks, plus a real enterprise example of the pain it prevents.

Pillar 1 — Data Discovery: the Problem Without It

What goes wrong

Nobody has a map of what data exists. An analyst who needs "customer lifetime value" has no way to know a table with exactly that already exists three teams over — so they rebuild it, badly, from scratch.

The compounding cost

Every rebuild is a slightly different definition of the same metric. Six months later, three teams have three different "customer lifetime value" numbers, and nobody can say which one is right.

Pillar 2 — Data Audit: the Problem Without It

What goes wrong

Queries against sensitive tables leave no record. If a customer's data was viewed by someone who shouldn't have, there is no way to find out — not this week, not ever.

The compounding cost

A compliance audit or a legal discovery request that asks "prove nobody outside the billing team accessed this table in March" has no evidence to produce, regardless of whether anything actually went wrong.

Pillar 3 — Data Lineage: the Problem Without It

What goes wrong

Nobody can say, with confidence, what feeds a given table or dashboard — or what else would break if that table's schema changed tomorrow.

The compounding cost

A well-intentioned schema change silently breaks four downstream dashboards nobody knew depended on it. The first anyone hears about it is an angry message from a VP whose report is now blank.

Pillar 4 — User & Identity Management: the Problem Without It

What goes wrong

Every tool — the warehouse, the BI platform, the file store — manages its own separate list of who's allowed in. There is no single place that says "this is everyone with access, and here's what they can do."

The compounding cost

An employee leaves. Revoking their access means separately remembering, and separately doing, the same removal in every one of those systems — and it's exactly the step someone forgets.

Pillar 5 — Access Control: the Problem Without It

What goes wrong

The only available lever is often "grant the whole table" or "grant nothing." There's no native way to say "this row only" or "every column except this one."

The compounding cost

Teams either over-share (give everyone the whole table because narrower access isn't achievable) or under-share (block a whole table over one sensitive column, and now legitimate analysis can't happen either).

Part 4

Unity Catalog Architecture

The object model everything above is actually built on — one hierarchy, a handful of object types, and how storage is wired in underneath it

Metastore → Catalog → Schema

metastore                     # one per region/account
  |-- gbmart                  CATALOG
        |-- bronze            SCHEMA
        |     |-- customers, orders, ...   TABLE
        |-- silver            SCHEMA
        |     |-- customers, orders, ...   TABLE
        |-- gold              SCHEMA
              |-- dim_customer   TABLE
              |-- dim_product    TABLE
              |-- fact_sales     TABLE

The three levels, plainly

Metastore — the top-level container for a whole region/account, created once by an admin. Catalog — the biggest unit you'll actually work in day to day (gbmart); often maps to an environment or a business domain. Schema — a grouping inside a catalog (bronze, silver, gold); the medallion layers you've been building all course are schemas, not catalogs.

What Lives Inside a Schema

Tables & Views

What you've built all course — managed/external Delta tables, and views defined on top of them

Volumes

Governed storage for non-tabular files — the same mechanism Day 1's HOL uses for raw CSVs instead of a raw ADLS key, so file access follows the same GRANT model as tables

Functions

SQL functions — including the row-filter and masking functions built later this session. Securable objects too, just like a table

Models

Unity Catalog also governs ML models via Model Registry — same permission model, same catalog/schema location, for a completely different kind of asset

Everything above sits at the schema level and follows the exact same GRANT/REVOKE hierarchy — governance in Unity Catalog isn't a special case per object type, it's one consistent model applied everywhere.

Managed vs. External Tables

Managed tableExternal table
Who owns the filesUnity Catalog — it decides where they liveYou — files live at a location you named, UC just points at it
DROP TABLEDeletes the underlying data tooOnly removes the catalog entry — the actual files stay put
GlobalMart exampleMost of gbmart.bronze/silver/gold.* — created with plain saveAsTableRaw ADLS files under the gbmart-ext-loc external location — never a table themselves, but accessed the same governed way

Why this distinction matters day to day: dropping a managed table by mistake is destructive — the data is gone. Dropping an external table is a metadata-only mistake — annoying, but the real files are untouched and re-registerable.

Storage Credentials & External Locations

Storage Credential

A keyless, Unity-Catalog-managed identity that's allowed to talk to a specific cloud storage account — ecomprojectscredentials in the real GlobalMart setup. Nobody ever pastes a raw storage account key into a notebook; UC holds the credential centrally instead.

External Location

A named, governed pointer at one path in that storage account — gbmart-ext-loc, pointing at abfss://.../raw-data. Grant READ FILES/WRITE FILES on the location itself, the same GRANT syntax as a table.

The pattern to remember: Storage Credential answers "how do we authenticate to this cloud account at all," External Location answers "which specific path, and who's allowed near it." Every Autoloader read in this course goes through exactly this pair, not a hardcoded key.

Connections — Brief Overview

A Connection is Unity Catalog's object for querying an external system live — Postgres, MySQL, Snowflake — without copying its data into Databricks first (Lakehouse Federation).

Not the same thing as Lakeflow Connect. GlobalMart's real Postgres ingestion (Day 2) uses Lakeflow Connect — a managed CDC ingestion pipeline that copies changes into Bronze. A Connection is for querying a source live, in place, occasionally — a different tool for a different situation, and out of scope for a deep dive today.

Part 5

Fine-Grained Access Control

Beyond "can you see the table" — controlling exactly which rows and which column values a given reader sees, inside a table they already have SELECT on

What Is Fine-Grained Access Control?

Table-level access answers one question

"Can this person query this table at all?" — a yes/no gate, granted once.

FGAC answers a sharper one

"Given that they CAN query it — which rows, and which column values, do they actually see?" Three mechanisms, covered next: row-level security, column-level security, and dynamic views.

Row-Level Security

A row filter is a SQL function returning BOOLEAN — a row is visible only if the function returns true for it. Attach once, and every reader of that table — any tool, any notebook, any BI dashboard — is filtered automatically. No application code anywhere has to remember a WHERE clause.

CREATE OR REPLACE FUNCTION your_catalog.your_schema.region_filter(region STRING)
RETURNS BOOLEAN
RETURN region = 'US';

ALTER TABLE your_catalog.your_schema.your_table
SET ROW FILTER your_catalog.your_schema.region_filter ON (region);

Today's hands-on demo uses exactly this simple fixed-literal version (region = 'US') on purpose — deterministic no matter which account runs it, which is exactly what a repeatable classroom demo needs.

In production, the function body is usually role-aware instead of a fixed literal:

RETURN CASE
    WHEN is_account_group_member('global_admins') THEN true
    WHEN is_account_group_member('us_sales_team') THEN region = 'US'
    ELSE false
END;

Column-Level Security

The column equivalent of a row filter — instead of true/false per row, it returns a transformed value for one column, so unauthorized readers see a masked version instead of the real one.

This is exactly Data Masking — important enough to get its own dedicated part of this session (Part 6, next). Row filters and masks are siblings: same attach mechanism (ALTER TABLE), same "enforced for every reader automatically" guarantee, different axis — rows vs. column values.

Dynamic Views — the Older, More Manual Technique

Before native row filters and masks existed as a feature, teams got the same effect by baking the logic directly into a view's own SELECT, using current_user() or is_account_group_member() inline:

CREATE VIEW your_catalog.your_schema.customers_dynamic AS
SELECT
  customer_id,
  CASE WHEN is_account_group_member('pii_readers')
       THEN email ELSE '***' END AS email
FROM your_catalog.your_schema.customers
WHERE is_account_group_member('global_admins')
   OR region = 'US';

The gap native row filters/masks close: a dynamic view only protects people who query through that view. Anyone with direct SELECT on the base table bypasses it entirely. A native row filter or mask, attached to the table itself, protects every path in — the view, a notebook, a BI tool, all of it.

When you'd still reach for a dynamic view today: highly custom per-query logic that doesn't fit a simple row-filter/mask function shape, or governing a non-Delta source where native row filters aren't available.

Part 6

Data Masking

Sharing data broadly for analytics while keeping the specific values that identify a person out of view

What Is Data Masking, and Why It's Required

What it is

Transforming or obscuring a sensitive value so the row is still usable and queryable — you can still count, join, and group by it — but the raw value itself isn't revealed to a reader who shouldn't see it.

Why it's required

Compliance laws protecting PII (GDPR, HIPAA), the principle of least privilege, and simply reducing the blast radius of any single compromised account — a stolen credential that can only see masked emails is a much smaller incident than one that sees everything raw.

Dynamic Data Masking in Unity Catalog

CREATE OR REPLACE FUNCTION your_catalog.your_schema.email_mask(email STRING)
RETURNS STRING
RETURN CONCAT('***', SUBSTRING(email, INSTR(email, '@'), LENGTH(email)));

ALTER TABLE your_catalog.your_schema.your_table
ALTER COLUMN email SET MASK your_catalog.your_schema.email_mask;

Dynamic is the key word: nothing is pre-computed or stored masked. The function runs at query time, per row, per reader — the same underlying table shows different values depending on who's asking, right now, not a separately-maintained "masked copy" that can drift out of sync with the real data.

Today's demo runs the unconditional version — masked for absolutely everyone, including you, for the same determinism reason as the row filter. A production version swaps in a CASE/is_account_group_member(...) body: full value for one authorized role, redacted for everyone else.

Masking Real Sensitive Columns

ColumnMasking patternWhy this shape
Email***@example.com — hide the local part, keep the domainDomain alone is often useful for analysis (which company); the identifying local part isn't
PAN (India tax ID) / SSNXXXXX1234X — mask most digits, keep a short suffix visibleA visible tail lets support staff confirm "is this the right record" without ever seeing the full number — the standard banking pattern
SalaryBucket into a range ("50k-75k") or return NULL for non-HR rolesAggregate analysis (average salary by department) still works on buckets; an individual's exact number stays protected

Each of these is the same CREATE FUNCTION + ALTER COLUMN ... SET MASK mechanism from the previous slide — only the function body changes to match the column's own sensitivity shape.

Why a Practice Table, Not gbmart

1. It's disruptive to everyone else, immediately

The instant a row filter or mask is attached to a shared table, every other student's and the instructor's next query against it is filtered/masked too — mid-class, with no warning.

2. It isn't a quiet, reversible change

Unlike a SELECT, attaching a row filter or a mask is a standing change to the table's own metadata. Undoing it needs another explicit statement — it doesn't expire on its own.

Compute note: row filters and column masks are enforced on supported compute only — a SQL warehouse, a shared-access-mode cluster, or a recent single-user runtime. If your cluster doesn't support them, the demo's cells print a clear fallback message instead of failing.

Fine-Grained Access Control vs. RBAC

Not competitors — one is layered on top of the other

Two Different Questions, Both Needed

RBACFine-Grained Access Control
Decides access based onWho you are — your role/groupWhat's in the data itself — a row's region, a column's sensitivity
GranularityObject-level — the whole table or schema, all or nothingRow-level and column-level, within a table you already have access to
Mechanism hereGRANT SELECT ON SCHEMA gold TO analystsRow filters, column masks, dynamic views
Answers"Can this group reach this table at all?""Given that they can — what exactly do they see once they're in?"

The relationship: RBAC is the gate. FGAC is what happens once you're through it. The sales team gets SELECT on gold via RBAC — then a row filter (FGAC) ensures each rep only sees their own region's rows within that same grant.

Bringing It Together

A Real-World Scenario

Healthcare · Banking · Retail — same governance requirements, dressed differently by industry

The Scenario

A hospital network's data platform (the richest version of this scenario — the same shape shows up as a bank's customer-account data, or a retailer's loyalty-program data):

RequirementWho needs it, and why
Multiple teams share the same underlying dataBilling, clinical research, and hospital administration all need the same patient encounter records — for different purposes
Analysts should only see relevant recordsA clinical researcher studying cardiology cases shouldn't see psychiatric or oncology patient records at all
Sensitive columns (PII) must remain maskedSocial Security Number, full date of birth, and home address should never be visible to a research analyst who only needs diagnosis codes and outcomes
Auditors must be able to track every accessRegulators can demand, at any time, a complete record of who viewed a specific patient's data and when

How Unity Catalog Solves All Four, at Once

RequirementUnity Catalog mechanism
Multiple teams, one datasetRBAC — GRANT SELECT at the schema level for each team's group; everyone reads the same one authoritative table, not separate copies
Analysts see only relevant recordsRow-level security — a row filter keyed on department/specialty, so the cardiology team's query against the exact same table as the oncology team returns different rows automatically
PII stays maskedDynamic data masking on SSN, DOB, and address — full value for the billing team's group, redacted for the research analysts, same underlying column
Auditors track every accessAudit logs — every one of the above queries is already recorded in system.access.audit, with no extra system built for the purpose

One table. One set of grants, filters, and masks, defined once at the object level. Every reader — billing, research, administration, a future auditor — gets exactly the slice they're entitled to, automatically, without a single line of access-control code living in any of their tools.
