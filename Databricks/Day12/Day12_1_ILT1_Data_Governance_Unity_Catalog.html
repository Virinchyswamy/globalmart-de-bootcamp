Section 1

The Permissions Model

One hierarchy, four levels. Every privilege you grant sits at one of these levels — and grants are inherited downward.

One Hierarchy, Four Levels

metastore                     # one per region/account
  |-- gbmart                  CATALOG
        |-- bronze            SCHEMA
        |     |-- customers, orders, ...   TABLE
        |-- silver            SCHEMA
        |     |-- customers, orders, ...   TABLE
        |-- gold              SCHEMA
              |-- dim_customer   TABLE
              |-- dim_product    TABLE
              |-- fact_sales     TABLE

Functions and views sit at the same level as tables — including the row-filter and masking functions built later in this session. They're securable objects inside a schema too.

Principals and the Standard Privilege Set

Principal typeTypical use
UserOne person's own login/access
GroupThe normal case — grant to a group, add/remove members, never re-grant
Service principalJobs, pipelines, automation — no human login
PrivilegeGrants...
USE CATALOG / USE SCHEMA"Step into" — necessary but not sufficient alone
SELECTRead rows from a table/view
MODIFYINSERT/UPDATE/DELETE/MERGE
CREATE TABLE / CREATE FUNCTIONCreate new tables / functions in a schema
ALL PRIVILEGESEverything valid at that level, combined

USE CATALOG/USE SCHEMA trip people up: being able to "step into" gbmart.gold doesn't let you read anything inside it — you also need SELECT on the schema or the table itself.

GRANT / REVOKE Syntax, and Inheritance

-- Read access to an entire schema -- present AND future tables
GRANT USE CATALOG ON CATALOG main TO `analysts`;
GRANT USE SCHEMA ON SCHEMA main.YOUR_SCHEMA TO `analysts`;
GRANT SELECT ON SCHEMA main.YOUR_SCHEMA TO `analysts`;

-- Narrower: only one specific table
GRANT SELECT ON TABLE main.YOUR_SCHEMA.practice_customers TO `analysts`;

-- Take it away again
REVOKE SELECT ON SCHEMA main.YOUR_SCHEMA FROM `analysts`;
Granting SELECT at......covers
CATALOG gbmartEvery schema and table, now and later
SCHEMA gbmart.goldEvery table today — and any table added next month
TABLE gbmart.gold.fact_salesOnly that one table

Memorize the middle row: a schema-level grant is a standing rule for whatever exists at query time, not a one-time snapshot.

Reading the Real gbmart Grants — Live, Read-Only

SHOW GRANTS is itself just a read — it changes nothing. Wrapped in try/except: this demo account may not own gbmart, and a permission error here is a normal Unity Catalog boundary, not a bug.

We check three real levels: the gbmart catalog itself, the gold schema, and one specific table (fact_sales).

grant_checks = [
    ("CATALOG gbmart", f"SHOW GRANTS ON CATALOG {CATALOG}"),
    ("SCHEMA gbmart.gold", f"SHOW GRANTS ON SCHEMA {CATALOG}.gold"),
    ("TABLE gbmart.gold.fact_sales",
     f"SHOW GRANTS ON TABLE {CATALOG}.gold.fact_sales"),
]
for label, stmt in grant_checks:
    try: spark.sql(stmt).display()
    except Exception as e:
        print("Normal UC boundary, not a bug.")
Section 2

Row-Level Security — Row Filters

A row filter is a SQL function returning BOOLEAN — a row is visible only if the function returns true for it.

Define and Attach a Row Filter

Attach it once with ALTER TABLE ... SET ROW FILTER, and every reader of that table — any tool, any notebook, any BI dashboard — is filtered automatically. No application code anywhere has to remember a WHERE clause.

CREATE OR REPLACE FUNCTION your_catalog.your_schema.region_filter(region STRING)
RETURNS BOOLEAN
RETURN region = 'US';

ALTER TABLE your_catalog.your_schema.your_table
SET ROW FILTER your_catalog.your_schema.region_filter ON (region);

The hands-on demo uses exactly this simple fixed-literal version (region = 'US') on purpose — deterministic no matter which account runs it, which is exactly what a repeatable classroom demo needs.

In Production: Role-Aware Row Filters

A real deployment's function body is usually role-aware rather than a fixed literal, so different groups see different slices of the same table:

-- Illustrative only -- what a role-aware version looks like in production
RETURN CASE
    WHEN is_account_group_member('global_admins') THEN true
    WHEN is_account_group_member('us_sales_team') THEN region = 'US'
    WHEN is_account_group_member('in_sales_team') THEN region = 'IN'
    ELSE false
END;
Section 3

Column-Level Security — Masking

The column equivalent of a row filter: instead of true/false per row, it returns a transformed value for one column.

Define and Attach a Masking Function

CREATE OR REPLACE FUNCTION your_catalog.your_schema.email_mask(email STRING)
RETURNS STRING
RETURN CONCAT('***', SUBSTRING(email, INSTR(email, '@'), LENGTH(email)));

ALTER TABLE your_catalog.your_schema.your_table
ALTER COLUMN email SET MASK your_catalog.your_schema.email_mask;

Attach with ALTER TABLE ... ALTER COLUMN ... SET MASK, and every reader of that column gets the function's output instead of the raw value — same mechanism as a row filter, applied per-column.

The hands-on demo runs the unconditional version — masked for absolutely everyone, including you — for the same determinism reason as the row filter. A production version swaps in a CASE/is_account_group_member(...) body, full value for one role, redacted for everyone else.

Why a Practice Table, Not gbmart

1. It's disruptive to everyone else, immediately

The instant a row filter or mask is attached to a shared table, every other student's and the instructor's next query against it is filtered/masked too — mid-class, with no warning.

2. It isn't a quiet, reversible change

Unlike a SELECT, attaching a row filter or a mask is a standing change to the table's own metadata. Undoing it needs another explicit statement — it doesn't expire on its own.

Compute note: row filters and column masks are enforced on supported compute only — a SQL warehouse, a shared-access-mode cluster, or a recent single-user runtime. If your cluster doesn't support them, the demo's cells print a clear fallback message instead of failing.

Lineage — Two Different (Related) Things

"Lineage" gets used loosely, but this session means two specific, different things — a common trip-up.

DESCRIBE HISTORY vs. Catalog Explorer Lineage

DESCRIBE HISTORYUnity Catalog Lineage
ScopeOne table's own version timelineCross-object graph: tables, notebooks, jobs, dashboards
Answers"What changed, and when?""What fed this table, what consumes it?"
Captured byThe Delta transaction logUnity Catalog observing every query
GranularityTable + versionTable-level and column-level
How you see itDESCRIBE HISTORY <table>Catalog Explorer's Lineage tab

Both are automatic — neither needs manual tagging — but they answer different questions.

Real Version History — gbmart.gold.dim_customer

dim_customer is SCD2 (Day 6/10) — genuinely interesting history, since Day 10's SCD2 MERGE demo created new versions on top of Day 6's initial build.

HISTORY_TABLE = f"{CATALOG}.gold.dim_customer"
try:
    spark.sql(f"DESCRIBE HISTORY {HISTORY_TABLE}") \
        .select("version","timestamp","operation") \
        .limit(10).display()
except Exception as e:
    print("No SELECT, or not present yet.")

Bonus (optional): some workspaces additionally expose lineage as queryable metadata — system.access.table_lineage / column_lineage — if an account admin has enabled it. 100% read-only either way; Catalog Explorer's Lineage tab always works regardless.

Wrap-Up

Key Takeaways

🔑 Permissions

  • One hierarchy — metastore → catalog → schema → table/view/function
  • Grants at a higher level are inherited by everything below, including objects created later

👁️ Row Filters & Masking

  • Both apply to every reader automatically — zero application-side filtering code
  • Never attach either to a real shared table you don't own — practice first

🧬 Lineage

  • DESCRIBE HISTORY and Catalog Explorer lineage are both automatic, but answer different questions
