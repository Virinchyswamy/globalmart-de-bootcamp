    Input 5 — the real answer

    schemaEvolutionMode = "failOnNewColumns". The requirement is explicit: fail and alert on a new column, don't silently evolve. "addNewColumns" (Autoloader's default) is the opposite of what's asked here — it's the value you'll switch to later in Assessment 2 when you actually want the new column let in.

    1b

    A real gotcha in suppliers.csv specifically — an embedded newline

    SUP-05's OfficeAddress field genuinely contains a line break inside it ("12/A, Anna Salai ↵ Chennai 600002"). Read the file with default CSV options and Spark splits that one row into two records at the newline — you'll get 11 rows in Bronze instead of 10, and nothing will look obviously wrong until you count.

    .option("multiLine", "true")
.option("escape", '"')

    Both options together tell Spark to treat the quoted field as one value regardless of the embedded newline. Add these to the Autoloader read for suppliers specifically — check your row count against the source (10) before moving on to Silver, not after.

    2

    The shipping_tier column-name problem — real, not hypothetical

    The real shipping_tier.csv header row is: ShippingTierID, TierName, Cost (Rs), MaxDeliveryDays, IsAvailableOnline. Delta table columns can't contain parentheses or the exact character sequence in Cost (Rs) without column-name escaping — that's the literal cause of the AnalysisException in Input 6. Fix it in the ingestion code, before the write, not by hand-editing the CSV:

    df = df.withColumnRenamed("Cost (Rs)", "cost_inr")
    Input 6 — the real answer

    Cause: Delta (and Spark's Parquet-backed storage underneath it) disallows spaces and several special characters — including parentheses — in column names unless you escape every reference with backticks everywhere, forever. Fix: rename the column immediately after the Autoloader read, before the writeStream — one clean identifier, no backticks needed downstream, ever.

    Input 10 — the Time Travel restore skill check

    A separate scenario from your real build: your update script accidentally wrote carrier_id = NULL to all 115 rows instead of just the 3 orphaned ones. You need the 112 correct values back without erasing the _data_note column you'd already added since.

    -- 1. Find the version right before the bad write
DESCRIBE HISTORY gbmart.silver_as.shipments;
-- read the version/timestamp column for the commit just before the bad UPDATE

-- 2. Restore only the 112 rows, from the old version, without touching _data_note
MERGE INTO gbmart.silver_as.shipments AS target
USING (
    SELECT shipment_id, carrier_id
    FROM gbmart.silver_as.shipments VERSION AS OF <good_version>
    WHERE carrier_id IS NOT NULL
) AS source
ON target.shipment_id = source.shipment_id
WHEN MATCHED AND target.carrier_id IS NULL THEN UPDATE SET
    target.carrier_id = source.carrier_id;

    Targeted column-level restore, not a full RESTORE TABLE — that would roll back _data_note too, which the question explicitly rules out.

    Assessment 1 Task 3 — Dimensional Model

    Read the Provided Star Schema Before You Build Anything

    This task is conceptual, not code — the actual schema is already designed for you in the downloaded Star Schema workbook. What you're demonstrating is that you understand why it's shaped the way it is.

    Input 14 — why not dim_order_items?

    order_id, product_id, quantity_purchased, unit_price, discount_amount, line_total are transactional measures tied to a specific point-in-time event (an order line), not descriptive attributes of a stable business entity. A dimension describes a "who/what/where" that changes slowly; these columns change with every order. They belong in a fact table (or as measures on an existing one), not a dimension — building dim_order_items would be modeling a fact as if it were a dimension.

    Input 15 — Kimball, and why

    6-month timeline, 10 analysts querying via SQL, a well-understood and stable source schema, 3 engineers. Kimball star schema wins here specifically because it optimizes for fast, analyst-friendly querying on a well-defined domain within a tight timeline — Data Vault's audit/hub-satellite overhead and Inmon's normalize-first layer both cost more time than this project has, for a benefit (deep auditability, enterprise-wide integration) this specific brief doesn't ask for.

    Before Task 4: from the workbook, write down for yourself — the fact table's grain (one row per what?), which keys are surrogate vs. natural, and which foreign keys allow NULL (this directly foreshadows the orphaned-carrier handling in Task 4).

    Assessment 1 Task 4 — Gold Layer

    3 Dimensions, 1 Fact, 2 Aggregated Tables

    Correction: both agg objects are real materialized Delta tables (saveAsTable), not SQL views — an earlier draft of this guide called them views. Pre-computing and writing them means downstream dashboards don't re-run the aggregation on every query; the tradeoff is you must re-run these two steps after every incremental load to keep them current (see the incremental section later).

    ObjectBuilt fromNotes
    dim_suppliersilver_as.suppliersSurrogate key, e.g. sha2(supplier_id, 256)
    dim_carriersilver_as.carriersSame pattern
    dim_shipping_tiersilver_as.shipping_tierSame pattern
    fact_shipmentssilver_as.shipments joined to all 3 dimsGrain: one row per shipment
    agg_carrier_performance (Delta table)fact_shipmentsDelivered shipments only
    agg_tier_analysis (Delta table)fact_shipmentsAll shipments
    A

    The two derived delivery metrics

    fact_df = fact_df.withColumn(
    "delivery_delay_days",
    when(col("actual_arrival").isNull(), None)
    .otherwise(datediff(col("actual_arrival"), col("expected_arrival")))
).withColumn(
    "is_on_time",
    when(col("actual_arrival").isNull(), None)
    .otherwise(col("actual_arrival") <= col("expected_arrival"))
)

    Both gated on actual_arrival IS NOT NULL — a shipment still in transit has no delay to report yet, and forcing a value there would be inventing data, not deriving it.

    B

    The orphaned-carrier join — keep the row, NULL the key

    fact_df = (
    shipments_df.alias("s")
    .join(dim_carrier.alias("c"), col("s.carrier_id") == col("c.carrier_id"), "left")
    .join(dim_supplier.alias("sup"), col("s.supplier_id") == col("sup.supplier_id"), "inner")
    .join(dim_shipping_tier.alias("t"), col("s.shipping_tier_id") == col("t.shipping_tier_id"), "inner")
)

    The carrier join is deliberately left, not inner — the 3 shipments referencing CAR-99 keep their row in fact_shipments with a NULL carrier surrogate key, matching the Silver decision to flag rather than quarantine them.

    C

    The two aggregation tables

    agg_carrier = (
    spark.table(FACT_SHIPMENTS)
    .join(dim_carrier.select("carrier_key", "carrier_id", "carrier_name"), on="carrier_key", how="left")
    .filter(col("shipment_status") == "Delivered")
    .groupBy("carrier_key", "carrier_id", "carrier_name")
    .agg(
        count("shipment_id").alias("total_shipments"),
        round(avg("delivery_delay_days"), 2).alias("avg_delay_days"),
        round(avg("shipping_cost_inr"), 2).alias("avg_cost_inr"),
        round(sum(when(col("is_on_time") == True, 1).otherwise(0)) / count("shipment_id") * 100, 1).alias("on_time_pct"),
    )
)
agg_carrier.write.format("delta").mode("overwrite").option("overwriteSchema", "true").saveAsTable("gbmart.gold_as.agg_carrier_performance")

    agg_tier_analysis follows the same shape, grouped by shipping_tier_key instead, and deliberately doesn't filter to Delivered — it needs every shipment, delivered or not, to answer cost-variance and volume questions across the whole tier, not just the completed ones.

    Real, verified output from an actual run of this exact pipeline (2026-07-15) — use this to sanity-check your own numbers, not to skip building it yourself: agg_carrier_performance shows XpressBees with 14 delivered shipments (the highest — matches Input 17), and the CAR-99 orphaned-carrier group nets exactly 3 shipments with a null carrier row, exactly as the flag-don't-quarantine decision predicts. agg_tier_analysis shows In-store Pickup at 28 total shipments (matches Input 18), followed by Standard (26), Express (24), Overnight (20), Local Delivery (17) — 28+26+24+20+17 = 115, the same clean-row total from Silver.

The pipeline failing on SupplierRating IS the alert it was built to give. The single config change that lets the new column in, without any ALTER TABLE or table-definition edit:

    B

    Input 6 — the checkpoint-deletion disaster (understand it, don't need to reproduce it)

    A conceptual scenario: checkpoint + schema-location folders got deleted by an unrelated cleanup job, then someone re-runs Autoloader against a folder now holding both suppliers.csv (10 rows) and suppliers_inc_02.csv (3 rows).

    The real answer, all 3 parts

    1. Row count: with no checkpoint, Autoloader has no memory of what it already ingested — it treats the whole folder as new and reprocesses both files. Since Bronze writes in append mode, the original 10 rows get appended a second time on top of what's already there: 23 rows in bronze_as.suppliers (10 original + 10 duplicated + 3 new), not 13.

    2. Schema-drift risk: with the schema location also gone, Autoloader has to re-infer the schema from scratch by sampling files. If it samples a file without SupplierRating first, or infers a different type for it than intended, the "agreed contract" for that column is silently rewritten — with no history to catch the drift.

    3. Production practice: checkpoint and schema-location paths should live in a protected prefix that generic cleanup/retention jobs are explicitly excluded from (or in a Unity Catalog Volume with its own access controls), never inside a general "raw data" bucket subject to broad lifecycle policies.

    Assessment 2 Task 2 — Incremental Silver

    CDF Read → Dedup → SCD1/SCD2 MERGE

    A

    Read only what changed

    changes_df = (
    spark.readStream.format("delta")
        .option("readChangeFeed", "true")
        .option("startingVersion", last_processed_version)
        .table("gbmart.bronze_as.carriers")
        .filter(col("_change_type").isin("insert", "update_postimage"))
)

    Filters out update_preimage (the stale "before" row of an update) and delete — the same real fix pattern already established in this course's own incremental Silver notebooks.

    B

    Input 9 — the 4-vs-3-rows MERGE failure

    CDF returns 4 rows for a source file with only 3. This is DELTA_MULTIPLE_SOURCE_ROW_MATCHING_TARGET_ROW_IN_MERGE — the exact real bug this course already hit and fixed once in the main incremental notebooks.

    Input 9 — the real answer

    1. Cause: one source row changed twice within the same CDF read window (e.g. two commits landed before Silver's last run), so CDF emits two change events for the same supplier_id — MERGE requires at most one source row per matched target row and fails the instant two source rows target the same key.

    2. Fix — dedupe before the MERGE:

    dedup_window = Window.partitionBy("supplier_id").orderBy(col("_commit_version").desc())
changes_df = (
    changes_df
    .withColumn("_rn", row_number().over(dedup_window))
    .filter(col("_rn" ) == 1)
    .drop("_rn")
)

    3. Which row wins: the one with the highest _commit_version — the latest real state, since that's what SCD1 is supposed to reflect.

    C

    Input 11 — SCD1 vs. SCD2, same target table

    # SCD1 -- what you actually built: latest state always wins, no history
target = DeltaTable.forName(spark, "gbmart.silver_as.carriers")
(target.alias("t")
    .merge(changes_df.alias("s"), "t.carrier_id = s.carrier_id")
    .whenMatchedUpdateAll()
    .whenNotMatchedInsertAll()
    .execute())

# SCD2 -- preserve ServiceRegion history, close the old row, insert a new current one
target.alias("t").merge(
    changes_df.alias("s"),
    "t.carrier_id = s.carrier_id AND t.is_current = true"
).whenMatchedAndCondition(
    "t.service_region != s.service_region"
).updateExpr({
    "is_current": "false",
    "effective_end": "current_timestamp()"
}).whenNotMatchedInsert(values = {
    "carrier_id": "s.carrier_id", "service_region": "s.service_region",
    "is_current": "true", "effective_start": "current_timestamp()",
    "effective_end": "null",
}).execute()
# then a second MERGE inserts the new current row for any carrier whose region just changed

    The real difference isn't the MERGE keyword — it's the match condition. SCD1 matches on the natural key alone and always overwrites. SCD2 matches on natural key + is_current = true, closes the old row instead of overwriting it, and inserts a fresh current row — same target table, genuinely different logic.
