    A real gotcha in suppliers.csv specifically

    One supplier's address field genuinely has a line break embedded inside it. Read with default CSV options and Spark splits that single row into two records at the newline — you'll silently get 11 rows in Bronze instead of 10, and nothing looks obviously wrong until you count.

  • Turn on the option that treats a quoted multi-line field as one value, and pair it with the matching quote-escape option — both together, not just one.
  • Check your row count against the source (10) as an explicit step before moving on to Silver, not after something downstream looks off.

Rename that one column to cost_inr (the confirmed target name, per the Data Dictionary) immediately after the Autoloader read, before the table write — a single rename step in the DataFrame, not a CSV edit.

    4

    Input 10 — the Time Travel restore skill check

    A separate scenario: an update script wrongly nulled carrier_id on all 115 rows instead of just the 3 that were actually orphaned, and you can't do a full table restore because it would erase a column you've since added.

  • First, look at the table's version history to find the exact version right before the bad update ran.
  • Then run a MERGE where the "source" side is a query against the table at that earlier version — this is Delta Time Travel, querying a specific historical snapshot directly.
  • Match on the shipment's ID, and only update carrier_id where it's currently null but had a real value in that earlier snapshot — that scopes the fix to exactly the 112 wrongly-affected rows.
  • Because this is a targeted MERGE and not a full RESTORE TABLE, every other column you've since added — including the one you can't afford to lose — is left completely untouched.

    Assessment 1 Task 3 — Dimensional Model

    Read the Provided Star Schema Before You Build Anything

    Conceptual, not code — the schema is already designed for you in the downloaded workbook. You're demonstrating you understand why it's shaped the way it is.

    Why not dim_order_items?

    Those columns describe a transactional event (one order line), not a stable business entity — they change with every order rather than slowly over time. That's fact-table material, not dimension material.

    Why Kimball star schema here?

    Tight timeline, analysts querying via SQL, a well-understood and stable source schema — this combination favors fast, analyst-friendly querying over the audit/integration overhead Data Vault or Inmon would add for a benefit this brief doesn't ask for.

    Before Task 4, write down for yourself: the fact table's grain, which keys are surrogate vs. natural, and which foreign keys are allowed to be null — this last one directly foreshadows the orphaned-carrier handling coming up.

    A

    The two derived delivery metrics

  • Add a "delay in days" column — the difference between actual arrival and expected arrival.
  • Add an "on time" flag — whether actual arrival happened on or before expected arrival.
  • Gate both behind "actual arrival is not null" — a shipment still in transit has nothing to report yet, so both should stay null for it rather than guessing.
    • B

    The orphaned-carrier join — keep the row, null the key

  • Join shipments to the carrier dimension using a left join, not inner — this is exactly what lets the 3 unresolvable-carrier shipments stay in the fact table with a null carrier key instead of vanishing.
  • Join to the supplier and shipping-tier dimensions with an inner join — every shipment does have a valid supplier and tier, so there's no need for the defensive left join there.
    • C

    The two aggregation tables

  • agg_carrier_performance: group the fact table by carrier, filtered to Delivered shipments only, computing shipment count, average delay, average cost, and on-time rate per carrier.
  • agg_tier_analysis: group by shipping tier across every shipment regardless of status, computing shipment count, average actual cost, and delay/on-time performance per tier.
  • Write and save both as real Delta tables, same as the fact table — not views. That means you re-run these two steps to refresh them after every incremental load, rather than getting a free automatic refresh.

    • Real, verified output from an actual run of this exact pipeline — use this to sanity-check your own numbers, not to skip building it yourself: agg_carrier_performance shows XpressBees with 14 delivered shipments (highest — matches Input 17), and the CAR-99 orphaned-carrier group nets exactly 3 shipments with a null carrier row. agg_tier_analysis shows In-store Pickup at 28 total shipments (matches Input 18), followed by Standard (26), Express (24), Overnight (20), Local Delivery (17) — 28+26+24+20+17 = 115, matching Silver's clean row total.

    CDF On, New Files In, Schema Actually Evolves This Time

  • Enable Change Data Feed on all 3 Bronze tables first — a one-time table property flip, done before any incremental file is uploaded.

  • Run the incremental SQL script in Supabase, then trigger a new Lakeflow Connect run to pull the new/updated shipment rows.
    • A

    The schema-evolution fix

    The source team added a new column that wasn't there in the first batch. Since Bronze was deliberately set to fail on a new column, this failure is the alert working as designed — not a bug. The fix: flip the schema-evolution setting to the mode that adds the new column automatically instead of failing on it, and re-run. No ALTER TABLE, no table-definition edit — Autoloader handles it. The 10 rows already in the table from the first batch will show the new column as null, since schema evolution never backfills history, it only opens the door going forward.

    B

    The checkpoint-deletion disaster (understand it, no need to reproduce it)

    A conceptual scenario: the checkpoint and schema-location folders got deleted by an unrelated cleanup job, then someone re-runs Autoloader against a folder that now has both the original file and the new incremental file sitting in it.

  • With no checkpoint, Autoloader has no memory of what it already loaded — it treats the whole folder as brand new and reprocesses everything, including the original file a second time. Since Bronze appends rather than merges, this means duplicated rows, not just the expected new ones.
  • With the schema location also gone, Autoloader has to re-infer the schema from scratch by sampling files — if it samples inconsistently, the "agreed" column types can silently drift with no history to catch it.
  • The real production fix: keep checkpoint and schema-location paths in a protected path that generic cleanup/retention jobs are explicitly excluded from, ideally with its own access controls.
    • ✓ Incremental Bronze Checkpoint

    CDF enabled on all 3 tables. Suppliers +3 (new column populated only for the new rows), carriers +2, shipments +10 new/8 updated.

    Assessment 2 Task 2 — Incremental Silver

    CDF Read → Dedup → SCD1/SCD2 MERGE

    A

    Read only what changed

  • Read the Bronze table's change feed rather than the whole table — starting from the version you last processed, not from the beginning.
  • Keep only the change types that represent a row's current state — new inserts and the "after" side of an update. Drop the "before" side of updates and any deletes, since those aren't the state you want reflected in Silver.
    • B

    The 4-vs-3-rows MERGE failure, and the fix

    The change feed can return more rows than the source file had, if one record changed more than once within the same read window. MERGE fails the moment two source rows target the same existing row.

  • Cause: the same natural key appears twice in the change-feed output because it was updated twice before Silver's last run picked it up.
  • Fix, before the MERGE runs: deduplicate the change rows by the natural key, keeping only the one with the highest commit version per key — a ranking window function, not a manual filter.
  • Which row wins: always the latest one, by commit version — that's the state SCD1 is supposed to reflect.
    • C

    SCD1 vs. SCD2, same target table

  • SCD1 (what you already built): match on the natural key alone, update every column in place when matched, insert when not — latest state always wins, no history kept.
  • SCD2 (the new requirement, for one specific column's history): match on the natural key and "this is the current row" together. When the tracked column's value has actually changed, don't update the existing row — close it out by marking it no-longer-current and stamping an end date, then insert a brand-new row carrying the new value, marked current, with a fresh start date.
  • The real difference isn't which MERGE keyword you use — it's the match condition and what happens on a match: overwrite in place (SCD1) vs. close-and-insert-new (SCD2), on the very same table.
    • ✓ Incremental Silver Checkpoint

    Suppliers = 12 rows, carriers = 11 rows, shipments = 125 rows. Confirm the carrier change feed read exactly 2 rows from Bronze before the MERGE.

    Assessment 2 Task 3 — Refresh Fact Table

    Same Gold Notebook, Zero Changes

    Re-run the exact Gold notebook from Assessment 1. It should just work.

    Why no code change is needed

    The two delivery-timeliness columns are recomputed from Silver's current state on every single Gold run — they're derived, not carried forward from a previous run. Once a shipment's actual arrival gets filled in via Silver's own MERGE, the very next Gold run naturally computes real values for it instead of null, because the derivation logic runs fresh every time, for every row it touches. Nothing about that logic needed to know "this is run 2."
