How This Works

Three phases. Phase 1 happens entirely in the UI — no notebook open yet. Phases 2 and 3 happen in the companion notebook, Day12_2_HOL1_Unity_Catalog_Permissions_UI_and_Code.ipynb — run its Setup cell first, before you do anything below.

2By Code

Back in the notebook: read that same grant with SHOW GRANTS, revoke it with SQL, then grant it back with SQL — same table, same privilege, same principal.

3Compare to Real Gold

Read-only SHOW GRANTS against the real gbmart catalog, schema, and table — see what access actually exists on the layer you've been building all course.

Why bother proving UI and code are "the same"? Because in a real job, you'll usually reach for whichever is faster in the moment — a quick one-off grant via the UI, a batch of grants scripted in a setup notebook. If you don't trust that they're the same underlying mechanism, you'll end up double-checking everything twice. Today removes that doubt.

Phase 1 🖱️ mouse only, no SQL

Grant It From the UI

Before this: run the companion notebook's Setup cell — it creates main.YOUR_SCHEMA.practice_customers, the table you'll grant access to below.

  • Open Catalog Explorer from the left sidebar.
  • Navigate to main → your practice schema (YOUR_SCHEMA) → practice_customers.
  • Click the Permissions tab at the top of the table's page.
  • Click Grant.
  • In the principal field, type account users — this is a built-in Unity Catalog group meaning "everyone in this account." It always exists, so there's nothing to set up first.
  • Check the SELECT privilege, then click Grant.

    • Why account users and not a named colleague? It's a real, built-in group every Databricks account already has — guaranteed to exist regardless of your specific workspace setup, so this step never blocks on "does that group exist yet."

    ✓ Phase 1 Checkpoint

    The Permissions tab should now list a new row: account users — SELECT. Don't move on until you can see it there, in the UI, with your own eyes.

    Phase 2 💻 back in the notebook

    Read It, Revoke It, Grant It Back — All by Code

    Open Day12_2_HOL1_Unity_Catalog_Permissions_UI_and_Code.ipynb and run the Phase 2 cells in order.

  • Read it: SHOW GRANTS ON TABLE main.YOUR_SCHEMA.practice_customers — the grant your UI click just created should appear here immediately.
  • Revoke it: REVOKE SELECT ON TABLE ... FROM \`account users\` — then SHOW GRANTS again; the row should be gone.
  • Grant it back: GRANT SELECT ON TABLE ... TO \`account users\` — the exact syntax ILT 4 showed you as illustrative-only. SHOW GRANTS one more time — it should look identical to what Phase 1's UI click produced.
    • REVOKE SELECT ON TABLE main.YOUR_SCHEMA.practice_customers FROM `account users`;
GRANT SELECT ON TABLE main.YOUR_SCHEMA.practice_customers TO `account users`;
    ✓ Phase 2 Checkpoint

    You should have seen SHOW GRANTS output the same privilege row three times: once from your UI click, once confirming it was gone after the code REVOKE, and once confirming it was back after the code GRANT. If the third result doesn't match the first, re-run the cells in order — a skipped cell is the usual cause.

    Phase 3 🔍 read-only, real gbmart

    What Access Actually Exists on Real Gold

    Run the notebook's Phase 3 cell — the exact same SHOW GRANTS mechanism you just used on your own tiny table, now pointed at gbmart, gbmart.gold, and gbmart.gold.fact_sales.

    If you see a permission error here, that's expected. Unity Catalog only lets you read grants on objects you own or administer — most learner accounts aren't owner/admin on the real gbmart catalog. The notebook cell wraps this in try/except and prints a clear message instead of failing. That message is the lesson: it's the exact same access-control model you just exercised on your own table, now protecting you from seeing something you're not entitled to see.

    ✓ Phase 3 Checkpoint

    Either you see real grant rows for gbmart, or you see the graceful permission-boundary message — both are a correct, complete run of this phase.

    Reference

    Privileges, at a Glance

    PrivilegeGrants the ability to...
    USE CATALOG"Step into" a catalog at all — necessary but not sufficient on its own
    USE SCHEMAStep into a schema — same idea, one level down
    SELECTRead rows from a table or view
    MODIFYINSERT/UPDATE/DELETE/MERGE rows
    CREATE TABLE / CREATE SCHEMA / CREATE FUNCTIONCreate new objects of that type inside the parent
    ALL PRIVILEGESEvery privilege valid at that level, combined
