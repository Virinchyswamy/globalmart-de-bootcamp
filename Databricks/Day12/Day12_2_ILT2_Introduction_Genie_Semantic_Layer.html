Section 1

What Is Databricks Genie?

A business user types "What was our revenue by category last month?" — and gets back a generated SQL query plus an answer. No SQL is written by the person asking.

What Actually Happens Behind the Scenes

1. Ask

A business user types a natural-language question into the Genie chat UI. No SQL, no join logic — plain English.

2. Genie Interprets

Genie's LLM reads the Genie Space's metadata — table/column names, comments, sample questions — to work out which tables, columns, and joins answer it.

3. SQL + Answer

Genie generates SQL, runs it against a warehouse, and returns the result — usually alongside the SQL itself, so a data engineer can verify what ran.

A Genie Space is a scoped, curated subset of a catalog — specific tables/views, instructions, sample questions, example SQL — deliberately narrower than "the whole catalog," so the LLM isn't guessing across hundreds of unrelated tables.

Be Honest About the Boundary

A Genie Space is set up entirely by clicking through the Databricks workspace UI — Catalog Explorer → Genie → New Space, selecting tables, writing instructions, adding sample questions — not by running code in a notebook.

What's deferred

The matching hands-on, "Set Up Genie on Gold Layer — Descriptions + Natural Language Queries," is a separate, later session done live in the workspace UI against the real gbmart Gold layer. Nothing in today's notebook creates a Genie Space — and nothing later in it will.

Section 2

What a Semantic Layer Is

And why an LLM — or a brand-new analyst — cannot make sense of raw column names without one.

Two Raw Facts About fact_sales

A column named Sales_amount (type decimal), and a column named Actual_price (type decimal). To an LLM — or a new analyst — those names alone answer none of the questions that matter.

Without a semantic layerWith a semantic layer
Sales_amountJust a decimal column. Safe to SUM? Pre- or post-discount? Unknown."Revenue in INR for this order line item — quantity × discounted price. Safe to SUM."
Actual_priceJust a decimal column. Looks summable like any other number."Original list price per unit, in INR. Non-additive — never SUM directly across products."

A Semantic Layer Is the Metadata That Answers These Questions First

Concretely, for this course, it's:

  • Table comments — what this table is, at what grain
  • Column comments — what a column means, whether it's safe to aggregate
  • Certified views with business-friendly names
  • Sample questions and example SQL registered on a Genie Space

None of this changes what the data is. All of it changes whether a raw schema is usable by something that has never seen your business before — exactly the position both Genie's LLM and a new hire are in on day one.

Section 4

The Part We CAN Script

Genie Space setup is UI-only. The semantic layer underneath it — table and column comments — is real, scriptable Databricks SQL, run against a safe practice copy.

Step A — Seed a Practice Copy, Look at the Raw Schema

The ONLY touch against the real table anywhere in this notebook — read-only
YOUR_SCHEMA = "main.YOUR_SCHEMA"
spark.sql(f"CREATE SCHEMA IF NOT EXISTS {YOUR_SCHEMA}")
PRACTICE_TABLE = f"{YOUR_SCHEMA}.fact_sales_practice"

# CREATE OR REPLACE -- idempotent, safe to re-run
spark.sql(f"""CREATE OR REPLACE TABLE {PRACTICE_TABLE}
    AS SELECT * FROM gbmart.gold.fact_sales LIMIT 100""")

"Before" — what an LLM sees with zero semantic layer: a list of names and types, and nothing else. Is it safe to SUM(Actual_price)? Is Sales_amount pre- or post-discount? What currency? None of that is answerable from dtypes alone.

Step B — Add Real Table + Column Comments

Must stay additivity-correct — a wrong comment is worse than no comment
MeasureAdditivityWhat the comment must say
Quantity_purchasedAdditiveSafe to SUM across any dimension
Sales_amountAdditiveSafe to SUM — this is the revenue measure
Actual_priceNon-additiveNever SUM/AVG directly across products
Discounted_priceNon-additiveDerive avg. selling price as SUM(Sales_amount)/SUM(Quantity_purchased)
spark.sql(f"COMMENT ON TABLE {PRACTICE_TABLE} IS '...'")

for column_name, comment_text in column_comments.items():
    spark.sql(f"ALTER TABLE {PRACTICE_TABLE} ALTER COLUMN {column_name} COMMENT '{comment_text}'")

Before vs. After — Why This Is the Whole Point

Before (Step A)After (Step C)
What a column name tells youActual_price, decimal — nothing elseSame column, plus: "non-additive, never SUM directly across products"
Can Genie answer "total sales"?Has to guess which of 3 decimal columns is revenueKnows Sales_amount is the additive revenue measure — stated directly
Can a new analyst self-serve?Only by asking someone who knows the rulesYes — the rule is attached to the column itself

Nothing about the underlying data changed between Step A and Step C — same 100 rows, same values. The only thing that changed is whether the schema can explain itself. That is the entire value of a semantic layer.

Sample Questions

Bootstrapping Genie's natural-language matching with worked question → SQL pairs.

Worked Examples Genie Can Pattern-Match Against

Illustrative only — not executed in this session. Every sample question maps to one of the two already-built Gold views, not a fresh query against raw fact_sales.

Sample questionMaps to
"What was our revenue by category last month?"SELECT category, SUM(total_revenue) FROM vw_monthly_category_sales ... GROUP BY category
"Which states generate the most revenue?"SELECT state, SUM(total_revenue) FROM vw_regional_sales GROUP BY state ORDER BY total_revenue DESC
"What is our average discount by category?"SELECT category, AVG(avg_discount_given) FROM vw_monthly_category_sales GROUP BY category
"How many orders came from each region?"SELECT state, city, total_orders FROM vw_regional_sales
