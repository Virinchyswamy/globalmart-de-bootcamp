1. Apache Spark — The Engine Under the Hood

Before Databricks, there was Apache Spark — an open-source distributed computing engine created at UC Berkeley in 2009. It solves one problem: processing massive datasets (terabytes to petabytes) faster than a single computer can.

DIY Apache Spark (raw)

  • Download and install Spark yourself
  • Manage your own cluster (YARN, Kubernetes)
  • Configure Hadoop dependencies manually
  • Set up notebooks (Jupyter) yourself
  • Write your own scheduling (Airflow)
  • Manage your own library versions
  • No built-in governance or access control

Databricks (managed Spark)

  • Spark pre-installed, pre-optimised, always up to date
  • Clusters with one click — auto-scale, auto-terminate
  • No config files — works out of the box
  • Built-in notebooks, collaboration, version control
  • Workflows for scheduling (no Airflow needed)
  • Managed library installation per cluster
  • Unity Catalog for governance built in
Key insight: Spark is the engine. Databricks is the platform that wraps Spark so you can use it without a DevOps team. All the PySpark code you write runs on Apache Spark under the hood.

2. What is Databricks?

Databricks is a cloud platform built on top of Apache Spark. It gives Data Engineers a fully managed environment for large-scale data processing — with notebooks, clusters, Delta Lake, scheduling, and governance all in one place. GlobalMart uses it to build and run the full Bronze → Silver → Gold pipeline.

📓 Notebooks Interactive cells mixing Python, SQL, Scala, and Markdown. Write and test pipeline logic, share with your team, run cells one at a time or all at once.
⚡ Clusters A group of VMs running Apache Spark. You create one, attach it to your notebook, and Spark distributes your job automatically. Auto-terminates when idle to save cost.
🏔️ Delta Lake The storage format for every table in the pipeline. Parquet files + a transaction log = ACID, time travel, streaming + batch. All Bronze/Silver/Gold tables are Delta.
📁 Unity Catalog Central metadata store. Controls who can access which table, column, or row. Tracks lineage from ADLS raw file to Gold table. Works across all Databricks workspaces.
⚙️ Workflows Scheduled multi-task pipelines (DAGs). Replaces Airflow for simple orchestration. Runs your ingestion → Silver → Gold chain on a timer with retry logic and alerting.
💬 Genie Natural-language Q&A on top of Gold Delta tables. Business users ask questions in plain English — no SQL required. Powered by AI with your data model as context.

3. Cluster Architecture — Driver + Workers

Every Spark job runs on a cluster. The driver is the brain (builds the execution plan, coordinates workers). The workers are the hands (each processes a partition of data in parallel). ADLS is the shared storage — data never fully moves into memory.

Your Notebook Code (Python / SQL)
    ↓
Driver Node (plans the job, builds DAG, tracks task completion, collects results)
    ↓ splits data into partitions → distributes tasks
Worker Node 1 (processes rows 1 – 1M)  reads/writes ↔ ADLS
Worker Node 2 (processes rows 1M – 2M) reads/writes ↔ ADLS
Worker Node 3 (processes rows 2M – 3M) reads/writes ↔ ADLS
(more workers can be added → linear speed improvement)
    ↓ partial results back to driver → final result assembled
Output (shown in notebook display() / written to Delta table)
Cluster TypeBest ForAuto-terminate?
All-Purpose ClusterInteractive notebook development — attach multiple notebooks, keep it running while you workConfigurable (set 30–60 min)
Job ClusterProduction Workflows — spins up for one job, terminates immediately after. Cheaper.Always (on job completion)
Single-Node ClusterSmall datasets / development — driver only, no workers. Free tier compatible.Configurable

Adding more workers = faster on large datasets. 100 GB on 2 workers: ~10 min. Same data on 6 workers: ~3 min. Spark handles the distribution automatically.

4. How Spark Actually Executes Code — DAG, Stages, Tasks

Spark does not execute code line by line. Instead it builds an execution plan (a Directed Acyclic Graph — DAG) and only runs it when you call an Action. This is called lazy evaluation.

You write (transformations — nothing runs yet):
df = spark.read.csv(raw_path)                       ← Transformation (read plan)
df2 = df.filter(df.status == "active")              ← Transformation (filter added to plan)
df3 = df2.groupBy("city").count()                ← Transformation (groupBy added)

df3.show()                                          ← ACTION — Spark builds + runs the DAG NOW

Spark splits into stages (separated by shuffles):
Stage 1: read CSV → filter rows    Task 1: partition 1   Task 2: partition 2   Task 3: partition 3
                                     ↓ shuffle (regroup by city key — network transfer)
Stage 2: aggregate count         Task 1: cities A–M   Task 2: cities N–Z

Shuffles are expensive — they move data across the network between worker nodes. Minimize them by filtering before groupBy and using broadcast joins for small tables.

6. PySpark vs Pandas — Key Differences

pandas

  • Runs on a single machine — one CPU
  • Data must fit in RAM (16 GB limit → crash on 20 GB)
  • Good for datasets under ~1 GB
  • Eager evaluation — every line runs immediately
  • No cluster, no distributed processing
  • Operations are usually fast for small data
  • Cannot read from ADLS natively

PySpark (Spark DataFrame)

  • Runs across a cluster — many CPUs, many machines
  • Data lives in ADLS, not in RAM — handles TB-scale
  • Built for datasets 1 GB → 1 TB+
  • Lazy evaluation — builds a plan, executes only on Action
  • Auto-distributes work across all worker nodes
  • Similar API to pandas — .select(), .filter(), .groupBy()
  • Native ADLS support via abfss://

8. Writing to Delta (Bronze / Silver / Gold)

# Full refresh — overwrite everything at this path
df.write.format("delta").mode("overwrite").save(bronze_path)

# Incremental — append new rows without deleting existing
df.write.format("delta").mode("append").save(bronze_path)

# Register in Unity Catalog (recommended for production)
df.write.format("delta").mode("overwrite").saveAsTable("globalmart.bronze.customers")

# Add new columns without breaking readers (schema evolution)
df.write.format("delta").mode("append").option("mergeSchema", "true").save(bronze_path)

9. Spark SQL — SQL on Delta Tables

Two ways to run SQL in Databricks: a %sql cell (pure SQL output) or spark.sql("...") inside Python (returns a DataFrame you can chain more operations on).

-- In a %sql cell: standard SQL on Delta tables
SELECT status, COUNT(*) AS order_count
FROM bronze.orders
GROUP BY status
ORDER BY order_count DESC;

-- Register a DataFrame as a temp view for SQL access
customers_df.createOrReplaceTempView("customers")
SELECT YEAR(RegistrationDate) AS yr, COUNT(*) AS cnt FROM customers GROUP BY yr

-- Use spark.sql() inside Python to get back a DataFrame
result_df = spark.sql("SELECT city, COUNT(*) AS cnt FROM customers GROUP BY city ORDER BY cnt DESC")
result_df.show(10)

-- Time travel query
SELECT * FROM bronze.orders VERSION AS OF 1;

-- See version history
DESCRIBE HISTORY bronze.orders;

11. PySpark Best Practices

Avoid df.collect() Pulls ALL rows into the driver's RAM. On a 10 GB table → out-of-memory crash. Use show() or display() instead.
Do Filter early Apply .filter() as early as possible in your chain. This reduces the data that flows through all later operations.
Do Select only needed columns Use .select("col1", "col2") instead of keeping all 30 columns through the whole pipeline. Reduces shuffle cost significantly.
Avoid count() before every action df.count() triggers a full scan. Avoid calling it multiple times on the same DataFrame — cache the count or avoid it until needed.
Do Broadcast small tables When joining a large table with a small reference table (e.g. payment_methods with 4 rows), use broadcast(dim) to avoid a shuffle join.
Avoid Hardcoding secrets Never put storage keys or passwords directly in notebook code. Use dbutils.secrets.get() in production, or at minimum environment variables.
