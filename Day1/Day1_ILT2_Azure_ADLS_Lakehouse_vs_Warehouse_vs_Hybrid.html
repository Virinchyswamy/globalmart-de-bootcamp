1. What is Cloud Computing?

Definition
Cloud computing is the delivery of computing services — servers, storage, databases, networking, software, and analytics — over the internet ("the cloud"), on demand, with pay-as-you-go pricing.

Instead of owning and maintaining physical hardware in a data center, you rent capacity from a cloud provider (Microsoft Azure, AWS, Google Cloud) and scale instantly based on demand.

On-Premises vs Cloud

Before cloud, every company had to buy and manage its own servers. Here is what that looked like, compared to cloud:

On-Premises (Traditional)
  • Buy servers upfront — huge capital expenditure (CapEx)
  • Takes 3–6 months to provision new hardware
  • Pay for full capacity even when idle
  • Your team manages hardware, networking, cooling
  • Hard to scale — buy more servers for every traffic spike
  • Single location — natural disaster = data loss
  • Security patches, OS upgrades are your responsibility
  • No built-in AI/ML tools — you build everything from scratch
Cloud (Azure)
  • No hardware to buy — pure operating expenditure (OpEx)
  • Provision resources in minutes with a few clicks
  • Pay only for what you use — scale to zero when idle
  • Microsoft manages hardware, networking, power, cooling
  • Scale up or down instantly — handle any traffic spike
  • Geo-redundant replication — data survives regional outages
  • Managed services handle OS patches, updates automatically
  • 300+ built-in services including AI, ML, IoT, analytics

Three Cloud Service Models

IaaS Infrastructure as a Service You rent raw compute, storage, and networking. You still install and manage the OS, middleware, and apps.

Examples: Azure Virtual Machines, Azure Virtual Network, Azure Blob Storage
PaaS Platform as a Service Microsoft manages the infrastructure AND the platform. You just deploy your code or data pipelines.

Examples: Azure Databricks, Azure App Service, Azure SQL Database, ADLS Gen2
SaaS Software as a Service Fully managed software delivered via browser. You just use it — no servers, no installs, no patches.

Examples: Microsoft 365, Power BI, Salesforce, GitHub
For GlobalMart's pipeline: We use PaaS services almost entirely — Azure Databricks (data processing) and ADLS Gen2 (storage). Microsoft manages the infrastructure; we focus on writing data pipelines.

4. ADLS Gen2 — The Storage Foundation

Azure Data Lake Storage Gen2 is cloud file storage optimised for big-data analytics. It stores any format — CSV, JSON, Parquet, Delta — cheaply at massive scale, and connects natively with Databricks via the abfss:// protocol.

Azure Blob Storage
  • Flat key-value store (folders are just name prefixes)
  • No real folder hierarchy — no folder-level permissions
  • Slower for analytics workloads
  • Default when you create a storage account
  • Uses wasbs:// protocol in Spark
ADLS Gen2
  • True hierarchical folder structure (same as a real file system)
  • Folder-level access control (RBAC + ACLs)
  • Optimised for Spark / Databricks analytics — 10–100× faster reads
  • Enabled by turning on Hierarchical Namespace in the storage account
  • Uses abfss:// (Azure Blob File System Secure) protocol

Key ADLS Gen2 Features

Feature Details
Storage tiers Hot (frequent access, highest cost), Cool (infrequent, lower cost), Archive (rarely accessed, cheapest). Move data between tiers via lifecycle policies.
Redundancy options LRS (3 copies in one data center), ZRS (3 copies across availability zones), GRS (copies in two regions), RA-GRS (read access from second region).
Encryption All data encrypted at rest by default using 256-bit AES. You can use Microsoft-managed keys or your own keys from Azure Key Vault (BYOK).
Access control RBAC roles at container or storage account level. POSIX-style ACLs at file and folder level. Unity Catalog manages access from Databricks without exposing storage keys.
Soft delete Deleted files can be recovered within a configurable retention period (up to 365 days). Critical for GDPR right-to-erasure requests and accidental deletion recovery.
Versioning Keep previous versions of every file. If data is accidentally overwritten, promote the previous version back to current.

5. Three Ways to Store and Query Data at Scale

Before choosing a Lakehouse, most organisations tried one of three approaches. Understanding what each one is — and why the Hybrid model was painful — explains why the Lakehouse architecture exists.

Data Warehouse

The classic enterprise approach

  • Structured, schema-on-write data only
  • ACID transactions — UPDATE, DELETE, MERGE
  • Very fast SQL queries with statistics + indexing
  • High storage cost (proprietary columnar format)
  • Cannot store raw files, JSON, images, ML features
  • Hard to work with for ML/AI teams
  • ETL must transform data before loading

Examples: Snowflake, Azure Synapse, Redshift, BigQuery
Data Lake

The "dump everything" approach

  • Store anything — CSV, JSON, images, logs, Parquet
  • Very cheap (object storage like ADLS or S3)
  • Schema-on-read — define structure at query time
  • No schema enforcement — data quality degrades fast
  • No ACID — no UPDATE or DELETE on files
  • Slow to query — no statistics, no indexing
  • Often becomes a "data swamp" without governance

Examples: Raw ADLS, raw AWS S3, raw GCS
Hybrid (DW + DL)

The painful compromise

  • Data Lake holds raw + ML data
  • Data Warehouse holds clean business data
  • Nightly ETL pipelines move data between the two
  • Same data stored twice — pay for both systems
  • Two sets of infrastructure, two access controls
  • Data freshness lag — batch ETL runs overnight
  • ML and analytics teams see different versions of data

Examples: ADLS + Synapse Analytics side by side

6. The Hybrid Problem — Why It Does Not Work Well

Most large companies still run a Hybrid today. The diagram below shows exactly why it creates pain for Data Engineers and Business teams.

Sources (Postgres, files, APIs)
    ↓
DATA LAKE (raw ADLS / S3 — cheap, unstructured)
    ↓ overnight ETL batch job (ADF / Spark job — can take hours)
DATA WAREHOUSE (Synapse / Snowflake — structured, queryable)
    ↓
Business reports (always 12–24 hours stale)

ML team also reads from DATA LAKE directly ← different access controls
Analytics team reads from DATA WAREHOUSE ← data is a different version

Problems:
  ✗  Same data stored twice — pay for both
  ✗  ML team and analytics team see different numbers
  ✗  ETL pipeline failure = DW is stale for 24h
  ✗  Two governance systems — who can see what?
  ✗  No DELETE in the lake — GDPR requests are a nightmare
  ✗  Schema changes break both systems independently

7. The Lakehouse — One Platform for Everything

The Lakehouse combines cheap lake storage (ADLS) with Data Warehouse features (ACID, schema, fast queries) by adding a transaction layer — Delta Lake — directly on top of the files. One system replaces both.

Sources (Postgres via Lakeflow Connect + ADLS file drops via Autoloader)
    ↓
BRONZE (raw Delta on ADLS — cheap storage, ACID protection)
    ↓ PySpark transformations
SILVER (clean Delta — schema enforced, deduped, SCD applied)
    ↓ star schema build
GOLD — fact_sales (business-ready, Z-ordered, fast to query)
    ↓
GENIE + Reports (same data, same access controls, no duplication)

ML team reads Silver/Gold too — same tables, no copy
Analytics team queries Gold via Genie — same tables
Unity Catalog governs access for everyone in one place

One-sentence takeaway: The Lakehouse gives you the low cost and flexibility of a Data Lake with the reliability and performance of a Data Warehouse — in one system, with no duplication.

Method Security When to use Code

SAS Token Medium — time-limited Temporary sharing SAS token in spark.conf or path
Service Principal (OAuth) Medium — app identity CI/CD pipelines, automation spark.conf.set("fs.azure.account.auth.type.{account}", "OAuth")
Unity Catalog External Location Highest — managed identity Production No spark.conf needed — Unity Catalog manages auth transparently

This bootcamp uses the Storage Account Key for simplicity. In production, Unity Catalog External Locations with managed identity are the standard — no keys ever in code.
