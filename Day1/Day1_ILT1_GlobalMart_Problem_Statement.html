1. What is Data Engineering?

Data Engineering is the discipline of building and maintaining the infrastructure and pipelines that collect, store, clean, and deliver data so that analysts, data scientists, and business users can trust and use it.

🔧 Build Pipelines Design and build data pipelines that move data from source systems (databases, APIs, files) into a central store — reliably, on schedule, every day.
🧹 Clean & Transform Fix data quality problems — nulls, duplicates, wrong types, inconsistent formats — so downstream consumers get accurate numbers they can trust.
📦 Model & Store Organise data into schemas (star schema, dimension tables, fact tables) that make analytical queries fast and the data self-explanatory to business users.
⚙️ Orchestrate & Schedule Automate the pipeline so it runs on a schedule — daily, hourly, or in real time — without manual intervention. Handle failures gracefully.
🔐 Govern Access Ensure the right people can access the right data — and the wrong people cannot. Maintain audit trails for compliance (GDPR, HIPAA).
📈 Enable Insights Deliver data in a form that analysts, data scientists, and business stakeholders can consume directly — through dashboards, SQL, or AI tools like Genie.

2. GlobalMart — Company Background

GlobalMart started as a small e-commerce player and grew fast — both in physical retail stores and online. As it grew, every team started asking the same question: "What does the data say?" But getting a straight answer became harder and harder.

Different teams pulled numbers from different places — and the numbers didn't match. Stakeholders stopped trusting reports. Decisions slowed down. What was supposed to make GlobalMart faster and smarter was instead creating friction between teams.

3. The 5 Problems

1 Data Silos — No Single Source of Truth Orders live in Postgres. Products and customers arrive as CSV files dropped into a folder. Finance has their own copy in Excel. Each team has a different version of the same number.
Symptom: "Our revenue report shows ₹4.2Cr but Finance says ₹3.9Cr — who's right?"
2 Data Inconsistency & Quality Issues Same customer appears three times with different spellings. Dates in three formats (DD/MM/YY, YYYY-MM-DD, epoch). Missing values in critical columns like shipping address.
Symptom: Reports show NULL for 8% of orders. Customer names duplicated causing double-counting.
3 Access Control & Compliance No rules on who sees what. Customer PII (phone, email, address) is visible to everyone. GDPR requires the right to erasure — but no one knows how to delete a row from a CSV file safely.
Symptom: An intern can download the full customer list. A GDPR erasure request takes 2 weeks to fulfill manually.
4 Complex & Duplicated Transformations Every team writes their own scripts to clean the same data. The sales team's Python script, the marketing team's SQL, and the finance team's Excel macro all do different things — all give different answers.
Symptom: 6 different SQL scripts, all called "clean_customers.sql". Nobody knows which is canonical.
5 Unclear Origin & Redundancy Nobody can trace where a number came from or when the data was last refreshed. The same dataset is copied five places. When one copy is updated, the others are not.
Symptom: "Is this the morning snapshot or last night's? I can't tell." Reports become unreliable — teams stop using them.
Result: nobody trusts the data, so nobody uses it the way it was meant to be used.

4. GlobalMart's Data — What We Have

Two source systems feed the pipeline. Every table you will work with in this bootcamp traces back to one of these two sources.

Table Source Description Key Columns Volume
orders Postgres CDC Every customer order placed — status, date, payment, shipping tier order_id, customer_id, order_date, status, payment_method_id, shipping_tier_id ~500K rows, grows daily
order_items Postgres CDC Line-item breakdown of each order — which products, how many, at what price order_item_id, order_id, product_id, quantity, unit_price, subtotal ~2M rows
customers ADLS File Drop Customer master — registration details, preferred payment method customer_id, first_name, last_name, email, phone, dob, registration_date ~6,666 rows per daily file
products ADLS File Drop Product catalog — name, category, supplier, price product_id, name, category, supplier_id, unit_cost, unit_price Static reference, ~10K rows
addresses ADLS File Drop Shipping addresses linked to orders address_id, order_id, street, city, state, pincode, country ~500K rows
payment_methods ADLS File Drop Reference table — maps payment method IDs to names (UPI, Card, Wallet, COD) payment_method_id, method_name 4 rows (PM-001 to PM-004)
suppliers ADLS File Drop Supplier master — who supplies each product supplier_id, name, country, contact_email ~200 rows
Gold output — fact_sales: The pipeline combines all of the above into one analytical table. Grain: one row per order line item. Connects to five dimension tables. This is what stakeholders actually query.

5. Why Databricks?

Before — Fragmented Toolbox

Data was shattered across separate tools — every handoff was a chance for something to break or go stale.

  • One tool to store files (ADLS, but unmanaged)
  • A different tool to schedule jobs (Azure Data Factory)
  • Another tool just for reporting (Power BI on stale data)
  • Manual email alerts for operational failures
  • No shared rulebook on who can see what
  • ML team using raw CSV files directly — different from what analytics team sees
  • No lineage — impossible to trace where a number came from
After — One Databricks Platform

Databricks replaces the scattered toolbox with one platform that does it all, on the same copy of the data.

  • Ingestion: Lakeflow Connect (CDC from Postgres) + Autoloader (incremental files)
  • Storage & transformation: Delta Lake, Bronze/Silver/Gold
  • Scheduling: Workflows (DAGs, retry logic, alerts)
  • Governance: Unity Catalog (who sees which column/row)
  • ML & Analytics: same Silver/Gold tables — no copy
  • Lineage: every number traces back to its source file automatically
  • Self-serve: Genie — stakeholders ask questions in plain English

7. fact_sales — The Business Requirement

Every decision GlobalMart wants to make — "Which products are selling?", "Which customers are churning?", "Which payment method has the highest failure rate?" — can be answered from one well-built Gold table.

Why this table is the point of the whole pipeline

Grain: one row per order line item
= one product in one order

Measures (numbers):
  • quantity
  • unit_price
  • line_total (quantity × unit_price)
Connects to dimensions:
  • dim_customer — who bought it
  • dim_product — what was sold
  • dim_date — when
  • dim_address — where it shipped
  • dim_payment_method — how it was paid
Answers the 5 business problems:
  • Single source of truth → fixes Problem 1
  • Built on validated Silver data → fixes Problem 2
  • Governed access via Unity Catalog → fixes Problem 3
  • Refreshed automatically by Workflows → fixes Problem 4
  • Lineage traces every number to source → fixes Problem 5
Same idea as "Inventory Mail Alerts → DC/Warehouse Manager" — except now it's a governed, always-current table that Genie can answer questions from directly, instead of a one-off email.
