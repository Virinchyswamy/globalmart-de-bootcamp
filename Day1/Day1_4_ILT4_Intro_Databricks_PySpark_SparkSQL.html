Apache Spark — The Engine Under the Hood

Before Databricks, there was Apache Spark — an open-source distributed computing engine created at UC Berkeley in 2009. It solves one problem: processing massive datasets, terabytes to petabytes, faster than a single computer ever could.

Key insight: Spark is the engine. Databricks is the platform that wraps Spark so you can use it without a DevOps team. Every line of PySpark you write runs on Apache Spark under the hood.

DIY Apache Spark vs Databricks

DIY Apache Spark (raw)

  • Download, install, and manage your own cluster
  • Configure Hadoop dependencies manually
  • Set up your own notebooks and scheduling (Airflow)
  • No built-in governance or access control

Databricks (managed Spark)

  • Spark pre-installed, pre-optimised, always current
  • Clusters with one click — auto-scale, auto-terminate
  • Built-in notebooks, Workflows for scheduling
  • Unity Catalog for governance, built in

What Is Databricks?

Think of Databricks as a supercharged Jupyter notebook that can process millions of rows using many computers at once — instead of just the one laptop in front of you.

Databricks is a cloud platform built on Apache Spark. It gives Data Engineers notebooks, clusters, Delta Lake, scheduling, and governance — all in one place. GlobalMart uses it to build and run the full Bronze → Silver → Gold pipeline.

Databricks Platform Components (1 of 2)

📓 Notebooks

Interactive cells mixing Python, SQL, and Markdown. Run cells one at a time or all at once.

⚡ Clusters

A group of VMs running Apache Spark. Auto-terminates when idle to save cost.

🏔️ Delta Lake

The storage format for every table in the pipeline — Parquet files plus a transaction log.

Databricks Platform Components (2 of 2)

📁 Unity Catalog

Central metadata store. Controls who can access which table, and tracks lineage from raw file to Gold table.

⚙️ Workflows

Scheduled multi-task pipelines. Runs your ingestion → Silver → Gold chain with retries and alerting.

💬 Genie

Natural-language Q&A on top of Gold Delta tables. Business users ask questions in plain English.

Cluster Architecture — Driver + Workers

Every Spark job runs on a cluster. Understanding the two roles inside it explains how Spark turns "millions of rows" into "a few seconds."

The Driver Is the Brain, Workers Are the Hands

Your Notebook Code (Python / SQL)
    ↓
Driver Node   (plans the job, builds the DAG, tracks completion, collects results)
    ↓ splits data into partitions → distributes tasks
Worker Node 1  (rows 1–1M)      reads/writes ↔ ADLS
Worker Node 2  (rows 1M–2M)     reads/writes ↔ ADLS
Worker Node 3  (rows 2M–3M)     reads/writes ↔ ADLS
    ↓ partial results back to driver → final result assembled
Output  (shown in display() / written to a Delta table)

More workers = faster, automatically

100 GB on 2 workers: about 10 minutes. The same data on 6 workers: about 3 minutes. Spark handles the distribution — you never write parallel-processing code yourself.

Choosing a Cluster Type

Cluster TypeBest ForAuto-Terminate?
All-Purpose ClusterInteractive notebook development — attach multiple notebooksConfigurable (30–60 min)

Single-Node ClusterSmall datasets / development — driver only, no workersConfigurable

Spark Doesn't "Cook" Until You Call an Action

Spark does not run code line by line. It builds a plan — a Directed Acyclic Graph (DAG) — and only executes it when you call an Action. This is called lazy evaluation.

# Transformations — just build the plan, nothing runs yet
df = spark.read.csv(raw_path)
df2 = df.filter(df.status == "active")
df3 = df2.groupBy("city").count()

# Action — THIS is what triggers execution
df3.show()

Under the Hood: DAG, Stages, and Shuffles

Spark splits your job into stages, separated by shuffles:

Stage 1: read CSV → filter rows      Task 1: partition 1   Task 2: partition 2   Task 3: partition 3
                                          ↓ shuffle (regroup by key — network transfer)
Stage 2: aggregate / count           Task 1: keys A–M      Task 2: keys N–Z

Shuffles are expensive — they move data across the network between worker nodes. Minimise them by filtering before groupBy, and use broadcast joins for small reference tables.

Notebooks & the PySpark DataFrame API

The core object in PySpark is the DataFrame — a distributed table of rows and columns, similar to pandas but built to run across a whole cluster.

Databricks Notebooks — Mixing Cell Types

PySpark vs pandas — Key Differences

pandas

  • Runs on a single machine — one CPU
  • Data must fit in RAM — crashes past ~16 GB
  • Eager evaluation — every line runs immediately
  • Cannot read from ADLS natively

PySpark (Spark DataFrame)

  • Runs across a cluster — many CPUs, many machines
  • Data lives in ADLS, not in RAM — handles TB-scale
  • Lazy evaluation — builds a plan, executes on Action
  • Native ADLS support via abfss://

The API looks almost the same as pandas — .select(), .filter(), .groupBy() — but it runs on 10 machines instead of 1.

Actions Trigger Execution

df.show(5)              # print first 5 rows
display(df)             # Databricks interactive output with charts
df.count()             # total row count — triggers a full scan
df.printSchema()       # column names and data types
df.toPandas()          # convert to pandas — only for small DataFrames!

Avoid df.collect() — it pulls every row into the driver's RAM. On a 10 GB table, that's an out-of-memory crash waiting to happen. Use show() or display() instead.

Writing to Delta — Bronze / Silver / Gold

# Full refresh — overwrite everything at this path
df.write.format("delta").mode("overwrite").save(bronze_path)

# Incremental — append new rows, keep existing ones
df.write.format("delta").mode("append").save(bronze_path)

# Add new columns without breaking readers (schema evolution)
df.write.format("delta").mode("append").option("mergeSchema", "true").save(bronze_path)

Spark SQL — Two Ways to Query Delta Tables

Option A — a %sql cell

SELECT status, COUNT(*) AS order_count
FROM bronze.orders
GROUP BY status

Option B — spark.sql() in Python

result_df = spark.sql("SELECT city, COUNT(*) FROM v GROUP BY city")
result_df.show()

Use %sql for quick exploration. Use spark.sql() when you need the result as a DataFrame you can chain more PySpark onto.

Connecting to ADLS from Databricks

GlobalMart storage account: amazonprojectadls · Container: amazon-data

  1. Set the storage key in Spark config, once per session: spark.conf.set("fs.azure.account.key.amazonprojectadls.dfs.core.windows.net", storage_key)
  2. Build the base path: base_path = "abfss://amazon-data@amazonprojectadls.dfs.core.windows.net"
  3. Read or write using sub-paths: raw_path = base_path + "/raw" and bronze_path = base_path + "/bronze"

PySpark Best Practices

❌ Avoid: df.collect()

Pulls all rows into the driver's RAM — an out-of-memory crash waiting to happen on big tables.

✅ Do: filter early

Apply .filter() as early as possible so less data flows through every later step.

✅ Do: select only needed columns

Use .select("col1","col2") instead of carrying all 30 columns through the whole pipeline.

❌ Avoid: count() before every action

df.count() triggers a full scan. Don't call it repeatedly on the same DataFrame.

✅ Do: broadcast small tables

Joining a huge table with a 4-row reference table? Use broadcast(dim) to skip the shuffle.

❌ Avoid: hardcoding secrets

Never put storage keys directly in notebook code — use dbutils.secrets.get() in production.
