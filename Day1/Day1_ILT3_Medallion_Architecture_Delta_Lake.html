1. Why Three Layers?

Raw data from GlobalMart's two sources (Postgres CDC + ADLS file drops) has problems: null values, duplicate rows, inconsistent date formats (DD/MM/YYYY vs YYYY-MM-DD), trailing spaces in customer names, columns named differently across files. You cannot run business reports directly on raw CSV files without getting wrong numbers.

The Medallion Architecture solves this by passing data through three quality layers — each one making the data more trustworthy and more useful than the last. Raw data enters at Bronze and only business-ready data leaves at Gold.

LayerQuestion it answersWho created itWho reads it
🥉 BronzeWhat did the source send us, exactly as received?Autoloader / Lakeflow ConnectData Engineers only
🥈 SilverWhat is the true, clean version of this data?PySpark transformation jobsData Engineers + Analysts
🥇 GoldWhat business question does this answer?Star schema build (MERGE / write)Business + Genie + ML

3. Delta Lake — What Makes It Different

Delta Lake is NOT a separate database. It is a storage layer that lives on top of Parquet files in ADLS. The secret ingredient is a folder called _delta_log/ that sits alongside the data files and records every change ever made.

silver/customers/ ← your Delta table path in ADLS
    _delta_log/ ← Delta Lake's brain — one JSON file per version
        00000000000000000000.json (version 0 — initial overwrite: 6,666 rows written)
        00000000000000000001.json (version 1 — append: 200 new rows added)
        00000000000000000002.json (version 2 — MERGE: 5 rows updated, 1 deleted)
        00000000000000000003.json (version 3 — schema change: new column added)
    part-00000-a1b2c3.parquet ← actual data, columnar format
    part-00001-d4e5f6.parquet
    part-00002-g7h8i9.parquet (new file added by append in version 1)

Every time anything changes (write, update, delete, schema change), Delta writes a new JSON entry in _delta_log. This log is what gives Delta all of its superpowers — ACID, time travel, schema enforcement, and streaming support.

Key Delta Commands

-- See all versions of a Delta table
DESCRIBE HISTORY customers;

-- Query a previous version (time travel)
SELECT * FROM customers VERSION AS OF 1;
SELECT * FROM customers TIMESTAMP AS OF '2026-07-01 09:00:00';

-- Restore to a previous version
RESTORE TABLE customers TO VERSION AS OF 1;

-- Compact small files (run periodically for performance)
OPTIMIZE customers;
OPTIMIZE customers ZORDER BY (registration_date);

-- Remove old data files no longer referenced (default: 7-day retention)
VACUUM customers RETAIN 168 HOURS;

4. ACID — What It Means in Plain English

ACID is what makes Delta tables behave like a proper database instead of a bunch of loose files. Without ACID, two jobs writing simultaneously could corrupt your data — or a failed job could leave partial results.

A Atomicity All-or-nothing. If writing 6,666 customer rows fails halfway through, zero rows are visible. No partial data ever lands.
GlobalMart: if the Bronze write fails mid-run, the table looks exactly as it did before — no half-written files.
C Consistency Data always moves from one valid state to another. Schema rules are enforced — adding a column with the wrong type is rejected.
GlobalMart: if Silver enforces DateOfBirth as DATE, writing a string "N/A" will fail, not silently corrupt the column.
I Isolation Two jobs writing at the same time cannot corrupt each other. Delta uses optimistic concurrency — the second write is either serialised or rejected with a conflict error.
GlobalMart: Lakeflow Connect writing CDC events and a backfill job running simultaneously cannot produce garbled rows.
D Durability Once written and confirmed, data is never lost — even if the cluster crashes immediately after. The log entry is committed first.
GlobalMart: a worker node crash after write confirmation still means the data is safe. The log says it's committed.

5. Delta Write Modes — When to Use Which

overwrite Deletes all existing data at the path and writes fresh. Safe to re-run — idempotent.

Use when: small reference tables (payment_methods, suppliers) that are fully refreshed daily.

.mode("overwrite")
append Adds new rows on top of existing data. Never deletes anything already there.

Use when: large tables that grow over time — daily customer files, daily order batches.

.mode("append")
merge (UPSERT) Matches rows by a key — UPDATE existing rows and INSERT new ones. The most powerful mode.

Use when: SCD Type 1 (update changed rows), CDC event processing in Silver.

DeltaTable.merge(...)
ignore Does nothing if the destination already has data. Skips the write silently.

Use when: you only want to write if the table doesn't exist yet — rare in production pipelines.

.mode("ignore")

7. GlobalMart's Layer Format Map

Layer Format Write Mode Path Reason
Bronze Delta (from CSV/CDC) append (daily files) / overwrite (first run) amazon-data/bronze/ Preserves raw values with ACID protection. Append keeps full history.
Silver Delta only merge (upsert on key) amazon-data/silver/ Need UPDATE rows (SCD), enforce schema, validate quality. Only MERGE supports this.
Gold Delta only overwrite (full rebuild) or merge amazon-data/gold/ Fast queries via stats + Z-ordering. OPTIMIZE runs after each Gold write.
Schema evolution: Delta supports adding new columns without breaking existing readers. Set .option("mergeSchema", "true") when writing to automatically absorb new columns from the source.
VACUUM warning: After VACUUM, you cannot time-travel to versions older than the retention period (default 7 days). Do not run VACUUM on Bronze tables too aggressively — Bronze is your permanent audit trail.

8. fact_sales — The Gold Deliverable

The star schema separates measures (numbers that get summed/averaged) from dimensions (attributes used to slice and filter). fact_sales is the fact table — it holds the numbers and foreign keys to each dimension.

Why this table is the point of the whole pipeline

Grain: one row per order line item
= one product in one order

Measures (SUM / AVG these):
  • quantity
  • unit_price
  • line_total
Connects to (slice by these):
  • dim_customer — who bought it
  • dim_product — what was sold
  • dim_date — when
  • dim_address — where it shipped
  • dim_payment_method — how it was paid
Business questions it answers:
  • Revenue by product category this month
  • Top 10 customers by total spend
  • Payment method breakdown
  • Regional sales trends by city
  • Return rate by product
  • Average order value by loyalty tier
