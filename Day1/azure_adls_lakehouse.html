1. Why Azure Cloud?

GlobalMart's pipeline runs on Microsoft Azure. Instead of buying physical servers, Azure lets you rent exactly the compute and storage you need, pay only for what you use, and scale in minutes. Two Azure services are the foundation of everything: ADLS Gen2 (where data lives) and Azure Databricks (where data gets processed).

2. ADLS Gen2 — The Storage Foundation

Azure Data Lake Storage Gen2 is cloud file storage optimised for big-data analytics. It stores any format — CSV, JSON, Parquet, Delta — cheaply at massive scale, and connects natively with Databricks via the abfss:// protocol.

Azure Blob Storage
  • Flat key-value store (folders are just name prefixes)
  • No real folder hierarchy — no folder-level permissions
  • Slower for analytics workloads
  • Default when you create a storage account
ADLS Gen2
  • True hierarchical folder structure
  • Folder-level access control (RBAC + ACLs)
  • Optimised for Spark / Databricks analytics — 10–100× faster reads
  • Enabled by turning on Hierarchical Namespace in the storage account

3. Three Ways to Store and Query Data at Scale

Before choosing a Lakehouse, most organisations tried one of three approaches. Understanding what each one is — and why the Hybrid model was painful — explains why the Lakehouse architecture exists.

Data Warehouse

The classic enterprise approach

  • Structured, schema-on-write data only
  • ACID transactions — UPDATE, DELETE, MERGE
  • Very fast SQL queries
  • High storage cost (proprietary format)
  • Cannot store raw files, JSON, images, ML features
  • Hard to work with for ML/AI teams

Examples: Snowflake, Azure Synapse, Redshift, BigQuery
Data Lake

The "dump everything" approach

  • Store anything — CSV, JSON, images, logs, Parquet
  • Very cheap (object storage like ADLS or S3)
  • No schema enforcement — data quality degrades fast
  • No ACID — no UPDATE or DELETE on files
  • Slow to query — no statistics, no indexing
  • Often becomes a "data swamp" without governance

Examples: Raw ADLS, raw AWS S3, raw GCS
Hybrid (DW + DL)

The painful compromise

  • Data Lake holds raw + ML data
  • Data Warehouse holds clean business data
  • ETL pipelines move data between the two
  • Data is duplicated in both systems
  • Two sets of infrastructure, two access controls
  • Data freshness lag — batch ETL runs overnight

Examples: ADLS + Synapse Analytics side by side

4. The Hybrid Problem — Why It Does Not Work Well

Most large companies still run a Hybrid today. The diagram below shows exactly why it creates pain for Data Engineers and Business teams.

Sources (Postgres, files, APIs)
    ↓
DATA LAKE (raw ADLS / S3 — cheap, unstructured)
    ↓ overnight ETL batch job (ADF / Spark job — can take hours)
DATA WAREHOUSE (Synapse / Snowflake — structured, queryable)
    ↓
Business reports (always 12–24 hours stale)

ML team also reads from DATA LAKE directly ← different access controls
Analytics team reads from DATA WAREHOUSE ← data is a different version

Problems:
  ✗  Same data stored twice — pay for both
  ✗  ML team and analytics team see different numbers
  ✗  ETL pipeline failure = DW is stale for 24h
  ✗  Two governance systems — who can see what?
  ✗  No DELETE in the lake — GDPR requests are a nightmare

5. The Lakehouse — One Platform for Everything

The Lakehouse combines cheap lake storage (ADLS) with Data Warehouse features (ACID, schema, fast queries) by adding a transaction layer — Delta Lake — directly on top of the files. One system replaces both.

Sources (Postgres via Lakeflow Connect + ADLS file drops via Autoloader)
    ↓
BRONZE (raw Delta on ADLS — cheap storage, ACID protection)
    ↓ PySpark transformations
SILVER (clean Delta — schema enforced, deduped, SCD applied)
    ↓ star schema build
GOLD — fact_sales (business-ready, Z-ordered, fast to query)
    ↓
GENIE + Reports (same data, same access controls, no duplication)

ML team reads Silver/Gold too — same tables, no copy
Analytics team queries Gold via Genie — same tables
Unity Catalog governs access for everyone in one place

6. Full Comparison — Data Warehouse vs Data Lake vs Hybrid vs Lakehouse

Feature Data Warehouse Data Lake Hybrid (DW + DL) Lakehouse ✓

Handles unstructured data No Yes Lake side only Yes
ACID transactions Yes No DW side only Yes — Delta Lake
UPDATE / DELETE rows Yes No DW side only Yes — Delta MERGE
Schema enforcement Yes (rigid) No DW side only Yes (flexible)
Query performance High Low High (DW side) High — Z-order + statistics
ML / AI ready No Yes Lake side only Yes — same tables
Data freshness Depends on ETL Real-time possible 12–24h lag (batch ETL) Real-time via streaming
Data duplication Some None Always — stored twice None — one copy
Single governance layer DW only No Two systems to manage Yes — Unity Catalog
Time travel / audit No No No Yes — Delta log
Real-world examples Snowflake, Synapse, Redshift Raw ADLS / S3 ADLS + Synapse side by side Databricks + ADLS + Delta Lake

One-sentence takeaway: The Lakehouse gives you the low cost and flexibility of a Data Lake with the reliability and performance of a Data Warehouse — in one system, with no duplication.

Unity Catalog External Location Highest — managed identity Production No spark.conf needed — Unity Catalog manages auth

This bootcamp uses the Storage Account Key for simplicity. In production, Unity Catalog External Locations are the standard — no key in code.
