Why This Lab Exists

The Small-File Problem — and Why fact_sales Is Especially Prone to It

Every technique in this lab exists to solve one physical problem: too many small files. Understand that problem first, and Z-ORDER and Liquid Clustering both become obvious — they're just two different answers to "how do I keep this table's files organized as it keeps growing?"

📖 The book-torn-into-pages analogy

Imagine one bound book containing everything you'd ever want to look up, versus that same content torn into 200 loose, shuffled pages. Finding one chapter in the bound book is fast — you flip to roughly the right spot. Finding it in 200 shuffled pages means checking pages one at a time, because you no longer know where anything is. Delta tables work the same way: a query has to open every file that might contain a matching row. Fewer, well-organized files means fewer opens. Many small, disorganized files means the engine wastes time opening files that turn out to have nothing useful in them.

🔁 Why fact_sales gets there — and a one-time table doesn't

Day 4 HOL 2 introduced OPTIMIZE/ZORDER/Liquid Clustering on a practice table that was built once and never touched again — a closed book. fact_sales is the opposite: starting Day 9–10, it gets refreshed incrementally, via MERGE, every time new orders land. Each refresh run typically writes a handful of new, small files. Repeat that daily for months, and the table slowly tears itself back into loose pages — even if it started out perfectly compact.

This hands-on can't make you wait months to see that effect, so it fakes it on purpose: repartition(200) deliberately re-writes your practice copy across 200 small files in one shot — instantly reproducing the "torn apart" end state a real incrementally-refreshed table reaches naturally over time. Everything you measure afterward is measuring a recovery from that starting point.

The Core Concept

Two Techniques, No Jargon

Both techniques do the exact same underlying thing at a high level: physically group rows together in the same files based on the columns you tell them to care about, so a query filtering or joining on those columns can skip whole files it doesn't need to open at all. Where they genuinely differ is how expensive it is to keep that grouping up to date as the table keeps changing — and that difference is the entire point of this lab.

🗂️ Z-ORDER — a one-time, full-library re-shelving

Picture re-shelving an entire library by author and genre, in one huge weekend effort. When you run OPTIMIZE ... ZORDER BY (colA, colB), Spark looks at every file in the table and rewrites it so rows with similar values of colA/colB end up physically near each other. That's genuinely powerful — but it's a full-table operation every single time you run it. A week later, ten new books arrive. To keep the whole library properly shelved, you take the entire library back down and re-shelve it again from scratch — not just the ten new books.

💧 Liquid Clustering — a librarian who tidies continuously

CLUSTER BY (colA, colB) is set once, at table creation (or via ALTER TABLE) — it's a standing property of the table, not a one-time command. From then on, every OPTIMIZE call clusters incrementally: when ten new books arrive, only those ten (and maybe the shelf immediately around where they belong) get touched. The rest of the library, already properly shelved, is left completely alone.

This is the whole reason this lab exists. On a table that's touched once, Z-ORDER and Liquid Clustering can look basically identical — the "full re-shelve" cost only happens once either way. On a table refreshed daily forever, like the real fact_sales will be from Day 9–10 onward, that cost either resets to zero every day (Liquid Clustering) or gets paid in full, again, every single day (Z-ORDER). The gap doesn't show up in one query — it shows up over months of daily runs.

Before You Touch Anything

Why You Never Run This Against gbmart Directly

Every command in this lab physically rewrites data files — that's what makes it dangerous to run against a table other people rely on, and it's why the hands-on's very first scenario is entirely about getting you off of it.

  1. Clone what you need, once. Scenario 1 uses SHALLOW CLONE to copy fact_sales, dim_product, and dim_date into a schema only you own. A shallow clone gets its own independent transaction log without physically duplicating the underlying data files — instant, and safe to OPTIMIZE/ZORDER/CLUSTER BY against, repeatedly, without the source table ever being affected.
  2. A fourth table joins later, the same way. The regional query (Scenario 3) needs dim_address too — that one gets shallow-cloned right when it's first needed, not bundled into Scenario 1's setup. Same rule either way: the only thing this lab ever does against real gbmart tables is a one-time, read-only SHALLOW CLONE.
  3. Everything after that is yours alone. Every fragment, OPTIMIZE, ZORDER, CLUSTER BY, and simulated new-order append happens only against tables living in your own practice schema. You will not see gbmart.gold.* written to anywhere in this lab, ever.

Why this matters more here than it might seem: gbmart.gold.fact_sales is shared by your whole cohort and the instructor. If this lab told you to OPTIMIZE it directly, only the very first person to ever run the exercise would see a real "before" state — everyone after (including you, if you rehearse it twice) would find it already compacted and see nothing happen. Cloning is what makes this lab honestly repeatable, for you and for every other learner, every time.

The Three Query Shapes You'll Measure

A single query timing only tells you about one access pattern. This lab deliberately measures three genuinely different ways fact_sales gets queried in real reporting, so the comparison isn't an accident of picking a lucky (or unlucky) example.

🔍 Single-Product Point Lookup

Filters on one exact Product_ID and a narrow Time_ID range — the shape a support or merchandising tool would run.

Touches Product_ID + Time_ID

The one rule that predicts everything in Scenarios 4 and 5: Z-ORDER (and Liquid Clustering) only help a query that actually filters or joins on the exact columns you named — Product_ID and Time_ID here. A query that filters or joins on some other column is querying rows that are still scattered across files exactly as randomly as before, because nothing about how those rows are physically arranged changed for that column.

Notice which two of the three query shapes above touch Product_ID/Time_ID, and which one doesn't. That's the entire reasoning tool you need for Input 6's prediction — work it out yourself there before you run a single timing.

The Measurement That Actually Settles It

Why the First Timing Isn't the Interesting One

On a table clustered for the very first time, Z-ORDER and Liquid Clustering are doing something visually similar — both are physically grouping the same two columns, just with a different mechanism underneath. Don't be surprised if Scenario 4 and the first half of Scenario 5 come back looking roughly comparable. That's expected, and it's not the point.

What Scenario 5 actually does next

After both tables are clustered once, the lab appends a small batch of simulated new orders — a stand-in for one day of Day 9–10's real incremental MERGE refresh — to both tables, then re-runs OPTIMIZE on each and times it.

What that number actually reveals

Re-OPTIMIZE ... ZORDER BY re-evaluates clustering across the whole table again — its cost is tied to total table size, not to how much actually changed. Plain OPTIMIZE on a Liquid-clustered table only reorganizes the files touched by the new rows. That gap — not the first-pass query speed — is the real, sustainable difference between the two techniques.

✓ Concept check

At this lab's small practice scale, that gap might look modest in seconds. It's the same gap, though, that Day 9–10 will pay every single day, for as long as fact_sales exists, once real incremental refresh is running against it. A small per-run difference, repeated daily for years, is exactly the kind of cost that's invisible in a demo and very visible in a production bill.

Reinforce Before You Open the .md

Quick-Fire Concept Check

Click to reveal each answer. If any of these surprise you, re-read the section above before starting Scenario 1.

Why does this lab use SHALLOW CLONE instead of a plain "copy the table" (CREATE TABLE ... AS SELECT)?
A deep copy physically rewrites every row into new files — real time and real storage, every time you wanted a fresh practice copy. SHALLOW CLONE creates a new table pointing at the same underlying files, with its own brand-new transaction log layered on top — instant, and the source table's files are never touched by anything you do to the clone.
If Z-ORDER and Liquid Clustering give roughly the same query speed on the very first pass, why does it matter which one you pick for fact_sales?
Because "the same speed" is a one-time snapshot, and fact_sales is never queried just once — it's refreshed daily, forever, starting Day 9–10. What actually compounds over time isn't the first query's speed, it's the cost of re-clustering after every one of those daily refreshes — and that cost is where the two techniques genuinely diverge.
Do you have to re-run CLUSTER BY every time you want a Liquid-clustered table re-organized?
No. CLUSTER BY is set once, as a property of the table (at CREATE TABLE, or via ALTER TABLE). After that, a plain OPTIMIZE with no ZORDER BY clause automatically clusters incrementally on those same columns — the table already remembers what it's clustered on.
Why would a query that filters on Address_ID barely improve after Z-ORDERing by (Product_ID, Time_ID)?
Z-ORDER physically co-locates rows by the exact columns you name — it did nothing to how rows are arranged with respect to Address_ID. Rows matching a given Address_ID are still scattered across files just as randomly as before. Compaction (fewer, bigger files) gives that query a small indirect benefit from less file-open overhead, but nowhere near the direct data-skipping benefit a query gets when it filters or joins on the columns that were actually Z-ordered.
