Phase B — What Is a Bridge Table?

Every Day 6 dimension joins to fact_sales with a clean many-to-one relationship — a plain foreign key is enough. A bridge table exists for the opposite shape: many-to-many. Classic example: a bank account can have multiple joint holders, and a person can hold multiple accounts. Neither dimension can hold one foreign key to the other — a third table sits between them, one row per valid pairing.

dim_customer  <---  bridge_account_holder  --->  dim_account
  customer_id          customer_id, account_id        account_id
(one row per pairing)
Watch for double-counting. A $500 deposit touching 2 joint holders should not silently become $1,000 across a report.

Phase C — Does GlobalMart's fact_sales Need One?

Check the grain first, always. fact_sales has grain = one row per order line item. Walk each relationship at that grain:

Relationship at order_items grainShapeBridge needed?
order line → customermany-to-oneNo — plain FK
order line → productmany-to-oneNo — plain FK
order line → ordermany-to-oneNo — plain FK
order line → addressmany-to-oneNo — plain FK
order line → paymentmany-to-one (1:1 with order)No — plain FK
Conclusion: GlobalMart's core fact_sales does not need a bridge table today. order_items being the grain already resolves the one real many-to-many in this data (an order has many products, a product appears on many orders) — the grain choice did the work.

Where a real one would show up: if GlobalMart ran marketing campaigns where one product can be tagged under several campaigns at once, and one campaign covers many products — genuine many-to-many, no single FK holds it. Built as the worked example below.

Phase D — Build the Illustrative Bridge: Products ↔ Campaigns

# dim_campaign -- a small new dimension, synthetic/illustrative only
dim_campaign_df = spark.createDataFrame(campaign_rows, ["campaign_id", "campaign_name", "start_date", "end_date"])
    .withColumn("campaign_sk", sha2(col("campaign_id"), 256))

# bridge_product_campaign -- one row per (product, campaign) pairing, no measures of its own
bridge_df.write.format("delta").mode("overwrite").saveAsTable("gbmart.gold.bridge_product_campaign")

Deliberately overlapping data: one product tagged under two campaigns, one campaign covering three products — that is the many-to-many the bridge exists for.

Phase E — Prove the Double-Counting Risk, Then Query Correctly

# Joining dim_product through the bridge multiplies rows for any
# product tagged under more than one campaign -- see it happen first.
joined = dim_product_df.join(bridge_df, "product_id")  # row count grows

# The safe, business-correct version: attribute sales per campaign explicitly
SELECT c.campaign_name, SUM(f.Sales_amount) AS attributed_sales
FROM gbmart.gold.fact_sales f
JOIN gbmart.gold.bridge_product_campaign b ON f.Product_ID = b.product_id
JOIN gbmart.gold.dim_campaign c ON b.campaign_id = c.campaign_id
GROUP BY c.campaign_name
A multi-campaign product's sales get counted once per campaign it belongs to — that's a deliberate business decision (a sale genuinely counts toward every campaign running for that product), not a bug. This query reads gbmart.gold.fact_sales, built later today in HOL 2 — revisit this cell after HOL 2 if running in calendar order.

Key Takeaways

#Takeaway
1A bridge table exists for many-to-many relationships only — a plain FK is enough otherwise
2Check the grain before reaching for a bridge — GlobalMart's order_items grain already resolves its one real M:N
3A bridge table carries no measures of its own — pure connective plumbing
4Joining through a bridge can silently multiply rows — always check counts before/after
