Phase B — What Is a Bridge Table?

Every Day 6 dimension joins to fact_sales with a clean many-to-one relationship — many order lines share one customer, many share one product. A plain foreign key handles that perfectly.

The classic textbook case: joint bank accounts

  • One bank account can have multiple joint holders
  • One person can hold multiple accounts
  • Neither table can hold a single foreign key to the other — there's no one right answer
dim_customer  <---  bridge_account_holder  --->  dim_account
  customer_id         customer_id, account_id       account_id
                       (one row per pairing)

Watch for double-counting: a $500 deposit touching 2 joint holders should not silently become $1,000 across a report.

Phase C — Does GlobalMart's fact_sales Actually Need One?

Check the grain first, always. fact_sales (built next, in HOL 2) has grain = one row per order line item (order_items). Walk each relationship at that grain:

Relationship at the order_items grainShapeBridge needed?
order line → customermany-to-oneNo — plain FK
order line → productmany-to-oneNo — plain FK
order line → ordermany-to-oneNo — plain FK
order line → shipping addressmany-to-one (one primary address per customer)No — plain FK
order line → paymentmany-to-one (1:1 with orders in this model)No — plain FK

Conclusion: GlobalMart's core fact_sales does not need a bridge table today. This isn't a shortcut — order_items being the grain is exactly what already resolves the one real many-to-many in this data (an order has many products, a product appears on many orders). The grain choice did the work.

Where a Real GlobalMart Bridge Table Would Show Up

The marketing-campaign scenario

If GlobalMart started running marketing campaigns where:

  • One product can be tagged under several campaigns at once
  • One campaign covers many products

That's a genuine many-to-many — no single foreign key on either side can hold it.

This is exactly what we'll build next as a worked example — deliberately synthetic and illustrative. GlobalMart's real source systems (Postgres, ADLS) don't have a campaigns feed today; this is purely to make the bridge-table pattern concrete, not part of the graded pipeline.

Phase D — Build the Illustrative Bridge: Products ↔ Campaigns

Live build · gbmart.gold.dim_campaign + bridge_product_campaign
# dim_campaign -- a small new dimension, one row per campaign
campaign_rows = [
    ("CMP-01", "Diwali Mega Sale", ...),
    ("CMP-02", "New Year Electronics", ...),
    ("CMP-03", "Summer Furniture Fest", ...),
]
dim_campaign_df = spark.createDataFrame(campaign_rows,
    ["campaign_id", "campaign_name", "start_date", "end_date"]
).withColumn("campaign_sk", sha2(col("campaign_id"), 256))

dim_campaign_df.write.format("delta").mode("overwrite") \
    .saveAsTable("gbmart.gold.dim_campaign")
# bridge_product_campaign -- one row per (product, campaign)
# pairing. No measures of its own -- pure connective plumbing.

# Deliberately overlapping: product[0] is in two campaigns,
# campaign CMP-01 covers three products -- this IS the
# many-to-many the bridge exists for.
bridge_rows = [
    (sample_products[0], "CMP-01"),
    (sample_products[0], "CMP-02"),   # same product, 2nd campaign
    (sample_products[1], "CMP-01"),
    ...
]
bridge_df.write.format("delta").mode("overwrite") \
    .saveAsTable("gbmart.gold.bridge_product_campaign")

Phase E — Prove the Double-Counting Risk, Then Query Correctly

Live build · the mistake, then the fix

Joining dim_product straight through the bridge multiplies rows for any product tagged under more than one campaign — see it happen first:

joined = dim_product_df.join(
    bridge_product_campaign_df, "product_id"
)
# product[0] now appears twice -- once per campaign

This is exactly the mistake a bridge table can cause if you forget it's many-to-many.

The safe, business-correct version — attribute sales per campaign explicitly:

SELECT c.campaign_name, SUM(f.Sales_amount) AS attributed_sales
FROM gbmart.gold.fact_sales f
JOIN gbmart.gold.bridge_product_campaign b
  ON f.Product_ID = b.product_id
JOIN gbmart.gold.dim_campaign c
  ON b.campaign_id = c.campaign_id
GROUP BY c.campaign_name

A multi-campaign product's sales get counted once per campaign it belongs to — a deliberate business decision, not a bug. This reads gbmart.gold.fact_sales, built later today in HOL 2 — revisit this cell after HOL 2 if running in calendar order.

Key Takeaways

  1. A bridge table exists for many-to-many relationships only — a plain FK is enough otherwise
  2. Check the grain before reaching for a bridge — GlobalMart's order_items grain already resolves its one real M:N
  3. A bridge table carries no measures of its own — pure connective plumbing
  4. Joining through a bridge can silently multiply rows — always check counts before/after
