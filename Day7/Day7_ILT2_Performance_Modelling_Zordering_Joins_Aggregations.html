1. Fact Tables Have Different Performance Needs Than Bronze

Bronze is usually scanned wholesale or filtered on one column. A fact table gets queried almost always through a JOIN to a dimension, filtered on the dimension's attribute:

SELECT ... FROM fact_sales f
JOIN dim_product p ON f.Product_ID = p.product_id  -- join column
JOIN dim_date d     ON f.Time_ID = d.date_key      -- join column
WHERE p.category = 'Electronics'            -- filter lands on the DIMENSION

The columns that matter for fact_sales's performance are exactly the join keys used to reach the dimensions that carry the filters.

2. Broadcast Joins vs Sort-Merge Joins

Broadcast JoinSort-Merge Join
When Spark picks itOne side is small (default 10MB threshold)Both sides are large
How it worksSmall table copied whole to every executor — no shuffleBoth tables shuffled and sorted on join key, then merged
CostCheapExpensive — shuffles the big table across the cluster
GlobalMart exampledim_date, dim_payment_methodfact_sales ↔ dim_customer at real scale
This is why dimension tables are kept small and denormalized in a star schema — a small dimension gets broadcast almost for free, every time, without a manual hint.

3. Choosing Z-ORDER Columns — Not a Guess

Z-ORDER co-locates similar values into the same files so a filter skips most files entirely. The right choice comes from real query patterns:

Real query pattern (from HOL 2's views)Column filtered/joined onZ-ORDER candidate?
vw_monthly_category_salesProduct_ID, Time_IDYes — if volume justifies 2 columns
vw_regional_salesAddress_IDYes, if regional queries dominate
Ad-hoc single-customer lookupCustomer_IDOnly if this pattern is actually common
Z-ORDER isn't free. More columns means more rewrite cost on every OPTIMIZE, for diminishing returns (2–3 columns is the practical ceiling). Pick what your actual dashboards hit most.

4. Partition Pruning and Predicate Pushdown, Made Visible

Predicate pushdown: a filter like category = 'Electronics' is pushed to file-scan level — rows for other categories are never read into memory. Partition pruning: if a table is partitioned by a filtered column, whole partition folders are skipped. fact_sales itself isn't partitioned — per Day 4's guidance, it relies on Z-ORDER + data skipping instead; partitioning matters more for the large, append-heavy Bronze tables from Day 3–4.
