Phase 1–2 — Copy fact_sales, Fragment It, Baseline the Real Business Query

Day 4 HOL 2 measured a single-column filter. Today measures the exact join-and-aggregate shape of vw_monthly_category_sales — closer to what production dashboards actually run.

SELECT p.category, d.month, SUM(f.Sales_amount) AS revenue
FROM fact_sales_practice f
JOIN dim_product p ON f.Product_ID = p.product_id AND p.is_current = true
JOIN dim_date d     ON f.Time_ID = d.date_key
GROUP BY p.category, d.month

Phase 3 — OPTIMIZE + Z-ORDER on ILT 2's Columns

ILT 2 identified Product_ID and Time_ID as the right Z-ORDER columns for this exact query shape — a conclusion from the real view definitions, not a guess.

OPTIMIZE fact_sales_practice ZORDER BY (Product_ID, Time_ID)

Phase 4 — Liquid Clustering as an Alternative

CREATE TABLE fact_sales_liquid_practice
CLUSTER BY (Product_ID, Time_ID)
AS SELECT * FROM fact_sales_practice  -- OPTIMIZE re-clusters incrementally, no ZORDER BY re-spec needed

Phase 5 — Why This Matters More Here Than in Day 4

Day 4's practice table was a one-time static build. fact_sales is not — Day 9–10 refreshes it incrementally via MERGE every time new orders land, meaning new small files get added continuously. That's exactly why Liquid Clustering is the more natural long-term fit for fact_sales: it re-clusters incrementally on every OPTIMIZE, without full-table rewrites growing more expensive as the table grows.
