1. Why Order Matters: Dimensions Before Facts

A star schema can only be assembled in one direction: dimensions first, fact second. The fact table's whole job is to look up context by joining out to dimensions — if dim_product doesn't exist yet, there's nothing to join for pricing.

Day 6:  Silver  ──▶  dim_customer, dim_product, dim_date, dim_address, dim_payment_method, dim_orders
Day 7:  Silver + Gold dims  ──▶  fact_sales

This is why Day 6 explicitly stopped before building fact_sales — the only order that works, not a scheduling accident.

2. The Join Chain, Table by Table

fact_sales's grain is order_items. Everything else is a lookup from that grain — this is the exact chain GlobalMart's real Gold build uses:

StepJoinBrings in
1silver.order_items (the grain)order_item_id, order_id, product_id, quantity
2+ silver.orders on order_idcustomer_id, order_date
3+ silver.products (is_current=true)Actual_price, Discounted_price
4+ gold.dim_date on order_date=dateTime_ID (= date_key)
5+ silver.address (one per customer)Address_ID
6+ silver.payments on order_idPayment_ID
Why filter is_current=true on products? dim_product is SCD2 — a product can have multiple rows in Silver. Filtering to the current version keeps this a clean many-to-one join instead of fanning out order lines.

3. The One-to-Many Trap: Address

silver.address links to customer_id, not to a specific order — a customer can have more than one address on file. Joining straight on customer_id would silently fan out every order line for any multi-address customer.

# The fix: rank addresses per customer, Shipping wins, take rank 1 only
address_window = Window.partitionBy("customer_id").orderBy(
    when(col("address_type").contains("Shipping"), 0).otherwise(1)
)
address_primary = address_df.withColumn("_rank", row_number().over(address_window)).filter("_rank = 1")

4. The Big Decision: Natural Keys or Surrogate Keys?

Textbook Kimball: join to dimensions by surrogate key — that's what makes SCD2 history queryable. GlobalMart's real, running build makes a different, deliberate choice: fact_sales stores natural keys (Customer_ID, Product_ID, etc.) — only fact_sales_sk itself is generated.

Surrogate-key fact (textbook)Natural-key fact (GlobalMart's real build)
Point-in-time accuracyYes — lands on the SCD2 version active at order timeNo — resolves to whatever's current at query time
Join complexityHigher — needs effective-date range logicLower — plain equi-join on known IDs
Build/debug speed hereSlowerFaster — the reason it was chosen
Production-grade for a real BI teamPreferredAcceptable as a documented simplification
Not a mistake to fix in HOL 2 — build it exactly this way. Understanding why a real team makes this tradeoff, and what it costs, is the actual lesson.

5. Write Strategy: Overwrite Today, Incremental Later

Today's build uses mode("overwrite") — simple and always correct at GlobalMart's current volume. This doesn't scale forever: recomputing the whole fact table on every run gets wasteful as data grows. Day 9–10 replaces this with an incremental MERGE-based refresh touching only new/changed order lines — you're seeing the simple version first on purpose.
