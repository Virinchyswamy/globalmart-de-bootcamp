The Report We're Building

total_units_sold

no_photo_percentage

Which Tables Do We Need?

ex_transactions

One row per line item in an order. Has sales_amount, quantity, product_id, order_id.

ex_orders

One row per order. Has order_id, order_status. We need this to filter to delivered orders only.

ex_products

One row per product. Has product_id, category, sub_category, product_photos_qty.

Step 1 — Granularity mismatch

Transactions are at line-item level. Report needs category level. We must aggregate upward.

Step 2 — Filter delivered orders

JOIN ex_transactions with ex_orders and keep only order_status = 'delivered'.

Step 3 — Add category info

JOIN the result with ex_products to get category and sub_category.

Step 4 — Aggregate by category

GROUP BY category + sub_category, compute all 5 metrics.

This is the CTE pattern: Each step becomes a named CTE, making the logic easy to read and debug.

Live Demo — CTE Step 1: base_data

First CTE: aggregate transactions to product level | mskl-masterclass
-- CTE 1: base_data
-- Goal: bring transaction data to PRODUCT level
-- (transactions are at line-item level, too granular)
-- We also join ex_orders to keep only DELIVERED orders

WITH base_data AS (
    SELECT
        t.product_id,

        -- Total revenue from each product
        SUM(t.sales_amount) AS total_sales,

        -- Total units sold from each product
        SUM(t.quantity)     AS total_qty
    FROM ex_transactions t

    -- JOIN with orders table to apply the business rule:
    -- only count sales for orders that were actually delivered
    JOIN ex_orders o
        ON  t.order_id = o.order_id
        AND o.order_status = 'delivered'

    -- Group to product level (one row per product)
    GROUP BY t.product_id
)

-- Run this first to see the intermediate result
SELECT * FROM base_data;

What this CTE does

Collapses millions of transaction rows down to one row per product, with total sales and total units sold — but only for delivered orders.

Why join the filter on the JOIN line?
Writing AND o.order_status = 'delivered' directly on the JOIN line is equivalent to putting it in WHERE, but it's a common pattern in CTE-based queries to keep filters close to the relevant join.

Second CTE: add category info + flag products with no photos
WITH base_data AS (
    -- ... same as CTE 1 above ...
),

product_summary_data AS (
    SELECT
        p.product_id,
        p.category,
        p.sub_category,
        b.total_sales,
        b.total_qty,
        p.product_photos_qty,

        -- Create a 1/0 flag: 1 = no photo, 0 = has photo
        -- Later we SUM this column to count products with no photos
        CASE
            WHEN product_photos_qty = 0 THEN 1
            ELSE 0
        END AS prod_with_no_photo

    FROM ex_products p

    -- JOIN with base_data to bring in sales and qty
    -- Only products that actually had delivered sales appear
    JOIN base_data b
        ON p.product_id = b.product_id
)

SELECT * FROM product_summary_data;

The CASE WHEN flag trick

Instead of counting separately, we create a binary column: 1 for "no photo", 0 for "has photo".

Then in CTE 3, SUM(prod_with_no_photo) gives us the total count of products with no photos.

This is a very common industry pattern — far more flexible than using COUNT with a condition.

Data at this point: One row per product with its category, subcategory, sales, quantity, and a flag showing whether it has photos.

Live Demo — CTE Step 3: final_cte + Full Query

Third CTE: aggregate to category level and build the report
WITH base_data AS (
    -- ... CTE 1 ...
),
product_summary_data AS (
    -- ... CTE 2 ...
),

final_cte AS (
    SELECT
        category,
        sub_category,

        -- Count of distinct products in each group
        COUNT(product_id)              AS tot_products,

        -- Sum the 1/0 flag = count of no-photo products
        SUM(prod_with_no_photo)         AS no_photos,

        -- Total revenue for each category/sub-category
        SUM(total_sales)               AS total_sales_value,

        -- Total units sold
        SUM(total_qty)                 AS total_units_sold,

        -- Percentage of products with no photos
        -- Multiply by 1.0 to avoid integer division
        -- FORMAT(..., 'P2') shows it as "12.50%"
        FORMAT(
            1.0 * SUM(prod_with_no_photo)
                / COUNT(product_id),
            'P2'
        )                             AS no_photo_percentage

    FROM product_summary_data
    GROUP BY category, sub_category
)

-- Final output: the full report sorted alphabetically
SELECT * FROM final_cte
ORDER BY category, sub_category;

FORMAT('P2') explained

FORMAT(value, 'P2') formats a decimal as a percentage with 2 decimal places.

Example: FORMAT(0.5, 'P2') → 50.00%

Note: 1.0 * sum / count forces decimal math (not integer division).

The 3-CTE flow reads top-down:

  1. base_data → product-level sales (filtered to delivered)
  2. product_summary_data → adds category + photo flag
  3. final_cte → aggregates to category level
  4. Final SELECT → output the report

Full Solution Query — For Reference

Complete working query | Run in SSMS · mskl-masterclass
WITH base_data AS (
    -- CTE 1: Aggregate transactions to product level (delivered orders only)
    SELECT  t.product_id,
            SUM(t.sales_amount) AS total_sales,
            SUM(t.quantity)     AS total_qty
    FROM ex_transactions t
    JOIN ex_orders o ON t.order_id = o.order_id AND o.order_status = 'delivered'
    GROUP BY t.product_id
),
product_summary_data AS (
    -- CTE 2: Join with products table to get category info + photo flag
    SELECT  p.product_id, p.category, p.sub_category,
            b.total_sales, b.total_qty, p.product_photos_qty,
            CASE WHEN product_photos_qty = 0 THEN 1 ELSE 0 END AS prod_with_no_photo
    FROM ex_products p
    JOIN base_data b ON p.product_id = b.product_id
),
final_cte AS (
    -- CTE 3: Aggregate to category + sub_category level for the report
    SELECT  category, sub_category,
            COUNT(product_id)                                            AS tot_products,
            SUM(prod_with_no_photo)                                       AS no_photos,
            SUM(total_sales)                                             AS total_sales_value,
            SUM(total_qty)                                               AS total_units_sold,
            FORMAT(1.0 * SUM(prod_with_no_photo) / COUNT(product_id), 'P2') AS no_photo_percentage
    FROM product_summary_data
    GROUP BY category, sub_category
)
-- Final SELECT: change this line to answer each business question
SELECT * FROM final_cte ORDER BY category, sub_category;

Key Takeaways

Granularity thinking

Always ask: "What level is my data at, and what level does the report need?" Bridge the gap with aggregation.

Chained CTEs

Each CTE solves one piece of the problem. The next CTE builds on the previous one — like assembly lines.

CASE WHEN flags

Create a 1/0 column for a condition, then SUM it to count occurrences. Very common in real analytics work.

Business rules first

"Delivered orders only" was the key constraint. Always clarify business rules before writing any SQL.

Modular answering

Write the full report once, then modify only the final SELECT to answer each business question differently.
