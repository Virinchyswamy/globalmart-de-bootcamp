## Understanding the Problem

GlobalMart wants to launch a loyalty program and must classify customers based on their purchase behavior.  
To do this, you need to build a **customer-level summary table** that captures key behavioural metrics:

- Total orders
- Total returns
- Value of purchases
- Average basket size
- Average basket value
- Length of stay
- Purchase frequency
- Recency (days since last purchase)
- Recency / Frequency / Monetary segments (R, F, M bands)

Multiple tables must be combined:

- `ex_customers`
- `ex_orders`
- `ex_transactions`
- `ex_returns`

The final output should reflect **one row per customer** with all derived metrics and RFM segments that can be directly used for a **loyalty / segmentation engine**.

* * *

### Step 1: Identify the Required Metrics and Their Inputs

| Metric | Input Tables | Logic |
| --- | --- | --- |
| `tot_orders` | `ex_orders` | Count distinct orders |
| `tot_returns` | `ex_returns` | Count returned orders |
| `order_value` | `ex_transactions` | Sum of `sales_amount` |
| `avg_basket_size` | `ex_transactions` + orders | Total quantity / total orders |
| `avg_basket_value` | `ex_transactions` + orders | Total sales / total orders |
| `length_of_stay_days` | `ex_orders` | Difference between first and last purchase date |
| `order_purchase_frequency` | derived | `length_of_stay_days / tot_orders` (days/order) |
| `recency_days` | `ex_orders` | Days since last purchase as of `2018-09-01` |
| `recency_segment` | derived | Bucket based on `recency_days` |
| `frequency_segment` | derived | Bucket based on `order_purchase_frequency` |
| `monetary_segment` | derived | Bucket based on `order_value` |

* * *

### Step 2: Join the Tables Correctly

To compute all metrics:

- Customers join with Orders via `customer_id`.
- Orders join with Transactions via `order_id`.
- Orders **LEFT JOIN** with Returns to count returned orders.
- Filter to only **delivered orders** in the orders join.

This ensures:

- Only valid, delivered orders are considered for all metrics.
- Returned orders are counted even if some orders have no returns.

* * *

## Logic Behind Each Metric

1. **Total Orders (`tot_orders`)**  
Count distinct `order_id` from `ex_orders` (only where status = 'delivered').
2. **Total Returns (`tot_returns`)**  
Count distinct `order_id` from `ex_returns` (left-joined to orders).
3. **Total Order Value (`order_value`)**  
Sum of `sales_amount` from `ex_transactions`.
4. **Average Basket Size (`avg_basket_size`)**

    - Formula:

> 
> Total units purchased / total orders
    - Use `FLOOR()` to round **down** to the nearest lower integer.
5. **Average Basket Value (`avg_basket_value`)**

    - Formula:

> 
> Total order value / total orders
    - Format as currency: `'$ ' + value`.
6. **Length of Stay (days) – `length_of_stay_days`**

    - Difference between **first** and **last** order dates using:

> 
> `DATEDIFF(day, MIN(order_purchase_date), MAX(order_purchase_date))`.
7. **Order Purchase Frequency – `order_purchase_frequency`**

    - Formula:

> 
> `length_of_stay_days / tot_orders`
    - Interpreted as **average days between two orders**.
8. **Recency (days) – `recency_days`**

    - For this project, treat **`2018-09-01`** as the analysis / “today” date.
    - Recency is defined as:

> 
> Number of days since the customer’s **last delivered order** as of `2018-09-01`.
    - Implemented as:

> 
> `DATEDIFF(day, MAX(order_purchase_date), '2018-09-01')`
    - Lower `recency_days` = more recent / active customer.
9. **Recency Segment – `recency_segment`**  
These are **business parameters** to separate customers into Recency bands based on `recency_days`:

    - **High (High / Recent)** → `recency_days <= 18`
    - **Medium (Medium)** → `19 <= recency_days <= 31`
    - **Low (Low / Stale)** → `recency_days >= 32`

    Example: if `recency_days = 10`, the segment is `High`.
10. **Frequency Segment – `frequency_segment`**  
Based on `order_purchase_frequency` (average days between orders):

    - **High (High Frequency)** → `order_purchase_frequency <= 30`
    - **Medium (Medium Frequency)** → `31 <= order_purchase_frequency <= 38`
    - **Low (Low Frequency)** → `order_purchase_frequency > 38`

    Lower value = more frequent buyer.  
Example: if `order_purchase_frequency = 14`, the segment is `High`.
11. **Monetary Segment – `monetary_segment`**  
Based on total spend `order_value`:

    - **High (High Spend)** → `order_value > 6900`
    - **Medium (Medium Spend)** → `4300 <= order_value <= 6900`
    - **Low (Low Spend)** → `order_value < 4300`

    Example: if `order_value = 15000`, the segment is `High`.

## Final Working Solution (SSMS)

```sql
WITH customer_base AS (
    SELECT 
        c.customer_id,
        c.customer_name,
        
        COUNT(DISTINCT o.order_id) AS tot_orders,
        COUNT(DISTINCT r.order_id) AS tot_returns,
        
        SUM(t.sales_amount) AS order_value,
        
        FLOOR(SUM(t.quantity) / COUNT(DISTINCT o.order_id)) AS avg_basket_size,
        
        CONCAT('$ ', ROUND(SUM(t.sales_amount) / COUNT(DISTINCT o.order_id), 2)) 
            AS avg_basket_value,
        
        DATEDIFF(day, MIN(o.order_purchase_date), MAX(o.order_purchase_date)) 
            AS length_of_stay_days,

        DATEDIFF(day, MIN(o.order_purchase_date), MAX(o.order_purchase_date)) 
            / COUNT(DISTINCT o.order_id) 
            AS order_purchase_frequency,

        -- Recency: days since last delivered order as of 2018-09-01
        DATEDIFF(day, MAX(o.order_purchase_date), '2018-09-01') 
            AS recency_days
    FROM ex_customers c
    JOIN ex_orders o 
        ON o.customer_id = c.customer_id
       AND o.order_status = 'delivered'     
    JOIN ex_transactions t 
        ON t.order_id = o.order_id
    LEFT JOIN ex_returns r
        ON r.order_id = o.order_id
    GROUP BY 
        c.customer_id, 
        c.customer_name
)

SELECT
    customer_id,
    customer_name,
    tot_orders,
    tot_returns,
    order_value,
    avg_basket_size,
    avg_basket_value,
    length_of_stay_days,
    order_purchase_frequency,
    recency_days,

    -- Recency segment (R)
    CASE 
        WHEN recency_days <= 18 THEN 'High'
        WHEN recency_days BETWEEN 19 AND 31 THEN 'Medium'
        ELSE 'Low'
    END AS recency_segment,

    -- Frequency segment (F) - average days between orders
    CASE 
        WHEN order_purchase_frequency <= 30 THEN 'High'
        WHEN order_purchase_frequency BETWEEN 31 AND 38 THEN 'Medium'
        ELSE 'Low'
    END AS frequency_segment,

    -- Monetary segment (M) - total spend
    CASE 
        WHEN order_value > 6900 THEN 'High'
        WHEN order_value BETWEEN 4300 AND 6900 THEN 'Medium'
        ELSE 'Low'
    END AS monetary_segment

FROM customer_base;


```

## Common Mistakes

1. **Not using DISTINCT for counting orders or returns**  
`ex_transactions` has multiple rows per order, so ignoring `DISTINCT` inflates counts.
2. **Using `SUM(quantity) / SUM(order_id)`**  
Incorrect because `order_id` is not numeric and does not represent a count.
3. **Not using `FLOOR()` for `avg_basket_size`**  
The requirement clearly states: round down to the lower integer.
4. **Joining returns with `INNER JOIN`**  
This removes customers who have **no returns**. Use `LEFT JOIN` instead.
5. **Using `DATEDIFF` in the wrong order**  
`DATEDIFF(max, min)` is incorrect. Always:  
`DATEDIFF(day, min_date, max_date)`.
6. **Formatting currency incorrectly**  
The requirement expects `'$ ' + value` format for `avg_basket_value`.
7. **Calculating `length_of_stay_days` using `COUNT` instead of date difference**  
Must use `MIN` and `MAX` order dates, not the number of rows.
8. **Not adding the `order_status = 'delivered'` filter in the orders join**  
Missing this will include cancelled or invalid orders and distort all metrics.
9. **Computing Recency using `GETDATE()` instead of the fixed analysis date**  
For consistent evaluation, recency must use `'2018-09-01'` as the reference date.
10. **Using thresholds different from the agreed business parameters**  
R, F, and M segments must use the specified cut-offs so that customer groups are comparable and aligned with the business rules.
