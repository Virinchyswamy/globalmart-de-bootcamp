The Mission

GlobalMart's Challenge

The Problem

GlobalMart has thousands of customers but doesn't truly know them. They treat every customer the same — same promotions, same communication, same offers.

But a customer who spends ₹15,000/year and buys every month deserves a very different experience than one who bought once in 2016.

Your Role as Data Analyst

Build a customer-level summary table by joining data from 4 tables: customers, orders, transactions, returns.

Compute behavioural metrics and classify each customer into an RFM segment so the marketing team can target them correctly.

The RFM Framework

Every loyalty/segmentation model starts with these three dimensions:

R — Recency

How recently did the customer last buy? A recent buyer is engaged; a stale buyer may have churned.

High ≤ 18 days (very recent)Medium 19–31 daysLow ≥ 32 days (stale)
F — Frequency

How often do they buy? Measured as avg days between orders — lower = more frequent.

High ≤ 30 days between ordersMedium 31–38 daysLow > 38 days between orders
M — Monetary

How much do they spend? Total order value from all delivered orders.

High > ₹6,900 total spendMedium ₹4,300–₹6,900Low < ₹4,300 total spend

Fixed analysis date: 2018-09-01 — treat this as "today" for all recency calculations. This ensures everyone in the class gets the same result when they run the query.

Join Logic

ex_customers → joined to ex_orders via customer_id

ex_orders → joined to ex_transactions via order_id

ex_orders → LEFT JOIN ex_returns via order_id (some orders won't have returns)

Filter: order_status = 'delivered' applied on the orders join

Why LEFT JOIN for returns?
If we use INNER JOIN, customers with zero returns disappear from the result entirely. We want all customers — even those who never returned anything. LEFT JOIN preserves them (with NULL for return columns).

mskl-masterclass
-- The join structure (simplified view)
FROM ex_customers c

-- INNER JOIN: we only want customers who placed
-- at least one delivered order
JOIN ex_orders o
    ON o.customer_id = c.customer_id
   AND o.order_status = 'delivered'

-- INNER JOIN: link each order to its transaction lines
JOIN ex_transactions t
    ON t.order_id = o.order_id

-- LEFT JOIN: keep all orders, even those without returns
-- Returns will show as NULL for non-returned orders
LEFT JOIN ex_returns r
    ON r.order_id = o.order_id

-- Group to customer level (one row per customer)
GROUP BY
    c.customer_id,
    c.customer_name

Building the customer_base CTE

The core CTE: all metrics computed here | mskl-masterclass
mskl-masterclass
WITH customer_base AS (
    SELECT
        c.customer_id,
        c.customer_name,

        -- DISTINCT because ex_transactions has multiple rows per order
        -- Without DISTINCT, we'd count the same order multiple times
        COUNT(DISTINCT o.order_id)  AS tot_orders,

        -- LEFT JOIN means r.order_id is NULL for non-returned orders
        -- COUNT(DISTINCT NULL) = 0, so this still works correctly
        COUNT(DISTINCT r.order_id)  AS tot_returns,

        -- Total revenue from this customer's delivered orders
        SUM(t.sales_amount)         AS order_value,

        -- FLOOR rounds DOWN: avg units per order basket
        -- FLOOR(7.9) = 7, not 8
        FLOOR(SUM(t.quantity) / COUNT(DISTINCT o.order_id))
                                    AS avg_basket_size,

        -- CONCAT to format as "$ 250.50"
        CONCAT('$ ', ROUND(SUM(t.sales_amount) / COUNT(DISTINCT o.order_id), 2))
                                    AS avg_basket_value,

        -- Days between first-ever and last-ever delivered order
        DATEDIFF(day, MIN(o.order_purchase_date), MAX(o.order_purchase_date))
                                    AS length_of_stay_days,

        -- Avg days between two orders = length_of_stay / total_orders
        -- Lower number = more frequent buyer
        DATEDIFF(day, MIN(o.order_purchase_date), MAX(o.order_purchase_date))
            / COUNT(DISTINCT o.order_id)
                                    AS order_purchase_frequency,

        -- Days since last purchase as of our fixed analysis date 2018-09-01
        -- Lower number = more recent (active) customer
        DATEDIFF(day, MAX(o.order_purchase_date), '2018-09-01')
                                    AS recency_days

    FROM ex_customers c
    JOIN ex_orders o
        ON  o.customer_id = c.customer_id
       AND  o.order_status  = 'delivered'
    JOIN ex_transactions t
        ON t.order_id = o.order_id
    LEFT JOIN ex_returns r
        ON r.order_id = o.order_id
    GROUP BY
        c.customer_id,
        c.customer_name
)

-- Check the CTE output before adding segments
SELECT * FROM customer_base;

Final SELECT: Adding RFM Segments

CASE WHEN on top of the CTE | The segmentation logic
mskl-masterclass
-- ... WITH customer_base AS (...) above ...

-- Now use CASE WHEN to classify each customer
-- into High / Medium / Low for each RFM dimension

SELECT
    customer_id,
    customer_name,
    tot_orders,
    tot_returns,
    order_value,
    avg_basket_size,
    avg_basket_value,
    length_of_stay_days,
    order_purchase_frequency,
    recency_days,

    -- R: How recently did they buy?
    -- Lower recency_days = more recent buyer = High
    CASE
        WHEN recency_days <= 18              THEN 'High'
        WHEN recency_days BETWEEN 19 AND 31 THEN 'Medium'
        ELSE                                       'Low'
    END AS recency_segment,

    -- F: How often do they buy?
    -- Lower frequency (fewer days between orders) = High
    CASE
        WHEN order_purchase_frequency <= 30              THEN 'High'
        WHEN order_purchase_frequency BETWEEN 31 AND 38 THEN 'Medium'
        ELSE                                                    'Low'
    END AS frequency_segment,

    -- M: How much do they spend?
    -- Higher order_value = High monetary
    CASE
        WHEN order_value > 6900             THEN 'High'
        WHEN order_value BETWEEN 4300 AND 6900 THEN 'Medium'
        ELSE                                       'Low'
    END AS monetary_segment

FROM customer_base;

Reading RFM results

A customer with recency_segment = High, frequency_segment = High, monetary_segment = High is your best customer — a Promoter. Target with VIP perks.

A customer with all Low is a Detractor — focus on understanding why, not pushing more sales.

Pro tip: Because these CASE WHEN statements reference columns from customer_base (not from raw tables), the logic is completely clean. This is the power of building on a CTE.

Full Solution Query

Complete working query — run this end-to-end in SSMS
mskl-masterclass
WITH customer_base AS (
    SELECT
        c.customer_id,  c.customer_name,
        COUNT(DISTINCT o.order_id)  AS tot_orders,
        COUNT(DISTINCT r.order_id)  AS tot_returns,
        SUM(t.sales_amount)          AS order_value,
        FLOOR(SUM(t.quantity) / COUNT(DISTINCT o.order_id))   AS avg_basket_size,
        CONCAT('$ ', ROUND(SUM(t.sales_amount) / COUNT(DISTINCT o.order_id), 2))
                                       AS avg_basket_value,
        DATEDIFF(day, MIN(o.order_purchase_date), MAX(o.order_purchase_date))
                                       AS length_of_stay_days,
        DATEDIFF(day, MIN(o.order_purchase_date), MAX(o.order_purchase_date))
            / COUNT(DISTINCT o.order_id) AS order_purchase_frequency,
        DATEDIFF(day, MAX(o.order_purchase_date), '2018-09-01')
                                       AS recency_days
    FROM ex_customers c
    JOIN      ex_orders       o ON o.customer_id = c.customer_id AND o.order_status = 'delivered'
    JOIN      ex_transactions t ON t.order_id = o.order_id
    LEFT JOIN ex_returns      r ON r.order_id = o.order_id
    GROUP BY c.customer_id, c.customer_name
)
SELECT
    customer_id, customer_name, tot_orders, tot_returns, order_value,
    avg_basket_size, avg_basket_value, length_of_stay_days,
    order_purchase_frequency, recency_days,
    CASE WHEN recency_days <= 18 THEN 'High' WHEN recency_days BETWEEN 19 AND 31 THEN 'Medium' ELSE 'Low' END AS recency_segment,
    CASE WHEN order_purchase_frequency <= 30 THEN 'High' WHEN order_purchase_frequency BETWEEN 31 AND 38 THEN 'Medium' ELSE 'Low' END AS frequency_segment,
    CASE WHEN order_value > 6900 THEN 'High' WHEN order_value BETWEEN 4300 AND 6900 THEN 'Medium' ELSE 'Low' END AS monetary_segment
FROM customer_base;

Common Mistakes to Warn Your Class About

  • Not using DISTINCT for order count. ex_transactions has multiple rows per order. COUNT(order_id) inflates the count. Always use COUNT(DISTINCT order_id).
  • Using INNER JOIN for returns. Customers with zero returns disappear. Use LEFT JOIN ex_returns to keep all customers.
  • Forgetting FLOOR for avg_basket_size. The problem says "round down to lower integer." Without FLOOR, you get decimals.
  • Wrong DATEDIFF order for recency. Recency = days since last order. Formula: DATEDIFF(day, MAX(date), '2018-09-01') — NOT the other way around.
  • Using GETDATE() for recency instead of '2018-09-01'. The problem specifies a fixed reference date so everyone gets the same answer.
  • Missing the delivered filter. Not adding order_status = 'delivered' includes cancelled/pending orders and distorts all metrics.
  • Integer division for frequency. length_of_stay / tot_orders — if both are integers, SQL truncates. Fine here because the requirement says "round to nearest integer" — but be aware.

Class Discussion — Deepening the Thinking

Discussion Q1

"A customer placed 1 order 2 years ago worth ₹50,000. What is their RFM segment? Should they be a Promoter?"

→ High Monetary, but Low Recency + Low Frequency. This shows why you need ALL THREE dimensions — one metric alone can mislead.

Discussion Q2

"What might cause a customer to have very high tot_returns? Should we give them loyalty rewards?"

→ Maybe quality issues, buyer's remorse, or fraud. High returns despite high spend is a risk signal, not a loyalty signal.

Discussion Q3

"Why is the analysis date fixed at 2018-09-01 and not GETDATE()?"

→ The data is historical. Using GETDATE() would make everyone look like a stale, inactive customer since the data is from 2016–2018. A fixed reference date gives meaningful RFM values.
