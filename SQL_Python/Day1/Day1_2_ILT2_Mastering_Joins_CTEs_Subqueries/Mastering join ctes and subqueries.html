ORDER BY & Sorting

Run in SSMS · mskl-masterclass · table: orders

Sorting is just telling SQL "read the results back to me in this order" — one or more columns, ascending or descending. Nothing changes about the data itself.

mskl-masterclass
-- Basic ascending sort (default, no keyword needed)
SELECT * FROM orders
ORDER BY customer_id;

-- Descending sort: latest orders first
SELECT * FROM orders
ORDER BY order_purchase_date DESC;

-- Multi-column sort:
-- First group by customer, then within each customer
-- show latest purchase first
SELECT
    order_id,
    customer_id,
    order_purchase_date,
    order_status
FROM orders
ORDER BY customer_id ASC,
         order_purchase_date DESC;

-- Shortcut: use column position numbers instead of names
-- 2 = customer_id (2nd column), 6 = order_purchase_date
SELECT
    order_id, customer_id, vendor_id,
    ship_mode, order_status, order_purchase_date
FROM orders
ORDER BY 2, 6 DESC;

TOP N + OFFSET FETCH

-- Top 3 fastest deliveries
SELECT TOP 3
    order_id,
    DATEDIFF(day,
        order_purchase_date,
        order_delivered_customer_date
    ) AS delivery_days
FROM orders
WHERE order_status = 'delivered'
ORDER BY 2;

-- Pagination: skip 10, take next 3
-- Useful for "page 2" type results
SELECT
    order_id,
    DATEDIFF(day,
        order_purchase_date,
        order_delivered_customer_date
    ) AS delivery_days
FROM orders
WHERE order_status = 'delivered'
ORDER BY 2
OFFSET 10 ROWS
FETCH NEXT 3 ROWS ONLY;

SQL Order of Operations — The Critical Mental Model

How SQL Actually Runs

  1. FROM — SQL first finds the table(s) to work with
  2. JOIN … ON — Tables are merged; the ON condition is evaluated to match rows between them
  3. WHERE — Rows that don't match the filter are discarded
  4. GROUP BY — Remaining rows are grouped
  5. HAVING — Groups that don't match are discarded
  6. SELECT — Columns are selected / computed
  7. ORDER BY — Result is sorted for display

Key rules:

JOIN runs before WHERE — so ON filters during table merging, WHERE filters the combined result after.

You CANNOT use a SELECT alias inside WHERE — WHERE runs before SELECT.

You CAN use a SELECT alias inside ORDER BY — it runs after SELECT.

mskl-masterclass
-- We WRITE SQL top-to-bottom, but SQL EXECUTES in a different order

-- Step 6: SELECT (runs 6th — aliases created here)
SELECT
    c.customer_name,
    COUNT(DISTINCT o.order_id) AS total_orders,
    SUM(t.sales_amount)          AS total_spent

-- Step 1: FROM (runs 1st — SQL finds the base table)
FROM ex_customers c

-- Step 2: JOIN + ON (runs 2nd — tables are merged on matching customer_id)
JOIN ex_orders o
    ON c.customer_id = o.customer_id
JOIN ex_transactions t
    ON o.order_id = t.order_id

-- Step 3: WHERE (runs 3rd — filters the combined result AFTER joining)
-- Note: this runs AFTER JOIN, so you can filter on columns from any table
WHERE o.order_status = 'delivered'

-- Step 4: GROUP BY (runs 4th)
GROUP BY c.customer_name

-- Step 5: HAVING (runs 5th — filters groups AFTER aggregation)
HAVING COUNT(DISTINCT o.order_id) > 5

-- Step 7: ORDER BY (runs last — can use SELECT alias here)
ORDER BY total_spent DESC;

All 6 Types of JOINs — At a Glance

Think of each JOIN as answering a different business question about overlapping datasets.

only the overlap
INNER JOIN

Only rows that match in both tables. Customers who have orders.

all of left + overlap
LEFT JOIN

All rows from left table + matched rows from right. Shows customers with NO orders as NULL.

all of right + overlap
RIGHT JOIN

All rows from right table + matched rows from left. Mirror of LEFT JOIN.

everything, both sides
FULL OUTER JOIN

Everything from both tables. NULLs where no match exists on either side.

every row × every row
CROSS JOIN

Every possible combination. 5 employees × 4 departments = 20 rows. No ON clause needed.

↻
a table, joined to itself
SELF JOIN

Table joined with itself. Classic use: employee + their manager (same table).

JOINs in Action

Run in SSMS · mskl-masterclass

Same shape every time: pick two tables, say which columns must match, decide who gets kept when there's no match.

mskl-masterclass
-- INNER JOIN: customers who have placed orders
SELECT
    c.customer_id,
    c.customer_name,
    o.order_id,
    o.order_purchase_date
FROM ex_customers c
INNER JOIN ex_orders o
    ON c.customer_id = o.customer_id;

-- LEFT JOIN: ALL customers, even those with no orders
-- Unmatched customers will have NULL for order columns
SELECT
    c.customer_id,
    c.customer_name,
    o.order_id
FROM ex_customers c
LEFT JOIN ex_orders o
    ON c.customer_id = o.customer_id;

-- Find customers who have NEVER placed an order
-- The trick: filter WHERE order_id IS NULL after LEFT JOIN
SELECT
    c.customer_id,
    c.customer_name
FROM ex_customers c
LEFT JOIN ex_orders o
    ON c.customer_id = o.customer_id
WHERE o.order_id IS NULL;
mskl-masterclass
-- SELF JOIN: find employee and their manager
-- Both come from the same employees table
SELECT
    e1.employee_name AS Employee,
    e2.employee_name AS Manager
FROM employees e1
JOIN  employees e2
    ON e1.manager_id = e2.employee_id;

-- THREE-TABLE JOIN: customers + orders + transactions
-- This is the pattern used in Module 3 & 4
SELECT
    c.customer_name,
    o.order_id,
    SUM(t.sales_amount) AS order_total
FROM ex_customers c
JOIN ex_orders o
    ON c.customer_id = o.customer_id
JOIN ex_transactions t
    ON o.order_id = t.order_id
WHERE o.order_status = 'delivered'
GROUP BY
    c.customer_name,
    o.order_id
ORDER BY order_total DESC;

GROUP BY + Aggregate Functions

The 5 Aggregate Functions

FunctionWhat it returns
COUNT(*)Number of rows in each group
COUNT(DISTINCT col)Unique values in group
SUM(col)Total of all values
AVG(col)Average value
MAX(col) / MIN(col)Highest / lowest value

Rule: Every column in SELECT that is NOT inside an aggregate function MUST appear in GROUP BY.

mskl-masterclass
-- Total sales per customer
SELECT
    customer_id,
    SUM(sales_amount) AS total_sales
FROM orders
GROUP BY customer_id;

-- Orders per region with average delivery time
SELECT
    region,
    COUNT(order_id)   AS total_orders,
    AVG(DATEDIFF(day,
        order_purchase_date,
        order_delivered_customer_date
    ))                   AS avg_delivery_days
FROM ex_orders
WHERE order_status = 'delivered'
GROUP BY region
ORDER BY avg_delivery_days DESC;

-- Only customers who spent more than 5000
SELECT
    customer_id,
    SUM(sales_amount) AS total_sales
FROM orders
GROUP BY customer_id
HAVING SUM(sales_amount) > 5000;

WHERE vs HAVING — The Crucial Difference

WHERE filters ROWS (before grouping)

-- Filter individual rows first,
-- THEN count what's left per group
SELECT
    state,
    COUNT(*) AS customer_count
FROM ex_customers
WHERE state <> 'Unknown'
GROUP BY state;

Use WHERE when the condition applies to individual rows

HAVING filters GROUPS (after grouping)

-- Group first, THEN throw away
-- groups that are too small
SELECT
    state,
    COUNT(*) AS customer_count
FROM ex_customers
GROUP BY state
HAVING COUNT(*) > 50;

Use HAVING when the condition applies to an aggregated value

Quick Memory Trick: WHERE is a bouncer at the door (filters before the party). HAVING is a judge at the end (rules on the groups after they've formed). You can use BOTH in the same query!

Subqueries

A query inside another query | Run in SSMS
mskl-masterclass
-- Problem: find customers in specific states,
-- but the state column has typos and bad casing

-- Without subquery: messy, hard to read
SELECT
    state_name,
    COUNT(*) AS customer_count
FROM (
    -- Inner query: this is the "sub-query"
    -- It cleans the data before the outer query uses it
    SELECT
        customer_id,
        CASE
            WHEN TRIM(state) = 'calfornia'
                THEN UPPER('California')
            WHEN TRIM(state) = 'masachusets'
                THEN UPPER('Massachusetts')
            ELSE UPPER(TRIM(state))
        END AS state_name
    FROM mskl_customers
) AS t
GROUP BY state_name
HAVING state_name IN
    ('CALIFORNIA', 'ARIZONA', 'TEXAS');

How a Subquery Works

The inner query (inside the parentheses) runs first and produces a temporary result set.

The outer query then treats that result just like a normal table.

Think of it like: clean the ingredients (inner), then cook (outer).

Downside of subqueries: As they nest deeper, they become very hard to read. That's why CTEs exist.

CTEs (Common Table Expressions)

WITH clause | The cleaner alternative to subqueries
mskl-masterclass
-- Same logic as the subquery, but written as a CTE
-- CTE gives the subquery a NAME and moves it to the top

WITH customer_list AS (
    -- Step 1: Clean the state column once here
    SELECT
        customer_id,
        CASE
            WHEN TRIM(state) = 'calfornia'
                THEN UPPER('California')
            WHEN TRIM(state) = 'masachusets'
                THEN UPPER('Massachusetts')
            ELSE UPPER(TRIM(state))
        END AS state_name
    FROM mskl_customers
)

-- Step 2: Now use 'customer_list' just like a normal table
SELECT
    state_name,
    COUNT(*) AS customer_count
FROM customer_list
GROUP BY state_name
HAVING state_name IN
    ('CALIFORNIA', 'ARIZONA', 'TEXAS');

How a CTE Executes — Two Steps

① WITH customer_list AS ( ...clean the state column... )
↓ runs first, produces a named temp result
② SELECT state_name, COUNT(*) FROM customer_list ...

CTE vs Subquery

SubqueryCTE
Where writtenInside FROMBefore main query (WITH)
Named?Optional aliasAlways named
Reusable?NoYes — reference it many times
ReadabilityHarder to followMuch cleaner

Key insight: A CTE doesn't create a physical table. It's just a named temporary result that lives only for the duration of that query execution.

Multiple CTEs — stack them with commas!

WITH
cte_one AS (... first logic ...),
cte_two AS (... uses cte_one ...)
SELECT * FROM cte_two;
