## Overview
As GlobalMart’s data ecosystem grows, analysts like **Rahul** are finding that simple SELECT and WHERE  statements are no longer enough. The challenge lies in efficiently processing massive datasets, combining information across siloed tables, and producing increasingly complex, summarized reports under tight deadlines. Without mastering intermediate SQL concepts like complex joins and query structuring, data analysis quickly becomes slow, messy, and error-prone.

This self-paced, hands-on masterclass solves this problem by moving you from foundational SQL to **Intermediate data wrangling**. You will follow **Rahul**’s journey through interactive scenarios, learning to build robust and scalable queries using industry best practices.

### **What You'll Learn:**

**Data Retrieval and Organization**

- Understand the **SQL Order of Operations** to predict how your queries execute.
    
- Master the use of ORDER BY for effective **multi-column sorting** using both column names and index positions.
    
- Explore methods for limiting result sets, including TOP N and the OFFSET FETCH clauses.
    

**Merging and Summarizing Data**

- Learn how to use **INNER, LEFT, RIGHT, FULL OUTER, CROSS, and SELF JOINs** to combine data from multiple sources efficiently.
    
- Grasp the power of GROUP BY with **aggregate functions** SUM, COUNT, AVG to generate powerful summary metrics.
    
- Compare the purpose of the **WHERE** clause versus the **HAVING** clause for filtering rows before and after aggregation.
    

**Advanced Query Structuring**

- Explore the use of a **sub-query** to modularize and simplify complex logic within the FROM clause.
    
- Learn the primary benefit of using **Common Table Expressions (CTEs)**, created with the WITH clause, to improve query readability and maintainability.
    

By the end, you'll understand how to integrate **JOINS**, **GROUP BY**, and **CTEs**—so you can quickly merge customer and order data, summarize sales performance by region, and write streamlined, complex analytical queries. Test your knowledge throughout with scenario-based questions.

### **Understanding ORDER BY**


The `ORDER BY` keyword is used to sort the result-set in ascending or descending order.

The `ORDER BY` keyword sorts the records in ascending order by default. To sort the records in descending order, use the `DESC` keyword.


**Sharon:** Think of it like sorting data in Excel — you can sort alphabetically, numerically, or by date.  


In SQL, the `ORDER BY` clause works the same way.


By default, SQL sorts in **ascending order** —

- Smallest to largest (for numbers)
    
- A to Z (for text)
    
- Oldest to newest (for dates)
    

If you want to reverse the order, use **DESC** for _descending_.

### Order of Operations.


In SQL, there is something called **Order of Operations**. It's an extremely important concept.  Even though we _write_ SQL from top to bottom, SQL doesn’t _execute_ it that way.

Here’s the actual flow:

1. **FROM** – Find the table(s)
    
2. **WHERE** – Filter the rows
    
3. **GROUP BY** – Group the data
    
4. **HAVING** – Filter the groups
    
5. **SELECT** – Pick the columns
    
6. **ORDER BY** – Finally, sort the results


The following diagram will be super helpful to understand how a typical SQL query works:

![](https://mentorskool-platform-uploads.s3.ap-south-1.amazonaws.com/images/730dfb9a-4108-496a-818d-030128359e16_83d04ac6-cb74-4a96-a06a-e0d5442aa126_image.webp)

Read more about it from [here](https://learnsql.com/blog/sql-order-of-operations/).    


>[!NOTE] 

That’s why you can’t use an alias (from SELECT) inside WHERE — because the WHERE part executes _before_ SELECT.

### **Understanding JOINs**


**Mentor:**  Think of JOINs as connecting puzzle pieces. Each table has part of the picture, and the right type of JOIN helps you complete it.

Let’s look at the main types:


#### **1. INNER JOIN**


Returns only the matching rows from both tables.  
If a customer has no order, that customer won’t appear in the result.

```sql
SELECT    
   c.customer_id,    
   c.customer_name,    
   o.order_id,    
   o.order_purchase_date 
FROM customers c 
INNER JOIN orders o    
   ON c.customer_id = o.customer_id;
```

**Result:**  
Only customers who placed at least one order appear here.

---

#### **2. LEFT JOIN**


Returns **all records from the left table** (even if there’s no match in the right table).

```sql
SELECT    
   c.customer_id,    
   c.customer_name,    
   o.order_id 
FROM customers c 
LEFT JOIN orders o    
   ON c.customer_id = o.customer_id;
```

**Result:**  
All customers are listed, and if a customer hasn’t made any purchase, the order details show as **NULL**.

This is especially useful when you want to find customers _who haven’t yet ordered_.

---

#### **3. RIGHT JOIN**


The mirror of LEFT JOIN — it returns all rows from the **right table**, and matching ones from the left.

```sql
SELECT    
   d.department_id,    
   d.department_name,    
   e.employee_name 
FROM employees e 
RIGHT JOIN departments d    
  ON e.department_id = d.department_id;
```

**Result:**  
All departments appear — even if no employee is assigned.

---

#### **4. FULL OUTER JOIN**


Combines all records from both tables — even when there’s no match on either side.

```sql
SELECT    
   c.customer_id,    
   o.order_id 
FROM customers c 
FULL OUTER JOIN orders o    
   ON c.customer_id = o.customer_id;
```

**Result:**  
You’ll see every customer and every order — even if some have no link between them.

---

#### **5. CROSS JOIN**


Creates every possible combination of the two tables — known as the **Cartesian product**.


If GlobalMart has 5 employees and 4 departments:  
A `CROSS JOIN` gives **5 × 4 = 20** combinations.

```sql
SELECT *  
FROM employees  
CROSS JOIN departments;
```

---

#### **6. SELF JOIN**


When you join a table with itself — for example, finding employees who report to another employee in the same table.

```sql
SELECT    
   e1.employee_name AS Employee,    
   e2.employee_name AS Manager 
FROM employees e1 
JOIN employees e2    
   ON e1.manager_id = e2.employee_id;
```

### **Summarizing Data with GROUP BY**


The **GROUP BY** clause groups rows that share the same value in one or more columns.  
Then you can apply aggregate functions such as:

- **COUNT()** – Count the number of records
    
- **SUM()** – Add up values
    
- **AVG()** – Calculate averages
    
- **MAX() / MIN()** – Find highest or lowest values
    

---

#### **Example: Total Sales per Customer**


```sql
SELECT    
   customer_id,    
   SUM(sales_amount) AS total_sales 
FROM orders 
GROUP BY customer_id;
```

This query gives the total sales made by each customer.

---

#### **Example: Count of Orders per Region**

```sql
SELECT    
   region,    
   COUNT(order_id) AS total_orders 
FROM orders 
GROUP BY region;
```

---

### **Filtering Groups with HAVING**


**Rahul:**  I know WHERE filters data before grouping. What if I want to filter _after_ aggregation?

**Sharon:** Exactly — that’s what **HAVING** does.


Use **WHERE** to filter rows _before grouping_, and **HAVING** to filter _after grouping_.


#### Example:

```sql
SELECT    
   customer_id,    
   SUM(sales_amount) AS total_sales 
FROM orders 
GROUP BY customer_id 
HAVING SUM(sales_amount) > 5000;
```

This shows only those customers whose total sales exceed ₹5000.

---

 **Rahul:** Got it! So I can first merge the tables using JOINs, then summarize using GROUP BY and HAVING.

**Sharon:** Exactly. That’s the foundation of SQL analytics — combining and summarizing data efficiently.

### Understanding Subqueries


**A subquery is a query inside another query.**


It helps simplify complex logic — you can perform calculations or filtering in one part and then use that result in your main query.

Let’s look at an example. 

**Tags**


##### Input 2
**Type:** Text

Check the snapshot below. The line numbers next to the code are also kept for easy understanding. 

![](https://mentorskool-platform-uploads.s3.ap-south-1.amazonaws.com/images/c2e3b594-749a-4fbf-aaba-54156b2994b6_83d04ac6-cb74-4a96-a06a-e0d5442aa126_image.webp)

Now, recall the order of operations in SQL. Which operation should happen first? - From at line no. 4

Now, let's name the entire code block from line 5 to 10 with some name **t**

![](https://mentorskool-platform-uploads.s3.ap-south-1.amazonaws.com/images/173c541f-e86b-49c8-934f-9ec793472e03_83d04ac6-cb74-4a96-a06a-e0d5442aa126_image.webp)

So, effectively, the code becomes : 

    select 
    state_name,
    count(*) as customer_count
    from t
    group by state_name
    having state_name in ('California','Arizona','Texas')

Here **t** is nothing but the sub-query which encapsulates the complex logic hence making the job of the outer query easier. The code should look easy to interpret now. 

Sub-query helps simplify logic. I can write all my complex logic within the sub-query so that I don't have to repeat it again. 

However, there is another way which is even easier to implement as well as interpret. The idea of Common Table Expressions or CTEs

Check the below query :

    with customer_list as(
    	select 
    	customer_id,
    	case when trim(state) = 'calfornia' then upper('California')
    	when trim(state) = 'masachusets' then upper('massachusetts')
    	else upper(trim(state)) end as state_name
    	from mskl_customers
    	)
    select 
    state_name,
    count(*) as customer_count
    from customer_list
    group by state_name
    having state_name in ('California','Arizona','Texas')

In the above code, we are simplifying our logic early where the sub-query now appears inside the WITH clause. Interpret the code as follows :

![](https://mentorskool-platform-uploads.s3.ap-south-1.amazonaws.com/images/7029474b-1201-43b2-aba0-9306e097123f_83d04ac6-cb74-4a96-a06a-e0d5442aa126_image.webp)

The block of code highlighted under Green box is the sub-query which gets a name called **customer\_list**. 

Now, for the subsequent queries **customer\_list** acts just like a table (although this table doesn't exist physically)

The complex part of code is written early and wrapped up in a convenient name which you can use just like a table later.
