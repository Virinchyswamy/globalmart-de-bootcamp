Concept

📅 What are MTD and YTD? And Why SUM() OVER() with ORDER BY?

Regular SUM() — just a total

GROUP BY collapses everything into one row per group. You get one final total — not how it built up over time.

SUM() OVER() with ORDER BY — running total

With ORDER BY inside the window, SQL accumulates the total as it walks through rows in order. Each row shows: "how much did we sell from the start until this date?"

SUM(sales) OVER(
  PARTITION BY region, year, month
  ORDER BY order_date
)

This is MTD. The SUM resets at the start of each month (because PARTITION includes month).

RegionDateSalesMTDYTD
EastJan 51720.981720.981720.98
EastJan 101529.163250.143250.14
EastFeb 2900.00900.00 ← resets4150.14

The key difference:
MTD: PARTITION BY region, year, month → resets at start of each month
YTD: PARTITION BY region, year → resets at start of each year

Same ORDER BY order_date — the difference is just in PARTITION BY!

If MTD and YTD both use ORDER BY order_date, what creates the difference between them?

✅ The PARTITION BY clause. MTD partitions by month (so resets monthly), YTD partitions by year only (so accumulates all year).

Task 1: MTD & YTD Regional Sales 📅

Tables: ex_orders, ex_customers, ex_transactions, locations_01 | mskl-masterclass
mskl-masterclass
-- CTE 1: Get all delivered orders with region + sales
-- ex_ prefix tables are the 'extended' GlobalMart dataset
WITH DeliveredOrders AS (
    SELECT
        l.region,
        -- CAST to DATE removes the time component for cleaner grouping
        CAST(o.order_purchase_date AS DATE) AS order_date,
        t.sales_amount
    FROM ex_orders o
    JOIN ex_customers c
        ON o.customer_id = c.customer_id
    JOIN locations_01 l
        ON l.postal_code = c.postal_code
    JOIN ex_transactions t
        ON t.order_id = o.order_id
    -- Only delivered orders represent real completed revenue
    WHERE o.order_status = 'delivered'
),
-- CTE 2: Aggregate to one row per region+date, extract date parts
AggregatedSales AS (
    SELECT
        region,
        order_date,
        YEAR(order_date)               AS sales_year,
        MONTH(order_date)              AS sales_month,
        DATENAME(MONTH, order_date)   AS month_name,
        ROUND(SUM(sales_amount), 2)   AS total_sales
    FROM DeliveredOrders
    -- Must GROUP BY ALL non-aggregated columns
    GROUP BY region, order_date,
             YEAR(order_date),
             MONTH(order_date),
             DATENAME(MONTH, order_date)
)
-- Final: compute MTD and YTD using running SUM() OVER
SELECT
    region, order_date,
    sales_year AS Year, month_name AS Month_name,
    total_sales AS Sales,
    -- MTD: cumulative within same region + year + month
    SUM(total_sales) OVER(
        PARTITION BY region, sales_year, sales_month
        ORDER BY order_date
    ) AS MTD,
    -- YTD: cumulative within same region + year only (spans all months)
    SUM(total_sales) OVER(
        PARTITION BY region, sales_year
        ORDER BY order_date
    ) AS YTD
FROM AggregatedSales
ORDER BY region, order_date;

🎯 Predict the output

East region has these 3 rows after aggregation:

What values will appear in MTD and YTD for the Feb 2, 2023 row for East?

✅ MTD = 900.00 (first day of February — month starts fresh)

Common Mistake: Using ORDER BY month_name (alphabetical string) instead of ORDER BY order_date. Alphabetically, August comes before January — completely wrong accumulation order!

mskl-masterclass
-- Aggregate campaign metrics by campaign + channel name
SELECT
    c.campaign_id,
    ch.channel_name,
    -- SUM not COUNT — one campaign can have multiple metric rows
    SUM(cm.impressions)   AS impressions,
    SUM(cm.clicks)        AS clicks,
    SUM(cm.conversions)   AS conversions
FROM ex_campaigns c
JOIN ex_campaign_metrics cm
    ON c.campaign_id = cm.campaign_id
JOIN ex_channel ch
    ON c.channel_id = ch.channel_id
GROUP BY
    c.campaign_id,
    ch.channel_name;

Why SUM and not COUNT?
One campaign can run multiple times across different dates, products, or regions — each with its own metrics row. We need the total across all those rows, so SUM() is correct. COUNT would just count how many metric rows exist per campaign.

Which column links ex_campaigns to ex_channel? Which links ex_campaigns to ex_campaign_metrics?

✅ channel_id links campaigns → channel. campaign_id links campaigns → campaign_metrics.

Phase 1: Campaign → Transactions

A campaign promotes a product. Transactions contain that product. So JOIN on product_id to find all orders driven by this campaign.

WITH campaign_sales AS (
    SELECT
        c.campaign_id,
        t.order_id,
        t.sales_amount
    FROM ex_campaigns c
    -- campaign promotes product_id
    -- transaction records sales of that product
    JOIN ex_transactions t
        ON c.product_id = t.product_id
)

Phase 2: Order → Customer → Region

Now navigate from order to customer to location to find the region. Filter to delivered orders only.

, campaign_region AS (
    SELECT
        cs.campaign_id,
        o.customer_id,
        l.region,
        cs.sales_amount
    FROM campaign_sales cs
    JOIN ex_orders o
        ON cs.order_id = o.order_id
        -- AND in JOIN ON = filter rows during join
        AND o.order_status = 'delivered'
    JOIN ex_customers c
        ON o.customer_id = c.customer_id
    JOIN locations_01 l
        ON l.postal_code = c.postal_code
)

Task 3: Campaign Impact on Regional Revenue 🗺️

Full 2-CTE solution | 5-table chain | mskl-masterclass
mskl-masterclass
-- Full solution: campaign → product → transaction
--                       → order → customer → region
WITH campaign_sales AS (
    SELECT
        c.campaign_id,
        t.order_id,
        t.sales_amount
    FROM ex_campaigns c
    -- Product is the bridge: campaign promotes it,
    -- transaction records a sale of it
    JOIN ex_transactions t
        ON c.product_id = t.product_id
),
campaign_region AS (
    SELECT
        cs.campaign_id,
        o.customer_id,
        l.region,
        cs.sales_amount
    FROM campaign_sales cs
    JOIN ex_orders o
        ON cs.order_id = o.order_id
        -- Filter during the JOIN — only delivered orders = real revenue
        AND o.order_status = 'delivered'
    JOIN ex_customers c
        ON o.customer_id = c.customer_id
    JOIN locations_01 l
        ON l.postal_code = c.postal_code
)
SELECT
    region,
    campaign_id,
    -- DISTINCT: count each customer once even if they placed
    -- multiple orders from this campaign
    COUNT(DISTINCT customer_id)    AS customers_acquired,
    ROUND(SUM(sales_amount), 2) AS total_revenue
FROM campaign_region
GROUP BY region, campaign_id;

Expected Output Format

regioncampaign_idcustomerstotal_revenue
EastCMP00112015400.75
WestCMP0029511230.40

(Sample values — actual figures from your DB may differ)

Why do we use COUNT(DISTINCT customer_id) instead of COUNT(customer_id)?

✅ One customer can place multiple orders from the same campaign. Without DISTINCT, that customer gets counted multiple times. DISTINCT counts each customer only once — showing how many unique customers the campaign acquired.
