# Sales-Category Analysis Report of Globalmart
## Content Type
Scenario

## Overview
GlobalMart’s product portfolio spans multiple categories like Technology, Furniture, and Office Supplies — each with dozens of sub-categories and hundreds of SKUs. As sales grow, the management team wants to understand **which sub-categories drive the most revenue** within each category and how sales are distributed overall.

Basic aggregation reports can show total sales per sub-category, but they don’t reveal **how much each contributes to its category** or **which sub-category dominates overall performance**. To address this, GlobalMart’s data team is creating a **Sales–Category Analysis Report** using SQL with **window functions and common table expressions (CTEs)**.

This report helps the team:

- Calculate total and cumulative sales within each category.
    
- Measure each sub-category’s contribution percentage.
    
- Identify top-performing sub-categories contributing over 50% of category sales.
    

By combining aggregation with advanced SQL operations like `SUM() OVER()` and `RANK() OVER()`, the analysis provides a clear, data-driven view of where sales strength truly lies.

In this exercise, we’ll walk through how this SQL report is built step-by-step — from summarizing category-level sales to ranking sub-categories and highlighting key contributors.

## Learning Objectives
- Demonstrate use of JOIN, GROUP BY, and WHERE clause to ensure accurate filtering and calculations.
- Demonstrate knowledge of common table expressions (CTEs) to structure and simplify complex queries.
- Implement window functions to calculate cumulative totals, percentages, and rankings.

## Understanding the Problem


GlobalMart management wants to understand **how each product sub-category contributes to its parent category’s sales**. The report should not only show sales per sub-category but also:

1. **Total sales for the category** (`tot_cat_sales`)
    
2. **Cumulative sales** (`cumm_sales`) as we move through sub-categories
    
3. **Contribution % of each sub-category** to its category (`contrib_1`)
    
4. **Cumulative contribution %** up to that sub-category (`contrib_2`)
    

This helps management quickly identify which sub-categories drive the most value within each category.

---

## Step 1: What information do we need?


- **category** → Product category (Technology, Furniture, etc.)
    
- **sub_category** → Sub-group under category (e.g., Chairs, Phones, Paper).
    
- **sales** → Total sales for each sub-category.
    
- **tot_cat_sales** → Total sales of the entire category.
    
- **cumm_sales** → Running total of sales within category as we move sub-category by sub-category.
    
- **contrib_1** → `%` of sub-category sales / category sales.
    
- **contrib_2** → `%` cumulative sales / category sales.
    

---

## Step 2: Where is this data found?

|Table|Purpose|
|---|---|
|**ex_transactions**|Contains `sales_amount` (raw sales per product).|
|**ex_products**|Contains `category` and `sub_category` linked to each product.|

We join these two tables to link transactions with product categories.

---

## Logic Before Building the Solution


1. **Base Aggregation**
    
    - Aggregate sales by category and sub_category.
        
2. **Calculate Totals**
    
    - Compute category-level total sales (`tot_cat_sales`).
        
    - Compute cumulative sales (`cumm_sales`) within each category.
        
3. **Derive Percentages**
    
    - Contribution of sub-category = `sales / tot_cat_sales`.
        
    - Cumulative contribution = `cumm_sales / tot_cat_sales`.
        
4. **Formatting & Ordering**
    
    - Format as percentages.
        
    - Order by category and sales for readability.
        

---

## Final Working Solution

```sql
-- Step 1: Aggregate base data 
WITH base_data AS 
(     
SELECT          
   p.category,          
   p.sub_category,         
   ROUND(SUM(t.sales_amount), 0) AS sales     
FROM ex_transactions t     
JOIN ex_products p         
   ON p.product_id = t.product_id     
GROUP BY p.category, p.sub_category ),  
-- Step 2: Calculate category totals and cumulative sales 
running_totals AS 
(     
SELECT  *,         
   SUM(sales) OVER(PARTITION BY category) AS tot_cat_sales,         
   SUM(sales) OVER(PARTITION BY category ORDER BY sub_category) AS cumm_sales     
FROM base_data 
)  
-- Step 3: Final output with contributions 
SELECT      
   category,     
   sub_category,     
   sales,     
   tot_cat_sales,     
   cumm_sales,     
   FORMAT(1.0 * sales / tot_cat_sales, 'P2') AS contrib_1,     
   FORMAT(1.0 * cumm_sales / tot_cat_sales, 'P2') AS contrib_2 
FROM running_totals 
ORDER BY category, sales;
```

---

## Common Mistakes & Point Deductions


1. **Not joining products and transactions correctly** → `category` and `sub_category` won’t be available.
    
2. **Forgetting `PARTITION BY category` in window functions** → totals will be wrong (all categories lumped together).
    
3. **Not ordering inside `cumm_sales`** → cumulative sums will not align properly with sub-categories.
    
4. **Forgetting to format percentages (`FORMAT`)** → results will show as decimals (e.g., `0.2564` instead of `25.64%`).
    
5. **Ordering only by sales instead of category + sales** → output won’t be grouped by category as expected.

## Understanding the Problem


We must identify, **for each category**, the **first sub-category that causes the cumulative sales share to exceed 50%** of that category’s total sales.  
In other words, order sub-categories (by sales) within each category, compute cumulative sales, and pick the sub-category where the cumulative contribution first crosses 50%.

This highlights the _tipping point_ sub-category per category — the minimal set of sub-categories accounting for more than half the category sales.

---

## Step 1: What information do we need?

- `category` — product category.
    
- `sub_category` — product sub-category.
    
- `sales` — total sales per sub_category.
    
- `tot_cat_sales` — total sales for the category.
    
- `cumm_sales` — running cumulative sales within the category (based on chosen ordering).
    
- `contrib_1` — % contribution of the sub_category to the category (`sales / tot_cat_sales`).
    
- `contrib_2` — % cumulative contribution up to that sub_category (`cumm_sales / tot_cat_sales`).
    

---

## Step 2: Where is this data found?

|Table|Purpose|
|---|---|
|`ex_transactions`|`sales_amount` per transaction (source of sales)|
|`ex_products`|`category` and `sub_category` for each product|

We join `ex_transactions` → `ex_products`, aggregate sales by category/sub_category, then use window functions.

---

## Logic Before Building the Solution

1. Aggregate `sales` by `category, sub_category`.
    
2. Compute `tot_cat_sales` (sum over category).
    
3. Compute `cumm_sales` using `SUM(...) OVER (PARTITION BY category ORDER BY sales)` — **order by `sales` ascending** so cumulative builds from smaller to larger sub-categories (this matches the sample outputs where the first sub-category to push cumulative >50% is the middle-sized one).
    
4. Compute `contrib_1` and `contrib_2`.
    
5. Filter rows where `contrib_2 > 0.5` (cumulative share exceeds 50%).
    
6. From those rows, pick the **smallest sales** (first in ascending order) — we use `RANK()` over the filtered set and pick `ranks = 1`.
    

---

## Building the Solution — Step-by-Step (Phases)


**Phase 1 — Aggregate base sales by category/sub_category**

```sql
WITH base_data AS 
(   
SELECT     
   p.category,     
   p.sub_category,     
   ROUND(SUM(t.sales_amount), 0) AS sales   
FROM ex_transactions t   
JOIN ex_products p     
   ON p.product_id = t.product_id   
GROUP BY p.category, p.sub_category ),
```


**Phase 2 — Compute category totals and cumulative sales (order by sales ascending)**

```sql
running_totals AS 
(   
SELECT     *,     
   SUM(sales) OVER (PARTITION BY category) AS total_cat_sales,     
   SUM(sales) OVER (PARTITION BY category ORDER BY sales) AS cumm_sales   
FROM base_data ),
```


**Phase 3 — Compute contribution percentages (and keep numeric pct for logic)**

```sql
contribution_summary AS 
(   
SELECT     *,     
   FORMAT(1.0 * sales / total_cat_sales, 'P2') AS contrib_1,     
   1.0 * cumm_sales / total_cat_sales AS pct_contrib_2,     
   FORMAT(1.0 * cumm_sales / total_cat_sales, 'P2') AS contrib_2   
FROM running_totals ),
```


**Phase 4 — From rows where cumulative share > 50%, rank by sales (ascending) and pick the first one per category**

```sql
ranking_table AS 
(   
SELECT     *,     
RANK() OVER (PARTITION BY category ORDER BY sales) AS ranks   
FROM contribution_summary   
WHERE pct_contrib_2 > 0.5 )
```

## Final Working Solution

```sql
WITH base_data AS 
(   
SELECT     
   p.category,     
   p.sub_category,     
   ROUND(SUM(t.sales_amount), 0) AS sales   
FROM ex_transactions t   
JOIN ex_products p     
   ON p.product_id = t.product_id   
GROUP BY p.category, p.sub_category ), 
 running_totals AS 
(   
SELECT     *,     
   SUM(sales) OVER (PARTITION BY category) AS total_cat_sales,     
   SUM(sales) OVER (PARTITION BY category ORDER BY sales) AS cumm_sales   
FROM base_data 
),  
contribution_summary AS 
(   
SELECT     *,     
   FORMAT(1.0 * sales / total_cat_sales, 'P2') AS contrib_1,     
   1.0 * cumm_sales / total_cat_sales AS pct_contrib_2,     
   FORMAT(1.0 * cumm_sales / total_cat_sales, 'P2') AS contrib_2   
FROM running_totals 
),  
ranking_table AS 
(   
SELECT     *,     
   RANK() OVER (PARTITION BY category ORDER BY sales DESC) AS ranks   
FROM contribution_summary   
WHERE pct_contrib_2 > 0.5 
)  
SELECT   
   category,   
   sub_category,   
   sales,   
   total_cat_sales,   
   cumm_sales,   
   contrib_1,   
   contrib_2 
FROM ranking_table 
WHERE ranks = 1;
```

---

## Common Mistakes & Point Deductions


1. **Wrong ORDER direction for cumulative sum** — using `ORDER BY sales DESC` will accumulate from largest to smallest and pick a different sub-category (not the intended tipping point).
    
2. **Applying the `pct_contrib_2 > 0.5` filter too early** (inside the window calculation) — you must compute window functions first, then filter.
    
3. **Not partitioning window functions by `category`** — will mix categories together.
    
4. **Using `ROW_NUMBER()` or `RANK()` before filtering** — ranking must be computed over the filtered set so the smallest sales among those exceeding 50% becomes rank = 1.
    
5. **Not preserving a numeric `pct_contrib_2` for logic** — formatting to `'P2'` before logic prevents numeric comparisons. Keep an unformatted numeric column for WHERE, then format for display.
    
6. **Not handling ties** — `RANK()` handles ties by assigning same rank; if you want break ties differently, consider `ROW_NUMBER()` with a deterministic tie-breaker.
