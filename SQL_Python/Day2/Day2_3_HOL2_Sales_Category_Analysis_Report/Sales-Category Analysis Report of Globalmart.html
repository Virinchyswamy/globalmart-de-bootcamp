The Challenge

Two Reports for Upper Management 📋

GlobalMart's management asks: which sub-categories matter most? They want two outputs built from the same data.

Result 1 — Full Contribution Table

One row per sub-category showing:

  • sales — total sales for that sub-category
  • tot_cat_sales — category total
  • cumm_sales — running total within the category
  • contrib_1 — that sub-category's % share
  • contrib_2 — cumulative % up to that sub-category

Result 2 — The Tipping Point

For each category, identify the first sub-category where the cumulative contribution exceeds 50%.

This is the "tipping point" sub-category — the one that pushes cumulative sales past the halfway mark of its category.

Result 2 is built by filtering Result 1 — not a separate query from scratch!

Column-by-column breakdown

ColumnHow to get it
salesGROUP BY → SUM(sales_amount)
tot_cat_salesSUM(sales) OVER(PARTITION BY category)
no ORDER BY — full category total
cumm_salesSUM(sales) OVER(PARTITION BY category ORDER BY sales)

contrib_1FORMAT(sales / tot_cat_sales, 'P2')
contrib_2FORMAT(cumm_sales / tot_cat_sales, 'P2')

Critical difference:
tot_cat_sales uses SUM without ORDER BY → full category total on every row.
cumm_sales uses SUM with ORDER BY → builds up row by row.
Same PARTITION BY, completely different behavior.

Live Demo — Result 1: Full Contribution Table 📊

Tables: ex_transactions, ex_products | mskl-masterclass
-- CTE 1: Aggregate raw sales by category + sub_category
WITH base_data AS (
    SELECT
        p.category,
        p.sub_category,
        -- ROUND to 0 decimal places for clean numbers
        ROUND(SUM(t.sales_amount), 0) AS sales
    FROM ex_transactions t
    JOIN ex_products p
        ON p.product_id = t.product_id
    GROUP BY p.category, p.sub_category
),
-- CTE 2: Add category total and cumulative sales
-- SUM without ORDER BY = full total per category
-- SUM with ORDER BY = running total ascending by sales
running_totals AS (
    SELECT *,
        SUM(sales) OVER(
            PARTITION BY category
            -- No ORDER BY: static total for whole category
        ) AS tot_cat_sales,
        SUM(sales) OVER(
            PARTITION BY category
            ORDER BY sales
            -- ORDER BY sales: accumulates ascending
        ) AS cumm_sales
    FROM base_data
)
-- Final SELECT: format percentages for display
SELECT
    category, sub_category,
    sales, tot_cat_sales, cumm_sales,
    -- * 1.0 forces decimal division (integer ÷ integer = 0)
    FORMAT(1.0 * sales / tot_cat_sales, 'P2') AS contrib_1,
    FORMAT(1.0 * cumm_sales / tot_cat_sales, 'P2') AS contrib_2
FROM running_totals
ORDER BY category, sales;

• B2 is what we want in Result 2.

The 2-Step Logic for Result 2

Step 1: From Result 1 rows, keep only those where contrib_2 > 50%. These are all sub-categories that are AT or PAST the tipping point.

Step 2: Within those filtered rows, pick the one with the lowest sales per category (the smallest one that pushed past 50%). That's rank 1 when ranking by sales ascending.

Critical: Keep pct_contrib_2 as a NUMBER!
You need to filter: WHERE pct_contrib_2 > 0.5
If you only have FORMAT(..., 'P2') → '58.97%' — that's a TEXT string. You cannot compare text with 0.5. Always create a separate numeric column for logic, format separately for display.

Live Demo — Result 2: The Tipping Point Per Category 🎯

Full 4-CTE solution | ex_transactions, ex_products | mskl-masterclass
WITH base_data AS (
    -- Same as Result 1 step 1
    SELECT p.category, p.sub_category,
           ROUND(SUM(t.sales_amount), 0) AS sales
    FROM ex_transactions t
    JOIN ex_products p
        ON p.product_id = t.product_id
    GROUP BY p.category, p.sub_category
),
running_totals AS (
    -- Add total and cumulative columns
    SELECT *,
        SUM(sales) OVER(PARTITION BY category)
            AS total_cat_sales,
        SUM(sales) OVER(PARTITION BY category
                        ORDER BY sales)
            AS cumm_sales
    FROM base_data
),
contribution_summary AS (
    -- CRITICAL: create BOTH numeric pct AND formatted string
    -- Numeric pct_contrib_2: used in WHERE below
    -- contrib_2 (formatted): shown in final output
    SELECT *,
        FORMAT(1.0 * sales / total_cat_sales, 'P2')
            AS contrib_1,
        1.0 * cumm_sales / total_cat_sales
            AS pct_contrib_2,
        FORMAT(1.0 * cumm_sales / total_cat_sales, 'P2')
            AS contrib_2
    FROM running_totals
),
ranking_table AS (
    -- FILTER first: only rows where cumulative is past 50%
    -- Then RANK these remaining rows by sales
    -- The smallest sales = first to tip past 50% = rank 1
    SELECT *,
        RANK() OVER(
            PARTITION BY category
            ORDER BY sales DESC
        ) AS ranks
    FROM contribution_summary
    -- pct_contrib_2 is numeric here → comparison works!
    WHERE pct_contrib_2 > 0.5
)
-- ranks = 1 picks the tipping point sub-category per category
SELECT
    category, sub_category,
    sales, total_cat_sales, cumm_sales,
    contrib_1, contrib_2
FROM ranking_table
WHERE ranks = 1;

🚫 Common Mistakes — Module 7

MistakeConsequence
No ORDER BY in cumm_salesRunning total not meaningful — random order
Same window for tot and cummBoth look identical — one is wrong
Applying WHERE pct > 0.5 too earlyTries to filter before window fn runs — error or wrong result
FORMAT before using for numeric compare'58.97%' is a string — can't compare to 0.5
RANK before filteringRanks across all rows — wrong tipping point
ORDER BY sub_category in cummAlphabetical order ≠ ascending sales order

The formatting trap explained:

-- This creates a STRING '58.97%' — cannot compare!
FORMAT(1.0 * cumm / total, 'P2') AS pct

-- This creates a NUMBER 0.5897 — can compare!
1.0 * cumm / total AS pct_numeric

-- The rule: always keep TWO columns:
-- 1. Numeric for WHERE logic
-- 2. FORMAT() for display output

❓ True or False: You can write WHERE FORMAT(cumm/total,'P2') > '50.00%' to filter by 50% contribution.

✅ False. String comparison with '>' in SQL compares alphabetically — '9%' would sort "greater than" '50%' because '9' > '5'. Always compare numeric values.

Summary

What We Built 🚀

Result 1 — 3-CTE pattern

base_data — aggregate sales per sub-cat
running_totals — add tot_cat + cumm_sales window fns
Final SELECT — format % for display

Result 2 — Extended to 4 CTEs

contribution_summary — keep numeric pct AND formatted %
ranking_table — filter WHERE pct > 0.5, then RANK
Final WHERE — ranks = 1 gives one row per category

The Big Lesson: The difference between tot_cat_sales and cumm_sales is ONE thing — ORDER BY inside the window. Without ORDER BY: full group total. With ORDER BY: row-by-row running total. This distinction powers all cumulative analysis.
