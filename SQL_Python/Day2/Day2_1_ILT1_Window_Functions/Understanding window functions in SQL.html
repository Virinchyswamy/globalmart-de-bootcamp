The Core Problem — GROUP BY Collapses Rows

Rajiv needs the category total beside every sub-category row. GROUP BY can't do that — it collapses all rows into one.

❌ GROUP BY (collapses)
GROUP BY category → all sub-cat rows disappear
Furniture→ 1 row
Bookcases52
Chairs107
Tables33
Furniture TOTAL192
The sub-category rows are gone. You have 192 but you lost 52, 107, 33. Can't compute % because those numbers no longer exist in the result.
→
✅ Window Function (keeps all rows)
SUM() OVER(PARTITION BY category) → new column added
Bookcases52192 added
Chairs107192 added
Tables33192 added
All 3 rows kept. Category total (192) sits beside every row. Now: 52/192 = 27.1%, 107/192 = 55.7%, 33/192 = 17.2% — all computable.

🎯 Golden rule: A window function adds a new column to your existing rows. It never removes or collapses rows. Your row count stays exactly the same.

The OVER() Clause — What Each Part Does

-- Every window function follows this pattern:

function_name(column) OVER (
    PARTITION BY group_column   -- optional
    ORDER BY     sort_column     -- optional*
    ROWS BETWEEN ...              -- optional
)

PARTITION BY — the non-collapsing GROUP BY

Splits rows into windows. The function resets and runs independently inside each window. Omit it → function runs across all rows globally.

ORDER BY — defines row order inside each window

Required for RANK(), LAG(), LEAD(). Tells SQL which row comes "before" or "after" for ranking and lookback calculations.

🏫 The Classroom Analogy

500 students split into 4 regional classrooms. PARTITION BY region = each classroom is its own independent window. Rank is computed within each classroom, not across all 500 students.

Remove PARTITION BY → one global rank for all 500 students merged together.

📍 Where can it appear?

ClauseAllowed?

WHERE❌ No — runs before SELECT

⚠️ Two Pitfalls in Every Percentage Calculation

Pitfall 1 — Integer Division Returns 0 Silently

SQL Server sees two integers and divides as integers. Decimal is dropped. No error is raised. The result is just wrong.

-- ❌ Both integers → SQL drops the decimal
SELECT 57 / 250          -- returns: 0 ❌
SELECT 100 / 300        -- returns: 0 ❌

-- ✅ Multiply by 1.0 first → forces decimal
SELECT 57 * 1.0 / 250  -- returns: 0.228 ✅
SELECT 100 * 1.0 / 300 -- returns: 0.333 ✅

Your contribution column would silently show 0.00% for every single row. No error message. You'd only catch it if you double-check the math manually. Always add * 1.0.

Pitfall 2 — Division by Zero Crashes the Query

If the previous month had 0 orders, the entire query crashes with a runtime error. Happens silently in production.

-- ❌ If prev_month = 0 → crash!
(curr - prev) * 1.0 / prev

-- ✅ NULLIF converts 0 to NULL
-- number ÷ NULL = NULL (no crash)
(curr - prev) * 1.0
/ NULLIF(prev, 0)

How NULLIF works

NULLIF(a, b) — returns NULL when a equals b, otherwise returns a unchanged.

So NULLIF(prev, 0): if prev=0 → NULL → result is NULL. If prev=500 → 500 → normal division continues.

❓ What does SELECT 75 / 100 return in SQL Server?

✅ Returns 0 — not 0.75. Integer division. Write 75 * 1.0 / 100 to get 0.75.

All three rank rows. The difference only shows up when there are ties.

ROW_NUMBER()

Unique number for every row. Ties get different numbers — which one gets which is arbitrary (depends on SQL's internal order).

Use when: pagination, deduplication, each row needs a unique ID.

RANK()

Tied rows share the same rank. After a tie, the next rank is skipped — gap appears. B=2, C=2, then D=4 (3 is skipped).

Use when: Olympics-style — ties share rank, stakeholders expect gaps.

DENSE_RANK()

Tied rows share rank. No gaps — next distinct value gets next consecutive number. B=2, C=2, D=3.

Use when: ties share rank AND gaps would confuse the business report.

❓ You use RANK() and 3 customers tie for 2nd place. What rank does the next customer get?

✅ Rank 5 — three customers share rank 2, so ranks 3 and 4 are both skipped. Sequence: 1, 2, 2, 2, 5. With DENSE_RANK() it would be: 1, 2, 2, 2, 3.

Report 2 — Vendor Rank Within Each Region

WITH base_data AS (
    SELECT
        o.order_id,
        lp.partner_name,
        l.region
    FROM ex_orders o
    JOIN ex_logistics_partners lp
        ON o.partner_id = lp.partner_id
    JOIN ex_customers c
        ON o.customer_id = c.customer_id
    JOIN ex_locations l
        ON c.postal_code = l.postal_code
    WHERE o.order_delivered_date IS NOT NULL
),
delivery_summary AS (
    SELECT region, partner_name,
           COUNT(order_id) AS delivery_count
    FROM base_data
    GROUP BY region, partner_name
)
SELECT *,
    FORMAT(
        delivery_count * 1.0
        / SUM(delivery_count)
          OVER(PARTITION BY region), 'P2'
    ) AS delivery_share,
    RANK() OVER(
        PARTITION BY region
        ORDER BY delivery_count DESC
    ) AS vendor_rank
FROM delivery_summary;

⚡ PARTITION BY changes the entire question

Business QuestionPARTITION BY
Vendor share within each regionPARTITION BY region
Region share within each vendorPARTITION BY partner_name
Share across all regions globallyOVER() — no partition

Same raw data, same COUNT. Only PARTITION BY changes. But the % results are completely different because the denominator changes.

❓ If you remove PARTITION BY from RANK(), what happens to vendor_rank?

✅ Rank becomes global across all regions combined. Vendor A might be rank 1 in East and rank 5 overall. The region-level leaderboard completely disappears.

🚨 Report 3 — Why WHERE Fails + The CTE Fix

-- ❌ FAILS — do not run this
SELECT *,
    RANK() OVER(
        PARTITION BY region
        ORDER BY order_amount DESC
    ) AS ranking
FROM order_summary
WHERE
    RANK() OVER(        ← ERROR HERE
        PARTITION BY region
        ORDER BY order_amount DESC
    ) <= 3;
-- "Windowed functions can only appear
--  in the SELECT or ORDER BY clauses"

Why? — SQL execution order

① FROM / JOIN
② WHERE ← runs here
③ GROUP BY
④ HAVING
⑤ SELECT ← window computed here
⑥ ORDER BY

WHERE runs at step ②. Window functions run at step ⑤. The rank column doesn't exist yet when WHERE tries to filter it.

✅ Fix — compute in CTE, filter outside

Once ranking sits inside a CTE, it's a plain integer column. The outer WHERE can filter integers.

WITH rank_table AS (
    SELECT *,
        RANK() OVER(
            PARTITION BY region
            ORDER BY order_amount DESC
        ) AS ranking
    FROM sales_summary
)
-- Now "ranking" is just a number column
-- WHERE can filter any number column ✅
SELECT *
FROM rank_table
WHERE ranking <= 3;

❓ Why does WHERE ranking <= 3 work in the outer query but WHERE RANK() OVER(...) <= 3 doesn't?

✅ After the CTE, ranking is already computed — it's a stored integer. SQL can filter integers in WHERE. But RANK() OVER(...) is a function call — it needs to be evaluated in SELECT first, and WHERE runs before SELECT.

Report 3 — Top 3 Customers Per Region (Full Query)

3-CTE pattern: Base data → Aggregate → Window + Filter

WITH base_data AS (
    SELECT l.region, c.customer_name,
           t.Sales_Amount
    FROM ex_orders o
    JOIN ex_transactions t ON o.order_id = t.Order_ID
    JOIN ex_customers c  ON o.customer_id = c.customer_id
    JOIN ex_locations l  ON c.postal_code = l.postal_code
    WHERE o.order_status NOT IN ('canceled', 'unavailable')
),
sales_summary AS (
    SELECT region, customer_name,
           SUM(Sales_Amount) AS order_amount
    FROM base_data
    GROUP BY region, customer_name
),
rank_table AS (
    SELECT region, customer_name, order_amount,
        FORMAT(
            order_amount * 1.0
            / SUM(order_amount)
                OVER(PARTITION BY region),
            'P2'
        ) AS contribution,
        RANK() OVER(
            PARTITION BY region
            ORDER BY order_amount DESC
        ) AS ranking
    FROM sales_summary
)
SELECT * FROM rank_table
WHERE ranking <= 3
ORDER BY region, ranking;

💡 Try these variations

WHERE ranking = 1 → only #1 per region

Swap RANK() → DENSE_RANK() → no gaps when two customers tie 2nd

Remove PARTITION BY region → global top 3, not per region

❓ Two customers tie for rank 2 using RANK(). You filter WHERE ranking <= 3. How many rows do you get per region?

✅ 4 rows — rank 1 (1 customer), rank 2 (2 customers, tied), rank 4 (1 customer — rank 3 is skipped). Use DENSE_RANK() if you want exactly 3 rows.

LAG() and LEAD() — The Full Picture

Both functions bring a value from a different row into the current row. LAG looks back. LEAD looks forward.

Full syntax — 3 parameters

LAG(column, offset, default)
column Which column's value you want from the other row (required)
offset How many rows back. Default = 1. LAG(col, 2) = 2 rows back (optional)
default What to return instead of NULL when no previous row exists. LAG(col, 1, 0) returns 0 for first row (optional)
What LAG and LEAD produce — one row per month
Jan256 ordersLAG = NULLLEAD = 384
Feb384 ordersLAG = 256 ← JanLEAD = 579
Mar579 ordersLAG = 384 ← FebLEAD = NULL

Feb row now has both Feb's count (384) AND Jan's count (256) in the same row → MoM = (384−256)/256 = 50%

When to use which

FunctionDirectionUse Case
LAG()⬆ backwardMoM, YoY, compare with prior period
LEAD()⬇ forwardDays until next event, forecast vs actual

⚠️ Year Boundary Trap

Without PARTITION BY order_year — the window spans all years. January 2018 looks at December 2017 as its "previous row":

Dec 2017900 orders
Jan 2018→ LAG = Dec 2017 ❌

January should have LAG = NULL (no previous month in 2018). But without the partition it bleeds across years.

-- ✅ Always add PARTITION BY order_year
LAG(order_count)
  OVER(PARTITION BY order_year
       ORDER BY month_seq)

MoM Analysis — Think Before You Type

Robert asks: "Show me month-on-month % change in total orders for 2017 and 2018." — Before writing any SQL, answer these 5 questions.

①

What is one row in my result?

Each row = one month of one year. So the grain is: year + month.

GROUP BY year, month
②

What columns does each row need?

Year, month name (to display), orders this month, orders last month, % change.

5 columns needed
③

Where does "orders last month" come from?

It's not in raw data. It's this month's row shifted by one. That is exactly what LAG() does.

LAG(order_count)
④

What defines "previous month" — ORDER BY what?

Month NUMBER (1–12), not month NAME. "April" sorts before "August" alphabetically — completely wrong chronological order.

ORDER BY MONTH(date)
⑤

What resets the window — PARTITION BY what?

January should not look at December of the prior year. The LAG window must restart for each new year.

PARTITION BY order_year
⑥

What can go wrong in the division?

Integer division → add * 1.0. Previous month could be 0 → wrap with NULLIF(prev, 0).

* 1.0 + NULLIF(prev, 0)

🧠 The habit: Every time you get a time-series business question, run through these 6 questions first. The answers map directly to the SQL clauses. You write better queries faster when the thinking happens before the typing.

MoM — Full Query Annotated Line by Line

WITH base_data AS (
    -- Extract year, month number, month name from date
    -- month number (1-12) for ORDER BY → correct chronology
    -- month name (January, February…) for display only
    SELECT
        o.order_id,
        DATENAME(month, o.order_purchase_date) AS month_name,
        MONTH(o.order_purchase_date)            AS month_seq,
        YEAR(o.order_purchase_date)             AS order_year
    FROM ex_orders o
    WHERE YEAR(o.order_purchase_date) <> 2016
    -- 2016 data is partial — removing it avoids a
    -- misleading spike in the first row of each year
),
order_summary AS (
    -- One row per month per year — our base for LAG
    SELECT
        month_name, month_seq, order_year,
        COUNT(order_id) AS order_placed
    FROM base_data
    GROUP BY month_name, month_seq, order_year
),
order_lag AS (
    -- LAG shifts order_placed DOWN by 1 row
    -- So Feb sees Jan's count, Mar sees Feb's count
    -- PARTITION BY year → window resets at Jan ✅
    -- ORDER BY month_seq → 1,2,3…12 (not Jan,Feb… alphabetically)
    SELECT *,
        LAG(order_placed)
            OVER(PARTITION BY order_year
                 ORDER BY month_seq)
            AS prev_month_orders
    FROM order_summary
)
SELECT
    order_year, month_name,
    order_placed, prev_month_orders,
    FORMAT(
        (order_placed - prev_month_orders) * 1.0
        / NULLIF(prev_month_orders, 0), 'P2'
    ) AS MoM_change
FROM order_lag
ORDER BY order_year, month_seq;

Expected result (sample)

yearmonthordersprevMoM %
2017January256NULLNULL
2017February384256+50.00%
2017March579384+50.78%

January always returns NULL — no previous month in that year's window. Expected and correct.

Common mistake to check

If your Feb MoM looks right but Jan shows a number instead of NULL — you forgot PARTITION BY order_year. January is pulling December from the prior year.

❓ Feb→Mar 2017 MoM % change?

✅ 50.78% — March had significantly more orders. If you see ~40% or a negative, check PARTITION BY year is present in your LAG() clause.

Year-to-Date (YTD) — What Is It and Why?

Robert asks: "Show monthly revenue for 2017 AND the running total from January to that month."

YTD = a running odometer

Your car odometer never resets mid-year. January adds to 0. February adds to January. March adds to January + February. It keeps accumulating.

YTD revenue in March = January revenue + February revenue + March revenue.

It resets to 0 on January 1st of each new year.

Monthly vs YTD — see the difference
Jan₹10LYTD: ₹10L
Feb₹15LYTD: ₹25L
Mar₹12LYTD: ₹37L
Apr₹18LYTD: ₹55L
May₹9LYTD: ₹64L

MoM vs YTD — what each answers

QuestionUse
Did this month do better than last month?MoM (LAG)
How much have we made so far this year?YTD (running SUM)
Are we on track vs last year's annual target?YTD comparison
How did August perform standalone?Monthly revenue (simple GROUP BY)

Why can't we just use SUM with GROUP BY?

GROUP BY would give us the monthly total per row — but that collapses. We'd lose other months.

SUM() OVER(PARTITION BY year) gives the full year total on every row — also wrong. That's ₹64L on every row, not accumulating.

We need something that sums up to and including each row. That requires a frame clause — next slide.

The Frame Clause — How ROWS BETWEEN Works

The frame clause tells SQL: "when computing this window function, which rows should be included in the calculation for this current row?"

-- Full syntax with frame clause:
SUM(monthly_revenue) OVER(
    PARTITION BY order_year
    ORDER BY     month_seq
    ROWS BETWEEN
        UNBOUNDED PRECEDING  -- start of partition
        AND
        CURRENT ROW          -- this row
)

UNBOUNDED PRECEDING

Start from the very first row of the current partition (January of this year). "Unbounded" = no limit going backward.

CURRENT ROW

Stop at the row being computed right now. So for March, the frame is Jan + Feb + Mar only.

Visual — watch the frame expand row by row

← (current row) shows which row is being computed. The gold block is the CURRENT ROW. All blue blocks before it = UNBOUNDED PRECEDING. Sum of all blocks in the frame = YTD for that row.

❓ What's the difference between SUM(rev) OVER(PARTITION BY year) and SUM(rev) OVER(PARTITION BY year ORDER BY month ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW)?

✅ The first puts the full year total on every row (same number repeated). The second accumulates — January gets Jan's total, February gets Jan+Feb, March gets Jan+Feb+Mar. That's the YTD running total.

YTD Revenue — Full Query Annotated

Using the same 6-question thinking framework — then writing the SQL that follows from the answers

WITH monthly_sales AS (
    -- Grain: one row per month per year
    -- Need both month_seq (for ORDER BY) and
    -- month_name (for display)
    SELECT
        YEAR(o.order_purchase_date)             AS order_year,
        MONTH(o.order_purchase_date)            AS month_seq,
        DATENAME(month, o.order_purchase_date) AS month_name,
        SUM(t.Sales_Amount)                    AS monthly_revenue
    FROM ex_orders o
    JOIN ex_transactions t
        ON o.order_id = t.Order_ID
    WHERE YEAR(o.order_purchase_date) <> 2016
    GROUP BY
        YEAR(o.order_purchase_date),
        MONTH(o.order_purchase_date),
        DATENAME(month, o.order_purchase_date)
)
SELECT
    order_year,
    month_name,
    FORMAT(monthly_revenue, 'N0')  AS monthly_revenue,
    -- YTD: sum from Jan (UNBOUNDED PRECEDING)
    -- up to this month (CURRENT ROW)
    -- resets at start of each year (PARTITION BY year)
    FORMAT(
        SUM(monthly_revenue) OVER(
            PARTITION BY order_year
            ORDER BY     month_seq
            ROWS BETWEEN UNBOUNDED PRECEDING
                         AND CURRENT ROW
        ), 'N0'
    ) AS ytd_revenue
FROM monthly_sales
ORDER BY order_year, month_seq;

Expected result structure

yearmonthmonthlyYTD
2017January₹X₹X
2017February₹Y₹X+Y
2017March₹Z₹X+Y+Z
2018January₹A₹A ← resets!

January 2018 YTD resets to January 2018's own value — PARTITION BY year ensures this.

Try combining MoM + YTD

Add a LAG() column for MoM and a ROWS BETWEEN for YTD in the same SELECT. Both window functions can coexist in a single query — each has its own OVER() clause defining its own window independently.

❓ What happens to the YTD column if you remove PARTITION BY order_year from the SUM OVER?

✅ YTD never resets. January 2018 would continue accumulating from December 2017. By December 2018, the YTD would include all of 2017 AND 2018 combined — completely wrong. Always partition by year.

The Universal Framework — Any Time Series Question

A business question comes in. Here's how to break it down into SQL — before writing a single line of code.

① What is the grain?

One row in my result represents: one [month/region/customer/product]?
This tells you your GROUP BY columns.

② What does each row need to show?

List the output columns. For each one — does this come from raw data, GROUP BY, or a window function?

③ Which window function solves each column?

NeedFunction
Total within a group, beside each rowSUM OVER(PARTITION BY)
Rank within a groupRANK / DENSE_RANK
Compare with prior periodLAG()
Compare with future periodLEAD()
Running/cumulative totalSUM + ROWS BETWEEN

④ What resets the calculation? → PARTITION BY

Each region has its own ranking? → PARTITION BY region
Each year has its own MoM cycle? → PARTITION BY year
Global calculation? → no PARTITION BY

⑤ What defines order within the window? → ORDER BY

Ranking by sales? → ORDER BY sales DESC
Month sequence? → ORDER BY MONTH(date) — not DATENAME!
Time series? → ORDER BY date column

⑥ What are the edge cases?

First row of window → LAG returns NULL — handle it?
Year boundary → need PARTITION BY year
Division → * 1.0 for integers, NULLIF for zero denominator
Filtering on window result → CTE first, then WHERE

🎯 The pattern: Questions ①② define your CTEs. Questions ③④⑤ define your OVER() clauses. Question ⑥ defines your guardrails. Write SQL after all six are answered.
