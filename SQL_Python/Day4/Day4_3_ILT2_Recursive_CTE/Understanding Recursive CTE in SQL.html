How to build connected chains when you don't know in advance how long they are. Naman Prasad's first real ticket at Regional Health Network is about to teach him the difference.

The Assignment

Naman's Problem — a Question With No Fixed Length 🏥

The Care Coordination Office's Ask

Bhaskar Chauhan from the Care Coordination Office pings Naman with what sounds, at first, like a simple question:

"Patient P001 went to Emergency, then Radiology, then Cardiology, then ICU — all on the same day. What is the longest connected pathway for each patient?"

The catch: Naman has no idea in advance how many departments any given patient visits. Could be 2. Could be 10. His first instinct — "I'll just write a JOIN for each hop" — dies the moment he realizes he'd need a different query for every possible chain length.

The PatientVisits Table

Connection rule: visit A connects to visit B when A.to_department = B.from_department, for the same patient, on the same day.

What Standard SQL Cannot Do

Data for Patient P001 on 2025-01-15:

EmergencyRadiology

CardiologyICU
PediatricsDermatology

The real chain: Emergency → Radiology → Cardiology → ICU. And a shorter, separate one: Pediatrics → Dermatology. Nothing in the raw table tells SQL these 3 rows are one story and that 4th row is a different one.

RegionalHealthNet
SELECT * FROM PatientVisits
WHERE patient_id = 'P001'
-- Shows 4 separate rows. Cannot chain them.

What plain SQL structurally cannot do: connect rows where one's destination equals the next one's source; build the path string as it grows; count hops per chain; handle a chain of unknown length — because "unknown length" means an unknown number of JOINs, and you can't write an unknown number of anything.

The fix: a Recursive CTE. It extends the chain one hop at a time, automatically, until there's nothing left to connect — no matter how long the chain turns out to be.

The Relay Race Analogy

A Recursive CTE works like a relay race.

Runner 1 starts at the beginning and runs their leg, then hands the baton to Runner 2. Runner 2 runs and hands off to Runner 3. This keeps going until nobody is left to receive the baton.

🏁

Base Case (Anchor)

Runner 1 starts the race — the starting point. Every chain begins here.

Does NOT reference the CTE
🏃

Recursive Case

Runner 2, 3, 4… each takes the baton from the previous runner and extends the chain by one hop.

REFERENCES the CTE
🛑

Termination

The race ends the moment no new runner can be found — the recursive case returns zero rows, and SQL stops on its own.

The Structure — Two Mandatory Parts

A Recursive CTE always has exactly this shape. This is the one template worth memorizing today.

Template
WITH cte_name AS (

    -- PART 1 — BASE CASE (Anchor Member)
    -- Does NOT reference the CTE itself. Runs once.
    -- Produces the STARTING rows (hop 1)
    SELECT ... FROM source_table WHERE [starting condition]

    UNION ALL     ← mandatory connector between the two parts

    -- PART 2 — RECURSIVE CASE (Recursive Member)
    -- REFERENCES the CTE (joins against the previous iteration's rows)
    -- Runs repeatedly, extending the chain by one hop each time
    -- Stops the moment it finds zero new rows
    SELECT ... FROM source_table
    JOIN cte_name ON [connection logic]
    WHERE [termination guard]
)
SELECT ... FROM cte_name    -- use it like any normal table

UNION ALL, not UNION — UNION removes duplicates. A recursive CTE wants every row from every iteration, even if two rounds coincidentally produce identical-looking rows. UNION ALL keeps everything; plain UNION would silently drop legitimate paths.

The JOIN in Part 2 joins the source table against the CTE's own previous-iteration result. That self-reference is the entire mechanism — previous result + one more hop = new result, over and over.

Part 1 — The Base Case (Starting Rows)

Job of the Base Case: produce every starting seed. Here, every individual visit row becomes a starting seed — a "path of length 1."

RegionalHealthNet
WITH patient_pathway AS (

    -- BASE CASE: every visit row is a "path of length 1"
    SELECT
        v.date,
        v.patient_id,
        v.from_department,
        v.to_department,
        CAST(v.from_department + ' > ' + v.to_department AS VARCHAR(MAX)) AS pathway,
        1 AS transfer_count   -- every starting row = 1 hop
    FROM PatientVisits v
    -- no WHERE here — every row is a valid starting seed
pathwaytransfer_count
Emergency > Radiology1
Radiology > Cardiology1
Cardiology > ICU1
Pediatrics > Dermatology1

What CAST() is doing here

CAST(... AS VARCHAR(MAX)) — SQL needs to know the data type up front. Since the pathway string keeps growing (we append ' > department' every round), we cast to VARCHAR(MAX) so it can hold any length without truncating mid-story.

Part 2 — The Recursive Case (Extending the Chain)

Job of the Recursive Case: take each path from the previous iteration, find the next connected visit, and produce one extended path.

RegionalHealthNet
    UNION ALL

    -- RECURSIVE CASE: extend each path by one more hop
    SELECT
        v.date,
        v.patient_id,
        pp.from_department,    -- KEEP the original start (from previous iteration)
        v.to_department,       -- NEW destination (this new visit)
        CAST(pp.pathway + ' > ' + v.to_department AS VARCHAR(MAX)) AS pathway,
        pp.transfer_count + 1 AS transfer_count
    FROM PatientVisits v
    JOIN patient_pathway pp    -- ← JOIN against the CTE itself (previous iteration)
        ON  v.from_department = pp.to_department   -- new start = previous end
        AND v.patient_id     = pp.patient_id       -- same patient
        AND v.date           = pp.date             -- same day
    WHERE pp.transfer_count < 20    -- termination guard — no infinite loops
)

The connection logic, in one line: v.from_department = pp.to_department — "the NEW visit's starting point must equal where the PREVIOUS path ended." That's the whole chaining mechanism.

What pp.pathway + new dept does: previous pathway "Emergency > Radiology" + new destination "Cardiology" → "Emergency > Radiology > Cardiology." The string grows every round; the origin is never lost.

Notice Emergency → Radiology appears standalone AND embedded inside the hop-2 and hop-3 rows — different rows, different transfer_count. We keep all of them; the outer query ranks and keeps only the longest.

RegionalHealthNet
WITH patient_pathway AS (
    SELECT date, patient_id, from_department, to_department,
           CAST(from_department+' > '+to_department AS VARCHAR(MAX)) AS pathway,
           1 AS transfer_count
    FROM PatientVisits
    UNION ALL
    SELECT v.date, v.patient_id, pp.from_department, v.to_department,
           CAST(pp.pathway+' > '+v.to_department AS VARCHAR(MAX)),
           pp.transfer_count + 1
    FROM PatientVisits v
    JOIN patient_pathway pp
        ON v.from_department=pp.to_department
       AND v.patient_id=pp.patient_id AND v.date=pp.date
    WHERE pp.transfer_count < 20
)
-- Outer query: longest path per patient via ROW_NUMBER
SELECT date, patient_id, pathway AS longest_day_pathway
FROM (
    SELECT date, patient_id, pathway,
           ROW_NUMBER() OVER(
               PARTITION BY date, patient_id
               ORDER BY transfer_count DESC
           ) AS rn
    FROM patient_pathway
) ranked
WHERE rn = 1
ORDER BY patient_id;

Expected output: P001 → Emergency > Radiology > Cardiology > ICU  ·  P002 → Pediatrics > Dermatology > Pharmacy > Discharge  ·  P003 → Oncology > Laboratory > Surgery > Recovery

⚠️ Preventing Infinite Recursion

When does this actually happen? If the data has a cycle — Department A sends to B, B sends back to A — the recursive case never returns zero rows. It extends forever: A→B→A→B→A→B… This is the SQL equivalent of Naman's laptop fan spinning up at 2am.

Strategy 1 — Level / Hop Limit (most common)

-- Add this to the recursive case:
WHERE pp.transfer_count < 20

-- Or SQL Server's built-in option:
SELECT * FROM patient_pathway
OPTION (MAXRECURSION 50)

-- Default if omitted: MAXRECURSION 100
-- Unlimited (dangerous!): MAXRECURSION 0

Use when you know the max depth. Patient pathways, org charts, flight routes — rarely more than 10-15 levels deep in practice.

Strategy 2 — Track Visited Nodes

-- Base Case: start tracking
SELECT ..., to_department AS visited
FROM PatientVisits
UNION ALL
-- Recursive: extend tracking, block repeats
SELECT ..., pp.visited + ',' + v.to_department
FROM PatientVisits v
JOIN patient_pathway pp ...
WHERE pp.visited NOT LIKE
      '%,'+v.to_department+',%'

Use when the data might actually have cycles — social networks, supply chains, anything where A can point to B and B can point back to A.

Live Demo — Bonus Round

Same Pattern, Different Domain — Org Chart Hierarchy

Recursive CTE isn't a hospital-only trick — any parent-child hierarchy fits this exact template
Employees
-- employee_id | name      | manager_id
-- 1           | CEO Alice | NULL
-- 2           | VP Bob    | 1
-- 4           | Dir. Dave | 2
-- 7           | Mgr Grace | 4
-- 10          | Jack      | 7

WITH org_chart AS (
    -- Base: start at VP Bob (id=2)
    SELECT employee_id, name,
           manager_id, 1 AS level
    FROM Employees
    WHERE employee_id = 2

    UNION ALL

    -- Recursive: each person's direct reports
    SELECT e.employee_id, e.name,
           e.manager_id, oc.level + 1
    FROM Employees e
    JOIN org_chart oc
        ON e.manager_id = oc.employee_id
)
SELECT * FROM org_chart ORDER BY level;

Recursive CTE Checklist

  1. Base Case — the starting rows (anchor). Does NOT reference the CTE.
  2. UNION ALL — connects both parts, keeps every row.
  3. Recursive Case — JOINs against the CTE to extend paths.
  4. Connection logic — links rows (from = previous to).
  5. Termination guard — prevents the 2am infinite loop.

In the patient pathway CTE, what happens if Naman forgets AND v.patient_id = pp.patient_id in the recursive JOIN?

✅ The query would cross-connect patients — P001's visit to Radiology could connect to P002's visit FROM Radiology, even though they're different people. Without the patient_id guard, the recursive case chains visits across every patient in the table. The same logic applies to AND v.date = pp.date — drop that and chains cross dates too. Both guards exist to keep chains inside the same patient, the same day.
