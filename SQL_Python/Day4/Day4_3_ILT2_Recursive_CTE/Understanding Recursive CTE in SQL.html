Understanding Recursive CTE in SQL

How to build connected chains when you don't know in advance how long they are

Sarah's Problem

Sarah works at Regional Health Network. The Care Coordination Office asked her:

"Patient P001 went to Emergency, then Radiology, then Cardiology, then ICU — all on the same day. What is the longest connected pathway for each patient?"

The catch: Sarah doesn't know in advance how many departments a patient visits. It could be 2, 3, or 10.

The PatientVisits Table

ColumnMeaning
dateVisit date
patient_idWhich patient
from_departmentLeft this department
to_departmentArrived at this department
Connection rule: Visit A connects to Visit B when A.to_department = B.from_department for the same patient on the same day.

What Standard SQL Cannot Do

Here is the data for Patient P001 on 2025-01-15:

from_departmentto_department
EmergencyRadiology
RadiologyCardiology
CardiologyICU
PediatricsDermatology

The chain is: Emergency → Radiology → Cardiology → ICU

And there's a shorter separate chain: Pediatrics → Dermatology

Standard SQL problem:

SELECT * FROM PatientVisits
WHERE patient_id = 'P001'
-- Shows 4 separate rows.
-- Cannot chain them!

What normal SQL CANNOT do:

  • Connect rows where one's destination = next one's source
  • Build the path string: Emergency → Radiology → Cardiology → ICU
  • Count how many hops are in each chain
  • Handle chains of unknown length

Solution: Recursive CTE. It keeps extending the chain, one hop at a time, until there's nothing left to connect.

The Relay Race Analogy

A Recursive CTE works like a relay race.

Runner 1 starts at the beginning and runs their leg.
They hand the baton to Runner 2. Runner 2 runs and hands it to Runner 3.
This keeps going until nobody is left to receive the baton.

🏁

Base Case (Anchor)

Runner 1 starts the race. This is the starting point. Every chain begins here.

DOES NOT reference the CTE itself
🏃

Recursive Case

Runner 2, 3, 4 … each takes the baton from the previous runner and extends the chain by one hop.

REFERENCES the CTE itself
🛑

Termination

The race ends when no new runner can be found. The recursive case returns zero rows → SQL stops.

Stops automatically

Applied to P001's pathway:

🏁 Emergency → Radiology
Base Case: row 1
→
🏃 + Cardiology
Round 1 extension
→
🏃 + ICU
Round 2 extension
→
🛑 No next hop
ICU goes nowhere

The Structure — Two Mandatory Parts

A Recursive CTE always has exactly this shape. Memorise the template:

WITH cte_name AS (

    ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
    PART 1 — BASE CASE (Anchor Member)
    ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
    • Does NOT reference the CTE itself
    • Runs once
    • Produces the STARTING rows (hop 1)
    SELECT ... FROM source_table WHERE [starting condition]

    UNION ALL     ← mandatory connector between the two parts

    ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
    PART 2 — RECURSIVE CASE (Recursive Member)
    ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
    • REFERENCES the CTE (joins against previous iteration's results)
    • Runs repeatedly — each time extending the chain by one hop
    • Stops when it finds zero new rows
    SELECT ... FROM source_table
    JOIN cte_name ON [connection logic]
    WHERE [termination guard]
)
SELECT ... FROM cte_name    -- use the CTE like any normal table

UNION ALL — why not UNION? Because UNION removes duplicates. In recursive CTEs, we want ALL rows from ALL iterations accumulated together. UNION ALL keeps everything.

The JOIN in Part 2 — it joins the source table against the CTE's PREVIOUS iteration. That's how the chain grows: previous result + one more hop = new result.

Part 1 — The Base Case (Starting Rows)

Job of the Base Case: Produce all the starting seeds. In our problem — every individual visit in the table becomes a starting seed (hop 1 path).

WITH patient_pathway AS (

    -- BASE CASE: every single visit row is a "path of length 1"
    SELECT
        v.date,
        v.patient_id,
        v.from_department,    -- where this path started
        v.to_department,      -- where this path currently ends
        CAST(v.from_department + ' > ' + v.to_department AS VARCHAR(MAX)) AS pathway,
        1 AS transfer_count   -- ← each starting row has 1 hop
    FROM PatientVisits v
    -- NOTE: no WHERE here — every row is a valid starting seed

What the Base Case produces for P001:

pathwaytransfer_count
Emergency > Radiology1
Radiology > Cardiology1
Cardiology > ICU1
Pediatrics > Dermatology1

What CAST does:

CAST(... AS VARCHAR(MAX)) — SQL needs to know the data type upfront. Since the pathway string will grow (we keep adding ' > department' to it), we cast it to VARCHAR(MAX) so it can hold any length.

The from_department column in the Base Case is also remembered because the Recursive Case will KEEP it — it always stores "where the entire path originally started."

Part 2 — The Recursive Case (Extending the Chain)

Job of the Recursive Case: Take each path from the previous iteration, find the next connected visit, and produce an extended path.

    UNION ALL

    -- RECURSIVE CASE: extend each path by one more hop
    SELECT
        v.date,
        v.patient_id,
        pp.from_department,    -- KEEP original starting dept (from previous iteration)
        v.to_department,       -- NEW destination (from this new visit)
        CAST(pp.pathway + ' > ' + v.to_department AS VARCHAR(MAX)) AS pathway,
        pp.transfer_count + 1 AS transfer_count   -- increment hop counter
    FROM PatientVisits v
    JOIN patient_pathway pp    -- ← JOIN against the CTE (previous iteration)
        ON  v.from_department = pp.to_department   -- new start = previous end
        AND v.patient_id     = pp.patient_id       -- same patient
        AND v.date           = pp.date             -- same day
    WHERE pp.transfer_count < 20    -- ← termination guard (prevent infinite loop)
)

The connection logic — key line:

v.from_department = pp.to_department

Translation: "The NEW visit's starting point must be the SAME as where the PREVIOUS path ended." This is how we chain visits together.

What pp.pathway + new dept does:

Previous pathway: Emergency > Radiology
New destination: Cardiology
Result: Emergency > Radiology > Cardiology

The path string GROWS each iteration — we never lose track of where the chain started.

Step-by-Step: How Iteration Works for P001

SQL runs the recursive case in rounds. Each round produces new paths. UNION ALL collects all paths from all rounds.

BASE CASE Starting paths (hop 1 — every visit is a seed)
Emergency → Radiology  hop 1
Radiology → Cardiology  hop 1
Cardiology → ICU  hop 1
Pediatrics → Dermatology  hop 1
ROUND 1 Extend paths where "base end = new start" (hop 2)
Emergency → Radiology → Cardiology  hop 2  (Radiology→Cardiology connected to Emergency→Radiology)
Radiology → Cardiology → ICU  hop 2  (Cardiology→ICU connected to Radiology→Cardiology)
ROUND 2 Extend paths where "round 1 end = new start" (hop 3)
Emergency → Radiology → Cardiology → ICU  hop 3  (Cardiology→ICU connected to E→R→C)
ROUND 3 ICU has no outgoing visits → recursive case finds zero rows → STOP
Total rows in CTE for P001 = 4 + 2 + 1 = 7 rows. UNION ALL has collected paths from all rounds. The outer query will then pick the longest one.

All Paths Collected — What the CTE Contains

After UNION ALL, the CTE for P001 holds all 7 rows from all iterations. The longest path per patient is what we want.

ALL 7 ROWS IN THE CTE FOR P001:

Emergency → Radiology hop 1
Radiology → Cardiology hop 1
Cardiology → ICU hop 1
Pediatrics → Dermatology hop 1
Emergency → Radiology → Cardiology hop 2
Radiology → Cardiology → ICU hop 2
Emergency → Radiology → Cardiology → ICU hop 3 ← LONGEST

Why does UNION ALL keep duplicates?

Notice Emergency → Radiology appears in hop 1 AND is embedded in the hop-2 and hop-3 paths. These are different rows (different transfer_count). We need ALL of them — the outer query will rank by length and pick only the longest.

Pattern for all 3 patients:

PatientLongest PathwayHops
P001Emergency → … → ICU3
P002Pediatrics → … → Discharge3
P003Oncology → … → Recovery3

Full Query — Finding the Longest Path Per Patient

The CTE builds all paths. The outer query picks the longest one per patient using ROW_NUMBER().

WITH patient_pathway AS (
    -- Base Case: every visit = hop 1
    SELECT date, patient_id, from_department, to_department,
           CAST(from_department + ' > ' + to_department AS VARCHAR(MAX)) AS pathway,
           1 AS transfer_count
    FROM PatientVisits
    UNION ALL
    -- Recursive Case: extend by one hop
    SELECT v.date, v.patient_id, pp.from_department, v.to_department,
           CAST(pp.pathway + ' > ' + v.to_department AS VARCHAR(MAX)),
           pp.transfer_count + 1
    FROM PatientVisits v
    JOIN patient_pathway pp
        ON v.from_department=pp.to_department AND v.patient_id=pp.patient_id AND v.date=pp.date
    WHERE pp.transfer_count < 20
)
-- Outer query: pick LONGEST path per patient using ROW_NUMBER
SELECT date, patient_id, pathway AS longest_day_pathway
FROM (
    SELECT date, patient_id, pathway,
           ROW_NUMBER() OVER(
               PARTITION BY date, patient_id
               ORDER BY transfer_count DESC   -- longest path gets rn = 1
           ) AS rn
    FROM patient_pathway
) ranked
WHERE rn = 1
ORDER BY patient_id
Expected output:  P001 → Emergency > Radiology > Cardiology > ICU  |  P002 → Pediatrics > Dermatology > Pharmacy > Discharge  |  P003 → Oncology > Laboratory > Surgery > Recovery

Preventing Infinite Recursion

When does infinite recursion happen?

If your data has a cycle — e.g., Department A sends to B, B sends back to A — then the recursive case never finds zero rows. It keeps extending forever: A→B→A→B→A→B…

Strategy 1 — Level / Hop Limit (most common)

-- Add this to the recursive case:
WHERE pp.transfer_count < 20

-- Or use SQL Server's built-in option:
SELECT * FROM patient_pathway
OPTION (MAXRECURSION 50)

-- Default if you omit: MAXRECURSION 100
-- Unlimited (dangerous!): MAXRECURSION 0

Use when you know the maximum depth. Patient pathways, org charts, flight routes — rarely more than 10-15 levels.

Strategy 2 — Track Visited Nodes

-- Base Case: start tracking
SELECT ..., to_department AS visited
FROM PatientVisits

UNION ALL

-- Recursive: extend tracking
SELECT ..., pp.visited + ',' + v.to_department
FROM PatientVisits v
JOIN patient_pathway pp ...
WHERE pp.visited NOT LIKE
      '%,' + v.to_department + ',' + '%'

Use when data might have cycles — social networks, supply chains, systems where A can reference B and B can reference A.

Bonus: Org Chart Hierarchy — Same Pattern

Recursive CTE is perfect for any parent-child hierarchy. Example: find all employees under VP Bob.

-- Employees table:
-- employee_id | name      | manager_id
-- 1           | CEO Alice | NULL
-- 2           | VP Bob    | 1
-- 4           | Dir. Dave | 2
-- 7           | Mgr Grace | 4
-- 10          | Jack      | 7

WITH org_chart AS (
    -- Base: start at VP Bob (id=2)
    SELECT employee_id, name,
           manager_id, 1 AS level
    FROM Employees
    WHERE employee_id = 2

    UNION ALL

    -- Recursive: find each person's direct reports
    SELECT e.employee_id, e.name,
           e.manager_id, oc.level + 1
    FROM Employees e
    JOIN org_chart oc
        ON e.manager_id = oc.employee_id
)
SELECT * FROM org_chart ORDER BY level

Output — all reports under VP Bob:

namelevelWhat this means
VP Bob1Starting manager
Director Dave2Direct report of Bob
Director Eve2Direct report of Bob
Manager Grace3Report of Dave
Manager Henry3Report of Eve
Analyst Jack4Report of Grace

Connection logic: e.manager_id = oc.employee_id — "this employee's manager = someone already in the CTE." That's how you go one level deeper each iteration.

Recursive CTE checklist:

1
Base Case — the starting rows (anchor). Does NOT reference the CTE.
2
UNION ALL — connects both parts.
3
Recursive Case — JOINs against the CTE to extend paths.
4
Connection logic — links rows (from = previous to).
5
Termination guard — prevents infinite loops.

Quiz — In the patient pathway CTE, what would happen if you forgot AND v.patient_id = pp.patient_id in the recursive JOIN?

The query would cross-connect patients. P001's visit to Radiology would connect to P002's visit FROM Radiology — even though they are different patients. Without the patient_id guard, the recursive case chains visits across all patients. Same logic applies to AND v.date = pp.date — omitting it would cross dates too. Both guards are essential to keep chains within the same patient on the same day.
