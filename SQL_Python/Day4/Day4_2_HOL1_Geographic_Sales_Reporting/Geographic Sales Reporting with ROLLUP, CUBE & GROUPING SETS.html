The Assignment

Three Requests, One Underlying Table 📊

Why Expansion Planning Needs This

GlobalMart leadership is planning next year's expansion — new fulfillment centers, new marketing budget allocation. Everyone needs the same sales-by-geography numbers, sliced a different way for their own decision. Aayush, three weeks into the Sales Analytics team, is the one person all three requests land on.

Three Tasks, Three Stakeholders

  • Task 1: Ananya Seth, VP of Sales, wants a clean region → state → city drill-down — ROLLUP
  • Task 2: the Chief Strategy Officer wants every possible geographic slice for exploratory analysis — CUBE
  • Task 3: Finance wants exactly 4 specific levels for their budget model, not one row more — GROUPING SETS

Tables used (all 3 tasks): ex_transactions → ex_orders → ex_customers → ex_locations  ·  Filter: order_status = 'delivered' on every single one — cancelled orders don't get to vote on the expansion strategy.

Database Setup — The 4-Table Join

All three tasks reuse this exact join. Build and verify it once, then just swap the GROUP BY clause for each task — this is the whole reason Aayush can knock out 3 stakeholder requests before lunch.

mskl-masterclass
-- Phase 1: verify the join before adding any GROUP BY
SELECT
    l.region,
    l.state,
    l.city,
    t.sales_amount
FROM ex_transactions t
JOIN ex_orders o
    ON t.order_id = o.order_id
    AND o.order_status = 'delivered'  -- filter inside the JOIN
JOIN ex_customers c ON o.customer_id = c.customer_id
JOIN ex_locations l  ON c.postal_code = l.postal_code
ORDER BY l.region, l.state, l.city;
TableKey column(s)Purpose
ex_transactionsorder_id, sales_amountRevenue source
ex_ordersorder_id, customer_id, order_statusLink + filter delivered
ex_customerscustomer_id, postal_codeBridge to location
ex_locationspostal_code, region, state, cityGeographic hierarchy

Gotcha: there's also a locations_01 table floating around from earlier modules — it doesn't have a city column. Use ex_locations for all three tasks today.

1Hierarchical Sales Report — ROLLUP

The ask: Ananya wants a report that rolls up cleanly — city level, then state level, then region level, then a grand total. Delivered orders only. "Something I can hand straight to the board without translating it first," she says.

Expected output shape:

regionstatecitytotal_sales
CentralIllinoisChicago125,000
CentralIllinoisNULL250,000 — state total
CentralNULLNULL500,000 — region total
NULLNULLNULL2,500,000 — grand total

Build in 4 phases: join + verify → filter + select → apply ROLLUP → ROUND() and ORDER BY.

mskl-masterclass
-- Task 1: city → state → region → grand total
SELECT
    l.region,
    l.state,
    l.city,
    ROUND(SUM(t.sales_amount), 2) AS total_sales
FROM ex_transactions t
JOIN ex_orders o
    ON t.order_id = o.order_id
    AND o.order_status = 'delivered'
JOIN ex_customers c ON o.customer_id = c.customer_id
JOIN ex_locations l  ON c.postal_code = l.postal_code
GROUP BY ROLLUP(l.region, l.state, l.city)
ORDER BY l.region, l.state, l.city;

Common mistakes on Task 1: forgetting order_status = 'delivered' (pulls in cancelled orders); wrong column order in ROLLUP (wrong hierarchy — remember, right-to-left roll-up); missing ROUND() (the board does not need 6 decimal places of precision); using locations_01 by muscle memory from an earlier module.

2Comprehensive Analysis — CUBE

The ask: the Chief Strategy Officer doesn't want a hierarchy — they want to explore every combination. Sales by city across all regions, by state across all regions, all of it, before they've even decided what question they're really asking. Classic strategy-team energy.

What CUBE adds on top of ROLLUP — for 3 columns, 2³ = 8 groupings:

GroupingIn ROLLUP?In CUBE?
(region, state, city)✓✓
(region, state)✓✓
(region)✓✓
()✓✓
(region, city)✗✓
(state, city)✗✓
(state)✗✓
(city)✗✓

When does (state) without (region) matter? "How much does Illinois sell nationally, across ALL regions?" is exactly the (state)-only grouping, region=NULL. ROLLUP structurally cannot answer this — CUBE can, because it never assumes a hierarchy exists.

mskl-masterclass
-- Task 2: every geographic combination — 2³ = 8 groupings
SELECT
    l.region,
    l.state,
    l.city,
    ROUND(SUM(t.sales_amount), 2) AS total_sales
FROM ex_transactions t
JOIN ex_orders o
    ON t.order_id = o.order_id
    AND o.order_status = 'delivered'
JOIN ex_customers c ON o.customer_id = c.customer_id
JOIN ex_locations l  ON c.postal_code = l.postal_code
GROUP BY CUBE(l.region, l.state, l.city)
ORDER BY l.region, l.state, l.city;

Same 4-table join, ONE word changed: ROLLUP became CUBE. Everything else — the join, the filter, the SELECT list — is identical. That's the entire point of learning these as a family, not three unrelated features.

3Custom Report — GROUPING SETS

The ask: Finance needs exactly 4 grouping levels for their budget allocation model — no more, no less. Their model breaks if an unexpected row shows up, so "close enough" is not an acceptable answer here.

Finance's exact 4 groupings:

#GroupingPurpose
1(region, state, city)City-level detail
2(region, state)State subtotals within region
3(region)Region subtotals
4()Grand total

Wait — isn't this just ROLLUP? For this specific request, yes, the output is identical. But GROUPING SETS is what you reach for the moment Finance adds "actually, drop the city-level rows, we only need state and above" — a one-line edit, versus rethinking your whole hierarchy.

mskl-masterclass
-- Task 3: Finance's exact 4-level custom report
SELECT
    l.region,
    l.state,
    l.city,
    ROUND(SUM(t.sales_amount), 2) AS total_sales
FROM ex_transactions t
JOIN ex_orders o
    ON t.order_id = o.order_id
    AND o.order_status = 'delivered'
JOIN ex_customers c ON o.customer_id = c.customer_id
JOIN ex_locations l  ON c.postal_code = l.postal_code
GROUP BY GROUPING SETS (
    (l.region, l.state, l.city),  -- city detail
    (l.region, l.state),           -- state subtotal
    (l.region),                     -- region subtotal
    ()                               -- grand total
)
ORDER BY l.region, l.state, l.city;

Common mistakes on Task 3: forgetting the trailing () (no grand total — Finance notices immediately); mismatched parentheses nesting (syntax error); tossing in an extra grouping "just in case" (breaks Finance's model, which expects exactly 4); forgetting the comma between grouping sets.

Live Demo — Bonus Round

Making the Report Actually Readable

Same Task 1 query · GROUPING() added · Aayush, showing off slightly
mskl-masterclass
-- Ananya's board deck can't have a column full of "NULL"
-- GROUPING() + CASE WHEN turns subtotal rows into labels
SELECT
    CASE WHEN GROUPING(l.region) = 1 THEN 'ALL REGIONS'
         ELSE l.region END AS region,
    CASE WHEN GROUPING(l.state) = 1 THEN 'ALL STATES'
         ELSE l.state END AS state,
    CASE WHEN GROUPING(l.city) = 1 THEN 'ALL CITIES'
         ELSE l.city END AS city,
    ROUND(SUM(t.sales_amount), 2) AS total_sales
FROM ex_transactions t
JOIN ex_orders o     ON t.order_id = o.order_id AND o.order_status = 'delivered'
JOIN ex_customers c ON o.customer_id = c.customer_id
JOIN ex_locations l  ON c.postal_code = l.postal_code
GROUP BY ROLLUP(l.region, l.state, l.city);

The CFO walks in with a new ask: "Show me (region, state) combinations and (state) totals alone, in one query — but skip city-level and skip the grand total entirely." Which operator?

✅ GROUPING SETS — this is a non-hierarchical, custom combination. ROLLUP structurally cannot produce (state) without (region) above it. CUBE would hand back extra combinations the CFO explicitly didn't ask for.

GROUP BY GROUPING SETS ((l.region, l.state), (l.state))

⚡ One Optimization Habit Worth Keeping From Day 3

All three of today's operators scan the same joined result set once — but "once" on a 4-table join over the full transaction history is still expensive if you forget what you learned yesterday.

🔴 Aayush's first draft (before coffee)

SELECT *
FROM ex_transactions t
JOIN ex_orders o ON ...
JOIN ex_customers c ON ...
JOIN ex_locations l ON ...
GROUP BY CUBE(l.region, l.state, l.city)

SELECT * on a CUBE query means every one of the 8 groupings drags every column along for the ride. On a table this size, that's the difference between a query and a coffee break.

🟢 Aayush's second draft (after coffee)

SELECT l.region, l.state, l.city,
       SUM(t.sales_amount) AS total_sales
FROM ex_transactions t
JOIN ex_orders o ON ... AND o.order_status = 'delivered'
JOIN ex_customers c ON ...
JOIN ex_locations l ON ...
GROUP BY CUBE(l.region, l.state, l.city)

Only the 4 columns anyone actually asked for, plus the WHERE-equivalent filter baked into the JOIN. Same 8 groupings, a fraction of the data movement.

Wrap-Up

3 Stakeholders, 1 Join, 3 Keywords 🎯

Task 1 — ROLLUP

Same 4-table join → GROUP BY ROLLUP(region, state, city) → Ananya gets her board-ready hierarchy.

Task 2 — CUBE

One word changed → GROUP BY CUBE(region, state, city) → the CSO gets every cross-cut they could ask for.

Task 3 — GROUPING SETS

Explicit list → GROUP BY GROUPING SETS(...) → Finance gets exactly 4 rows-shapes, nothing their model can't handle.

Aayush closed all three tickets before lunch. Nobody needed to know it was the same join three times over.
