The Story

Someone Started a Rumour at GlobalMart

"Did you hear? The CEO is relocating the entire GlobalMart office to Antarctica. Free penguins for everyone."

Someone said this to a colleague. That colleague told another. And another. And another.

The gossip_chain table captures who told whom:

The Question We Need to Answer:

Starting from Yogesh — who are ALL the people who eventually heard this rumour, directly or indirectly? How many hops did it take to reach each person?

Why can't normal SQL answer this?

Because we don't know in advance how long the chain is. Yogesh told Sujit (1 hop). Sujit told Sukrit (2 hops). Sukrit told Sushant (3 hops)… We need the query to keep going automatically until the chain ends. That's exactly what Recursive CTE does.

Write the Recursive CTE

The Challenge:

Write a Recursive CTE using #gossip_chain to find all people who heard the rumour starting from Yogesh.

Your output must show: the person's name, the full chain path (how they heard it), and how many hops from Yogesh.

Expected output format:

person_who_heard_ithops_from_yogeshhow_they_heard_it
Sujit1Yogesh → Sujit
Sukrit2Yogesh → Sujit → Sukrit
Sushant3Yogesh → Sujit → Sukrit → Sushant
… continues until the chain ends

Rules:

  • Use #gossip_chain as your source table
  • Start with WHERE from_person = 'Yogesh' in the Base Case
  • Add a termination guard: WHERE level < 20
  • Order results by hops_from_yogesh ASC

Think Before You Code — 3 Questions

Discuss with your group for 2 minutes. Answer these before writing a single line.

1
What is the Base Case here?
Where does the chain START? What rows does the Base Case produce? How many rows come out of the Base Case for this data?
2
What is the Recursive Case doing?
It takes the previous result and finds "who did this person tell next?" — what is the JOIN condition? Which column from the CTE connects to which column from the table?
3
When does the recursion STOP?
Gaurav heard the rumour but told nobody. What happens when the Recursive Case tries to find "who did Gaurav tell?" — what does it return? And why does that make SQL stop?

Group challenge: whichever group can answer all 3 correctly out loud first gets +2 bonus points before coding begins.

Hint 1 — The Base Case

Base Case = the starting row

Yogesh started the rumour. So the Base Case asks: "What rows in gossip_chain have Yogesh as the from_person?" There is exactly one: Yogesh → Sujit. That one row is our starting seed.

-- BASE CASE: Yogesh told one person (Sujit)
SELECT
    from_person,
    to_person,
    CAST(from_person + ' → ' + to_person AS VARCHAR(MAX)) AS chain,
    1 AS level
FROM #gossip_chain
WHERE from_person = 'Yogesh'   -- only Yogesh's direct tell

What this produces:

from_personto_personchainlevel
YogeshSujitYogesh → Sujit1

Just ONE row. But this becomes the seed for the recursive case. From Sujit, we'll find who Sujit told. From that person, who they told. And so on.

Hint 2 — The Recursive Case

Recursive Case = "who did this person tell next?"

Take the previous result (e.g., Sujit). Find the row in gossip_chain where from_person = Sujit. That gives us Sukrit. Extend the chain: Yogesh → Sujit → Sukrit. Repeat.

Connection rule: g.from_person = cte.to_person — "the new row's sender = the previous result's receiver"

UNION ALL

-- RECURSIVE CASE: who did each person tell next?
SELECT
    g.from_person,
    g.to_person,
    CAST(rt.chain + ' → ' + g.to_person AS VARCHAR(MAX)) AS chain,
    rt.level + 1 AS level
FROM #gossip_chain g
JOIN rumour_trail rt
    ON  g.from_person = rt.to_person   -- ← connection: new sender = previous receiver
WHERE rt.level < 20                        -- ← termination guard

The connection rule: g.from_person = rt.to_person means "I want to find the row where the SENDER is the same person who was the RECEIVER in the previous step." This is how we follow the chain one hop at a time.

When it stops: When Gaurav is the rt.to_person, SQL looks for a row in gossip_chain where from_person = 'Gaurav'. There is none. Recursive Case returns 0 rows. SQL stops automatically.

The Full Answer

WITH rumour_trail AS (

    -- ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
    -- BASE CASE: Yogesh is where the rumour started
    -- ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
    SELECT
        from_person,
        to_person,
        CAST(from_person + ' → ' + to_person AS VARCHAR(MAX)) AS chain,
        1 AS level
    FROM  #gossip_chain
    WHERE from_person = 'Yogesh'

    UNION ALL

    -- ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
    -- RECURSIVE CASE: who did each person tell next?
    -- ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
    SELECT
        g.from_person,
        g.to_person,
        CAST(rt.chain + ' → ' + g.to_person AS VARCHAR(MAX)) AS chain,
        rt.level + 1
    FROM #gossip_chain g
    JOIN rumour_trail rt
        ON g.from_person = rt.to_person   -- connection: sender = previous receiver
    WHERE rt.level < 20
)
-- OUTER QUERY: show everyone who heard the rumour
SELECT
    to_person   AS person_who_heard_it,
    level       AS hops_from_yogesh,
    chain       AS how_they_heard_it
FROM   rumour_trail
ORDER BY level, to_person

Wrap-Up

What You Just Built — In Plain English

🏁

Base Case

The starting row. WHERE from_person = 'Yogesh' gave us hop 1: Yogesh → Sujit. The chain starts here. Runs once.

🔄

Recursive Case

Extends the chain one hop at a time. g.from_person = rt.to_person is the rule that chains each new row to the previous result. Runs once per hop.

🛑

Termination

When Gaurav's row is in the CTE, SQL looks for from_person = 'Gaurav' — finds nothing. Recursive Case returns 0 rows. SQL stops automatically.

The one rule that connects everything:

-- sender of new row = receiver of previous row
JOIN rumour_trail rt
    ON g.from_person = rt.to_person

This is the SAME pattern as patient pathways, flight routes, org charts, supply chains. Change the table and column names — the structure is identical.
