EXISTS and NOT EXISTS

A smarter way to ask: "does related data exist for this row?"

Sarah from GlobalMart got three urgent questions from leadership before annual planning:

1
Dormant customers — signed up but never placed any order
2
VIP customers — placed more than 20 delivered orders
3
Dead stock products — never appeared in any delivered sale

What We Will Learn

PatternWhat it does

Tables: ex_customers, ex_orders, ex_transactions, ex_products

First — What Does "Correlated" Mean?

Think of a bouncer at a club.

For each person in the queue, the bouncer checks the guest list.
He checks one person at a time — not the whole queue at once.
For Person A → check list. For Person B → check list. For Person C → check list.
Each check depends on who is standing in front of him.

Non-Correlated Subquery

Runs once. Returns a fixed list. Outer query filters against that list.

SELECT customer_name
FROM ex_customers
WHERE customer_id IN (
    SELECT customer_id
    FROM ex_orders
    -- no reference to outer table
)

Subquery runs once → returns a list of IDs → outer query filters by that list.

Correlated Subquery

Runs once per row in the outer query. It references a column from the outer query.

SELECT c.customer_name
FROM ex_customers c
WHERE EXISTS (
    SELECT 1
    FROM ex_orders o
    WHERE o.customer_id = c.customer_id
    -- ↑ references outer row!
)

For Customer A → run subquery. For Customer B → run subquery. And so on.

The word "correlated" = the inner query is linked to (correlated with) the current row of the outer query. Change the outer row, the inner query changes too.

EXISTS vs NOT EXISTS — In Plain English

✅

EXISTS

"Is there at least one matching row in the related table?"

If YES → include this row
If NO → skip this row

Use when: you want rows that HAVE related data
🚫

NOT EXISTS

"Are there zero matching rows in the related table?"

If ZERO → include this row
If any rows found → skip this row

Use when: you want rows that HAVE NO related data

The Template — memorise this structure

SELECT columns
FROM   outer_table o
WHERE  EXISTS (          -- or NOT EXISTS
    SELECT 1           -- SELECT 1 is standard: we only care if a row exists, not what it contains
    FROM   inner_table i
    WHERE  i.foreign_key = o.primary_key  -- ← this is the correlated link
)

Why SELECT 1? — Because we do not need any value from the subquery. We only need to know: did any row come back? The 1 is a placeholder. You could write SELECT * too — same result.

Analysis 1

NOT EXISTS — Find Dormant Customers

Business ask: Find all customers who signed up but placed zero orders — re-engagement email campaign targets.

SELECT
    c.customer_id,
    c.customer_name,
    c.postal_code
FROM ex_customers c                         -- outer table: every customer
WHERE NOT EXISTS (                             -- only keep customers where subquery finds ZERO rows
    SELECT 1
    FROM   ex_orders o
    WHERE  o.customer_id = c.customer_id    -- ← correlated link: ties order to THIS customer
)

In plain English — what SQL does per customer:

1
Take Customer A from ex_customers
2
Run the subquery: "Go to ex_orders and count orders where customer_id = A"
3
If zero orders found → NOT EXISTS = TRUE → include Customer A in results
4
If any orders found → NOT EXISTS = FALSE → skip Customer A
5
Repeat for Customer B, C, D … for every customer in the table

Why NOT LEFT JOIN + IS NULL?

You could also find dormant customers using LEFT JOIN + WHERE order_id IS NULL. Both work. But NOT EXISTS is:

  • Cleaner to read ("does NOT exist")
  • NULL-safe (no accidental silent failures)
  • Can stop as soon as one match is found (efficient)

How NOT EXISTS Evaluates — Row by Row

SQL processes each customer in ex_customers one at a time, runs the subquery for each, and decides:

EVALUATION PER ROW:

CUST-0023 → 0 orders in ex_orders → NOT EXISTS = TRUE → INCLUDE ✓
CUST-0041 → 5 orders found → NOT EXISTS = FALSE → SKIP ✗
CUST-0100 → 0 orders in ex_orders → NOT EXISTS = TRUE → INCLUDE ✓
CUST-0156 → 12 orders found → NOT EXISTS = FALSE → SKIP ✗
CUST-0200 → 0 orders in ex_orders → NOT EXISTS = TRUE → INCLUDE ✓

Key insight: "stops early"

For NOT EXISTS: SQL only needs to find one matching row to stop and return FALSE. It does not count all orders. As soon as one order is found → done → skip this customer. This makes NOT EXISTS very efficient.

Analysis 2

EXISTS + HAVING — Find VIP Customers

Business ask: Find customers with more than 20 delivered orders — candidates for the VIP Loyalty Program.

SELECT
    c.customer_id,
    c.customer_name
FROM ex_customers c
WHERE EXISTS (
    SELECT 1
    FROM   ex_orders o
    WHERE  o.customer_id = c.customer_id  -- correlated link
    AND    o.order_status = 'delivered'
    GROUP BY o.customer_id
    HAVING   COUNT(o.order_id) > 20     -- ← aggregate check INSIDE the subquery
)

Row-by-row evaluation:

CUST-0041 25 delivered orders → HAVING 25 > 20 = TRUE EXISTS = TRUE ✓ VIP
CUST-0100 15 delivered orders → HAVING 15 > 20 = FALSE EXISTS = FALSE ✗ Skip
CUST-0089 32 delivered orders → HAVING 32 > 20 = TRUE EXISTS = TRUE ✓ VIP

⚠ Common Mistake — WHERE Does HAVING Go?

GROUP BY and HAVING must be inside the subquery.

Why? The outer query operates on ex_customers — one row per customer. It has no aggregate data. Only the subquery has the COUNT of orders per customer.

If you put HAVING in the outer query, SQL cannot find a COUNT to compare against.

Analysis 3

NOT EXISTS + JOIN Inside — Dead Stock Products

Business ask: Find products that have never appeared in a delivered sale.
The challenge: ex_transactions has product_id, but order_status is in ex_orders.

SELECT
    p.product_id,
    p.product_name,
    p.category
FROM ex_products p                          -- outer: every product
WHERE NOT EXISTS (
    SELECT 1
    FROM   ex_transactions t
    JOIN   ex_orders o  ON  t.Order_ID = o.order_id  -- ← JOIN inside the subquery!
    WHERE  t.Product_ID  = p.product_id            -- correlated link
    AND    o.order_status = 'delivered'              -- only count delivered sales
)

Why is the JOIN inside the subquery?

1
ex_transactions has Product_ID — needed to link to the current product (correlation)
2
ex_orders has order_status — needed to check if the sale was delivered (filter)
3
We need both tables inside the subquery to answer: "Was this product ever in a delivered order?"
4
Joining them inside the subquery lets us check this in a single, clean NOT EXISTS

Per-product evaluation:

Product P001:
 → subquery finds 3 delivered transactions
 → NOT EXISTS = FALSE → SKIP (it was sold)

Product P099:
 → subquery finds 0 delivered transactions
 → NOT EXISTS = TRUE → INCLUDE (dead stock!)

Product P202:
 → subquery finds 0 delivered transactions
 → NOT EXISTS = TRUE → INCLUDE (dead stock!)

The NOT IN NULL Trap — Why NOT EXISTS is Safer

Warning: NOT IN silently returns 0 rows if the subquery contains any NULL

No error. No warning. Just wrong results. This is one of SQL's most dangerous traps.

NOT IN — breaks with NULLs:

-- Suppose ex_orders has:
-- customer_id: 101, 102, NULL, 105

WHERE customer_id NOT IN (101, 102, NULL, 105)

-- SQL expands this to:
WHERE customer_id != 101
  AND customer_id != 102
  AND customer_id != NULL   ← UNKNOWN!
  AND customer_id != 105

-- Any comparison with NULL = UNKNOWN
-- UNKNOWN makes the whole WHERE = UNKNOWN
-- Result: 0 rows returned!

Even though many customers are genuinely absent from the orders table — NOT IN returns nothing because of one NULL in the subquery.

NOT EXISTS — NULL-safe:

SELECT c.customer_id
FROM ex_customers c
WHERE NOT EXISTS (
    SELECT 1
    FROM ex_orders o
    WHERE o.customer_id = c.customer_id
)
-- Checks ROW EXISTENCE, not value equality
-- NULL rows in ex_orders do NOT affect this
-- Works correctly every time

Rule to memorise:

When checking for absence of related records, always use NOT EXISTS instead of NOT IN. It is NULL-safe, clear to read, and often faster.

Quiz + Summary

Q1 — What is the key difference between a correlated and a non-correlated subquery?

A — A correlated subquery executes once; non-correlated executes once per outer row
B — A correlated subquery references the outer query's row; non-correlated does not
C — A correlated subquery always uses EXISTS; non-correlated always uses IN
D — A correlated subquery is always faster
B is correct. A correlated subquery references a column from the outer query (e.g. WHERE o.customer_id = c.customer_id). This makes it re-run for every outer row. A non-correlated subquery is independent — it runs once and returns a fixed result.

Q2 — In the VIP customer query, why must GROUP BY and HAVING go INSIDE the subquery?

A — SQL Server does not allow HAVING in outer queries
B — The outer query has no aggregate data — only the subquery has COUNT per customer
C — HAVING only works with EXISTS, not in outer queries
D — It makes the query run faster
B is correct. The outer query operates on ex_customers — one row per customer, no aggregations. Only the subquery knows how many orders each customer has (via COUNT). HAVING must be where the COUNT happens.
