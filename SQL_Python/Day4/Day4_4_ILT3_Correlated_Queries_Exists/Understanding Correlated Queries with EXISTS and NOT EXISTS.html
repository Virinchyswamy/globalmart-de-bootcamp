First — What Does "Correlated" Mean?

Think of a bouncer at a club.

For each person in the queue, the bouncer checks the guest list — one person at a time, never the whole queue at once. For Person A → check list. For Person B → check list. Each check depends on who is standing in front of him right now.

Non-Correlated Subquery

Runs once. Returns a fixed list. The outer query filters against that list.

SELECT customer_name
FROM ex_customers
WHERE customer_id IN (
    SELECT customer_id
    FROM ex_orders
    -- no reference to outer table
)

Correlated Subquery

Runs once per outer row. References a column from the outer query.

SELECT c.customer_name
FROM ex_customers c
WHERE EXISTS (
    SELECT 1
    FROM ex_orders o
    WHERE o.customer_id = c.customer_id
    -- ↑ references the outer row
)

"Correlated" means the inner query is linked to the current row of the outer query. Change the outer row, the inner query's answer changes with it.

EXISTS vs NOT EXISTS — In Plain English

✅

EXISTS

"Is there at least one matching row in the related table?" YES → include this row. NO → skip it.

Use when you want rows that HAVE related data
🚫

NOT EXISTS

"Are there zero matching rows in the related table?" ZERO → include this row. Any found → skip it.

Use when you want rows that HAVE NO related data

The Template — Memorize This Structure

SELECT columns
FROM   outer_table o
WHERE  EXISTS (          -- or NOT EXISTS
    SELECT 1           -- SELECT 1: we only care IF a row exists, not what it contains
    FROM   inner_table i
    WHERE  i.foreign_key = o.primary_key  -- ← the correlated link
)

Why SELECT 1? We don't need any value back — just whether a row came back at all. 1 is a placeholder; SELECT * would work identically, just slower to type.

Analysis 1

NOT EXISTS — Find Dormant Customers

The ask: customers who signed up but placed zero orders — re-engagement email campaign targets.

mskl-masterclass
SELECT
    c.customer_id,
    c.customer_name,
    c.postal_code
FROM ex_customers c                    -- outer: every customer
WHERE NOT EXISTS (                        -- keep only where subquery finds ZERO rows
    SELECT 1
    FROM   ex_orders o
    WHERE  o.customer_id = c.customer_id  -- correlated link
)

What SQL does per customer

  1. Take Customer A from ex_customers
  2. Run subquery: "any orders in ex_orders where customer_id = A?"
  3. Zero found → NOT EXISTS = TRUE → include A
  4. Any found → NOT EXISTS = FALSE → skip A
  5. Repeat for every customer in the table

Why not LEFT JOIN + IS NULL instead? Both work. NOT EXISTS is cleaner to read ("does NOT exist"), NULL-safe, and can stop scanning the moment one match is found — genuinely faster on a wide orders table, not just prettier syntax.

Analysis 2

EXISTS + HAVING — Find VIP Customers

The ask: customers with more than 20 delivered orders — candidates for the VIP Loyalty Program.

mskl-masterclass
SELECT
    c.customer_id,
    c.customer_name
FROM ex_customers c
WHERE EXISTS (
    SELECT 1
    FROM   ex_orders o
    WHERE  o.customer_id = c.customer_id
    AND    o.order_status = 'delivered'
    GROUP BY o.customer_id
    HAVING   COUNT(o.order_id) > 20  -- aggregate check INSIDE the subquery
)
CUST-004125 delivered → 25 > 20VIP ✓
CUST-010015 delivered → 15 > 20 falseSkip ✗
CUST-008932 delivered → 32 > 20VIP ✓

Common mistake — where does HAVING go? GROUP BY and HAVING must be inside the subquery. The outer query runs over ex_customers — one row per customer, no aggregation. Only the subquery has a COUNT to compare against. Put HAVING in the outer query and SQL has nothing to check it against.

Analysis 3

NOT EXISTS + JOIN Inside — Dead Stock Products

The ask: products that have never appeared in a delivered sale. The wrinkle: ex_transactions has product_id, but order_status lives in ex_orders — two tables, one existence check.

mskl-masterclass
SELECT
    p.product_id,
    p.product_name,
    p.category
FROM ex_products p                     -- outer: every product
WHERE NOT EXISTS (
    SELECT 1
    FROM   ex_transactions t
    JOIN   ex_orders o  ON  t.Order_ID = o.order_id  -- ← JOIN inside the subquery
    WHERE  t.Product_ID  = p.product_id       -- correlated link
    AND    o.order_status = 'delivered'         -- only delivered sales count
)

Why is the JOIN inside the subquery?

  1. ex_transactions has Product_ID — needed to correlate to the current product
  2. ex_orders has order_status — needed to check the sale was actually delivered
  3. Both tables are needed to answer one question, so both live inside the same NOT EXISTS

Per-product evaluation

Product P001: 3 delivered transactions found
 → NOT EXISTS = FALSE → SKIP (it was sold)

Product P099: 0 delivered transactions found
 → NOT EXISTS = TRUE → INCLUDE (dead stock)

Product P202: 0 delivered transactions found
 → NOT EXISTS = TRUE → INCLUDE (dead stock)

⚠️ The NOT IN NULL Trap — Why NOT EXISTS Is Safer

Warning: NOT IN silently returns 0 rows the moment its subquery contains even one NULL. No error. No warning. Just quietly, confidently wrong results — one of SQL's most dangerous traps, precisely because it fails silently instead of loudly.

NOT IN — breaks with NULLs:

-- Suppose ex_orders has customer_id: 101, 102, NULL, 105

WHERE customer_id NOT IN (101, 102, NULL, 105)

-- SQL expands this to:
WHERE customer_id != 101
  AND customer_id != 102
  AND customer_id != NULL   ← UNKNOWN!
  AND customer_id != 105

-- Any comparison with NULL = UNKNOWN
-- UNKNOWN anywhere in an AND chain = whole thing UNKNOWN
-- Result: 0 rows returned. Every time. Silently.

NOT EXISTS — NULL-safe:

SELECT c.customer_id
FROM ex_customers c
WHERE NOT EXISTS (
    SELECT 1
    FROM ex_orders o
    WHERE o.customer_id = c.customer_id
)
-- Checks ROW EXISTENCE, not value equality
-- NULL rows in ex_orders don't affect this at all

Rule to memorize: checking for absence of related records → always NOT EXISTS, never NOT IN. NULL-safe, clearer to read, and often faster.

Live Demo — Bonus Round

EXISTS Doesn't Only Belong in WHERE

A pattern nobody teaches until someone actually needs it · Agnik, mildly proud of this one
mskl-masterclass
-- Swarna's actual next question: "can you just add a
-- column that flags VIPs, instead of a separate list?"
SELECT
    c.customer_id,
    c.customer_name,
    CASE WHEN EXISTS (
        SELECT 1 FROM ex_orders o
        WHERE o.customer_id = c.customer_id
          AND o.order_status = 'delivered'
        GROUP BY o.customer_id
        HAVING COUNT(o.order_id) > 20
    ) THEN 'VIP' ELSE 'Regular' END AS customer_tier
FROM ex_customers c;
customer_idcustomer_namecustomer_tier
CUST-0041Rohan IyerVIP
CUST-0100Meera NairRegular
CUST-0023Priya MehtaRegular

Same EXISTS subquery, different job: instead of filtering rows out with WHERE, it's now a boolean check feeding a CASE WHEN — every customer stays in the result, just labeled. One tiny change in placement, one new use case unlocked.

Recap & Quiz

Pattern Reference ⚡

What's the key difference between a correlated and a non-correlated subquery?

A — Correlated runs once; non-correlated runs once per outer row
B — Correlated references the outer query's row; non-correlated does not
C — Correlated always uses EXISTS; non-correlated always uses IN
D — Correlated is always faster
✅ B. A correlated subquery references a column from the outer query (e.g. o.customer_id = c.customer_id), so it re-runs per outer row. A non-correlated subquery is independent — runs once, returns a fixed result.

In the VIP query, why must GROUP BY / HAVING sit inside the subquery?

A — SQL Server forbids HAVING in outer queries
B — The outer query has no aggregate data — only the subquery has a per-customer COUNT
C — HAVING only works with EXISTS
D — It makes the query run faster
✅ B. The outer query runs over ex_customers, one row per customer, no aggregation happening there. Only the subquery has computed a COUNT to compare against 20.
