The Assignment

Dev's QBR Assignment 📊

The Ask

Dev Jaishwal, three weeks into the data analyst role, gets pulled aside by Kriti Tiwari, VP of Sales, the Friday before the Quarterly Business Review. "Just need one report — sales per store within region, region subtotals, and a grand total. Should be quick, right?" Dev has learned that "should be quick" from a VP means "block out your weekend."

What Leadership Actually Wants — All In One Report

  • Sales per store within each region (full detail)
  • Region subtotals (all stores in that region combined)
  • Grand total for the entire company

Dev's first instinct: write 3 separate SELECT queries and stitch them together with UNION ALL. It works. It is also exactly the kind of thing that turns a Friday into a weekend.

The Problem With the UNION ALL Approach

Before ROLLUP existed for Dev, this is what "one report, three levels" looked like — three separate queries, manually glued together, with NULL placeholders typed in by hand so the columns line up.

mskl-masterclass
-- Query 1: Sales by region and store
SELECT region, store, SUM(sales)
FROM sales_data GROUP BY region, store

UNION ALL

-- Query 2: Sales by region only
-- Manually typing NULL to line up with query 1's "store" column
SELECT region, NULL, SUM(sales)
FROM sales_data GROUP BY region

UNION ALL

-- Query 3: Grand total
-- Two manual NULLs this time
SELECT NULL, NULL, SUM(sales)
FROM sales_data;

Problems with this approach:

  • N separate queries to write, and to keep in sync forever
  • Manually-typed NULL placeholders — one column added later, one broken report
  • One missing query = a silently incomplete report
  • The table gets scanned N times instead of once

Where this session is going: ROLLUP, CUBE, and GROUPING SETS are GROUP BY extensions that generate every one of these levels in one query, one table scan. SQL inserts the NULLs for you — Dev never types one by hand again.

ROLLUP Hierarchical Subtotals

ROLLUP builds a hierarchy of subtotals, rolling up from the most detailed row all the way to the grand total. For n columns, ROLLUP produces n+1 grouping levels — and it always rolls up right-to-left, so column order defines the hierarchy.

mskl-masterclass
GROUP BY ROLLUP(region, state, city)

-- 3 columns → 3+1 = 4 levels:
-- Level 1: (region, state, city)  ← full detail
-- Level 2: (region, state)        ← state subtotal
-- Level 3: (region)               ← region subtotal
-- Level 4: ()                     ← grand total

-- Try swapping the column order — the hierarchy
-- swaps with it. ROLLUP(city, state, region) rolls
-- up city→state→region, not the other way round.

Key tip: a NULL in ROLLUP output means "aggregated across all values at this level" — it is not missing data. Its position in the row tells you exactly which subtotal you're looking at.

Output for ROLLUP(region, state, city):

CUBE All Possible Combinations

CUBE generates every possible subset of the grouping columns — not just the neat hierarchy ROLLUP gives you. For n columns, that's 2ⁿ grouping combinations.

mskl-masterclass
GROUP BY CUBE(region, state, city)

-- 3 columns → 2³ = 8 combinations
#GroupingDescription
1(region, state, city)Full detail
2(region, state)Region + state
3(region, city)Region + city
4(region)Region only
5(state, city)State + city
6(state)State only — across all regions
7(city)City only — across all regions
8()Grand total

Caution — exponential growth:

  • 3 columns → 8 groupings
  • 4 columns → 16 groupings
  • 5 columns → 32 groupings
  • CUBE on a wide GROUP BY over a big table is how you accidentally ruin someone's lunch break waiting on a query

ROLLUP vs CUBE: ROLLUP gives you 4 of CUBE's 8 combinations. CUBE's extra 4 include things like "state totals across ALL regions" — cross-dimensional views ROLLUP simply cannot produce, because ROLLUP never breaks its own hierarchy.

GROUPING SETS Precisely What You Need

GROUPING SETS lets you name exactly which combinations to compute — no hierarchy assumption, no exponential blow-up. It's the most efficient and most explicit of the three.

Finance needs exactly 3 levels — not all 4 of CUBE(region, store)'s 4 combinations:

mskl-masterclass
SELECT
    region,
    store,
    SUM(sales_amount) AS total_sales
FROM sales_data
GROUP BY GROUPING SETS (
    (region, store),  -- ① detailed
    (region),          -- ② regional summary
    ()                  -- ③ grand total
    -- notice: no store-only row. Finance never asked
    -- "which store sold the most across every region" —
    -- so we don't waste a single row computing it.
)
ORDER BY region, store;

Output — no store-across-regions row:

regionstoretotal_sales
CentralChicago180,000
CentralDallas200,000
CentralNULL380,000 — region total
EastNew York225,000
EastNULL350,000 — region total
NULLNULL1,250,000 — grand total

Notice what's missing: no row with region=NULL and a store value. Finance never asked for "top store company-wide," so GROUPING SETS never computes it — this is the row-count savings CUBE can't give you.

The GROUPING() Function — Telling NULLs Apart

Here's the trap: what if region itself can legitimately be NULL in the raw data (an unassigned store, say)? Now a NULL in the output could mean "this is a subtotal" or "the data was actually missing." GROUPING() tells them apart.

mskl-masterclass
SELECT
    region,
    state,
    SUM(sales_amount) AS total_sales,
    -- 1 = this NULL is a subtotal row
    -- 0 = this is a real value (or a real NULL from the data)
    GROUPING(region) AS is_region_subtotal,
    GROUPING(state)  AS is_state_subtotal
FROM sales_data
GROUP BY ROLLUP(region, state);

NULLNULL2,500,00011

Where this earns its keep: once GROUPING() is in the SELECT list, you can also swap "NULL" for a friendly label with CASE WHEN — turning that region subtotal row into "region: East — ALL STATES" instead of a bare NULL a stakeholder will squint at.

Live Demo

All Three Operators on Real GlobalMart Data

Tables: ex_transactions, ex_orders, ex_customers, ex_locations · mskl-masterclass · Dev, screen-sharing, slightly nervous
mskl-masterclass
-- Run each block separately and compare row counts

-- ROLLUP: 4 levels (region+state detail, region subtotal, grand)
SELECT l.region, l.state,
       ROUND(SUM(t.sales_amount),2) AS total_sales
FROM ex_transactions t
JOIN ex_orders o
    ON t.order_id = o.order_id
    AND o.order_status = 'delivered'
JOIN ex_customers c ON o.customer_id = c.customer_id
JOIN ex_locations l  ON c.postal_code = l.postal_code
GROUP BY ROLLUP(l.region, l.state)
ORDER BY l.region, l.state;

-- CUBE: change just ONE word → watch new rows appear
-- where region=NULL but state has a real value
-- GROUP BY CUBE(l.region, l.state)

-- GROUPING SETS: only region+state detail and the grand
-- total — no region-only subtotal row at all this time
-- GROUP BY GROUPING SETS ((l.region, l.state), ())

What to watch for as each block runs:

  • ROLLUP: rows with state=NULL are region totals; the one row with BOTH NULL is the grand total
  • CUBE: extra rows appear with region=NULL and state set — a "state total nationwide" ROLLUP never gives you
  • GROUPING SETS: exactly the rows named in the list, not one more

If Dev runs ROLLUP(l.region, l.state) and counts 4 distinct regions with 2-3 states each, roughly how many total rows come back?

✅ One row per (region, state) detail combination + one subtotal row per region + one grand total row. With 4 regions and ~2.5 states each on average: ~10 detail rows + 4 region subtotals + 1 grand total ≈ 15 rows. Run it to check the real number — GlobalMart's regions aren't perfectly even.

Quiz 1 — Choose the Right Operator

Scenario: Kriti asks for a hierarchical sales report — by region, then by state within region, then by city within state — with subtotals at every level and a grand total. Nothing more, nothing extra.

Which aggregation operator fits best?

A — GROUPING SETS
B — CUBE
C — UNION ALL
D — ROLLUP
✅ D — ROLLUP. ROLLUP(region, state, city) generates exactly 4 levels: (region, state, city) → (region, state) → (region) → () — the standard drill-down hierarchy the request describes, in that exact order. CUBE would hand back 8 combinations including cross-regional totals nobody asked for. GROUPING SETS would need every level spelled out by hand. UNION ALL needs 4 separate queries — which is precisely the weekend Dev is trying to avoid.

Quiz 2 — True Statements About GROUPING SETS

Which of the following statements about GROUPING SETS are TRUE? (Select 2)

A — It is more efficient than CUBE when you only need specific groupings
B — It lets you specify exactly which groupings you need
C — It can only be used with two columns maximum
D — It generates all possible combinations automatically
✅ A and B are TRUE. GROUPING SETS computes only the groupings you list, so it's cheaper than CUBE's automatic 2ⁿ — and it gives you explicit, row-by-row control over exactly what the report contains. C is FALSE — any number of columns is fine. D is FALSE — automatic generation of every combination is CUBE's job, not GROUPING SETS'.
Quiz 3 & Recap

Reading NULLs, and the Full Comparison ⚡

In a ROLLUP(region, state, city) output, a row reads region='East', state=NULL, city=NULL. What is this row?

A — Grand total row for all regions
B — A query error that needs fixing
C — The state and city data is missing from the database
D — Subtotal for the East region — all states and cities combined
✅ D. In ROLLUP output, NULL means "aggregated across all values at this level" — never missing data. region='East' with state and city both NULL is the East region subtotal. The grand total row would have NULL in all three columns, not just two.
