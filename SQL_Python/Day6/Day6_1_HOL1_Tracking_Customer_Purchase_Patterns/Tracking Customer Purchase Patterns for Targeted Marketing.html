💬 Robert, from Finance, has asked whether we can "just rank everything against everything, channels don't really matter." They do. Ranking Email against Paid Search is like ranking a marathon time against a 100m sprint.

The Core Idea — Window Operations, in SQL and pandas

groupby().agg() collapses every group into one row — you lose the detail. A window operation computes a value across rows while keeping every row visible. You already know this from SQL's OVER (PARTITION BY ...). Today it gets a pandas name.

FamilypandasSQL equivalentBehaviour
Rankingrank(method='min')RANK()Ties share rank; next rank skips (1, 1, 3)
Rankingrank(method='dense')DENSE_RANK()Ties share rank; no gap (1, 1, 2)
Rankingrank(method='first')ROW_NUMBER()Unique sequential number; no ties
Running totalgroupby().cumsum()SUM() OVER (...)Cumulative total per group
Running averagegroupby().expanding().mean()AVG() OVER (...)Running average per group

✅ The whole lab is really just this table, applied twice. groupby().agg() reduces N rows to 1. Everything in this table keeps all N rows and adds a new column of per-row context.

⚠️ Always sort by the grouping key and date before cumsum() or expanding(). Unsorted data produces confidently wrong running totals — no error, just silently wrong numbers.

Task 1 — The SQL Approach First

Before any pandas: what would this look like as one SQL query? Aggregate the daily metrics, join in the lookups, then rank within channel using a window function.

SQL approachaggregate → join → window-rank
A CTE first collapses the daily grain to one row per campaign (this is your GROUP BY). The outer query then joins in campaign metadata and channel name, computes rates inline, and ranks with three window functions — all partitioned by channel_name, all reading the same underlying total.
WITH campaign_agg AS (
  SELECT campaign_id,
         SUM(impressions) AS total_impressions,
         SUM(clicks)      AS total_clicks,
         SUM(conversions) AS total_conversions,
         SUM(bounces)     AS total_bounces,
         SUM(conversions) * 1.0 / COUNT(DISTINCT metric_date) AS avg_daily_conversions
  FROM ex_campaign_metrics
  GROUP BY campaign_id
)
SELECT
  c.campaign_id, ch.channel_name, c.campaign_type, c.budget,
  ca.total_impressions, ca.total_clicks, ca.total_conversions, ca.total_bounces,
  ROUND(ca.avg_daily_conversions, 2) AS avg_daily_conversions,
  ROUND(ca.total_clicks * 100.0 / ca.total_impressions, 2) AS click_through_rate,
  ROUND(ca.total_conversions * 100.0 / ca.total_clicks, 2)   AS conversion_rate,
  DATEDIFF(day, c.start_date, c.end_date) + 1 AS campaign_duration_days,
  RANK()       OVER (PARTITION BY ch.channel_name ORDER BY ca.total_conversions DESC) AS channel_rank,
  DENSE_RANK() OVER (PARTITION BY ch.channel_name ORDER BY ca.total_conversions DESC) AS dense_channel_rank,
  ROW_NUMBER() OVER (PARTITION BY ch.channel_name ORDER BY ca.total_conversions DESC) AS row_num
FROM campaign_agg ca
JOIN ex_campaigns c  ON ca.campaign_id = c.campaign_id
JOIN ex_channel ch    ON c.channel_id = ch.channel_id
ORDER BY ch.channel_name, channel_rank;

SUM(clicks) AS total_clicks,Same idea, for clicks.
SUM(conversions) AS total_conversions,Same idea, for conversions — this becomes the ranking metric later in the query.
SUM(bounces) AS total_bounces,Same idea, for bounces.
SUM(conversions) * 1.0 / COUNT(DISTINCT metric_date)Total conversions divided by the number of distinct days recorded. * 1.0 forces floating-point division so the result isn't truncated to a whole number.

2
Aggregate daily metrics per campaign — this is your GROUP BY

Exactly the CTE from the SQL approach. Named aggregation (total_clicks=('clicks','sum')) reads almost like the SQL SUM(clicks) AS total_clicks it replaces.

campaign_agg = (
    metrics
    .groupby('campaign_id')
    .agg(
        total_impressions = ('impressions', 'sum'),
        total_clicks      = ('clicks',      'sum'),
        total_conversions = ('conversions', 'sum'),
        total_bounces     = ('bounces',     'sum'),
        distinct_dates    = ('metric_date', 'nunique'),
    )
    .reset_index()
)
campaign_agg['avg_daily_conversions'] = (
    campaign_agg['total_conversions'] / campaign_agg['distinct_dates']
).round(2)
campaign_agg.drop(columns='distinct_dates', inplace=True)
metrics.groupby('campaign_id')Buckets every daily row by which campaign it belongs to — the pandas equivalent of SQL's GROUP BY campaign_id.
.agg(total_impressions=('impressions','sum'), ...)Named aggregation: for each bucket, sum the named source column and label the result column. Reads almost exactly like SUM(impressions) AS total_impressions.
distinct_dates=('metric_date','nunique')Counts distinct dates per campaign — the pandas equivalent of COUNT(DISTINCT metric_date), needed only to compute the average below.
.reset_index()groupby() makes campaign_id the index by default; this promotes it back to a normal column so later merges can use it as a join key.
campaign_agg['avg_daily_conversions'] = (...) A new column, computed the same way as the SQL CTE: total conversions divided by distinct days.
.round(2)Matches the SQL ROUND(..., 2) — two decimal places for the report.
campaign_agg.drop(columns='distinct_dates', inplace=True)The helper column has done its job (computing the average) and is no longer needed in the final output, so it's dropped. inplace=True modifies the DataFrame directly instead of returning a copy.
3
Merge in campaign metadata and channel name — this is your JOIN

Two chained .merge() calls, same as two SQL JOINs. how='inner' because every campaign here should have a matching channel by design.

df = (
    campaign_agg
    .merge(campaigns, on='campaign_id', how='inner')
    .merge(channel,   on='channel_id',  how='inner')
)
campaign_agg.merge(campaigns, on='campaign_id', how='inner')First JOIN: attaches campaign metadata (dates, budget, type) by matching on the shared campaign_id column. how='inner' keeps only campaigns present in both.
.merge(channel, on='channel_id', how='inner')Second JOIN, chained directly onto the first: attaches the readable channel name by matching on channel_id, which just arrived from the previous merge.

Compute derived rates — the SELECT calculations

np.where() is pandas' inline CASE WHEN — it guards against dividing by zero, exactly like a defensive SQL CASE WHEN total_impressions > 0 THEN ... ELSE 0 END would.

df['campaign_duration_days'] = (df['end_date'] - df['start_date']).dt.days + 1

df['click_through_rate'] = np.where(
    df['total_impressions'] > 0,
    (df['total_clicks'] / df['total_impressions'] * 100).round(2),
    0.0
)
df['click_through_rate'] = df['click_through_rate'].apply(lambda x: f"{x}%")

df['conversion_rate'] = np.where(
    df['total_clicks'] > 0,
    (df['total_conversions'] / df['total_clicks'] * 100).round(2),
    0.0
)
df['conversion_rate'] = df['conversion_rate'].apply(lambda x: f"{x}%")
(df['end_date'] - df['start_date']).dt.days + 1Subtracting two datetime columns gives a duration; .dt.days pulls out the whole-number day count. + 1 matches SQL's DATEDIFF logic — both the start and end day count as active.
np.where(condition, value_if_true, value_if_false)pandas' inline CASE WHEN. Here: if impressions > 0, compute the real rate; otherwise return 0.0 and skip the division entirely, avoiding a divide-by-zero.
(df['total_clicks'] / df['total_impressions'] * 100).round(2)The click-through rate itself, as a percentage, rounded to 2 decimals — only evaluated for rows where the np.where condition is True.
df['click_through_rate'].apply(lambda x: f"{x}%")Runs a small function over every value in the column, appending a literal "%" so the final report shows "6.71%" instead of the bare number 6.71.
df['conversion_rate'] = np.where(...)Same guarded-division pattern as click_through_rate, this time conversions over clicks.
.apply(lambda x: f"{x}%")Same percentage-string formatting, applied to conversion_rate.
5
Rank within channel — the window functions

Three ranks, three methods, one pattern: groupby('channel_name')[...].rank(method=..., ascending=False). This is the exact table from Slide 3, now as code.

df['channel_rank'] = (
    df.groupby('channel_name')['total_conversions']
    .rank(method='min', ascending=False)
    .astype(int)
)
df['dense_channel_rank'] = (
    df.groupby('channel_name')['total_conversions']
    .rank(method='dense', ascending=False)
    .astype(int)
)
df['row_num'] = (
    df.groupby('channel_name')['total_conversions']
    .rank(method='first', ascending=False)
    .astype(int)

df.groupby('channel_name')['total_conversions']Buckets rows by channel — this is the PARTITION BY. Selecting ['total_conversions'] narrows to the one column being ranked.
.rank(method='min', ascending=False)Ranks within each bucket, highest conversions first. method='min' is pandas' name for SQL's RANK() — ties share the lowest rank, the next rank skips ahead.
.astype(int)rank() returns floats by default (e.g. 1.0); casting to int gives a clean whole-number rank for the report.
method='dense'Identical groupby/rank pattern, but this method name is pandas' equivalent of DENSE_RANK() — no gap is ever left after a tie.

Task 2 — The SQL Approach First

No GROUP BY needed this time — every row stays. SUM() OVER and AVG() OVER with an explicit frame do the accumulating.

SQL approachrunning SUM / AVG with an explicit frame
ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW tells SQL exactly which rows to accumulate: from the start of the partition up to (and including) the current row. That frame clause is the SQL name for what pandas calls "expanding."
SELECT
  campaign_id,
  metric_date,
  conversions AS daily_conversions,
  SUM(conversions) OVER (
      PARTITION BY campaign_id
      ORDER BY metric_date
      ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
  ) AS cumulative_conversions,
  ROUND(
    AVG(clicks) OVER (
        PARTITION BY campaign_id
        ORDER BY metric_date
        ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
    ), 2
  ) AS running_avg_clicks
FROM ex_campaign_metrics
ORDER BY campaign_id, metric_date;
SELECT campaign_id, metric_date,No GROUP BY this time — every input row is kept as its own output row.
conversions AS daily_conversions,Renames the raw column for clarity in the output — this single day's conversions, not a total.
SUM(conversions) OVER (A window function — computes a sum across a set of rows without collapsing them into one.
PARTITION BY campaign_idRestarts the running total at zero for every new campaign — rows from different campaigns never mix.
ORDER BY metric_dateDefines the order the running total accumulates in — oldest date first, so "cumulative" actually means something chronological.
ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROWThe frame: sum everything from the very first row of this campaign's partition up to and including the current row. This exact phrase is what "running" or "cumulative" means in SQL.
) AS cumulative_conversions,Names the resulting column.
ROUND( AVG(clicks) OVER (...), 2 )Same partition/order/frame as above, but averaging clicks instead of summing conversions — a running average, rounded to 2 decimals.
FROM ex_campaign_metricsThe daily-grain table — read directly, nothing pre-aggregated.
ORDER BY campaign_id, metric_date;Controls the final display order of the result set — separate from the ORDER BY inside each OVER(), which only controls the window's internal accumulation order.

Task 2 — Python, Step by Step

the ROWS UNBOUNDED PRECEDING frame, in pandas
1
Sort by campaign and date — non-negotiable

SQL's ORDER BY metric_date inside the OVER() clause guarantees row order for the window. pandas has no such built-in guarantee — you sort first, or the running totals are quietly wrong.

metrics_sorted = metrics.sort_values(by=['campaign_id', 'metric_date']).reset_index(drop=True)
metrics.sort_values(by=['campaign_id','metric_date'])Sorts by campaign first, then by date within each campaign — this ordering is what makes the next two steps' running totals mean anything at all.
.reset_index(drop=True)Renumbers the index 0, 1, 2... after sorting scrambled the original row order; drop=True discards the stale index instead of keeping it as a stray column.
2
Cumulative conversions per campaign

groupby('campaign_id')['conversions'].cumsum() — one line, and it's the pandas name for SUM() OVER (PARTITION BY campaign_id ORDER BY metric_date ROWS UNBOUNDED PRECEDING).

metrics_sorted['cumulative_conversions'] = (
    metrics_sorted
    .groupby('campaign_id')['conversions']
    .cumsum()
)
metrics_sorted.groupby('campaign_id')['conversions']Buckets rows by campaign (the PARTITION BY), narrowed to the conversions column — the one being accumulated.
.cumsum()Running total within each bucket, in the row order already established by the sort in Step 1. This one call is the entire pandas equivalent of the SQL SUM() OVER (...ROWS UNBOUNDED PRECEDING) block.
3
Running average of clicks per campaign

There's no cummean() in pandas — .expanding().mean() is the tool for a running average. Same partition-and-order logic as step 2.

metrics_sorted['running_avg_clicks'] = (
    metrics_sorted
    .groupby('campaign_id')['clicks']
    .expanding()
    .mean()
    .round(2)
    .values
)
metrics_sorted.groupby('campaign_id')['clicks']Same partitioning as Step 2, this time on the clicks column.
.expanding()Creates an "expanding window" per group — a window that grows by one row at a time, from the start of the group to the current row. There is no cummean() in pandas; this is the tool for a running average.
.mean()Computes the average over each expanding window — the running average, one value per row.
.round(2)Two decimal places, matching the SQL ROUND(...,2).
.valuesExtracts the plain array of numbers so it can be assigned directly into a new DataFrame column without pandas trying to align it by index.
4

metrics_sorted[[ 'campaign_id', 'metric_date', ... ]]Picks only the columns the final report needs — the SELECT column list.

Quick Quiz — Applying the Pattern
Click an option. Get instant feedback.

Which SQL clause is the direct equivalent of .expanding().mean()?

B. The window frame ROWS UNBOUNDED PRECEDING is exactly what "expanding" means — accumulate from the start of the partition to the current row.

You forget to sort before calling .cumsum(). What happens?

B — the most dangerous kind of bug. cumsum() just accumulates rows in whatever order they're in. Wrong order, wrong numbers, zero errors raised.

Where This Lab Usually Breaks

Ranking globally instead of per channel

Forgetting groupby('channel_name') before .rank() ranks every campaign against every other campaign — exactly the "channels don't matter" mistake Robert suggested. They matter.

Dividing before checking for zero

A campaign with 0 impressions but a currently-running record will crash total_clicks / total_impressions. np.where() exists specifically to dodge this.

Skipping the sort before cumsum/expanding

Covered on the last slide, worth repeating: this bug never throws an error. It just quietly produces a wrong running total. Always sort by group key + date first.

Confusing method='rank' with method='min'

There is no method='rank' in pandas — SQL's RANK() maps to pandas' method='min', which trips up almost everyone the first time.

Self-Check — Read the Output, Not Just the Code

❓ Two campaigns in "Social Media" both have 4200 total_conversions — the only tie in that channel. Using method='min' for channel_rank, what ranks do they get, and what does the campaign immediately below them get?

✅ Both tied campaigns get rank 1. The next campaign down gets rank 3 — not 2. method='min' (SQL's RANK()) always skips ahead by the number of tied rows.

❓ Same tie, but this time look at dense_channel_rank. What does the campaign below the tie get now?

✅ Rank 2. method='dense' never leaves a gap — it's counting distinct rank values, not row positions.
