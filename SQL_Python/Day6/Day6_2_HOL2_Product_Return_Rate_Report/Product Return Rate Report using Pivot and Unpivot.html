Four Tables — and One Trap

Tables: ex_orders, ex_returns, ex_transactions, ex_products.

⚠️ ex_returns does not contain product_id

You must join returns → orders to get order_id context, then orders → transactions → products to get category. Do these joins in the wrong order and you get a KeyError — the column you need simply hasn't arrived yet.

The join path

ex_transactions is the bridge — it's the only table holding both Order_ID and Product_ID together. Without it, orders and products can never meet.

The left-join rule

Products with zero returns must still appear with total_returns = 0. Always how='left' when merging returns onto orders — an inner join would silently erase every product with a clean track record.

Task 1 — The SQL Approach First

Two CTEs build the bridge, a third flags returns, and the final GROUP BY computes the rate from summed totals — never from an average of row-level rates.

SQL approachbridge join → flag → aggregate → rate
The order_product CTE is the bridge — the only place Order_ID and Product_ID sit in the same row. A correlated EXISTS against ex_returns is the SQL-native way to produce a 0/1 return flag per order, playing the same role as pandas' isin() a few slides from now.
WITH order_product AS (
  SELECT DISTINCT Order_ID, Product_ID FROM ex_transactions
),
orders_with_category AS (
  SELECT o.order_id, p.category
  FROM ex_orders o
  LEFT JOIN order_product op ON o.order_id = op.Order_ID
  LEFT JOIN ex_products p     ON op.Product_ID = p.product_id
)
SELECT
  category,
  COUNT(order_id) AS total_orders,
  SUM(CASE WHEN EXISTS (
      SELECT 1 FROM ex_returns r WHERE r.order_id = orders_with_category.order_id
  ) THEN 1 ELSE 0 END) AS total_returns,
  CONCAT(ROUND(
      SUM(CASE WHEN EXISTS (
          SELECT 1 FROM ex_returns r WHERE r.order_id = orders_with_category.order_id
      ) THEN 1 ELSE 0 END) * 100.0 / COUNT(order_id), 2
  ), '%') AS return_rate
FROM orders_with_category
GROUP BY category;
WITH order_product AS (First CTE — builds the bridge between orders and products, since neither table can reach the other directly.
SELECT DISTINCT Order_ID, Product_ID FROM ex_transactionsPulls only the two linking columns. DISTINCT collapses duplicate transaction line items so one order-product pair appears once, not once per line item.
), orders_with_category AS (Second CTE — attaches a category label to every order using the bridge just built.
SELECT o.order_id, p.categoryOnly the columns needed downstream: the order identifier and its category.
FROM ex_orders oStarts from every order — this table is the anchor, so every order will survive regardless of matches.
LEFT JOIN order_product op ON o.order_id = op.Order_IDBrings in the product each order relates to. LEFT JOIN keeps orders even if no transaction line matches.
LEFT JOIN ex_products p ON op.Product_ID = p.product_idBrings in the category for that product. LEFT JOIN again — a missing product shouldn't delete the order row.
) SELECT category,Closes the second CTE; the outer query now groups by category.
COUNT(order_id) AS total_orders,Counts every order row per category — the denominator for the rate later.
SUM(CASE WHEN EXISTS (...) THEN 1 ELSE 0 END)For each order, checks whether it appears anywhere in ex_returns; scores 1 if so, 0 if not, then sums those scores per category — a correlated-subquery way of counting returns.
SELECT 1 FROM ex_returns r WHERE r.order_id = orders_with_category.order_idThe correlated subquery itself — "does at least one row in ex_returns share this exact order_id?" EXISTS only cares whether any row comes back, not what's in it.
AS total_returns,Names the summed return-flag column.
CONCAT(ROUND(... * 100.0 / COUNT(order_id), 2), '%')Return count divided by order count, times 100 for a percentage, rounded to 2 decimals, then glued to a literal "%" character to make a display-ready string.
FROM orders_with_categoryReads from the second CTE — every order, already tagged with its category.
GROUP BY category;Collapses all order rows down to one row per category — the clause that turns COUNT/SUM from row-level into category-level totals.

Task 1 — Python, Step by Step (1 of 2)

same bridge join, now in pandas
1
Link orders to products via transactions — build the bridge

This is the order_product CTE. Only the two linking columns are pulled. drop_duplicates() matters here — a single order can generate several transaction line items, and without deduplicating, the same order-product pair would appear more than once.

order_product = transactions[['Order_ID', 'Product_ID']].drop_duplicates()
transactions[['Order_ID', 'Product_ID']]Selects only the two linking columns from the transactions table — everything else in that table is irrelevant to this bridge.
.drop_duplicates()Removes repeated order-product pairs. A single order with multiple transaction line items would otherwise appear more than once, inflating counts later. The pandas equivalent of the SQL SELECT DISTINCT above.
2
Bring in category from products

The second LEFT JOIN from the SQL approach. left_on/right_on are needed explicitly because the column casing differs between tables: Product_ID in transactions vs product_id in products.

order_category = order_product.merge(
    products[['product_id', 'category']],
    left_on='Product_ID', right_on='product_id', how='left'
)
order_product.merge(products[[...]], ...)Joins the bridge table to a narrowed-down products table containing only the two columns actually needed.
left_on='Product_ID', right_on='product_id'Explicit because the column name casing differs between the two tables — a single shared on= key would fail since no column is spelled identically in both.
how='left'Keeps every row from order_product even if a product_id has no match in products — matching the SQL LEFT JOIN in the approach above.
3
Merge category back onto orders

The first LEFT JOIN from the SQL approach, done last in Python because it needed category to already exist. how='left' again — every order row survives, matched or not.

orders_with_category = orders.merge(
    order_category[['Order_ID', 'category']],
    left_on='order_id', right_on='Order_ID', how='left'
)
orders.merge(order_category[[...]], ...)Joins the full orders table to the category lookup built in Step 2, narrowed to just the two needed columns.
left_on='order_id', right_on='Order_ID'Again explicit because of the casing mismatch — order_id in orders vs Order_ID in the transactions-derived table.
how='left'Every order row survives regardless of whether a category was found — orders is the anchor table for the whole report.

Task 1 — Python, Step by Step (2 of 2)

4
Flag returned orders — the CASE WHEN EXISTS, without a join

isin() is pandas' cleaner alternative to the correlated EXISTS subquery from the SQL approach — same 0/1 outcome, no extra rows, no join needed at all.

orders_with_category['is_return'] = orders_with_category['order_id'].isin(returns['order_id'])
orders_with_category['order_id'].isin(returns['order_id'])Checks each order_id against the full list of order_ids present in the returns table, returning True if found, False if not — a whole new boolean column, computed in one line, no join required.
orders_with_category['is_return'] = ...Assigns that True/False result as a new column named is_return, ready to be summed in the next step.
5
Group by category — the GROUP BY

Two aggregations at once: count on order_id gives total_orders. sum on the boolean is_return works because Python treats True as 1 and False as 0 — summing a boolean column literally counts the trues.

summary = orders_with_category.groupby('category').agg(
    total_orders  = ('order_id',  'count'),
    total_returns = ('is_return', 'sum')
).reset_index()
orders_with_category.groupby('category')Buckets every order row by its category — the pandas GROUP BY.
.agg(total_orders=('order_id','count'), ...)Named aggregation: counts how many order_id rows fall in each bucket, labeling the result total_orders.
total_returns=('is_return','sum')Sums the boolean is_return column per bucket. Because True=1 and False=0 in Python, this sum is literally a count of returned orders.
.reset_index()Promotes category from the groupby index back to a normal column, so it's usable in later steps like pivot_table() and melt().
6
Compute return rate — from totals, never from an average of rates

The rate is computed after grouping, from the already-summed totals — matching the SQL approach exactly, where the division happens outside the aggregate functions, not before them.

summary['return_rate'] = (
    summary['total_returns'] / summary['total_orders'] * 100
).map('{:.2f}%'.format)
summary['total_returns'] = summary['total_returns'].astype(int)
summary['total_returns'] / summary['total_orders'] * 100The rate, computed from the already-aggregated category-level totals — divide first, multiply by 100 to convert to a percentage.
.map('{:.2f}%'.format)Applies Python's string formatting to every value in the resulting Series, fixing 2 decimal places and appending a literal "%" — turns 15.0 into "15.00%".
summary['total_returns'] = summary['total_returns'].astype(int)The sum() of a boolean column can come back as a float in some pandas versions; this forces it back to a clean integer so the report doesn't show "180.0".
Checkpoint
Quick Quiz — Joins and Rate Math
Click an option. Get instant feedback.

Why is drop_duplicates() called on the transactions bridge before any merge?

B. A single order with multiple transaction line items would otherwise appear multiple times, silently inflating total_orders at the groupby step. This is deduplication for correctness, not performance or null-handling.

Why is return_rate computed after groupby(), not before it?

C. A product with 2 orders/1 return (50%) and another with 1000 orders/100 returns (10%) would average to 30% — nowhere near the true category rate of ~10.1%. Computing the rate from summed totals after grouping is the only mathematically correct order.

Task 2 — The SQL Approach First, Then Python

SQL approachrecap: your Day 3 PIVOT
Worth being honest here: summary already has one row per category — it's already "wide" in the SQL sense. A real SQL PIVOT earns its keep when you start from a long table (one row per category-metric pair). That's actually what melt() builds in Task 3 — so this pivot is really demonstrating the pandas API on data that doesn't strictly need reshaping yet.
SELECT category, [return_rate], [total_orders], [total_returns]
FROM long_format_summary
PIVOT (
    MAX(value) FOR metric IN ([return_rate], [total_orders], [total_returns])
) AS p;
SELECT category, [return_rate], [total_orders], [total_returns]The final column list — category stays a row identifier, each metric name becomes its own bracketed column.
FROM long_format_summaryPIVOT needs a long-format source: one row per category-metric pair, exactly the shape melt() produces in Task 3.
PIVOT ( MAX(value) FOR metric IN (...) )The reshape instruction: for each category, look across its rows, and for every metric name listed in IN(), place that row's value into a column of that name. MAX() is required syntactically even though only one value exists per category-metric pair.
) AS p;PIVOT must be aliased like any derived table.
pandas' pivot_table(), step by step
1
Pivot with aggfunc='first' — nothing to aggregate, just reshape

index='category' makes category the row identifier. Since summary already has one row per category, aggfunc='first' just returns the existing value — no arithmetic happens.

pivot_df = summary.pivot_table(
    index='category',
    values=['total_orders', 'total_returns', 'return_rate'],
    aggfunc='first'
).reset_index()
summary.pivot_table(Calls pandas' reshape function on the category summary built earlier.
index='category',Sets category as the row identifier for the output — one row per category, same role as PIVOT's SELECT column.
values=['total_orders', 'total_returns', 'return_rate']Names which columns should become the pivoted values — the same three names listed in the SQL PIVOT's IN() clause.
aggfunc='first'Normally pivot_table() would aggregate multiple matching rows with a function like sum or mean; here there's only ever one row per category already, so 'first' just passes the existing value through untouched — the pandas cousin of PIVOT's required MAX() when there's nothing to actually aggregate.
).reset_index()pivot_table() leaves category as the DataFrame's index; this promotes it back to a normal column so melt() can reference it by name in Task 3.

⚠️ Forgetting reset_index() is the classic mistake here — category becomes the DataFrame's index, not a column, and melt() in the next task won't be able to see it.

Task 3 — The SQL Approach First, Then Python

SQL approachrecap: your Day 3 UNPIVOT
Every non-key column named in the IN() list becomes its own row, tagged by the metric name it came from. This is the direct SQL cousin of what melt() does below.
SELECT category, metric, value
FROM pivot_df
UNPIVOT (
    value FOR metric IN (total_orders, total_returns, return_rate)
) AS u;
SELECT category, metric, valueThe long-format output columns — one identifier (category), one label column (metric), one value column.
FROM pivot_dfStarts from the wide table built in Task 2.
UNPIVOT ( value FOR metric IN (...) )For each row, takes every column named in IN() and turns it into its own output row: the column name becomes the metric value, the cell's contents become the value column.
) AS u;UNPIVOT also needs an alias, like any derived table.
pandas' melt(), step by step
1
Melt the wide table back to long

id_vars names the column(s) to keep as-is (the SQL cousin of the columns not listed in UNPIVOT's IN()). Everything in value_vars becomes rows instead of columns.

long_df = pivot_df.melt(
    id_vars='category',
    value_vars=['total_orders', 'total_returns', 'return_rate'],
    var_name='metric',
    value_name='value'
)
long_df = long_df.sort_values(['category', 'metric']).reset_index(drop=True)
pivot_df.melt(Calls pandas' unpivot function on the wide table from Task 2.
id_vars='category',Names the column(s) that stay exactly as they are — not unpivoted. The direct pandas cousin of whatever columns are not listed in SQL's UNPIVOT IN().
value_vars=['total_orders', 'total_returns', 'return_rate']Names the columns to fold into rows — matches the SQL UNPIVOT's IN() list exactly.
var_name='metric',Names the new column that will hold each original column's name (e.g. "total_orders").
value_name='value'Names the new column that will hold each original cell's value.
)Closes the melt() call — the result already has exactly three columns: category, metric, value.
long_df.sort_values(['category', 'metric'])melt() doesn't guarantee a tidy row order; this sorts by category then metric so the report reads predictably.
.reset_index(drop=True)Renumbers the index after sorting, discarding the old scrambled one.

Where This Lab Usually Breaks

Joining in the wrong order → KeyError

ex_returns has no product_id. Trying to join returns straight to products before going through orders and transactions raises a KeyError — the column genuinely does not exist yet at that point.

Using an inner join and losing clean products

A product with zero returns should still show total_returns = 0. An inner join where a left join was needed erases it from the report entirely — a silent, dangerous kind of wrong.

Forgetting reset_index() after pivot_table()

category quietly becomes the index instead of a column. melt() then can't find it as an id_vars target.

Averaging rates instead of summing totals first

Covered in the checkpoint, worth repeating: rate = SUM(returns) / SUM(orders), never AVG(per-row rate). The two give different — and only one correct — answer.
