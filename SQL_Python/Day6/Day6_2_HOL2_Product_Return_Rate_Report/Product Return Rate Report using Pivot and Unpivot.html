The Join Chain — Why Transactions is the Bridge

⚠️ Critical constraint — ex_returns does NOT contain product_id. ex_orders also does NOT contain product_id. The only path from return → product is: returns → orders → transactions → products. Getting this order wrong causes a KeyError. 
import pandas as pd

orders       = pd.read_csv("exorders.csv")
returns      = pd.read_csv("exreturns.csv")
products     = pd.read_csv("exproducts.csv")
transactions = pd.read_csv("extransactions.csv")

# Step 1: transactions bridges orders → products
# Pull only the two linking columns (no extra noise)
# drop_duplicates: one order may have many transaction lines
# → same Order_ID appears multiple times
# → would inflate counts during groupby!
order_product = transactions[['Order_ID', 'Product_ID']].drop_duplicates()

# Step 2: Bring in category from products
# NOTE: column names differ in case! Product_ID vs product_id
# → must use left_on / right_on, NOT just on='product_id'
order_category = order_product.merge(
    products[['product_id', 'category']],
    left_on='Product_ID',
    right_on='product_id',
    how='left'
)

Why each design decision matters

DecisionReason
drop_duplicates()Prevents one order from being counted multiple times
left_on / right_onColumn names differ in case (Order_ID vs order_id)
how='left'Keep all orders even if product has no match

❓ Why is drop_duplicates() on the transactions table needed before merging?

✅ An order with 3 products appears 3× in transactions. Without deduplication, each order would be counted 3× during groupby — inflating total_orders incorrectly. drop_duplicates() ensures each Order_ID appears once per product (or just once if we only need the order count).

Flagging Returns and Aggregating by Category

# Step 3: Merge category back onto orders table
orders_with_cat = orders.merge(
    order_category[['Order_ID', 'category']],
    left_on='order_id',     # orders uses lowercase
    right_on='Order_ID',    # transactions uses uppercase
    how='left'
)

# Step 4: Flag returned orders using isin()
# isin() returns True if order_id is in returns table
# True = 1, False = 0 → perfect for summing later
orders_with_cat['is_return'] = (
    orders_with_cat['order_id'].isin(returns['order_id'])
)

# Step 5: Aggregate — one row per category
summary = orders_with_cat.groupby('category').agg(
    total_orders  = ('order_id',  'count'),
    total_returns = ('is_return', 'sum')  # True=1, False=0
).reset_index()

Why isin() instead of merge for returns?

A left merge on returns would add extra columns and NaN handling complexity. isin() produces a clean boolean column (True/False) directly. True sums as 1, False sums as 0 — so .sum() on the boolean column gives the exact return count per category.

⚠️ Compute return rate AFTER groupby

# ❌ Wrong: rate per row, then average
# → mathematically incorrect (Simpson-like error)

# ✅ Correct: compute from aggregated totals
summary['return_rate'] = (
    summary['total_returns'] /
    summary['total_orders'] * 100
).map('{:.2f}%'.format)
summary['total_returns'] = summary['total_returns'].astype(int)

❓ Why is return rate calculated AFTER groupby, not before?

✅ If computed per row first (e.g., 1 return out of 1 order = 100%), then averaged, each row carries equal weight regardless of volume. A product with 2 orders (50% rate) and one with 1000 orders (10% rate) would average 30% — not the true 10.1%. Category-level totals give the mathematically correct rate.

pivot_table() — Wide Format for Side-by-Side Comparison

Long format (current): one row per category. Wide format (pivot): category as row index, each metric as a column — easier for humans to scan.

# Pivot: one row per category, metrics as columns
pivot_df = summary.pivot_table(
    index='category',
    values=['total_orders', 'total_returns', 'return_rate'],
    aggfunc='first'   # already 1 row/category — no aggregation needed
).reset_index()       # MUST call to make category a regular column

pivot_table() parameters

ParameterWhat it does
index=Column that becomes row identifier
values=Columns to spread as cell values
columns=Column whose values become new columns
aggfunc=How to combine duplicate cells
fill_value=Replace NaN with this value
📝 Why aggfunc='first'? — summary already has ONE row per category. There's nothing to aggregate. 'first' simply picks the single existing value. Using 'sum' would also work but is semantically misleading.
📝 Why reset_index()? — After pivot_table(), category becomes the DataFrame's index. reset_index() moves it back to a regular column so melt() can reference it by name in the next step.

❓ Forgetting reset_index() after pivot_table — what breaks next?

✅ The melt() call in the next step will fail — it needs id_vars='category' but category is the INDEX not a column, so pandas can't find it and raises a KeyError.

melt() — Unpivot Back to Long Format

Charting libraries (matplotlib, seaborn, Plotly) prefer long format — one row per data point. melt() is the exact inverse of pivot_table().

# Melt: wide → long (unpivot)
# id_vars: columns to KEEP as row identifiers (not unpivoted)
# value_vars: columns to COLLAPSE into rows
# var_name: name for the new "metric" column
# value_name: name for the new "value" column
long_df = pivot_df.melt(
    id_vars='category',
    value_vars=['total_orders', 'total_returns', 'return_rate'],
    var_name='metric',
    value_name='value'
)

long_df = long_df.sort_values(['category', 'metric']).reset_index(drop=True)

print(long_df)
#  category     metric   value
#  Clothing  return_rate  22.50%
#  Clothing  total_orders    800
#  Clothing  total_returns   180
#  Electronics return_rate  15.00%
#  ...

❓ In melt(), what does id_vars do vs what does value_vars do?

✅ id_vars = columns that stay as identifiers (repeat for each melted row). value_vars = columns that get collapsed into rows. Everything in value_vars becomes a value in the new var_name column.

Complete Solution — All Steps Together

import pandas as pd

orders   = pd.read_csv("exorders.csv")
returns  = pd.read_csv("exreturns.csv")
products = pd.read_csv("exproducts.csv")
trans    = pd.read_csv("extransactions.csv")

# 1. Bridge: transactions links orders → products
order_product = trans[['Order_ID','Product_ID']].drop_duplicates()

# 2. Add category from products
order_cat = order_product.merge(
    products[['product_id','category']],
    left_on='Product_ID', right_on='product_id', how='left')

# 3. Attach category to orders
df = orders.merge(
    order_cat[['Order_ID','category']],
    left_on='order_id', right_on='Order_ID', how='left')

# 4. Flag returns (isin = cleaner than a merge)
df['is_return'] = df['order_id'].isin(returns['order_id'])

# 5. Category-level summary
summary = df.groupby('category').agg(
    total_orders  = ('order_id', 'count'),
    total_returns = ('is_return', 'sum')
).reset_index()
summary['return_rate'] = (
    summary['total_returns'] / summary['total_orders'] * 100
).map('{:.2f}%'.format)
summary['total_returns'] = summary['total_returns'].astype(int)

# 6. Pivot — wide format
pivot_df = summary.pivot_table(
    index='category',
    values=['total_orders','total_returns','return_rate'],
    aggfunc='first'
).reset_index()

# 7. Melt — long format
long_df = pivot_df.melt(
    id_vars='category',
    value_vars=['total_orders','total_returns','return_rate'],
    var_name='metric', value_name='value'
).sort_values(['category','metric']).reset_index(drop=True)
Key Design Decisions
drop_duplicates()Prevents count inflation from multi-line orders
left_on / right_onColumn names differ in case between tables
isin()Cleaner boolean flag vs merge for returns
Rate after groupbyMathematically correct at category level
aggfunc='first'Already 1 row/category — no real aggregation
reset_index()Promotes index back to column for melt()

❓ Why does the solution use isin() instead of merging with the returns table?

✅ isin() produces a clean boolean column directly — no extra columns, no NaN handling needed. A left merge on returns would add return-specific columns and require dealing with NaN for non-returned orders. The boolean from isin() sums naturally (True=1, False=0).

❓ A student accidentally uses pivot() instead of pivot_table(). What error do they get if there are duplicate category entries?

✅ ValueError: Index contains duplicate entries, cannot reshape — pivot() requires unique (index, column) pairs. pivot_table() handles duplicates via aggfunc. For safe pivoting, always prefer pivot_table().
