Q1Technical

Ganadeep runs this query to find absent students:

SELECT COUNT(*) FROM students WHERE name = NULL

What does he get back?

AAn error — NULL isn't allowed in WHERE
BAll rows where name is NULL
C0 — the condition is always false
DNULL
Explanation
You can't use = NULL. NULL is not equal to anything — not even itself. Use IS NULL. WHERE name = NULL is always false, so COUNT returns 0. Ganadeep found 0 absences. He's celebrating. He shouldn't.
Q2Technical

Hritin writes a date filter. Prishita says it's slow. Why?

-- Hritin's query
WHERE YEAR(join_date) = 2026
AYEAR() doesn't work on date columns
BThe syntax is wrong — it should be WHERE(join_date) = YEAR(2026)
CWrapping a column in a function prevents the index from being used
DSQL Server doesn't support YEAR()
Explanation
When you wrap a column in a function (YEAR(join_date)), SQL must compute it for every single row before filtering. The index on join_date becomes useless. Fix: use a range — WHERE join_date >= '2026-01-01' AND join_date < '2027-01-01'.
Q3Technical

Raj writes this query and hits Run. What happens?

SELECT   dept, COUNT(*)
FROM     employees
WHERE    COUNT(*) > 5
GROUP BY dept
AWorks fine — returns departments with more than 5 employees
BError — aggregate functions aren't allowed in WHERE
CReturns empty result set
DReturns all departments
Explanation
Aggregate functions go in HAVING, not WHERE. WHERE runs before grouping (can't aggregate yet). Fix: replace WHERE COUNT(*) > 5 with HAVING COUNT(*) > 5.

Q6Technical

CSHIFT()
DPREV()
Explanation
LAG() looks backward — brings the previous row's value into the current row. LEAD() looks forward. SHIFT() and PREV() don't exist in SQL. Yogesh used LAG() and found his Monday count was 3. He's had worse weeks.
Q7Technical

Sushant writes this to find students who didn't miss class. The absences table has one row where name IS NULL. What does the query return?

SELECT name FROM students
WHERE  name NOT IN (
    SELECT name FROM absences
)
AAll students not in the absences table
B0 rows — the NULL poisons the result
CError — subquery returned NULL
D1 row
The NULL Trap
NOT IN with a NULL in the subquery returns 0 rows, always. Because SQL evaluates name NOT IN (..., NULL) as name != NULL — which is always UNKNOWN (not TRUE). Fix: use NOT EXISTS. Sushant found 0 students who attended. He has a problem.
Q8Technical

AThree separate queries joined with UNION ALL

Q9Technical

SELECT * FROM scores_cte;  -- query 2
AYes — CTEs are reusable across queries
BNo — a CTE only lives for the one statement it belongs to
CError on the WITH clause
DSecond SELECT returns NULL
Explanation
A CTE exists only for the single statement it's defined in. The second SELECT is a separate statement — it doesn't know about scores_cte. If you want reusability across statements, use a view or a temp table.
Q10Technical

Saket wants a running total of sales per salesperson over time. What goes in the blank?

SELECT salesperson, sale_date, amount,
    SUM(amount) OVER (___)
FROM sales
APARTITION BY sale_date ORDER BY salesperson
BORDER BY sale_date
CPARTITION BY salesperson ORDER BY sale_date
DGROUP BY salesperson
Explanation
PARTITION BY salesperson resets the running total for each new person. ORDER BY sale_date accumulates day by day within that person. Without PARTITION BY, you'd get a running total across all salespeople merged together — not what Saket wanted.
Q11Technical

Santosh writes a recursive CTE that starts at n = 1 and keeps going while n < 5. How many rows does it return?

WITH counter AS (
    SELECT 1 AS n          -- base case
    UNION ALL
    SELECT n + 1
    FROM   counter
    WHERE  n < 5          -- terminates here
)
SELECT * FROM counter
A4 rows
B5 rows
C6 rows
DInfinite loop
Explanation
Trace it: base case gives n=1. Then n=2, 3, 4, 5. When n=5, the WHERE (n < 5) is FALSE — recursion stops. Result: 1, 2, 3, 4, 5 → 5 rows. The last row (5) is produced, then the next iteration checks 5 < 5 = false, and stops.

Q13Technical

Bysani asks: what's the real difference between DELETE and TRUNCATE?

ANo difference — both remove all rows
BDELETE can have WHERE; TRUNCATE removes all rows, is faster, and can't be rolled back in some configs
CTRUNCATE is for tables, DELETE is for views
DDELETE is DDL, TRUNCATE is DML
Explanation
DELETE is DML — logs each row deletion, can have WHERE, can be rolled back. TRUNCATE is DDL — removes all rows by deallocating pages, faster, resets identity counters, but can't filter rows. Use TRUNCATE to empty a table fast; use DELETE when you need to filter.
Q14Technical

Shivam wants to rank students by score within each batch group. What goes inside OVER()?

RANK() OVER ( ___ ) AS group_rank
AORDER BY score DESC
BPARTITION BY group_name
CPARTITION BY group_name ORDER BY score DESC
DGROUP BY group_name ORDER BY score DESC
Explanation
PARTITION BY group_name resets the ranking for each group. ORDER BY score DESC determines the rank order within each group. Without PARTITION BY, you'd get a single global ranking — students would be ranked 1 through 25, ignoring groups. GROUP BY is not valid inside OVER().
Q15Technical

Sukrit wants to find managers who have at least one direct report. Which is most efficient?

AWHERE (SELECT COUNT(*) FROM emp WHERE manager_id = m.id) > 0
BWHERE EXISTS (SELECT 1 FROM emp WHERE manager_id = m.id)
CJOIN employees ON manager_id = id
DWHERE manager_id IS NOT NULL
Explanation
EXISTS stops as soon as it finds one matching row. COUNT(*) > 0 counts ALL matching rows, then checks if it's more than 0 — wasteful. EXISTS wins on performance whenever you just need to check if something exists, not how many there are.
Q16Riddle

I filter rows. But I only get to act after the groups are already formed. My cousin filters before the groups even exist. We look similar but we run at completely different moments.

Who are we?

Answer
HAVING (runs after GROUP BY — filters groups) and WHERE (runs before GROUP BY — filters rows). You can't use an aggregate function in WHERE. That's HAVING's job.
Q17Riddle

I look exactly like a table. I have a name. I can be queried with SELECT, WHERE, and JOIN. But the moment my one statement ends, I cease to exist. I leave no trace.

What am I?

Answer
A CTE — Common Table Expression (the WITH clause). It lives only for the duration of the single query it belongs to. Want it to persist? Use a temp table (#table) or a view.
Q18Riddle

I bring the value from the row before you into your current row. My twin brings the value from the row after you. Together, analysts use us to spot trends — "did things go up or down from yesterday?"

Who are we?

Answer
LAG() (looks backward — previous row) and LEAD() (looks forward — next row). Both are window functions. Both return NULL at the edges (no previous row on the first row, no next row on the last row).
Q19Riddle

I am NULL. Aman Shankar wrote WHERE name = NULL to find me. He found nothing. Aman Thapliyal wrote WHERE name != NULL. He also found nothing.

How must you treat me?

Answer
Use IS NULL and IS NOT NULL. NULL is not a value — it's the absence of a value. In SQL, NULL = NULL is UNKNOWN, not TRUE. NULL is not equal to itself. Only IS NULL can detect it.
Q20Riddle

I am the part of a Recursive CTE that runs exactly once. I produce the first rows. Without me, the recursion has no starting point — it simply cannot begin.

What am I called?

Answer
The Base Case (also called the Anchor Member). It's the SELECT before the UNION ALL that has no reference to the CTE itself. It runs once and produces the seed rows that the recursive part then builds upon.
Q21Riddle

I contain the word "ALL" but I never remove duplicates. My cousin does remove duplicates but costs more to run. We both stack result sets on top of each other.

Who are we?

Answer
UNION ALL (keeps all rows including duplicates — faster) and UNION (removes duplicates — slower because it has to sort and deduplicate). In Recursive CTEs, you must use UNION ALL — UNION is not allowed in the recursive part.
Q22Riddle

Devanand asked: "What's the thing in a Recursive CTE that stops the loop?" The instructor said: "It's not one thing — it's actually two mechanisms."

What are the two?

Answer
1. Natural termination: when the recursive JOIN produces zero matching rows, the loop stops automatically. 2. Safety guard: WHERE level < 20 (or similar) — prevents infinite loops if your data accidentally has cycles. Always add the safety guard.
Q23Riddle

I rotate your data 90 degrees. What were rows become my columns. My twin rotates it back the other way. Analysts love me for dashboards. DBAs tolerate me.

Who are we?

Answer
PIVOT (rows → columns) and UNPIVOT (columns → rows). PIVOT needs you to name the columns explicitly — SQL doesn't auto-detect them. For dynamic column names, you'd need dynamic SQL. That's a Day 5 problem.
