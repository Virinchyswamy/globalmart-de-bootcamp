Day 1 — Basic SQL

SELECT · WHERE · GROUP BY · HAVING · ORDER BY

Scenario: Instructor tracked how many chai cups each person consumed this week. Results are alarming.

-- Who has a chai problem? (threshold: > 8 cups/week)
SELECT
    name,
    SUM(cups)              AS total_cups,
    ROUND(AVG(cups), 1)   AS avg_per_day
FROM   chai_log
WHERE  week = 'Week 1'
GROUP BY name
HAVING   SUM(cups) > 8        -- HAVING filters AFTER grouping
ORDER BY total_cups DESC

Heemansh91.8borderline

Key distinction: WHERE filters before grouping (filters rows). HAVING filters after grouping (filters group results). You cannot use SUM() inside a WHERE.

JOIN rules of thumb:
INNER JOIN — only matching rows on both sides
LEFT JOIN — all from left + matches from right (NULL if no match)
RIGHT JOIN — all from right + matches from left (nobody uses this; just flip the tables and LEFT JOIN)

Day 1 — Subqueries

Subqueries — A Query Inside a Query

Scenario: Who scored above the batch average on the quiz? The query figures out the average itself.

-- The inner query runs FIRST
-- Then the outer query uses that result

SELECT name, score
FROM   quiz_scores
WHERE  score > (SELECT AVG(score) FROM quiz_scores)
ORDER BY score DESC

Step 1 — inner query runs:
SELECT AVG(score) FROM quiz_scores
Returns: 62.5

Step 2 — outer query uses it:
WHERE score > 62.5

Subqueries can go in: WHERE · FROM · SELECT · HAVING

Day 1 — CTEs

CTEs — WITH clause

Same result as the subquery. But now someone else can read your code without getting a headache.

Before (nested subquery — hard to read)

SELECT name, score
FROM quiz_scores
WHERE score > (
    SELECT AVG(score)
    FROM quiz_scores
    WHERE score > (
        SELECT MIN(score)
        FROM quiz_scores
    )
)

Nobody knows what this does. Including the person who wrote it.

After (CTE — readable)

WITH valid_scores AS (
    SELECT * FROM quiz_scores
    WHERE  score > (SELECT MIN(score) FROM quiz_scores)
),
avg_score AS (
    SELECT AVG(score) AS avg_val
    FROM valid_scores
)
SELECT v.name, v.score
FROM   valid_scores v, avg_score a
WHERE  v.score > a.avg_val
ORDER BY v.score DESC

CTE rules:

  • Starts with WITH cte_name AS ( ... )
  • Multiple CTEs: separate with commas, only one WITH
  • Each CTE can reference the ones above it
  • CTEs exist only for the duration of that query

Day 2 — Window Functions

ROW_NUMBER · RANK · DENSE_RANK

Scenario: Quiz leaderboard. Harsh and Raj both scored 85. How you handle the tie matters — pick the wrong function and someone files a complaint.

SELECT
    name, score,
    ROW_NUMBER()  OVER (ORDER BY score DESC) AS row_num,
    RANK()        OVER (ORDER BY score DESC) AS rnk,
    DENSE_RANK()  OVER (ORDER BY score DESC) AS d_rnk
FROM quiz_scores

ROW_NUMBER

Always unique. Ties get arbitrary order. 3, 4 — no debate.

RANK

Ties get same rank. Next rank skips. 3, 3, 5 — gap after tie.

DENSE_RANK

Ties get same rank. No skip. 3, 3, 4 — continuous.

LAG · LEAD · Running Total (SUM OVER)

Scenario: Tracking Yogesh's daily chai consumption. The running total is a cry for help.

SELECT
    day, cups,
    LAG(cups)  OVER (ORDER BY day) AS yesterday_cups,
    LEAD(cups) OVER (ORDER BY day) AS tomorrow_cups,
    SUM(cups)  OVER (ORDER BY day) AS running_total
FROM   chai_log
WHERE  name = 'Yogesh'
ORDER BY day

LAG

Looks back — brings the previous row's value into the current row.

LEAD

Looks forward — brings the next row's value into the current row.

SUM OVER

Accumulates. Each row adds to the previous total. Use PARTITION BY to reset per group.

Day 3 — SQL Optimization

SQL Optimization — Stop Making the DBA Cry

Three patterns that slow your query to a crawl, and how to fix them.

Pattern 1 — Function on column in WHERE

-- BAD: index can't be used
WHERE YEAR(order_date) = 2024
WHERE UPPER(name) = 'YOGESH'

Fix — filter on the value

-- GOOD: index works
WHERE order_date >= '2024-01-01'
  AND order_date <  '2025-01-01'
WHERE name = 'Yogesh'

Wrapping a column in a function forces SQL to compute it for every row before filtering.

Pattern 2 — SELECT *

-- BAD: pulls all columns
SELECT * FROM ex_orders
JOIN ex_customers ...
JOIN ex_locations ...

Fix — name your columns

-- GOOD: only what you need
SELECT
    o.order_id,
    c.customer_name,
    l.state
FROM ex_orders o ...

SELECT * also breaks when someone adds or removes a column. Name your columns.

Pattern 3 — Non-SARGable NULL check

-- BAD: can't use index
WHERE ISNULL(discount, 0) = 0

-- BAD: implicit conversion
WHERE customer_id = '12345'
-- (customer_id is INT)

Fix — explicit conditions

-- GOOD: sargable
WHERE (discount IS NULL
    OR discount = 0)

WHERE customer_id = 12345
-- (matching data types)

SARGable = Search ARGument ABLE — the query engine can use an index on it.

Also remember: Use EXISTS instead of COUNT(*) > 0. Avoid DISTINCT to fix a bad JOIN (fix the JOIN instead). Filter early — in WHERE, not HAVING.

Day 4 — ROLLUP · CUBE · GROUPING SETS

ROLLUP · CUBE · GROUPING SETS

Scenario: Class attendance by group and day. You want group totals, day totals, and a grand total — in one query.

-- ROLLUP: subtotals in hierarchy order
SELECT
    group_num,
    day,
    COUNT(*) AS attended
FROM   attendance
WHERE  attended = 1
GROUP BY ROLLUP(group_num, day)
-- CUBE: every possible combination
GROUP BY CUBE(group_num, day)

-- GROUPING SETS: you choose exactly which
GROUP BY GROUPING SETS(
    (group_num, day),  -- detail level
    (group_num),       -- group total only
    ()                 -- grand total
)

ROLLUP: Subtotals in hierarchy. (G1+Mon), then (G1 total), then grand total.
CUBE: Every combination — by day too, not just by group. Expensive. Only when you need all dimensions.
GROUPING SETS: Surgically precise. You say exactly which groupings you want.

NOT IN vs NOT EXISTS — the NULL trap

-- If bonus_attempts has even ONE NULL name:
WHERE name NOT IN (
    SELECT name FROM bonus_attempts
-- includes NULLs → returns 0 rows!
)

NOT IN with NULLs in the subquery = no rows returned. Ever. Silent and catastrophic. Use NOT EXISTS instead.

Day 4 — Recursive CTE

Recursive CTE — The Self-Referencing Loop

Scenario: Someone forwarded a meme in the class WhatsApp group. It spread. SQL traces the entire chain.

WITH meme_trail AS (

    -- BASE CASE: who sent it first?
    SELECT
        from_person, to_person,
        CAST(from_person + ' → ' + to_person
             AS VARCHAR(MAX))   AS chain,
        1                        AS hop
    FROM  meme_chain
    WHERE from_person = 'Raj'  ← anchor

    UNION ALL

        -- RECURSIVE CASE: who did each person send to?
    SELECT
        m.from_person, m.to_person,
        CAST(mt.chain + ' → ' + m.to_person
             AS VARCHAR(MAX)),
        mt.hop + 1
    FROM  meme_chain m
    JOIN  meme_trail mt
        ON  m.from_person = mt.to_person
    WHERE mt.hop < 20  ← safety guard
)
SELECT to_person, hop, chain
FROM   meme_trail
ORDER BY hop

Payal2Raj → Prishita → Payal
Ganadeep3Raj → … → Ganadeep

Base Case

Runs once. The starting row(s). The anchor.

Recursive Case

Joins back to CTE. Runs until JOIN returns 0 rows.

Termination

Gaurav told nobody → no match → stops automatically.

"Recursive CTE is just a loop with a memory. Each iteration knows what the previous one found."
