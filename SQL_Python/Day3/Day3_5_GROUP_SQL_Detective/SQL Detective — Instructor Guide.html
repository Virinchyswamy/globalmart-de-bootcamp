Group 1 · LogisticsAman S. · Aman T. · Amardeep · Aviskar · Bysani
ROUND 1 — CTE Top 5 Cities by Orders
WITH city_orders AS (
    SELECT l.city, l.state,
           COUNT(o.order_id) AS order_count
    FROM ex_orders o
    LEFT JOIN ex_customers c
        ON o.customer_id = c.customer_id
    LEFT JOIN ex_locations l
        ON c.postal_code = l.postal_code
    WHERE l.city IS NOT NULL
    GROUP BY l.city, l.state
)
SELECT TOP 5 city, state, order_count
FROM city_orders
ORDER BY order_count DESC
city | state | order_count
  • Exactly 5 rows
  • Ordered by order_count DESC
  • No NULL in city column
  • CTE used (not a subquery inline)
ROUND 2 — DATEDIFF Late Delivery Top 5 States
SELECT TOP 5
    l.state,
    COUNT(*)                                   AS late_orders,
    AVG(DATEDIFF(day,
        o.order_estimated_delivery_date,
        o.order_delivered_date))               AS avg_delay_days
FROM ex_orders o
LEFT JOIN ex_customers c ON o.customer_id=c.customer_id
LEFT JOIN ex_locations l ON c.postal_code=l.postal_code
WHERE o.order_delivered_date >
      o.order_estimated_delivery_date
  AND o.order_delivered_date IS NOT NULL
GROUP BY l.state
ORDER BY late_orders DESC
  • 5 rows · ordered by late_orders DESC
  • avg_delay_days is a positive number
  • No NULL in state column
Key concept: DATEDIFF(day, start, end) + WHERE delivered > estimated + IS NOT NULL guard on AVG

R1 Concept · CTE

CTE separates the aggregation logic from the TOP N selection. Students must understand that you cannot do SELECT TOP 5 ... GROUP BY directly — you aggregate first, then filter with TOP or HAVING in the outer query.

R2 Concept · DATEDIFF

DATEDIFF(day, start, end) — arguments are in order of start to end, NOT "which date comes later". The IS NOT NULL guard prevents NULL values from skewing the AVG.

If a group gets empty results in R2 — check they have the WHERE condition correct (delivered > estimated).
Group 2 · FinanceDevanand · Harsh · Heemansh · Hritin · Kumar Pratik
ROUND 1 — DENSE_RANK Top 5 Customers by Revenue
WITH customer_rev AS (
    SELECT c.customer_name,
           ROUND(SUM(t.Sales_Amount), 2) AS total_revenue
    FROM ex_transactions t
    LEFT JOIN ex_orders o
        ON t.Order_ID = o.order_id
    LEFT JOIN ex_customers c
        ON o.customer_id = c.customer_id
    GROUP BY c.customer_name
)
SELECT TOP 5
    customer_name,
    total_revenue,
    DENSE_RANK() OVER (ORDER BY total_revenue DESC)
        AS revenue_rank
FROM customer_rev
ORDER BY revenue_rank
  • 5 rows · ordered by revenue_rank ASC
  • revenue_rank starts at 1
  • Window function is in outer SELECT, not inside CTE
ROUND 2 — CASE WHEN in GROUP BY
SELECT
    CASE WHEN Discount > 0
         THEN 'Discounted'
         ELSE 'Full Price' END          AS price_type,
    COUNT(DISTINCT Order_ID)            AS order_count,
    ROUND(SUM(Sales_Amount), 2)         AS total_revenue,
    ROUND(AVG(Sales_Amount), 2)         AS avg_revenue
FROM ex_transactions
GROUP BY
    CASE WHEN Discount > 0
         THEN 'Discounted'
         ELSE 'Full Price' END
ORDER BY total_revenue DESC
  • Exactly 2 rows: 'Discounted' and 'Full Price'
  • CASE WHEN repeated exactly in GROUP BY
  • Uses COUNT(DISTINCT Order_ID)
  • Only ex_transactions — no joins
Key concept: SQL Server does not allow GROUP BY alias — the exact CASE WHEN expression must be repeated

R1 Concept · Window function over aggregate

You cannot apply DENSE_RANK() OVER (...) to a column that is itself the result of SUM() in the same SELECT level. The CTE creates an intermediate result set (flat table with total_revenue), and the window function is applied in the next SELECT on top of it.

R2 Concept · CASE WHEN in GROUP BY

SQL Server evaluates GROUP BY before SELECT aliases — so you must copy the full CASE WHEN logic into GROUP BY. This is a common mistake beginners make (trying to GROUP BY 'price_type').

Group 3 · CustomerGaurav · Ganadeep · Payal · Prishita · Raj
ROUND 1 — HAVING with Subquery
SELECT c.segment,
       ROUND(AVG(t.Sales_Amount), 2)  AS avg_order_value
FROM ex_transactions t
LEFT JOIN ex_orders o
    ON t.Order_ID = o.order_id
LEFT JOIN ex_customers c
    ON o.customer_id = c.customer_id
GROUP BY c.segment
HAVING AVG(t.Sales_Amount) > (
    SELECT AVG(Sales_Amount)
    FROM ex_transactions
)
ORDER BY avg_order_value DESC
  • Only segments above overall average appear
  • Ordered by avg_order_value DESC
  • HAVING used — not WHERE
ROUND 2 — Profit Margin by Segment
SELECT
    c.segment,
    ROUND(SUM(t.Sales_Amount), 2)        AS total_revenue,
    ROUND(SUM(t.COGS), 2)                AS total_cogs,
    ROUND(SUM(t.Sales_Amount-t.COGS),2)  AS total_profit,
    ROUND(SUM(t.Sales_Amount-t.COGS)
          / SUM(t.Sales_Amount)*100, 2)  AS profit_margin_pct
FROM ex_transactions t
LEFT JOIN ex_orders o ON t.Order_ID=o.order_id
LEFT JOIN ex_customers c ON o.customer_id=c.customer_id
GROUP BY c.segment
ORDER BY total_profit DESC
  • 3 rows: Consumer, Corporate, Home Office
  • profit_margin_pct between 0–100
  • Ordered by total_profit DESC
Key concept: margin = SUM(rev−cost)/SUM(rev)*100 — divide aggregate sums, not average of row-level ratios

R1 Concept · HAVING vs WHERE

WHERE filters rows before aggregation. HAVING filters groups after. A scalar subquery inside HAVING is evaluated once and compared against each group's aggregate value. Common mistake: putting the subquery in WHERE instead of HAVING.

R2 Concept · Profit margin aggregation

The margin formula must use SUM-level division. AVG(Sales_Amount - COGS) / AVG(Sales_Amount) gives a different (wrong) answer — the correct approach sums both numerator and denominator separately before dividing.

Group 4 · OperationsKamal · Sneha · Saket · Santosh · Shivam
ROUND 1 — Running Total (Window Function)
WITH monthly AS (
    SELECT YEAR(order_purchase_date)   AS yr,
           MONTH(order_purchase_date)  AS mo,
           COUNT(order_id)             AS monthly_orders
    FROM ex_orders
    WHERE order_purchase_date IS NOT NULL
    GROUP BY YEAR(order_purchase_date),
             MONTH(order_purchase_date)
)
SELECT yr, mo, monthly_orders,
       SUM(monthly_orders) OVER (
           ORDER BY yr, mo
       ) AS running_total
FROM monthly
ORDER BY yr, mo
  • One row per month
  • running_total grows monotonically (never decreases)
  • Ordered by yr, mo ASC
  • Window function in outer SELECT, not inside CTE
ROUND 2 — Ship Mode Speed (DATEDIFF ×2)
SELECT
    ship_mode,
    COUNT(order_id)                     AS total_orders,
    AVG(DATEDIFF(day,
        order_purchase_date,
        order_dispatched_date))         AS avg_days_to_dispatch,
    AVG(DATEDIFF(day,
        order_purchase_date,
        order_delivered_date))          AS avg_days_to_deliver
FROM ex_orders
WHERE order_dispatched_date IS NOT NULL
  AND order_delivered_date  IS NOT NULL
GROUP BY ship_mode
ORDER BY avg_days_to_deliver ASC
  • 3 rows (one per ship mode)
  • avg_days_to_deliver ascending (fastest first)
  • Both IS NOT NULL filters applied
  • Only ex_orders — no joins
Key concept: two separate DATEDIFF() calls in one SELECT, both wrapped in AVG() — one pass gives two different averages

R1 Concept · Cumulative SUM OVER

SUM(col) OVER (ORDER BY ...) without a PARTITION BY creates a running total across all rows ordered by the specified column(s). Each row's value is the sum of all previous rows plus itself. The CTE is needed because you cannot reference an aggregate alias in a window function in the same SELECT.

R2 Concept · Multiple DATEDIFF

DATEDIFF arguments: DATEDIFF(unit, earlier_date, later_date). Both calculations run per row before AVG aggregates them across the group. IS NOT NULL prevents partial order records from skewing averages.

Group 5 · StrategySujit · Sukrit · Sushant · Nikshitha · Yogesh
ROUND 1 — CTE Regional Summary
WITH region_summary AS (
    SELECT l.region,
           ROUND(SUM(t.Sales_Amount), 2)    AS total_revenue,
           COUNT(DISTINCT c.customer_id)    AS unique_customers,
           ROUND(AVG(t.Sales_Amount), 2)    AS avg_order_value
    FROM ex_transactions t
    LEFT JOIN ex_orders o ON t.Order_ID=o.order_id
    LEFT JOIN ex_customers c ON o.customer_id=c.customer_id
    LEFT JOIN ex_locations l ON c.postal_code=l.postal_code
    WHERE l.region IS NOT NULL
    GROUP BY l.region
)
SELECT region, total_revenue,
       unique_customers, avg_order_value
FROM region_summary
ORDER BY total_revenue DESC
  • One row per region (typically 4)
  • unique_customers uses DISTINCT customer_id
  • Ordered by total_revenue DESC
ROUND 2 — Revenue % by Region (Subquery in SELECT)
SELECT
    l.region,
    ROUND(SUM(t.Sales_Amount), 2)       AS total_revenue,
    ROUND(SUM(t.Sales_Amount) * 100.0
          / (SELECT SUM(Sales_Amount)
             FROM ex_transactions), 2)  AS revenue_pct
FROM ex_transactions t
LEFT JOIN ex_orders o ON t.Order_ID=o.order_id
LEFT JOIN ex_customers c ON o.customer_id=c.customer_id
LEFT JOIN ex_locations l ON c.postal_code=l.postal_code
WHERE l.region IS NOT NULL
GROUP BY l.region
ORDER BY total_revenue DESC
  • One row per region
  • revenue_pct values sum to ~100
  • Ordered by total_revenue DESC
  • * 100.0 (not * 100) for decimal result
Key concept: scalar subquery in SELECT — runs once per query, not per row. Returns the global total to use as the denominator

R1 Concept · COUNT(DISTINCT)

A customer who placed 10 orders would be counted 10 times with plain COUNT. COUNT(DISTINCT customer_id) collapses duplicates — giving the actual number of unique customers, not transaction count.

R2 Concept · Scalar subquery in SELECT

A subquery in the SELECT clause is evaluated once and returns a single value (scalar). Every row's SUM(Sales_Amount) is then divided by this global total. The * 100.0 forces float division — without the decimal, SQL Server would do integer division and return 0.
