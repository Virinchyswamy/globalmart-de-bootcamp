Why a Correlated Subquery?

We can't just do LEFT JOIN and check for NULL — that's one approach. The scenario specifically requires you to use NOT EXISTS.

NOT EXISTS runs a mini-subquery for each row of the outer query, checking if that order_id exists in ex_returns. If not → row is kept.

The word "correlated" means the subquery references a column from the outer query (o.order_id).

🔗 Understanding Correlated Subqueries

Regular Subquery — runs once

-- This subquery runs ONCE for the whole query
-- Result is a static list of values
SELECT * FROM orders
WHERE customer_id IN (
    SELECT customer_id FROM vip_customers
);
-- Subquery is independent — no outer reference

Correlated Subquery — runs per row

-- This subquery runs ONCE FOR EACH ROW in ex_orders
-- It references o.order_id from the outer query
-- ↓ This is the "correlation"
WHERE NOT EXISTS (
    SELECT 1
    FROM ex_returns r
    WHERE r.order_id = o.order_id
    -- ↑ o.order_id comes from outer query row
)

How it works row-by-row:

For each order in ex_orders, SQL asks: "Does this order_id appear anywhere in ex_returns?"

• If YES → NOT EXISTS = FALSE → row is EXCLUDED
• If NO → NOT EXISTS = TRUE → row is INCLUDED ✅

The SELECT 1 inside doesn't matter — SQL only cares whether the subquery returns ANY rows, not what it returns.

NOT EXISTS vs LEFT JOIN + IS NULL:
Both find the same rows. NOT EXISTS is often cleaner and more readable for "exclusion" logic. LEFT JOIN approach: LEFT JOIN ex_returns r ON o.order_id = r.order_id WHERE r.order_id IS NULL — same result, different style.

Live Demo — Find All Retained Orders 📦

Tables: ex_orders, ex_returns | mskl-masterclass
-- Main query: select delivered orders from ex_orders
-- that do NOT appear in ex_returns
SELECT
    o.order_id,
    o.customer_id,
    -- CAST removes the time portion from datetime
    -- so output shows clean dates like 2017-01-05
    CAST(o.order_purchase_date AS DATE) AS order_purchase_date,
    o.order_status
FROM ex_orders o
WHERE
    -- Condition 1: order was actually delivered
    o.order_status = 'delivered'
    -- Condition 2: this order_id does NOT exist in ex_returns
    -- Correlated: references o.order_id from outer query
    -- SELECT 1 = just checking for existence, value doesn't matter
    AND NOT EXISTS (
        SELECT 1
        FROM ex_returns r
        WHERE r.order_id = o.order_id
    )
ORDER BY order_purchase_date;

To get just the count, wrap in a CTE:

WITH summary AS (
    SELECT o.order_id, o.customer_id,
        CAST(o.order_purchase_date AS DATE) AS order_purchase_date,
        o.order_status
    FROM ex_orders o
    WHERE NOT EXISTS (
        SELECT 1
        FROM ex_returns r
        WHERE r.order_id = o.order_id
    ) AND o.order_status = 'delivered'
)
SELECT COUNT(*) AS order_count FROM summary;

❓ What does SELECT 1 mean inside a NOT EXISTS subquery?

✅ It means "return any value" — SQL only checks WHETHER rows exist, not WHAT they contain. SELECT 1, SELECT *, SELECT 'x' all behave identically inside EXISTS/NOT EXISTS.

Logic Walkthrough

For order CA-2015-154956:

1. Outer query: pick up CA-2015-154956 from ex_orders
2. Subquery runs: SELECT 1 FROM ex_returns WHERE order_id = 'CA-2015-154956'
3. Subquery FINDS a match → returns a row
4. NOT EXISTS = FALSE → this row is EXCLUDED

For order CA-2014-146500:

1. Outer query: pick up CA-2014-146500 from ex_orders
2. Subquery runs: SELECT 1 FROM ex_returns WHERE order_id = 'CA-2014-146500'
3. Subquery finds NO match → returns no rows
4. NOT EXISTS = TRUE → this row is INCLUDED ✅

NOT EXISTS vs LEFT JOIN NULL check — which to use?
Both find the same rows. In most SQL engines they perform similarly. The convention for this module uses NOT EXISTS because it directly expresses the intent: "find orders for which NO return record exists." It reads more naturally for exclusion logic.
