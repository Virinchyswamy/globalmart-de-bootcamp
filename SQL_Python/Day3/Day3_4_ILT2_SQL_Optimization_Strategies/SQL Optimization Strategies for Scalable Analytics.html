📚 Indexing — The Library Analogy

Without an index, SQL must check every row. With an index, it jumps directly to relevant rows. Think of it like a library.

📖
Clustered Index

Determines physical row order in the table. One per table. Auto-created on primary key. Best for range queries and sorting.

CREATE CLUSTERED INDEX
IX_Student_Score
ON student(total_score DESC);
🗂️
Non-Clustered Index

Separate structure with pointers. Multiple allowed per table. Best for WHERE, JOIN, ORDER BY columns.

CREATE NONCLUSTERED INDEX
IX_Student_Name
ON student(name ASC);
Scan TypeSpeedWhen
Index SeekFast ✅Index exists and is used
Index ScanMedium ⚠️Index exists but range is large
Table ScanSlow ❌No index — reads every row

❓ What is the PRIMARY function of a clustered index?

✅ It determines the physical order of rows in a table — rows are stored on disk in the index order. Since each table can only have ONE clustered index, choose wisely (usually the primary key).

❓ How do indexes improve SQL query performance?

✅ They allow the engine to perform an index seek — jumping directly to relevant rows using pointers instead of scanning the entire table. Like using a library index card vs browsing every shelf.

Best Practice for Indexing:
• Always define primary keys on every table
• Use numeric keys (INT/BIGINT) over string IDs
• Create non-clustered indexes on WHERE/JOIN/ORDER BY columns
• Avoid indexing rarely-queried columns

⚡ Best Practices 1–3: The Query Foundation

1 Fetch Only Necessary Columns — No SELECT *

❌ SELECT * FROM transactions WHERE order_date >= '2025-05-01' — scans ALL columns including shipping_address, billing_address etc.

✅ SELECT product_id, SUM(quantity * price - discount) AS total_sales FROM transactions WHERE order_date >= '2025-05-01' GROUP BY product_id

SELECT * can process 10 GB; targeted SELECT may only scan 3 GB. Same result, 3× the cost difference.

2 Apply WHERE Conditions Early — Don't Wait Until HAVING

❌ GROUP BY state, product_category HAVING state = 'New York' — groups ALL 50M rows first, then filters. Wasteful.

✅ WHERE state = 'New York' GROUP BY product_category — filters first, only 2M rows go into GROUP BY.

HAVING is for filtering AFTER aggregation. Use WHERE for row-level filtering before aggregation.

3 Start WITH the Highest Granularity Table and Join Forward

❌ FROM locations (500 rows) → JOIN customers → JOIN orders → JOIN transactions (100M rows) — data explodes outward

✅ FROM transactions (100M rows) → JOIN orders → JOIN customers → JOIN locations — reduces as you go

Transactions has the most rows (highest granularity). Start there, join toward smaller lookup tables.

⚡ Best Practices 4–6: Filtering, Types & Deduplication

4 Filter High-Cardinality Columns First

High cardinality = many unique values (customer_id, order_id). Low cardinality = few unique values (state, category).

✅ Filtering on order_id or customer_id first eliminates most rows immediately. Cardinality hint: WHERE customer_id = 10298 AND state = 'New York' — customer filter first.

High-cardinality filters narrow the dataset dramatically. Fewer rows = cheaper subsequent operations.

5 Choose Data Types Wisely — Numeric IDs Over String IDs

❌ customer_id = 'CUST_000001' (VARCHAR) — string comparison, larger index, slower join

✅ customer_id = 1002 (INT) — numeric comparison, compact index, faster join

INT uses 4 bytes. VARCHAR(20) uses up to 20 bytes. 5× storage difference × millions of rows = significant performance gap.

6 Prefer GROUP BY Over DISTINCT

❌ SELECT DISTINCT customer_id FROM transactions — fetches all rows, THEN removes duplicates

✅ SELECT customer_id FROM transactions GROUP BY customer_id — groups during the scan, reduces early

GROUP BY groups rows AS they are scanned. DISTINCT first materialises all rows, then deduplicates. GROUP BY is faster and also gives you aggregations.

❓ Why is GROUP BY preferred over DISTINCT for large datasets?

✅ GROUP BY groups data during the scan itself, reducing unnecessary memory usage. DISTINCT fetches all rows first, then eliminates duplicates — two passes instead of one.

⚡ Best Practices 7–10: Architecture-Level Wins

7 Pre-Aggregate Using Views or Temp Tables

If the same complex joins run for every daily/weekly dashboard, save the result as a VIEW. Downstream queries hit the lightweight view instead of re-running expensive joins.

CREATE VIEW monthly_sales_summary AS
SELECT l.region,
    FORMAT(o.order_date, 'yyyy-MM') AS month,
    SUM(t.sales_amount) AS total_sales
FROM transactions t
JOIN orders o ON t.order_id = o.order_id
JOIN locations l ON o.location_id = l.location_id
GROUP BY l.region,
    FORMAT(o.order_date, 'yyyy-MM');

8 Use Numeric Primary Keys + Clustered Indexes

Numeric PKs → faster joins, smaller indexes, more efficient sorting. Clustered indexes ensure rows are physically stored in join/filter order. Index Seek >> Table Scan.

9 GROUP BY Over DISTINCT (reinforced)

Applies everywhere you need unique rows. When aggregating counts, sums, or averages — GROUP BY is natural and efficient. DISTINCT is a last resort.

10 Pre-Aggregated Views / Summary Tables

Create scheduled summary tables (materialized views or temp tables) for repetitive report logic. Week-over-week sales? Pre-aggregate Sunday night. Dashboards query the summary, not raw 100M row tables.

❓ Which is MOST efficient for generating weekly regional sales reports?

✅ Creating a pre-aggregated view that summarises weekly sales, then querying the view. Avoids re-running complex joins and aggregations for every report request.

❓ Which query is MORE efficient for calculating total sales per product for May 2025?

a) SELECT * FROM transactions WHERE order_date >= '2025-05-01'
b) SELECT product_id, SUM(quantity * price - discount) FROM transactions WHERE order_date >= '2025-05-01' AND order_date < '2025-06-01' GROUP BY product_id

✅ b) — selects only needed columns, applies tight date range (upper bound included), and aggregates in-query. Option a) scans all columns and all dates from May onwards.

❓ Why are numeric primary keys preferred over alphanumeric strings?

✅ Numeric keys consume less storage and are faster for sorting, comparisons, and indexing. INT = 4 bytes, 'CUST_000001' = 12+ bytes. Every join and filter on this column benefits from the compact numeric type.

🔴 vs 🟢 — Slow Patterns and Their Fixes

🔴 SELECT * + no filter

SELECT *
FROM transactions
WHERE
  state = 'New York';

Scans ALL columns, ALL rows, then filters. Inefficient at scale.

🟢 Targeted SELECT + early filter

SELECT product_category,
  SUM(quantity * price) AS sales
FROM transactions
WHERE state = 'New York'
GROUP BY product_category;

Reads only needed columns. Filters before grouping. 3–5× faster.

🟢 Correct join order

FROM transactions t      -- 100M rows
JOIN orders o           -- 20M rows
  ON t.order_id = o.order_id
JOIN customers c        -- 5M rows
  ON o.customer_id = c.id
JOIN locations l        -- 500 rows
  ON c.location_id = l.id

Starts from fact table, joins progressively to smaller lookup tables.

The mindset shift: Don't write SQL that gets the correct answer. Write SQL that gets the correct answer using the least possible data. Every unnecessary column, every unfiltered row, every repeated aggregation costs money in the cloud.
