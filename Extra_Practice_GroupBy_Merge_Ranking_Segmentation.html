Concept

Why "How Often" + "How Much" Get Combined Into One Score

The business idea behind almost every tiering / segmentation report you'll be asked to build.

The shape of the question, in plain English

A business rarely wants just one number about a customer or a user — it wants a combined picture:

  • How often do they show up? (a frequency metric — smaller is usually better here, meaning less time between visits)
  • How much do they spend per visit, on average? (a value metric — bigger is usually better here)
  • Put those two together into one combined score, so you can sort everyone from "best" to "worst" using a single number
  • Turn that combined score into a small number of labeled groups (a "tier") that a non-technical stakeholder can act on
Why rank instead of just averaging the raw numbers: "days between orders" and "average order value" are measured in totally different units (days vs. dollars) — you can't average them directly. Converting each one to a rank first (a plain number from 1 upward) puts them on the same scale, so averaging the two ranks actually means something.
Python Concept

value_counts() — Count Every Unique Value in a Column

The fastest way to answer "what shows up most often in this column?"

The idea

  • .value_counts() looks at one column, finds every distinct value in it, and counts how many rows have each one
  • The result comes back sorted from most common to least common, automatically
  • .reset_index() turns that result from a "Series with a name as its index" back into a plain, ordinary DataFrame with real columns — mostly a cosmetic tidy-up step
import pandas as pd

df = pd.read_csv("some_table.csv")

# One line: count every unique value in a column, most common first
df['some_category_column'].value_counts().reset_index()

Illustrative result — counting reasons in a made-up column

reasoncount
Reason A15
Reason B9
Reason C6
Reason D4

One line of code, no GROUP BY, no manual counting — this is usually the very first thing you run on any categorical column you're seeing for the first time.

Python Concept

duplicated() & drop_duplicates() — Clean Before You Count

A repeated row silently gets counted twice in every SUM and COUNT that comes after it.

Checking first, then fixing

# duplicated() -- True/False per row, True means "this exact row
# already appeared earlier in the table"
df[df.duplicated()]

# drop_duplicates() removes those repeats, keeping the first copy
df = df.drop_duplicates()

# You can also check/drop duplicates on just ONE column,
# e.g. the same order_id appearing twice by mistake
df[df['order_id'].duplicated()]
df = df.drop_duplicates(subset=['order_id'])

Why this has to come first, always

  • Every groupby().agg() later in this deck trusts that each real-world event (each order, each visit) appears exactly once
  • If one got logged twice by accident, its value gets double-counted in every total, every average, and every rank downstream
  • There's no way to spot this after the fact from the final report — it just quietly looks like a slightly-too-high number
Habit to build: run .duplicated() checks on every raw table you load, before you do anything else with it — even if you don't expect duplicates. It costs one line and saves you from an invisible bug.
Python Concept

pd.to_datetime(..., format=...) and .dt.strftime()

Turning date text into a real date pandas can do math on — and turning it back into text when you need to display it.

Why format=... matters

  • A date column loaded from CSV is just text at first — "01/31/23 14:05", not an actual date pandas understands
  • pd.to_datetime() converts that text into a real datetime — but without format=..., pandas has to guess the layout, and can silently guess wrong (swapping day and month, for example)
  • Telling it the exact format up front removes all the guessing
df['order_date'] = pd.to_datetime(
    df['order_date'], format='%m/%d/%y %H:%M'
)

The format codes you'll actually use

CodeMeans
%Y4-digit year (2023)
%y2-digit year (23)
%mMonth number
%dDay of month
%H / %MHour (24h) / Minute

Going the other direction — once it's a real datetime, .dt.strftime(...) turns it back into text in whatever layout you want:

df['order_date'].dt.strftime('%Y-%m-%d')
# -> "2023-01-31" (readable, sortable, consistent)
Python Concept

Boolean Filtering — Keep Only the Rows You Actually Want

Before aggregating anything, decide which rows even count as "real" activity.

How it works, one piece at a time

df['order_status'] == 'delivered'
# -> a column of True/False, one value per row

delivered = df[df['order_status'] == 'delivered']
# -> wrapping the True/False column in [ ] keeps ONLY the True rows

Why this matters before you aggregate

  • A raw table usually contains successful rows and cancelled/failed/returned ones — a cancelled row has no real value to count
  • If you aggregate before filtering, those rows (often stored as 0 or blank) can drag your averages down for no real reason
  • Rule of thumb: decide "which status values count as real, finished activity" first, filter to just those, and then start aggregating
This is the exact same idea as a SQL WHERE status = 'delivered' — just written as df[df['status'] == 'delivered'] instead.
Python Concept

dropna(subset=[...]) — Remove Rows Missing a KEY Column Only

A blank customer_id makes a row un-groupable — but a blank in an unrelated column shouldn't cost you the whole row.

Check first, then decide

# See which rows are missing a customer_id
df[df['customer_id'].isna()]

# Remove ONLY rows missing customer_id -- leave everything else alone
df = df.dropna(subset=['customer_id'])

The gotcha: forgetting subset=[...]

  • dropna() with no arguments removes a row if any column in it has a missing value — not just the one you care about
  • On a wide table with many optional columns, that can silently delete far more rows than you intended
  • subset=['customer_id'] says exactly what it means: "only check this one column when deciding whether to drop a row"
Always specify subset=[...] when you only care about one or two key columns. Bare dropna() is one of the easiest ways to accidentally throw away good data.
Python Concept

groupby().agg() — Several Stats, One Row Per Entity, One Line of Code

The single most important pattern in this whole deck — everything else builds on top of it.

The named-aggregation syntax

summary = (
    df
    .groupby('customer_id')
    .agg(
        total_orders=('order_id', 'count'),
        total_value=('order_value', 'sum'),
        avg_value=('order_value', 'mean'),
    )
    .reset_index()
)

Read each line as: new_column_name = (source_column, 'how_to_combine_it'). Three completely different summaries, computed in one pass over the data.

Why .reset_index() again?

  • Right after .groupby('customer_id'), pandas makes customer_id the table's index, not a normal column
  • .reset_index() moves it back into an ordinary column — this matters because you'll need customer_id as a normal column to merge on later

Illustrative result — one row per entity:

customer_idtotal_ordersavg_value
C0013150.00
C0024120.00
Python Concept · The Gotcha

np.floor() vs round() vs int() — Three Different Answers From One Number

Picking the wrong one changes your final report's numbers, silently and consistently.

What each one actually does

  • np.floor(x) — always rounds down, no matter what the decimal part is
  • int(x) — truncates toward zero (chops off the decimal part entirely; same as floor for positive numbers)
  • round(x) — rounds to the nearest whole number... except Python uses "banker's rounding" (round half to even) for exact .5 values, which surprises almost everyone the first time

Side by side — verified in a real Python shell

valuenp.floor(value)round(value)int(value)
9.759.0109
6.56.066
7.57.087

Notice round(6.5) gives 6, not 7 — the "nearest even number" wins the tie. round(7.5) gives 8, also the nearest even number. This is not a bug, it's deliberate — but it will not match your intuition until you've seen it once.

Rule of thumb for this kind of report: when a spec says "round down," reach for np.floor() — it's unambiguous. Only use plain round() when you've specifically tested it against a .5 value and confirmed it behaves the way you expect.
Python Concept

merge(how='inner') vs merge(how='left')

Combining several one-row-per-entity tables into one wide table — the choice of "how" decides who survives.

The two you'll use constantly

# 'inner': keep a customer_id ONLY if it exists in BOTH tables
combined = orders_summary.merge(
    value_summary, on='customer_id', how='inner'
)

# 'left': keep EVERY row from the table on the left,
# even if there's no match on the right (fills NaN instead)
combined = combined.merge(
    returns_summary, on='customer_id', how='left'
)

Why the choice actually matters here

  • A customer who has never returned a single order simply won't appear in a returns-only table at all
  • If you merged that with how='inner', that customer would silently vanish from your entire report — not because anything went wrong, but because "inner" only keeps rows present on both sides
  • how='left' guards against this: it keeps every customer from your main table no matter what, filling in NaN (missing) wherever there's genuinely nothing to match
A good default: once you have your main, complete customer list, merge everything else onto it with how='left'. Only use how='inner' when losing unmatched rows is exactly what you want.
Python Concept

Subtracting Two Dates — and Getting a Plain Number of Days Out

Two datetime columns subtracted give you a duration — one more step turns that into a number you can do math with.

The two-step pattern

# Subtracting one datetime column from another gives a "Timedelta"
# -- a SPAN of time, not a plain number
span = df['last_order_date'] - df['first_order_date']

# .dt.days pulls out just the whole number of days from that span
df['days_active'] = span.dt.days

Worked example

First order: 2023-01-01. Last order: 2023-01-31.

2023-01-31 - 2023-01-01 = Timedelta('30 days')
.dt.days -> 30

This "days_active" number becomes the top of the fraction in the very next concept — a frequency metric is always some span of time divided by some count of events.

Python Concept

.rank(method='dense', ascending=...) — Same Idea as SQL's DENSE_RANK()

Now applied directly to a pandas column, no window function syntax required.

Reading the two arguments

  • method='dense' — tied values get the same rank, and the next distinct value's rank does not skip a number (1, 1, 2 — never 1, 1, 3)
  • ascending=True (the default) — the smallest value gets rank 1. Use this when a lower number is actually better.
  • ascending=False — the largest value gets rank 1. Use this when a higher number is better.

Applied to two different metrics, two different directions

# Fewer days between orders = more frequent = better
# -> smallest value should win -> ascending=True (default)
df['frequency_rank'] = (
    df['purchase_frequency'].rank(method='dense').astype(int)
)

# Bigger average order value = better
# -> largest value should win -> ascending=False
df['value_rank'] = (
    df['avg_value'].rank(method='dense', ascending=False).astype(int)
)
Before writing any .rank() call, ask yourself one question first: "for this metric, does a bigger number or a smaller number mean 'better'?" That answer tells you whether ascending should be True or False — get this backwards and every rank in your report is upside down.
Python Concept

Combining Two Ranks, Then Classifying With Your Own Function

apply() lets you run any custom if/elif/else logic, once per row — not just built-in math.

Step 1 — average the two rank numbers

df['avg_rank'] = (
    (df['frequency_rank'] + df['value_rank']) / 2
).astype(int)
# .astype(int) truncates any leftover .5 -- see the rounding slide above.
# (2 + 3) / 2 = 2.5 -> astype(int) -> 2, NOT 3

Step 2 — a plain function, handed to .apply()

def classify(rank):
    if rank >= 300:
        return 'Tier C'
    elif rank >= 150:
        return 'Tier B'
    else:
        return 'Tier A'

# .apply() runs classify() once per row, feeding it that row's avg_rank
df['segment'] = df['avg_rank'].apply(classify)

Whenever your logic needs "if this, then that, otherwise something else" — something a single column formula can't express — write a small function and hand it to .apply(). The exact number and names of the tiers, and where the thresholds sit, will be given to you in the real scenario — the mechanism here is the part worth knowing cold.

Python Concept

isin([...]) — Check Membership in a List, Cleanly

The tidy way to say "any of these specific values," without chaining multiple == with |.

The messy way vs. the clean way

# Works, but gets unwieldy fast
df[(df['value_rank'] == 1) | (df['value_rank'] == 2) | (df['value_rank'] == 3)]

# Same result, much cleaner
df[df['value_rank'].isin([1, 2, 3])]

When you'll reach for this

  • Pulling out "the top N" by rank (ranks 1 through N)
  • Filtering to a specific handful of categories at once, instead of one == per category joined with |
  • Reads almost like English: "where value_rank is in this list"

Then aggregate — collapse those clean rows into one row per customer:

summary = df.groupby('customer_id').agg(
    total_orders=('order_id', 'count'),
    avg_value=('value', 'mean')
).reset_index()
# C001: total_orders=2, avg_value=150.0  (from 100 and 200)
Walkthrough · Part 2 of 3

Bringing In Dates and Merging Everything Together

Now add the frequency metric, and combine every separately-aggregated table into one wide row.

Compute days_active and frequency

duration = df.groupby('customer_id').agg(
    first_order=('order_date', 'min'),
    last_order=('order_date', 'max')
).reset_index()

duration['days_active'] = (
    duration['last_order'] - duration['first_order']
).dt.days
# C001: first_order=Jan 1, last_order=Jan 31 -> days_active=30

Merge the pieces into one wide table

result = summary.merge(duration, on='customer_id', how='inner')

result['purchase_frequency'] = np.floor(
    result['days_active'] / result['total_orders']
).astype(int)
# C001: 30 days_active / 2 total_orders = 15.0 -> floor -> 15

This is exactly where merge(how='left') would matter more in a real dataset — for example, bringing in a returns table where plenty of customers never appear at all.

Walkthrough · Part 3 of 3

Ranking Both Metrics, Then Classifying

The final stretch — turn two raw numbers into ranks, average them, and label the result.

Rank each metric in its correct direction

# Lower purchase_frequency = more frequent = better -> ascending=True
result['frequency_rank'] = result['purchase_frequency'].rank(
    method='dense'
).astype(int)

# Higher avg_value = better -> ascending=False
result['value_rank'] = result['avg_value'].rank(
    method='dense', ascending=False
).astype(int)

Combine and classify

result['avg_rank'] = (
    (result['frequency_rank'] + result['value_rank']) / 2
).astype(int)

result['segment'] = result['avg_rank'].apply(classify)

# Once every customer has a segment, this is the line that tells you
# which group is largest -- the natural last step of a report like this:
result['segment'].value_counts()
A real-world gotcha worth carrying into the actual data: a customer with only 1 order ever has days_active = 0, which makes purchase_frequency = 0 — the smallest possible value. That customer will look "extremely frequent" by the raw number, when really they just don't have enough history yet. Worth noticing in a real report, not something the code fixes on its own.
