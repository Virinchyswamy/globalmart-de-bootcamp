Phase A Create Your Own Storage Credential

Same pattern as the real ecomprojectscredentials shown in ILT 2 — naming everything after yourself.

# Confirm it has "Storage Blob Data Contributor" on your storage account

Credential type : Azure Managed Identity
Credential name : <yourname>_credential
Access Connector ID: (paste Resource ID)
Verify: the credential appears in the list with status Active.

Phase B Create Your Own External Location

Mirrors the real gbmart-ext-loc shown in ILT 2.

# B3: Verify access — NO spark.conf.set, NO storage key
your_container = "amazon-data"
your_storage_account = "YOUR_STORAGE_ACCOUNT_NAME"
base_path = f"abfss://{your_container}@{your_storage_account}.dfs.core.windows.net"

files = dbutils.fs.ls(f"{base_path}/raw/")
If you see a permissions error, re-check the RBAC role assignment in Phase A.

Phase C Create Your Own Lakeflow Connect Pipeline

Mirrors the real ecom_gbmart_conn → orders_data_ingestion_cdc pipeline from ILT 2, pointing at your own Supabase project.

Prerequisite: your own orders / order_items tables need a live-updating updated_at column — the real pipeline's connector mode is query-based on that column. Add it with ALTER TABLE ... ADD COLUMN IF NOT EXISTS updated_at TIMESTAMP DEFAULT NOW(); if missing.
# Databricks → Catalog → Connections → + Add connection
Connection name : postgresql_<yourname>
Type : PostgreSQL
Host : aws-0-<region>.pooler.supabase.com

# Databricks → Data Ingestion → PostgreSQL (Preview)
Connection : postgresql_<yourname>
Tables : ✅ orders   ✅ order_items
Destination : <your_catalog>.bronze
Connector mode : Query-based  ← same mode as the real GlobalMart pipeline
Cursor column : updated_at

Phase D Prove CDC (and Its Limit)

We only test INSERT/UPDATE below — your pipeline is query-based, the same blind spot on DELETEs as GlobalMart's real pipeline.

INSERT INTO orders (order_id, customer_id, order_date, status, ...)
VALUES ('O-TEST-001', 'CUST-99999', NOW(), 'pending', ...);

UPDATE orders SET status = 'shipped' WHERE order_id = 'O-TEST-001';

Re-run the pipeline → expect Upserted: 1 — only the changed row, not the whole table.

Bonus (D5/D6): now DELETE FROM orders WHERE order_id = 'O-TEST-001'; in Supabase and re-run the pipeline. The row stays in Bronze — a query-based connector on updated_at has no way to notice a row disappeared. Only log-based/WAL replication (ILT 1 / HOL 2) would catch this.
