Section 1

Why Do Data Engineers Need Version Control?

Two familiar stories — and the tool that fixes both.

The Problem Without Version Control

Story 1 — Monday, Tuesday, Wednesday

  • Monday: you write a notebook that cleans customer data — it works perfectly
  • Tuesday: you add a new column
  • Wednesday: the pipeline breaks — the new column had a bug

What do you do? You can't go back to Monday's working version — you overwrote it.

Story 2 — Two Engineers, One File

  • Two engineers are both editing the same notebook at the same time
  • One saves their version, the other saves theirs
  • One person's work is simply gone

Version control solves both problems.

What Version Control Does for You

ProblemHow Version Control Fixes It
Accidentally broke working codeRoll back to any previous version instantly
Two engineers editing the same fileMerge changes safely, see who changed what
Need to audit what changedFull history of every change ever made
Deploying to production safelyTest in dev/test branch before touching prod
Onboarding a new team memberThey clone the repo and have everything immediately

Instructor question: "Has anyone ever accidentally deleted or overwritten code and lost work? That never happens with Git."

Section 2

Git Basics (Very Simple)

Git is the most popular version control tool in the world. GitHub is a website where you store your Git repositories online — like Google Drive, but for code.

6 Git Concepts You Need to Know

ConceptSimple MeaningReal-Life Analogy
RepositoryA folder that tracks all changes to all files inside itA project folder with a complete history
BranchA separate copy of the code you can work on safelyA rough draft that doesn't affect the published version
CommitSave a snapshot of your current changes with a messagePressing Save + writing a note about what you saved
PushUpload your commits from Databricks to GitHubSyncing your phone photos to Google Photos
PullDownload the latest changes from GitHub into DatabricksRefreshing your email to get new messages
MergeCombine changes from one branch into anotherCombining two documents into one final version

How It All Flows

GitHub (online)
    │
    │  ← push (upload your changes)
    │  → pull (download latest changes)
    │
Databricks Repos (your local working copy)
    │
    ├── dev branch     (where you write new code)
    ├── test branch    (where you test before going live)
    └── prod branch    (the live, running pipeline — only tested code here)

Tell students: "GitHub is the source of truth. Databricks Repos is your working copy. Always push your work to GitHub so it is safe and shared."

Section 3

The Dev → Test → Prod Branch Strategy

The most important practical concept of this session. Every professional data team uses this pattern.

Never Write Code Directly on Production

dev

Who: individual engineers
What runs: new features, bug fixes, experiments
Data: sample/test data

test

Who: QA / team review
What runs: integration testing, data quality checks
Data: full data, read-only

prod

Who: automated pipelines only
What runs: the final, approved, live pipeline
Data: live production data

The rule: code only moves forward — dev → test → prod. It never goes backwards. You never edit prod directly.

For GlobalMart

globalmart-lakehouse/          ← your GitHub repo
    │
    ├── branch: dev            ← you write here every day
    │       notebooks/
    │           bronze_ingestion.ipynb
    │           silver_customers.ipynb
    │
    ├── branch: test           ← tested and reviewed code
    │
    └── branch: prod           ← only fully approved code

Ask the class: "Why would a company care about keeping prod separate from dev?"

If a bug reaches prod, business dashboards break, Finance gets wrong numbers, reports fail. The cost is very high.

Section 4

Databricks Repos — Connecting GitHub

Instead of saving notebooks only inside Databricks, they also live in GitHub — version-controlled and shareable.

Part A + B — GitHub Setup, Then Databricks Setup

Part A — GitHub (do this first)

  1. github.com → log in → + New repository
  2. Name it globalmart-lakehouse, set Private, add a README
  3. Settings → Developer Settings → Personal Access Tokens (classic)
  4. Generate new token → scope: repo → copy it immediately

Part B — Databricks

  1. Username (top right) → Settings → Linked Accounts → Git Integration
  2. Select GitHub → paste Personal Access Token + username → Save

Common mistake: closing the GitHub token page before copying it. Remind students to copy it first — you can't see it again.

Part C — Clone the Repo into Databricks

  1. In the left sidebar, click Repos
  2. Click Add Repo
  3. Paste your GitHub repo URL: https://github.com/YOUR_USERNAME/globalmart-lakehouse
  4. Click Create Repo
  5. Your repo now appears in Databricks under Repos
  6. Any notebook you create inside this folder is automatically tracked by Git
Section 5

The Daily Git Workflow

This is the workflow you'll follow every single day of the bootcamp from today onwards.

Every Day: Pull → Branch → Code → Commit → Push

  1. Pull latest changes — get any changes your teammates made
  2. Make sure you're on the dev branch
  3. Write your code in the notebook
  4. Commit — Stage changes → write a message → Commit
  5. Push to GitHub — now your code is safe
Bad messageGood message
updateAdd null check for customer email in silver layer
fixFix date format in orders table from MM/DD to YYYY-MM-DD
changesAdd bronze ingestion notebook for customers table

Rule: your commit message should tell a new team member exactly what changed and why.

Live Demo — Verify You're Inside a Git Repo

Goal: by the end, everyone has a dev branch and one pushed notebook
notebook_path = dbutils.notebook.entry_point.getDbutils().notebook().getContext().notebookPath().get()
print(f"Current notebook path: {notebook_path}")

if "/Repos/" in notebook_path:
    print("This notebook IS inside a Databricks Repo — Git tracking is active.")
else:
    print("NOT in a Repo. Move it to your Repos folder to enable Git tracking.")

If the path contains /Repos/, it's Git-tracked. If it contains /Users/, it is not.

Live Demo — One Shared Config Notebook, Called With %run

Change the storage account name in ONE place → every notebook picks it up
# config/setup.ipynb — uses the External Location pattern (no storage key)
STORAGE_ACCOUNT_NAME = "YOUR_STORAGE_ACCOUNT_NAME"
BASE_PATH   = f"abfss://amazon-data@{STORAGE_ACCOUNT_NAME}.dfs.core.windows.net"
BRONZE_PATH = f"{BASE_PATH}/raw"

# In any other notebook, instead of repeating all that code:
%run ../config/setup
# BRONZE_PATH, SILVER_PATH, GOLD_PATH are now ready to use
