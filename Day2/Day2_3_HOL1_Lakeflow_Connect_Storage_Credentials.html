Phase A

Recall from ILT 2: the Storage Credential is Databricks' employee badge for Azure. Same pattern as the real ecomprojectscredentials — naming everything after yourself.

Azure Portal → search "Access Connectors for Azure Databricks"
  → find the one linked to your Databricks workspace

Phase C

Create Your Own Lakeflow Connect Pipeline

Mirror the real ecom_gbmart_conn → orders_data_ingestion_cdc pipeline from ILT 2 — pointing at your own Supabase project.

C0 — Set Up orders/order_items for CDC in Supabase

Mirrors exactly what was done to prepare GlobalMart's real tables (ILT 2). Run each step individually in the Supabase SQL Editor — verify the output before running the next.

-- 1. updated_at column + trigger to refresh it
ALTER TABLE orders ADD COLUMN IF NOT EXISTS
  updated_at TIMESTAMPTZ NOT NULL DEFAULT now();

CREATE TRIGGER trg_orders_updated_at
BEFORE INSERT OR UPDATE ON orders
FOR EACH ROW EXECUTE FUNCTION set_updated_at();
-- (same pattern on order_items)

-- 2. REPLICA IDENTITY FULL — required for CDC to capture
--    full row images on UPDATE/DELETE, not just the PK
ALTER TABLE orders REPLICA IDENTITY FULL;
ALTER TABLE order_items REPLICA IDENTITY FULL;

-- 3. Publication — exposes both tables to Lakeflow Connect
CREATE PUBLICATION <yourname>_pub
  FOR TABLE orders, order_items;

Load data via CSV import, not INSERTs

At GlobalMart's real volume — ~126,000 orders rows, ~377,000 order_items rows — row-by-row INSERTs aren't practical.

Supabase → Table Editor → orders
  → Insert → Import data from CSV
  → upload orders.csv

Supabase → Table Editor → order_items
  → Insert → Import data from CSV
  → upload order_items.csv

Verify: SELECT COUNT(*) FROM orders; / order_items;, and SELECT * FROM pg_publication_tables WHERE pubname = '<yourname>_pub' to confirm both tables are published.

C2 — Create the Ingestion Pipeline

Databricks → Data Ingestion → PostgreSQL (Preview)

Connection : postgresql_<yourname>
Tables     : ✅ orders   ✅ order_items

Destination (Unity Catalog):
  Catalog : <your_catalog>         ← your own Unity Catalog catalog
  Schema  : bronze

Table configuration (per table):
  Primary key      : order_id / order_item_id
  Cursor column    : updated_at        ← must increase on every change, see note below
  History tracking : SCD1 or SCD2      ← SCD1 for latest-state-only, SCD2 to keep every version
  Schedule         : skip it — do not add one   ← see note below

→ Create Pipeline → Start

Why updated_at and not order_date? order_date is set once and never changes again — a later status update gives the pipeline no signal. updated_at is refreshed by the C0 trigger on every INSERT and UPDATE. It has no way to represent a DELETE.

Skip the schedule — leave it unset and trigger runs manually via Start. A production deployment would add a periodic schedule (e.g. hourly) later; that's a separate decision, not needed here.

This pipeline's cursor column is updated_at, so each run queries WHERE updated_at > last_seen_value — that's query/cursor-based capture, not WAL streaming. REPLICA IDENTITY FULL and the C0 publication are correct Postgres-side setup for logical replication in general, but this pipeline doesn't use them to stream the WAL. It captures INSERT and UPDATE, but cannot detect DELETEs — which Phase D proves.

Phase D

Prove CDC, and See the Real Limit

Change a row, re-run, watch only the change sync. Then see the real limit of cursor-based capture for yourself: because this pipeline queries on updated_at instead of reading the WAL, a hard DELETE does not sync.

D1–D2 — Make a Change, Re-Run the Pipeline

Run in Supabase SQL Editor, then re-run your pipeline in Databricks
INSERT INTO orders (order_id, customer_id, order_date, status, payment_method_id, shipping_tier_id)
VALUES ('O-TEST-001', 'CUST-99999', NOW(), 'pending', 'PM-001', 'STD');

UPDATE orders SET status = 'shipped' WHERE order_id = 'O-TEST-001';

Expected after re-running the pipeline: Status: Completed, Upserted: 1 — only the 1 changed row, not the whole orders table.

D3–D4 — Confirm It Landed via CDC, Not a Full Reload

result_df = spark.sql(f"""
    SELECT order_id, customer_id, status
    FROM {your_catalog}.bronze.orders
    WHERE order_id = 'O-TEST-001'
""")
result_df.show(truncate=False)

new_orders_count = spark.sql(f"SELECT COUNT(*) AS n FROM {your_catalog}.bronze.orders").collect()[0]["n"]
print(f"orders row count now: {new_orders_count:,} (was {orders_count:,} — should be +1)")

Status should read 'shipped' — the UPDATE was captured, not just the INSERT.

D5–D6 (Bonus) — Prove the DELETE Is NOT Captured

This pipeline is cursor/query-based, not WAL streaming
-- In Supabase SQL Editor:
DELETE FROM orders WHERE order_id = 'O-TEST-001';
-- Re-run your pipeline, same as D2, then verify below:
still_there_df = spark.sql(f"SELECT * FROM {your_catalog}.bronze.orders WHERE order_id = 'O-TEST-001'")
if still_there_df.count() > 0:
    print("As expected: the deleted row is STILL in Bronze — cursor-based capture can't see a DELETE.")

The row has nothing left to match — each run queries WHERE updated_at > last_seen_value, and a deleted row isn't "updated," it's just gone. This is true whether you chose SCD1 or SCD2 history tracking in C2: neither one can capture a change the pipeline never observed. REPLICA IDENTITY FULL and the C0 publication remain correct setup for logical replication in general — this pipeline just doesn't use them.
