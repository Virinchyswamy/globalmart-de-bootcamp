Phase A

Create Your Own Storage Credential

Recall from ILT 2: the Storage Credential is Databricks' employee badge for Azure. Same pattern as the real ecomprojectscredentials — naming everything after yourself.

A1–A2 · Find Your Access Connector, Confirm Its Permissions

A1 — Find (or create) your Access Connector

Azure Portal → search "Access Connectors for Azure Databricks"
  → find the one linked to your Databricks workspace
  → Settings → Properties → copy the Resource ID

If none exists:
  Azure Portal → Create a resource
  → "Azure Databricks Access Connector"
  → same Resource Group as your Databricks workspace

A2 — Confirm RBAC on your storage account

Azure Portal → your storage account (from Day 1)
  → Access Control (IAM) → Role assignments
  → confirm: Storage Blob Data Contributor

If missing:
  → Add role assignment → Storage Blob Data Contributor
  → Assign to: Managed Identity → your Access Connector

A3 — Create the Storage Credential in Databricks

Databricks → Catalog icon → External Data → Storage Credentials → Create credential
Credential type    : Azure Managed Identity
Credential name    : <yourname>_credential        e.g. virinchy_credential
Access Connector ID: (paste the Resource ID from A1)
Comment            : Managed identity for my Day 1 storage account
→ Create

Verify: the credential appears in the list with status Active.

Phase B

Create Your Own External Location

The door your badge unlocks — map your ADLS container to the credential from Phase A. Mirrors the real gbmart-ext-loc.

B1–B2 · Create and Test the External Location

B1 — Create the location

Databricks → Catalog icon → External Data
  → External Locations → Create location

External location name : <yourname>_external
URL : abfss://<container>@<storage-account>
      .dfs.core.windows.net/
Storage credential : <yourname>_credential
→ Create

B2 — Test the connection

Click "Test connection" on the External Location you just created.

Expected: ✅ Connection test succeeded — lists files under your container.

Permissions error? Go back to A2 and re-check the RBAC role assignment.

B3–B5 — Verify Access: Zero Hardcoded Keys

Run these cells to prove Unity Catalog is handling auth

Phase C

Create Your Own Lakeflow Connect Pipeline

Mirror the real ecom_gbmart_conn → orders_data_ingestion_cdc pipeline from ILT 2 — pointing at your own Supabase project.

Prerequisite — Check Your updated_at Column

You should already have your own Supabase project with orders and order_items tables populated.

Check that both tables have an updated_at column that actually gets refreshed on UPDATE — the real pipeline uses a query-based connector keyed on updated_at. Without it, incremental sync has nothing to detect changes with.

ALTER TABLE orders ADD COLUMN IF NOT EXISTS updated_at TIMESTAMP DEFAULT NOW();
ALTER TABLE order_items ADD COLUMN IF NOT EXISTS updated_at TIMESTAMP DEFAULT NOW();

C1 — Create the Connection

Databricks → Catalog icon → Connections → + Add connection

Connection name : postgresql_<yourname>          e.g. postgresql_virinchy
Type            : PostgreSQL
Host            : aws-0-<region>.pooler.supabase.com
Port            : 5432
Database        : postgres
Username        : postgres.<your_project_ref>
Password        : (from your Supabase credentials)
SSL             : Require
→ Test connection → Create

C2 — Create the Ingestion Pipeline

Databricks → Data Ingestion → PostgreSQL (Preview)

Connection : postgresql_<yourname>
Tables     : ✅ orders   ✅ order_items

Destination (Unity Catalog):
  Catalog : <your_catalog>         ← your own Unity Catalog catalog
  Schema  : bronze

Table configuration (per table):
  Primary key    : order_id / order_item_id
  Connector mode : Query-based
  Cursor column  : updated_at        ← same mode as GlobalMart's real pipeline

→ Create Pipeline → Start

C3–C4 — Record the First Run, Verify in Unity Catalog

Fill in your own catalog name, then run
your_catalog = "YOUR_CATALOG_NAME"

orders_count = spark.sql(f"SELECT COUNT(*) AS n FROM {your_catalog}.bronze.orders").collect()[0]["n"]
items_count  = spark.sql(f"SELECT COUNT(*) AS n FROM {your_catalog}.bronze.order_items").collect()[0]["n"]

spark.sql(f"DESCRIBE EXTENDED {your_catalog}.bronze.orders").show(truncate=False)
# Look for: Type = STREAMING_TABLE, Catalog Name = your_catalog (not hive_metastore)
Phase D

Prove CDC (and Its Limit)

Change a row, re-run, watch only the change sync. Then prove the query-based trade-off for yourself: a hard DELETE does not sync.

D1–D2 — Make a Change, Re-Run the Pipeline

Run in Supabase SQL Editor, then re-run your pipeline in Databricks
INSERT INTO orders (order_id, customer_id, order_date, status, payment_method_id, shipping_tier_id)
VALUES ('O-TEST-001', 'CUST-99999', NOW(), 'pending', 'PM-001', 'STD');

UPDATE orders SET status = 'shipped' WHERE order_id = 'O-TEST-001';

Expected after re-running the pipeline: Status: Completed, Upserted: 1 — only the 1 changed row, not the whole orders table.

D3–D4 — Confirm It Landed via CDC, Not a Full Reload

result_df = spark.sql(f"""
    SELECT order_id, customer_id, status
    FROM {your_catalog}.bronze.orders
    WHERE order_id = 'O-TEST-001'
""")
result_df.show(truncate=False)

new_orders_count = spark.sql(f"SELECT COUNT(*) AS n FROM {your_catalog}.bronze.orders").collect()[0]["n"]
print(f"orders row count now: {new_orders_count:,} (was {orders_count:,} — should be +1)")

Status should read 'shipped' — the UPDATE was captured, not just the INSERT.

D5–D6 (Bonus) — Prove the DELETE Blind Spot

This is expected behavior, not a bug
-- In Supabase SQL Editor:
DELETE FROM orders WHERE order_id = 'O-TEST-001';
-- Re-run your pipeline, same as D2, then verify below:
still_there_df = spark.sql(f"SELECT * FROM {your_catalog}.bronze.orders WHERE order_id = 'O-TEST-001'")
if still_there_df.count() > 0:
    print("Confirmed: the deleted row is STILL in Bronze.")

A query-based connector on updated_at has no way to notice a row disappeared — a DELETE leaves no row behind to carry an updated_at value. Only log-based (WAL) replication, covered in HOL 2, would catch this.
