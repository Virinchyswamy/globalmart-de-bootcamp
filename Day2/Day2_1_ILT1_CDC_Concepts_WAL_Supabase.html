Recall Incremental Load — It Has a Blind Spot

From Day 1: Incremental Load reads only new rows using a watermark (a date filter). It works great for inserts. But watch what happens with an update:

Day 1:  CustomerID=C001, email=raj@old.com, city=Mumbai   ← loaded to Bronze
Day 5:  CustomerID=C001, email=raj@new.com, city=Delhi    ← customer UPDATED

Incremental load with a date filter:

WHERE created_at > last_run
→ C001 was created before last_run, so it's SKIPPED
→ Bronze still shows raj@old.com in Mumbai — wrong

CDC captures the UPDATE — it logs that C001 changed from Mumbai to Delhi, and that change flows to Bronze → Silver → Gold automatically.

The 3 Change Types CDC Captures

Any change to a database row is one of exactly three operations:

OperationExampleResult in Lakehouse
INSERTNew customer signs upNew row added
UPDATECustomer changes cityExisting row updated (or history tracked)
DELETECustomer deletes accountRow removed (or marked deleted)

The rest of today is about where CDC reads these 3 operations from: PostgreSQL's Write-Ahead Log.

What Is WAL? Think "Bank Transaction Journal"

Imagine a bank that writes down every transaction in a journal before it updates anyone's balance:

Bank transaction journal:
  10:00 — Raj transferred ₹1000 to Priya
  10:01 — Account balance updated: Raj -₹1000, Priya +₹1000
  10:02 — New customer opened account

PostgreSQL does the exact same thing with a file called the Write-Ahead Log (WAL):

PostgreSQL WAL:
  10:00 — INSERT into customers: {id=C001, name=Raj, city=Mumbai}
  10:01 — UPDATE customers: C001 city changed Mumbai → Delhi
  10:02 — DELETE from customers: C999 removed

WAL's original purpose: crash recovery — if Postgres crashes, it replays the WAL to restore data. CDC repurposes it: read the WAL stream instead of querying the table, and you capture every single change.

Logical Replication — Making WAL Readable

By default, WAL is a binary format only Postgres understands. Logical replication decodes it into human-readable change events.

WAL (binary):      0x4F02A1B4...
After decoding:    {"op": "UPDATE", "table": "customers",
                    "id": "C001", "city": {"old": "Mumbai", "new": "Delhi"}}

How to enable it in Supabase

  1. Supabase Dashboard → Database → Replication
  2. Enable Row Level Changes for the tables you want to track
  3. This sets wal_level = logical in the PostgreSQL config — Supabase handles the rest

We'll do this for real in HOL 2 — for now, understand it's a one-time setup in the Supabase UI.

CDC Architecture for GlobalMart

Now that you know what WAL and logical replication are — where does GlobalMart actually plug in?

Full CDC Pipeline — 3 Ways to Read the WAL Stream

Supabase PostgreSQL
       │
   WAL stream (logical replication)
       │
       ▼
  [Option A: Lakeflow Connect]     ← Databricks-managed (ILT 2)
  [Option B: Debezium → Kafka]     ← production-grade, self-managed, complex to operate
  [Option C: Direct JDBC polling]  ← manual, for learning the mechanics (today + HOL 2)
       │
       ▼
  Bronze (Delta)  →  Silver (MERGE)  →  Gold (always current)

Today's JDBC + WAL walkthrough is deliberately manual — it exists so you understand what a managed tool is doing for you before you use it. HOL 2 repeats this exercise hands-on for the same reason: seeing the raw mechanics builds the intuition that makes a managed tool trustworthy instead of a black box.

What GlobalMart Actually Uses

Lakeflow Connect is the production tool for orders and order_items — a managed Databricks ingestion pipeline. No JDBC code, no manual slot management, no Debezium/Kafka cluster to run. You configure a connection once, stored centrally in Unity Catalog, and point a pipeline at the tables you want.

Lakeflow Connect can detect changes two different ways: reading the WAL directly (log-based), or polling a cursor column on a schedule (query-based).

Which mode does GlobalMart's real pipeline actually use — and what does that trade-off cost? That's exactly what ILT 2 reveals, using the real, currently-running pipeline as a worked example. Don't assume yet.

What you can say for certain today

  • Databricks manages the connection, scheduling, retries, schema handling
  • First run = full snapshot; every run after = incremental only
  • Lands as a governed Unity Catalog table

Live Demo — Reading Tables Directly From Supabase

No CSV file needed — Spark queries the live database
customers_df = spark.read \
    .jdbc(
        url        = jdbc_url,
        table      = "customers",
        properties = connection_properties
    )

print(f"Rows: {customers_df.count():,}")

You can also push a SQL query down to Postgres — read only what changed:

query = """
    (SELECT * FROM customers
     WHERE updated_at > NOW() - INTERVAL '30 days'
     ORDER BY updated_at DESC) AS recent_customers
"""

This is the CDC/incremental pattern — reading only changed rows via a watermark, the same limitation we opened with today (it still misses deletes).

Live Demo — Simulating a Full Ingestion Pipeline by Hand

What a managed pipeline does under the hood
tables_to_ingest = ["customers", "orders", "orders_items", "products",
                    "payments", "addresses", "returns", "suppliers",
                    "payment_methods", "shipping_tier"]

for table_name in tables_to_ingest:
    df = spark.read.jdbc(url=jdbc_url, table=table_name, properties=connection_properties)
    df.write.format("delta").mode("overwrite").saveAsTable(f"{GBMART_CATALOG}.bronze.{table_name}")

This is exactly what an ingestion pipeline does under the hood: connect via JDBC, read each table, save to Bronze as a governed table — the same destination the real Lakeflow Connect pipeline in ILT 2 lands into. We do it by hand here so the mechanics aren't a black box.
