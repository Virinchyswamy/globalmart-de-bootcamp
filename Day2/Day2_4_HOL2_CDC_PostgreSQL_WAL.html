Why this HOL, right after HOL 1? HOL 1 set up Lakeflow Connect for GlobalMart's real orders/order_items tables — but running in query-based mode (cursor: updated_at), not WAL.

This HOL teaches the other connector mode: log-based, reading the WAL directly through a replication slot. The Problem

Why Watermarks Miss Deletes

A concrete walk-through, before the mechanics.

A Ghost Row Watermarking Can't See

DAY 1 — Source table: poc_orders
  OR-00001 | CUST-10001 | 2026-06-01  ← exists
  OR-00002 | CUST-10002 | 2026-06-01  ← exists
  OR-00003 | CUST-10003 | 2026-06-01  ← exists

Watermark ingestion reads all 3 rows → Bronze has 3 ✓
DAY 2 — Customer cancels OR-00003 → DELETED
  OR-00001 | CUST-10001 | 2026-06-01
  OR-00002 | CUST-10002 | 2026-06-01

Watermark (WHERE updated_at > last_watermark):
  → No rows returned — nothing was "updated"
  → Bronze still has 3 rows ← OR-00003 is a ghost!

WAL / CDC ingestion:
  → Replication slot recorded: DELETE OR-00003
  → Bronze gets the DELETE event → Silver applies it
  → Truth preserved ✓

How PostgreSQL WAL Works — The Replication Slot as Bookmark

Every INSERT / UPDATE / DELETE in Postgres is first written
to the Write-Ahead Log (WAL) — before the table is updated.

A logical replication slot is a bookmark in the WAL.
  → It remembers the position of the last change you read.
  → Next read picks up exactly where you left off —
    no duplicates, no gaps.
pg_logical_slot_get_changes('slot_name', NULL, NULL)
  → Returns all new WAL entries since your last read.
  → DRAINS the slot — run it again and you get nothing
    until the next change.

This is what Debezium, Fivetran, and Airbyte all use under the hood — and what Lakeflow Connect's log-based mode automates.

Pre-Work B — Enable CDC (Logical Replication Slot)

Critical timing: create the slot AFTER the initial 200-row load and BEFORE any Day 2 changes. Too early and the initial inserts flood the WAL. Too late and you miss the Day 2 changes.

-- 1. Confirm logical replication is enabled (Supabase default)
SHOW wal_level;  -- Expected: logical

-- 2. Create a publication — declares which table to track
CREATE PUBLICATION poc_orders_pub FOR TABLE public.poc_orders;

-- 3. Create the replication slot — the bookmark Databricks reads from
SELECT pg_create_logical_replication_slot('poc_orders_slot', 'test_decoding');

What Is test_decoding?

PostgreSQL ships with two logical decoding plugins:

test_decoding

Outputs human-readable text:

'table public.poc_orders: INSERT:
 order_id[text]:"OR-00201"
 customer_id[text]:"CUST-10001"'

Good for: learning, debugging, quick POCs. Included in Supabase's free tier — what we use today.

wal2json

Outputs structured JSON (must be installed separately):

{"kind":"insert","schema":"public",
 "table":"poc_orders","columnnames":[...]}

Good for: production pipelines (easier to parse). For production, use Debezium or Supabase Realtime CDC.

UPDATE public.poc_orders SET shipping_tier_id = 'EXPRESS' WHERE ...;

-- Customer cancels an order (DELETE)

-- Verify: 200 + 5 - 1 = 204 rows
SELECT COUNT(*) FROM public.poc_orders;

What the Replication Slot Captures

After 8 statements (5 INSERTs + 2 UPDATEs + 1 DELETE), the slot holds:

  BEGIN <xid>
  table public.poc_orders: INSERT: order_id[text]:'OR-90001' ...
  COMMIT <xid>
  ... (5 INSERTs total)

  BEGIN <xid>
  table public.poc_orders: UPDATE: order_id[text]:'OR-000XX' ... shipping_tier_id[text]:'EXPRESS'
  COMMIT <xid>

  BEGIN <xid>
  table public.poc_orders: DELETE: order_id[text]:'OR-000XX'
  COMMIT <xid>

Total: 8 statements × 3 rows (BEGIN + event + COMMIT) = 24 rows

CDC Capture — Reading the Replication Slot

pg_logical_slot_get_changes('poc_orders_slot', NULL, NULL)

  slot_name = 'poc_orders_slot'
  upto_lsn  = NULL  → drain everything to current WAL position
  upto_nchanges = NULL  → no limit

Returns 3 columns: lsn, xid, data

This function DRAINS the slot. Run 1 → 24 rows. Run 2 → 0 rows, already drained. The slot moves forward — old events are gone.

That's why we .cache() the result — so .count() and .show() read the same data without draining the slot twice.

Step 4–6 — Capture, Inspect, and Parse CDC Events

cdc_raw_df = jdbc_read(
    "(SELECT * FROM pg_logical_slot_get_changes('poc_orders_slot', NULL, NULL)) AS cdc_events"
).cache()  # critical — drains on first read

data_events_df = (
    cdc_raw_df
    .filter(col("data").startswith("table "))  # drop BEGIN/COMMIT noise
    .withColumn("_cdc_op", regexp_extract(col("data"), r"table public\.poc_orders: (INSERT|UPDATE|DELETE):", 1))
    .withColumn("_order_id", regexp_extract(col("data"), r"order_id\[text\]:'([^']+)'", 1))
)

Each statement = 3 WAL rows (BEGIN + event + COMMIT). 24 raw rows parse down to 8 real events by _cdc_op.

Step 7 — Append CDC Events to Bronze

bronze_cdc_df.write.format("delta") \
    .mode("append") \
    .option("mergeSchema", "true") \
    .save(bronze_poc_orders)

Note the mode difference: overwrite for the Day 1 initial load, append for CDC events — Bronze is append-only for changes.

What Silver Does With This Next

CDC INSERT  → MERGE ... WHEN NOT MATCHED THEN INSERT
CDC UPDATE  → MERGE ... WHEN MATCHED THEN UPDATE
CDC DELETE  → MERGE ... WHEN MATCHED THEN DELETE
              (or: SET is_deleted = true)

Result: silver.poc_orders always reflects the
CURRENT state — 204 rows, 2 updated, 1 gone.
