Why Data Engineers Need Version Control

Monday's notebook works. Tuesday you add a column. Wednesday the pipeline breaks — and you overwrote Monday's working version. Or: two engineers edit the same notebook, one save wins, the other's work vanishes.

ProblemHow Version Control Fixes It
Accidentally broke working codeRoll back to any previous version instantly
Two engineers editing the same fileMerge changes safely, see who changed what
Need to audit what changedFull history of every change ever made
Deploying to production safelyTest in dev/test branch before touching prod

Git Basics — 6 Concepts

ConceptSimple Meaning
RepositoryA folder that tracks every change to every file inside it
BranchA separate copy of the code you can work on safely
CommitSave a snapshot of your current changes with a message
PushUpload your commits from Databricks to GitHub
PullDownload the latest changes from GitHub into Databricks
MergeCombine changes from one branch into another

The Dev → Test → Prod Branch Strategy

devIndividual engineers. New features, bug fixes, experiments. Sample/test data.
testQA / team review. Integration testing, data quality checks. Full data, read-only.
prodAutomated pipelines only. The final, approved, live pipeline. Live production data.
Code only moves forward: dev → test → prod. Never backwards. Never edit prod directly.

Databricks Repos — Connecting GitHub

GitHub.com  (create repo, generate Personal Access Token)
    │
    ▼
Databricks → Settings → Linked Accounts → Git Integration
    │ (paste token + username)
    ▼
Databricks → Repos → Add Repo → paste GitHub URL
    │
    ▼
Every notebook created here is now Git-tracked

The Daily Git Workflow

# Every day, in order:
1. Pull latest changes  # get teammates' work
2. Confirm you're on the dev branch
3. Write your code
4. Commit  # Stage → write message → Commit
5. Push  # now it's safe in GitHub
Bad messageGood message
updateAdd null check for customer email in silver layer
fixFix date format in orders table from MM/DD to YYYY-MM-DD

Shared Config Pattern (No Storage Key)

# config/setup — uses the External Location from HOL 1, not a raw key
STORAGE_ACCOUNT_NAME = "YOUR_STORAGE_ACCOUNT_NAME"
BASE_PATH = f"abfss://amazon-data@{STORAGE_ACCOUNT_NAME}.dfs.core.windows.net"

# In any other notebook:
%run ../config/setup
One place to change the storage account name → every notebook that calls %run ../config/setup picks it up. No key ever appears in git history.
