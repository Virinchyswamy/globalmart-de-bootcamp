Recap: From Watermarks to a Managed Pipeline

In ILT 1 we saw why a simple WHERE updated_at > last_run watermark falls apart:

  • It misses DELETEs entirely — the row is just gone, nothing to filter on
  • It only catches an UPDATE if the source table actually has an updated_at column
  • At scale, re-scanning even the changed slice on a timer is wasteful

The gold-standard fix — reading the Write-Ahead Log (WAL) directly through a replication slot — is what we did by hand with raw JDBC in ILT 1 (and go deeper in HOL 2), so the mechanics aren't a mystery.

Today's question: Lakeflow Connect can run either strategy as a managed pipeline. Which one does GlobalMart actually use?

Lakeflow Connect Has Two Connector Modes

ModeHow It Detects ChangesCatches DELETEs?
Log-based (WAL / replication slot)Reads the database's write-ahead log directlyYes — a DELETE is a WAL event like any other
Query-based (cursor column)Runs WHERE cursor_col > last_value on a schedule — same idea as a watermarkNo — same blind spot as manual watermarking

GlobalMart's real, running pipeline uses the query-based mode, with updated_at as the cursor column — not WAL replication. This is a deliberate, honest trade-off: Databricks still manages the connection, scheduling, retries, and schema handling for you, but it does not magically give you DELETE-capture for free just because it's Lakeflow Connect.

What Changes With a Managed Pipeline

Manual JDBC + WAL (ILT 1 / HOL 2)Lakeflow Connect — query-based (GlobalMart's real pipeline)
You open the JDBC connectionDatabricks manages the connection
You create the replication slotNo replication slot — polls with a cursor column instead
You call pg_logical_slot_get_changes()Databricks runs the cursor query on a schedule
You parse INSERT/UPDATE/DELETE textDatabricks applies INSERT/UPDATE only (no DELETE capture)
You write to Bronze yourselfLands as a governed, managed Unity Catalog table
Captures DELETEs, more code to maintainLess code to maintain, same DELETE blind spot as a watermark
Section 2

How Lakeflow Connect Works End to End

Five steps, from a stored connection to a governed table in Unity Catalog.

Connection → Pipeline → Snapshot → Sync → Destination

  1. Connection — a Unity Catalog object storing host/port/credentials. Created once, reused by any number of pipelines.
  2. Ingestion Pipeline — pick a Connection, pick tables, pick a connector mode, pick a destination catalog/schema.
  3. First Run — Full Snapshot — reads every row currently in the source table(s) as the initial state.
  4. Every Run After — Incremental Sync — reads only what changed since the last run.
  5. Destination — a governed Unity Catalog table: full lineage, access control, audit.

Why This Matters for orders & order_items

These two GlobalMart tables are live, continuously changing — order status moves pending → shipped → delivered, line items get added or corrected.

Re-reading the whole table on a timer (Autoloader-style) would either miss changes or waste enormous compute at GlobalMart's volume (~500K orders, ~2M order_items). Even in query-based mode, Lakeflow Connect beats a hand-rolled watermark script because Databricks manages the connection, scheduling, retries, and schema evolution for you.

Worked Example: The Real Pipeline

This is the actual, currently-running Lakeflow Connect pipeline behind GlobalMart's Bronze orders/order_items tables — not a hypothetical. In HOL 1 you'll build your own, named after yourself.

Step 1 — The Connection (Already Created)

Databricks → Catalog → Connections → ecom_gbmart_conn

  Connection name : ecom_gbmart_conn
  Type            : PostgreSQL
  Host            : aws-0-ap-south-1.pooler.supabase.com
  Port            : 5432

This is a Unity Catalog Connection object — host/port/credentials are stored once, centrally, and referenced by name.

No password ever appears in the pipeline definition itself. That's the whole governance win in one sentence.

Step 2 — The Ingestion Pipeline (Real Spec)

Pipeline name : orders_data_ingestion_cdc
Compute       : serverless          ← no cluster to size or manage
Connection    : ecom_gbmart_conn
Source type   : POSTGRESQL

  Source                                  Destination (Unity Catalog)
  ─────────────────────────────────       ──────────────────────────────
  postgres.globalmart.orders         →    gbmart.bronze.orders
  postgres.globalmart.order_items    →    gbmart.bronze.order_items

  Table configuration:
    primary_keys      : orderid           ← real source column, NO underscore
                         orderitemid       ← order_id gets the underscore later, in Silver
    connector mode     : query_based
    cursor_columns     : updated_at       ← THIS is what makes it query-based, not WAL

Notice: the source column is orderid, not order_id. Bronze lands data exactly as the source names it — the clean, underscored name is a Silver-layer standardization.

First Run vs. Every Run After

First Run — Full Snapshot

Status     : Completed
orders     : Upserted ~500,000 rows
order_items: Upserted ~2,000,000 rows
Catalog    : gbmart.bronze

Every Run After — Only Rows Where updated_at Advanced

Order O-10021 gets updated → updated_at = now()
  → Upserted: 1  ← only that row, not all 500K

Someone DELETEs a row entirely in Supabase
  → Nothing to upsert — no updated_at to trigger on
  → The row silently stays in Bronze forever

This is the real, documented trade-off of query-based mode from Slide 4 — playing out in production.

GlobalMart's Full Ingestion Tool Assignment

Not every table needs Lakeflow Connect — match the tool to the source's shape:

TableSourceToolWhy
orders, order_itemsPostgres (Supabase)Lakeflow Connect (query-based)Continuously updated — INSERT + UPDATE tracked; DELETEs are not
customers, addresses, payments, returnsADLS file dropAutoloader — IncrementalGrows over time — append + watermark
products, payment_methods, shipping_tier, suppliersADLS file dropAutoloader — Full loadSmall / periodically refreshed — overwrite is safe

Decision rule: live database with continuous INSERT/UPDATE/DELETE → Lakeflow Connect. File that lands in ADLS and grows over time → Autoloader + Incremental. Small file, fully refreshed each time → Autoloader + Full load.

Section 4

The Other Half of Today

Why hardcoded storage keys are a problem — and the two Unity Catalog building blocks that replace them.

Since Day 1, Every Notebook Has Started Like This

storage_account_name = "YOUR_STORAGE_ACCOUNT_NAME"
storage_account_key  = "YOUR_STORAGE_ACCOUNT_KEY"  # ← 88-char secret

spark.conf.set(
    f"fs.azure.account.key.{storage_account_name}.dfs.core.windows.net",
    storage_account_key
)
ProblemWhat It Means
Security riskAnyone who opens the notebook sees a key with full read/write access
Git exposureA committed key stays in git history even after being deleted from the file
Key rotationRotating the key breaks every notebook that hardcodes it, all at once
No audit trailAzure sees "the key was used" — not which user, from which notebook
All-or-nothingEveryone with the key has full read/write — no read-only option

Current Flow vs. What We Want

CURRENT FLOW (key-based):
  Notebook → spark.conf.set(key) → Spark driver → ADLS
                    ↑
              secret lives in plain text in the notebook cell

WHAT WE WANT:
  Notebook → abfss://... → Unity Catalog checks permission → ADLS
                                        ↑
                              no key anywhere — auth handled centrally

The fix is two Unity Catalog objects, created once by an admin, then reused by every notebook.

The Two Unity Catalog Building Blocks

Think of it like an office building: an employee badge proves who you are, and a specific door only opens for badges that are allowed through it.

Storage Credential = the badge

Databricks' identity card for Azure. It wraps an Azure Managed Identity (the Databricks Access Connector) — an Azure resource granted "Storage Blob Data Contributor" on your ADLS account. No password, no key, nothing that can leak.

External Location = the door it unlocks

A registered ADLS path + which Storage Credential is allowed to use it.

External Location: gbmart-ext-loc
  URL:                abfss://ecom-gbmart-data
                       @ecomadlsdata.dfs.core.windows.net/
  Storage Credential: ecomprojectscredentials

The Full Auth Chain

Notebook uses abfss://ecom-gbmart-data@ecomadlsdata.dfs.core.windows.net/raw-data/
       ↓
Unity Catalog: "This path is covered by External Location 'gbmart-ext-loc'"
       ↓
Storage Credential: "Use managed identity 'ecomprojectscredentials'"
       ↓
Azure RBAC: "That managed identity has Storage Blob Data Contributor on ecomadlsdata"
       ↓
ADLS Gen2: access granted — data returned

At no point does a key appear anywhere in the notebook.

Worked Example — Real External Location, Before vs. After

BEFORE (key-based auth):

storage_account_name = "YOUR_STORAGE_ACCOUNT_NAME"
storage_account_key  = "YOUR_STORAGE_ACCOUNT_KEY"  # ← secret

spark.conf.set(...)

AFTER (Unity Catalog external location):

# No setup cell needed — External Location handles auth.
base_path = "abfss://ecom-gbmart-data@ecomadlsdata
              .dfs.core.windows.net/raw-data"

In HOL 1 you'll create your own Access Connector–backed Storage Credential and External Location against your own Day-1 storage account, and run dbutils.fs.ls() with zero keys in the notebook. gbmart-ext-loc stays the shared, real location the rest of the course's pipeline reads from.
