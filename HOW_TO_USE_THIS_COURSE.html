1. The Classroom Workflow — What Happens, In Order

Every ILT (Instructor-Led Training) and HOL (Hands-On Lab) session follows the same repeatable pattern:

  1. Open the .html — explain the concept on screen, no code runs yet. This is the "why" — the diagrams, the comparison tables. Learners read along, ask questions.
  2. Run the .ipynb live — open the matching notebook in Databricks and hit Run All in front of the class. It must complete with zero errors and zero placeholders — the "how," demonstrated for real against the live gbmart workspace (or, for standalone concept modules, against real read-only metadata / plain Python).
  3. Learners redo it (HOL only) — for Hands-On Labs, learners now repeat the same pipeline in their own Databricks accounts. A small number of clearly-marked YOUR_SCHEMA/_______ blanks are expected and intentional — that's the exercise.
  4. Import the .md (Day 1 only, so far) — for the one hands-on that has an LMS version, import the .md file into the LMS so learners can also complete it as a tracked, graded exercise outside Databricks.

ILT vs. HOL, in one line: ILT sessions are almost entirely .html + a light or no-code .ipynb — they teach a concept. HOL sessions are a full .ipynb build with real PySpark/SQL against gbmart — they teach a skill. A few sessions are also tagged DEMO (instructor-only walkthrough, no learner redo) or REF (optional certification-prep reference material, not scheduled class time).

Not every ILT is pipeline-flow content. A handful of sessions are deliberately standalone modules: real Databricks/DE knowledge, illustrated with GlobalMart-flavored examples, but not wired into the Bronze→Silver→Gold narrative and not required for later days to make sense. Day 2 ILT/HOL 3 (Code Versioning Concepts) was the first of these. Day 10 ILT 2/3 (orchestration DAG concepts, Databricks Workflows vs Airflow) and the Day 11/12 ILT sessions (Section 7) follow the same pattern — each still includes real, runnable code (topological sorts, retry simulations, real metadata reads, practice-schema demos), just against plain Python or a personal schema instead of the shared pipeline tables.

2. The Three File Types, and What Each One Is For

.ipynb — The real, running pipeline

A fully-working Databricks notebook. For HOLs, it must run top-to-bottom with Run All, zero errors, against the real gbmart catalog — this is what you demo live and what learners rebuild. For ILTs, it's often lighter or purely conceptual (some ILTs have no notebook at all where the HTML carries the whole session); standalone-module ILTs instead run real plain-Python or read-only-SQL demos.

.html — The concept explainer

A single self-contained styled page (open it directly in any browser — no server needed) covering the "why" before the "how": diagrams, comparison tables, common mistakes, a submission checklist for HOLs. Shown on screen before touching Databricks. Every .ipynb in this course has a matching .html with the same filename.

.md — LMS-importable hands-on

A markdown file formatted specifically for your LMS's import function — scenario + globally-numbered inputs, so learners can complete the exercise as a tracked, gradable assignment outside Databricks entirely. Confirmed working for Day 1's HOL and now also Day 12's Assessment 2 (the Supply Chain Pipeline scenario). Build more only via the globalmart-hol-md-builder skill below — never hand-write one from the reference-folder template (see Section 9).

New since the last update — three skills now build all of this, don't hand-write it. .claude/skills/globalmart-notebook-builder builds a Day N ILT/HOL .ipynb; globalmart-hol-md-builder builds the matching LMS-import .md in the one confirmed-working format; globalmart-slide-deck-builder builds the matching .html deck, reading the real .ipynb/.md content first and rotating real Chennai 2026 learner names through worked examples. Each skill bundles its own references/ — architecture facts, the fact_sales schema, naming rules, safety rules — read fresh every time, never from memory, because several of these facts have drifted wrong more than once during this build (Section 4a).

2. Naming Convention — Now Sort-Order Safe

Day{N}/Day{N}_{order}_ILT{x}_Topic_Name.ipynb   # Instructor-Led Training — concept session
Day{N}/Day{N}_{order}_HOL{x}_Topic_Name.ipynb   # Hands-On Lab — learners build it themselves
Day{N}/Day{N}_{order}_DEMO_Topic_Name.ipynb     # Instructor-only live walkthrough, no learner redo
Day{N}/Day{N}_{order}_REF_Topic_Name.ipynb      # Optional / cert-prep reference, not scheduled class time

The {x} suffix (ILT1, ILT2, HOL1, HOL2...) is the order to run them in, within that type — not a difficulty ranking; always teach/run them in numeric order. When a day has only one ILT or HOL, the number is sometimes omitted (e.g. Day 1's HOL has no 1).

New as of 2026-07-04 — the leading {order} digit. All ~50 HTML files across Day 1–12 (and their notebooks) now carry it — e.g. Day 1 runs Day1_1_ILT1 → Day1_2_ILT2 → Day1_3_ILT3 → Day1_4_ILT4 → Day1_5_HOL → Day1_6_REF.

Why it was added: plain alphabetical sort put DEMO and HOL (D, H) before ILT (I), and REF (R) after — so a file browser used to list a hands-on or reference file before the concept session that introduces it. The prefix makes file-browser order equal teaching order, in every folder, from now on.

4. Casing Rule & fact_sales — Natural Keys, Not Surrogate

Bronze vs. Silver casing — the rule that trips people up most. Bronze preserves the source's raw casing exactly (PascalCase from CSVs, e.g. CustomerID; the CDC source's own casing for orders). Silver renames everything to lowercase snake_case (customer_id). That renaming is Silver's job — if you ever see PascalCase in a Silver notebook, something's wrong; if you see snake_case in Bronze, same.

fact_sales — the course's centerpiece — uses natural keys, not surrogate keys. Every dimension (built Day 6) has a proper surrogate key, but the fact table (built Day 7) joins to all six of them by natural business key (Customer_ID, Product_ID, Order_ID, Address_ID, Payment_ID, Time_ID) instead — the only surrogate key it generates is its own row identity, fact_sales_sk. This is a real, deliberate, and explicitly-taught simplification (Day 6 ILT 3 + Day 7 HOL 2), not a mistake to "fix" if you see it. Grain = one row per order line item. Measures = Quantity_purchased, Sales_amount (additive); Actual_price, Discounted_price (non-additive — never SUM/AVG directly). One more wrinkle worth knowing: Order_ID genuinely does join dim_orders on its natural key and plays a degenerate-dimension-style role in the fact (never via dim_orders.order_sk) — while Payment_ID is a pure non-joiner, sitting in a completely different ID space from dim_payment_method. Day 6 ILT 3 covers this in full.

5. Where The Content Came From — the "Sayli" Grounding Pattern

A colleague (sayli) already has a complete, real, working implementation of much of this pipeline in the same shared Databricks workspace — Bronze/Silver/Gold builds, the CDC pipeline, incremental/SCD2 merge scripts. Wherever her real, proven code exists for a topic, it was used as the answer key: pulled read-only, then rebuilt in this repo with GlobalMart's naming, full comments, and a teaching narrative wrapped around it. Where no equivalent exists (pure concept/lecture sessions, or topics she hasn't reached yet), content was written fresh from the architecture spec and calendar.

Nothing was ever written to, modified in, or triggered against her account. If you or an assistant ever pull more content from there in the future, keep it strictly read-only.

6. Safety Rules Baked Into Every Notebook

✓ No notebook in this repo starts a cluster, job, pipeline, or SQL warehouse on its own. Every "run this" instruction assumes you're already attached to a running all-purpose cluster — nothing here provisions or triggers billable compute by itself.

✓ Write-heavy HOLs never write directly to shared gbmart tables. Any exercise involving MERGE/SCD/CDF uses a SHALLOW CLONE or a personal practice schema (main.YOUR_SCHEMA) instead — first introduced in Day 10, retrofitted into Day 9 HOL 2 and Day 4 HOL 2, and used again for Day 11's DLQ demo and Day 12's row-filter/masking demo. This is what makes the exercise repeatable for every cohort and every rehearsal, instead of only working once.

✓ Orchestration and cost topics never call a real Jobs/Clusters/Pipelines API. Day 10 ILT 2/3 and Day 11 ILT 2 teach job/cluster configuration as inspectable Python dicts, constructed and printed — never submitted anywhere. Any streaming .trigger(...) in this course either uses availableNow=True (terminates on its own) or explicitly calls .stop() before the cell can finish — a real gap of exactly this kind was found and fixed in Day 3's cert-prep reference notebook during a safety audit.

✓ VACUUM ... RETAIN 0 HOURS never appears anywhere in this course. It permanently deletes file history — any VACUUM shown is illustrative/commented-out only.

✓ No real storage-account key ever gets committed — even in an "instructor answer key" notebook. GitHub's push protection actually caught one during this build: a real Azure storage key was hardcoded in a Day 12 assessment answer notebook (00_mount_storage.py) and blocked the push. It was replaced with a placeholder before the push was retried. The rule in Section 4a applies to every notebook in the repo, not just learner-facing ones — mount/setup notebooks written for your own rehearsal use are not exempt.

8. Lessons From This Build — Worth Knowing Before You Extend It

Never trust a subagent's self-report alone

Day 6 was once silently overwritten by a background process that had reported failure but auto-resumed hours later with a stale, pre-verification mental model — wrong catalog name, missing dimension, wrong measures. It was only caught by directly reading the content, not by any failure signal. Independently re-check anything an automated process touches: file validity, a safety-pattern search, and an actual read of the content, every time — before teaching from it.

"4 sources" and the Bronze table count are the recurring traps (Section 4) — worth repeating here because they're the facts most likely to silently drift back into future material: GlobalMart has 2 real ingestion pathways and 8 real Bronze tables, not 4/6/7. Both have resurfaced more than once while extending this course.

Working files leak into the wrong folder, including the repo root. Debug screenshots, notebook re-exports, and closing-day activities have all landed loose at the repo root or inside the wrong day's subfolder at least once during this build, instead of their correct DayN/ location — caught only by a deliberate git status + naming audit, not automatically. Do this audit periodically, not just when something visibly breaks.

GitHub's secret scanner is a real backstop, not a formality. A hardcoded Azure storage key in a Day 12 answer notebook was caught and blocked at push time (Section 6) — a reminder that "it's just an instructor answer key, not learner-facing" is not a reason to relax the never-hardcode-a-key rule.

9. The One Gotcha: LMS .md Import Format

The reference for making the hands/ folder looks like the obvious template to copy — plain headers, no frontmatter, inputs renumbering from 1 in every scenario. It is not the import format. It's an export dump (what the LMS produces when you read content back out), confirmed the hard way by a real failed import.

Reference folder style (export — do NOT copy this)Actual import format (use this)
FrontmatterNoneYAML block: name, content_type, overview, learning_objectives, etc.
Input numbering##### Input 1, resets to 1 every new scenario## Input 1 … ## Input 30, numbered globally, never resets

Confirmed working, currently correct: Day1/Day1_5_HOL_PySpark_SparkSQL_ADLS.md and the Day12/assessment/ scenario .md files. If you ever build another hands-on .md, use the globalmart-hol-md-builder skill (Section 2), which encodes this exact format — never hand-copy the reference folder's.
