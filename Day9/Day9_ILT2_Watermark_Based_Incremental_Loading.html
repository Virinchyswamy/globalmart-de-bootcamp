The Mechanism, in One Query

SELECT * FROM source_table WHERE updated_at > :last_watermark_value;
-- ...then, only after that batch is successfully written downstream:
UPDATE control_table SET last_watermark_value = MAX(updated_at) FROM this_batch;
Requirement 1The source column must be reliably bumped on every change. GlobalMart's Postgres orders table has a trigger, trg_orders_updated_at, that does this automatically on every UPDATE.
Requirement 2The watermark must only advance after a confirmed successful write. Advance it too early and a failed run silently loses that batch forever.

GlobalMart's Real Pipeline Configuration

Not a hypothetical — this is the live spec for orders_data_ingestion_cdc (built Day 2):

{
  "name": "orders_data_ingestion_cdc",
  "spec": {
    "catalog": "gbmart", "schema": "bronze", "serverless": true,
    "ingestion_definition": {
      "connection_name": "ecom_gbmart_conn", "source_type": "POSTGRESQL",
      "objects": [
        { "source_table": "orders", "primary_keys": ["orderid"], "cursor_columns": ["updated_at"] },
        { "source_table": "order_items", "primary_keys": ["orderitemid"], "cursor_columns": ["updated_at"] }
      ]
    }
  }
}
Note orderid, not order_id — Bronze keeps the source's own naming, no underscores. Day 5's Silver layer is what renames these. Bronze is always raw-as-received.

Proving the Blind Spot (Carried Forward from Day 2)

If a row is hard-deleted from postgres.globalmart.orders, this query never sees it — no row is left to have a newer updated_at. It sits in gbmart.bronze.orders forever, undeleted, with zero signal. This is exactly what Day 2's HOL proved hands-on. CDF (ILT 3, next) is the strategy that closes this gap — which is why it's what GlobalMart uses for the Bronze → Silver hop.
