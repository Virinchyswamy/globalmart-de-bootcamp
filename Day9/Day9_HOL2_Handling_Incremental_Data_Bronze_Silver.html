Part 1 CDF-Based Incremental Refresh: payments

payments is 1:1 with orders and doesn't need SCD2 history — when a payment record changes, Silver just needs the current value. That makes this a plain upsert MERGE, the simplest form of the pattern (SCD2 dimension history is Day 10's job).

Why a practice clone, not the real gbmart.silver.payments? This exercise's whole point is watching a MERGE consume pending changes, then run again and find nothing left. Against the real shared table, only the first person in the cohort to run it would ever see a non-zero merge. A SHALLOW CLONE in your own schema gives the same real data and real CDF mechanics, but a version history that's entirely yours — repeatable every time.

StepWhat it does
0SHALLOW CLONE gbmart.bronze.payments / gbmart.silver.payments into your own schema
1Read last processed Bronze version from your schema's _incremental_control
2Read CDF since last_version + 1
3Drop update_preimage rows
4Standardize columns (same logic as Day 5's full load)
5MERGE into your silver_payments_practice clone — update matched, insert new
6Advance the control table to the newest version processed
