Day 9 — ILT 3: CDF-Based Incremental Loading (Bronze to Silver via MERGE)

Why CDF, Not Just Reading The Whole Table Again

Without CDF: Silver reads all 126,000+ orders every run -> slow, expensive, gets worse over time
With CDF: Silver reads only the ~800 rows that changed -> fast, cheap, constant cost

CDF is a Delta Lake table property. Once enabled, every INSERT/UPDATE/DELETE is automatically recorded as a row-level event — Delta does it as part of the transaction, no separate logging code.

What CDF Records

ColumnDescription
_change_typeinsert, update_preimage, update_postimage, or delete
_commit_versionDelta table version the change happened in
_commit_timestampWhen the change was committed
An UPDATE produces two CDF rows — old values (update_preimage) and new values (update_postimage). Filter out update_preimage when you only want "what does this row look like now."

The Bronze → Silver MERGE Pattern

StepWhat it does
1Find last Bronze version Silver already processed (control table — same idea as ILT 2, tracking a version number instead of a timestamp)
2Read Bronze's CDF starting from last_version + 1
3Drop update_preimage rows
4Apply Day 5's cleaning/standardization to just this changed set
5MERGE into Silver
6Record the new last-processed version
Same six-step shape as ILT 2's watermark loader — read only what's new, process, write, advance the marker. CDF just uses a Delta version number as the marker instead of a business timestamp.
