Recap

Recap — Where CDF Fits

The Gap From ILT 2 / HOL 1

Cursor/watermark loading works great — until a row is hard-deleted. No newer updated_at is ever produced, so the delete is never noticed.

Today's Fix

Strategy 3 from ILT 1 — Delta Change Data Feed. It doesn't depend on a business column at all, so it closes that gap completely.

Why CDF, Not Just Re-Reading the Whole Table

Like a bank statement that lists only this month's transactions, instead of reprinting your entire life-savings history every single statement. CDF is a Delta Lake table property — once enabled, every INSERT / UPDATE / DELETE against that table is automatically recorded as a row-level event. Delta does it as part of the transaction itself; no separate logging code needed.

Without CDF:  Silver reads all 126,000+ orders every run
              -> slow, expensive, gets worse over time

With CDF:     Silver reads only the ~800 rows that changed
              -> fast, cheap, constant cost

What CDF Actually Records

ColumnDescription
_change_typeinsert, update_preimage, update_postimage, or delete
_commit_versionThe Delta table version the change happened in
_commit_timestampWhen the change was committed

Note the two update_* types — an UPDATE produces two CDF rows: the row's old values (update_preimage) and its new values (update_postimage). When you only care about "what does this row look like now," filter out update_preimage.

Rollout, Step 1

Enabling CDF — Bronze

A single, idempotent metadata change — no extra compute cost, safe to run more than once.

Enabling CDF on Bronze Tables

BRONZE_TABLES = [
    "customers", "products", "addresses",
    "payments", "payment_methods", "returns"
]

for table in BRONZE_TABLES:
    spark.sql(f"ALTER TABLE gbmart.bronze.{table} "
              "SET TBLPROPERTIES (delta.enableChangeDataFeed = true)")

orders and order_items are deliberately skipped — they're owned by the Lakeflow Connect pipeline and already use the cursor/watermark strategy from ILT 2 instead. This is real and idempotent — running it again does nothing harmful.

Live Check — Confirm CDF Enabled

Run against real gbmart — read-only
spark.sql("DESCRIBE HISTORY gbmart.bronze.customers") \
    .select("version", "timestamp", "operation") \
    .orderBy("version", ascending=False) \
    .show(5, truncate=False)

DESCRIBE HISTORY will show a new version where the table property changed.

Enabling CDF on Silver Too

Enable it now, before Silver has any incremental readers — for the same reason Bronze needed it enabled early. Turning CDF on late means missing whatever changed in the gap.

This isn't required for today's Gold layer — built via full overwrite, not incremental MERGE — it's about keeping the option open for later, at zero cost now.

Reading a Change Feed

cdf_df = (
    spark.read.format("delta")
        .option("readChangeFeed", "true")
        .option("startingVersion", last_processed_version + 1)
        .table("gbmart.bronze.products")
)

No separate API to learn — reading changes since a version is one option pair on a normal batch read.

Putting It Together

The Bronze → Silver MERGE Pattern

This is the shape every CDF-based incremental Silver refresh follows — HOL 2 builds a real one.

The Bronze → Silver MERGE Pattern, Step by Step

  1. Find the last Bronze version Silver has already processed (a control table — same idea as ILT 2, just tracking a version number instead of a timestamp)
  2. Read Bronze's CDF starting from last_version + 1
  3. Drop update_preimage rows — you only want each changed row's current state
  4. Apply the same cleaning/standardization transformations used for the full load, to just this smaller changed set
  5. MERGE the result into Silver — update matched rows, insert new ones
  6. Record the new last-processed version

Notice this is structurally the same six-step shape as ILT 2's watermark loader (read only what's new → process → write → advance the marker) — CDF just uses a Delta version number as its marker instead of a business timestamp column.
