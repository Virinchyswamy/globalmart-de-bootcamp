The Core Idea

One Question, Asked Every Run: "What's New Since Last Time?"

Strip away the Delta/Spark syntax and a watermark loader is just a bookmark in a book. You don't re-read every page each time you sit down — you check the bookmark, start there, and move the bookmark forward when you stop.

📑 The control table is the bookmark

One row per source table, holding the single highest updated_at value ever successfully loaded. Before the very first run, that value is set to an ancient timestamp (1970-01-01) — which just means "treat everything as new."

🔁 The loader is four steps, every run

  1. Read the current watermark from the control table.
  2. Pull only source rows newer than that watermark.
  3. If anything came back, write it (create or MERGE).
  4. Only after that write succeeds, advance the watermark.

Why step 4 comes dead last, on purpose: if the watermark advanced before the write was confirmed, a failed run would quietly lose that batch forever — the loader would believe it already loaded rows it never actually wrote anywhere. Writing first, advancing second, is the one ordering rule that makes this pattern safe to re-run after a crash.

Run 2 is easy to skip and it's the one that actually separates "incremental" from "happened to load everything once." Without it, you'd have no evidence the WHERE updated_at > :last_watermark filter is doing anything at all — Run 1 alone looks identical whether the filter works or the loader just always does a full reload.

The Known Limitation, Not a Bug

Why a Watermark Can Never See a Delete

This isn't a mistake in the code you'll write — it's a structural fact about the pattern itself, and it's worth understanding exactly why.

🕳️ The mechanism of the gap

The loader's whole filter is WHERE updated_at > :last_watermark. A hard delete removes the row entirely — there's no row left to have an updated_at at all, newer or otherwise. The filter has nothing to see, so it reports zero changes, correctly, even though something very real just happened upstream.

🔗 The exact same gap, at GlobalMart scale

orders_data_ingestion_cdc is configured with query_based_connector_config: cursor_columns: ["updated_at"] — the same cursor mechanism you just built by hand, at production scale. A hard-deleted order in Postgres has this identical blind spot in real gbmart.bronze.orders today.

This is exactly the gap Change Data Feed closes (Day 9 ILT 3, right after this lab) — CDF records every DELETE as its own event, because it reads Delta's transaction log directly instead of filtering a business timestamp column. The watermark pattern isn't broken here — it's just answering a question ("what's new?") that a delete was never going to answer yes to.

Reinforce Before You Open the Notebook

Quick-Fire Concept Check

Click to reveal each answer. If any of these surprise you, re-read the section above before you start.

Is this lab building GlobalMart's actual orders/order_items pipeline?
No. That pipeline is the real, managed orders_data_ingestion_cdc Lakeflow Connect connector (Day 2). This lab teaches the general control-table pattern by hand — useful for any source that isn't already on a managed CDC connector, but not literally what GlobalMart's own pipeline does.
Why does Run 2 (the no-op run) matter more than it looks like it should?
It's the only run that proves the loader is actually filtering by watermark instead of just reloading everything every time. Run 1 alone can't tell the difference between "the filter works" and "there is no filter" — both produce 5 rows on a cold start.
Why does the watermark advance only after the write succeeds, never before?
If the watermark advanced first and the write then failed, the next run would believe those rows were already loaded — because the bookmark says so — and would never attempt them again. Writing first, advancing second, means a crash mid-run can always be safely retried from where it actually left off.
Why can't a watermark filter ever catch a hard delete, no matter how the code is written?
The filter only ever looks at rows that still exist, checking whether their updated_at is newer than the watermark. A hard delete leaves no row behind to check at all — there's nothing for the filter to catch, correctly, even though the delete is a completely real change.
