Why Build This By Hand?

The real orders_data_ingestion_cdc pipeline (Day 2) already does cursor-based incremental loading for you — Lakeflow Connect manages the watermark internally, invisibly. This lab has you build the exact same mechanism yourself, against a small practice table, so it stops being a black box.

⚠ Setup: replace YOUR_SCHEMA with something unique to you. This lab works entirely in main.YOUR_SCHEMA — you will not touch any shared GlobalMart table.

Phase A Simulate an Upstream Source

A small Delta table with an updated_at column stands in for "a Postgres table with an updated_at trigger" — this lets you cause changes on demand instead of waiting for real data to change.

Phase B Control Table + Initial Load

CREATE TABLE practice_ingestion_control (
  source_table          STRING,
  last_watermark_value TIMESTAMP,
  last_run_at         TIMESTAMP
) USING DELTA;

-- seeded at epoch (1970-01-01) = "nothing loaded yet, pull everything"

The loader function does 4 steps every time it runs: read the watermark → pull only rows newer than it → MERGE into the target → only on success, advance the watermark to the newest value just loaded.

Phase D Simulate a Real Change

Update one row's amount (bumping its updated_at, like GlobalMart's real trigger would) and insert one brand-new row. Run 3 should show exactly 2 changed rows — not all 6.

Phase E Prove the Blind Spot Yourself

Delete a row from the upstream source, then run the loader again. Expect 0 rows detected — and the deleted row still sitting in your target table, undeleted, forever. This is the same gap the real orders_data_ingestion_cdc pipeline has today.
