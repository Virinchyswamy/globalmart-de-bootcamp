The Problem: Why Full Re-Scans Stop Scaling

Imagine re-reading an entire 500-page book from page one — every single time — just to find the one new sentence someone added at the end. That's exactly what a full load does: read the entire source, transform all of it, overwrite or rebuild the target, on every run.

Why This Breaks Down at Scale

  • Fine when a table is 500 rows
  • Not fine when a table is 126,000+ rows and growing by a few hundred a day
  • Re-processing everything to catch ~200 new rows wastes compute and time
  • At real production scale (millions of rows), a 2-minute job can become a 2-hour job

What "Incremental Loading" Actually Means

The Definition

On every run, touch only the rows that are new or changed since the last run — nothing more.

The hard part isn't the definition — it's knowing which rows those are. It turns out there's more than one way to answer that question.

GlobalMart Already Has 3 Answers

The real pipeline doesn't use one incremental strategy — it uses three, for three different reasons. This session walks through all three before Day 9's hands-on labs build two of them yourself.

Section 2

The Three Strategies Already Running in GlobalMart's Pipeline

1 · File Checkpoint

Tracks which files have already been read. Autoloader, for 6 of 8 Bronze file-drop sources.

2 · Cursor / Watermark

Tracks which rows have a business timestamp newer than last time. Lakeflow Connect, for orders / order_items.

3 · Delta Change Data Feed

Tracks row-level Delta transactions, including deletes. Used for the Bronze → Silver refresh.

Strategy 1 (Recap) — File Checkpoint (Autoloader)

Already fully covered in Day 3-4: Autoloader's cloudFiles.schemaLocation + checkpointLocation remember which files have already been streamed into Bronze. Drop a new file in, re-run — only the new file gets processed.

What It's Good At

Cheap, simple, works great when each new batch of data arrives as a brand-new file — a new day's customers_020626.csv, a new products_020626.json.

Silently misses: a change made inside a file Autoloader already processed. If someone hand-edited a file after it landed and re-uploaded it with the same name, the checkpoint would skip it — as far as Autoloader is concerned, that file is already done. File-level tracking has no idea what happened inside a file it already saw.

Strategy 2 — Cursor / Watermark Column

This is what the real orders_data_ingestion_cdc pipeline does (Day 2). Instead of tracking files, it tracks a business column — updated_at — and on every run asks the source: "give me every row where updated_at is newer than the last value I saw."

table_configuration: {
  primary_keys: ["orderid"],
  query_based_connector_config: { cursor_columns: ["updated_at"] }
}

What It's Good At

Works on any table with a reliable, always-bumped timestamp column — no logical replication or CDF needed on the source, just a WHERE updated_at > X query. Exactly why it's the right choice for reading a Postgres OLTP table over a plain connection.

Silently misses: a hard DELETE. No row is left with a newer updated_at to signal the row is gone — it just vanishes from the next query result. GlobalMart's real orders_data_ingestion_cdc pipeline has exactly this blind spot today.

Strategy 3 — Delta Change Data Feed (CDF)

CDF doesn't watch files, and it doesn't rely on a business column at all. It's a Delta Lake feature — once turned on for a table, every INSERT / UPDATE / DELETE is automatically recorded as a row-level change event, tagged with _change_type, _commit_version, and _commit_timestamp. A downstream reader asks Delta "give me everything that changed since version N" and gets back exactly that.

What It's Good At

The most complete picture — inserts, updates, and deletes, all captured automatically with zero reliance on the source having a well-behaved timestamp column.

What it costs: only works between two Delta tables (Bronze → Silver, Silver → Gold) — not something you can point at an external Postgres source. It also has a retention/storage cost — the changelog must eventually be vacuumed with a retention window in mind, same as time-travel history.
