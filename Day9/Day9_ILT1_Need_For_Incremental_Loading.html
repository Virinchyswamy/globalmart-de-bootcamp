The Problem

Every notebook so far does a full load: read everything, overwrite or rebuild the target. That's fine at 500 rows. At 126,000+ rows and growing daily, re-processing everything to catch 200 new rows wastes time and compute — and only gets worse as GlobalMart grows.

Incremental loading means touching only what's new or changed since last run. GlobalMart's real pipeline already answers "what's new" three different ways.

Strategy 1 (Recap) — File Checkpoint

Autoloader's checkpointLocation remembers which files it already streamed. Good for new files landing regularly. Misses: a change made inside a file it already processed — as far as Autoloader's checkpoint is concerned, that file is done.

Strategy 2 — Cursor / Watermark Column

The real orders_data_ingestion_cdc pipeline asks the source: "give me rows where updated_at is newer than my last watermark." Works against any queryable source with a reliable timestamp column.

⚠ Blind spot: a hard DELETE produces no row with a newer updated_at — the deleted row just vanishes from the query result with zero signal. GlobalMart's real pipeline has exactly this gap today.

Strategy 3 — Delta Change Data Feed (CDF)

A Delta Lake table property. Once enabled, every INSERT/UPDATE/DELETE is automatically recorded — including deletes, closing Strategy 2's exact gap. Only works Delta-to-Delta (Bronze→Silver, Silver→Gold), not against an external source directly.
