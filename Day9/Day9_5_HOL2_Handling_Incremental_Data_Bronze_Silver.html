Overview

Two Parts, Two Strategies

Part 1 — CDF Path

Build a real incremental Bronze → Silver refresh for gbmart.payments, using Delta CDF + MERGE — a plain upsert, not the SCD2 dimension-history version (that's Day 10's job).

Part 2 — Watermark Path

Verify the real orders/order_items Lakeflow Connect pipeline actually picked up a change, using the same checks a production on-call engineer would run.

Part 1 — Why payments?

payments is a good first CDF target: it's 1:1 with orders, and — unlike customers/products — doesn't need SCD2 history. When a payment record changes, Silver just needs the current value, not every past version.

The Simplest Form of the Pattern

That makes this a plain upsert MERGE — the simplest version of the CDF pattern you saw in ILT 3.

Why a Practice Clone, Not the Real Table?

This exercise's whole point is watching a MERGE consume a batch of pending changes, then run again and find nothing left. Against the real shared table, only the first person to run this in the whole cohort would ever see a non-zero merge — everyone after (including you, rehearsing before class) would see "0 changed rows," and the exercise would look broken.

CREATE OR REPLACE TABLE bronze_payments_practice
  SHALLOW CLONE gbmart.bronze.payments;

CREATE OR REPLACE TABLE silver_payments_practice
  SHALLOW CLONE gbmart.silver.payments;

A SHALLOW CLONE in your own schema gives you the same real data and the same real CDF mechanics, but a version history that's entirely yours — repeatable every time, for every student, forever.

The 6-Step Refresh Pattern

  1. Read last processed Bronze version from your schema's control table
  2. Read Bronze's CDF since last_version + 1
  3. Drop update_preimage rows
  4. Standardize columns (same logic as the Day 5 full load)
  5. MERGE into your silver_payments_practice clone — update matched, insert new
  6. Advance the control table to the newest version processed

Running the Refresh — Twice

Run against your own practice clones
# Run 1 (first ever run, last_bronze_version = -1): reprocesses all history — expected.
refresh_silver_payments()

# Run 2 (immediately after, nothing changed): expect "Changed rows since last run: 0"
refresh_silver_payments()

Run 2 finding zero changes is the real proof this is incremental — not a coincidence of running it once.

On-Call Verification

Part 2 — Verify the Watermark Pipeline

Unlike Part 1, you don't build the ingestion yourself here — the real orders_data_ingestion_cdc pipeline (Day 2) already owns it. Your job is to verify it actually picked up a change, the same way a production on-call engineer would.

Three Verification Checks

CheckConfirms
Row counts on orders / order_itemsCompare before/after a re-trigger
Top rows by updated_at DESCWhich rows the most recent run picked up
DESCRIBE HISTORYA new version confirms the pipeline actually wrote something

If your instructor makes a change in the source Postgres tables and re-triggers the pipeline during class, run these checks after that happens. If not, run them anyway to see the current state — the counts just won't have moved.

Next Step
