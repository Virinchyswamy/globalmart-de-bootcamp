The Mechanism, in One Query

Every watermark-based incremental load boils down to the same idea: ask the source "what changed since I last checked?" instead of re-reading everything — like asking a librarian for books returned since Tuesday instead of re-counting the whole shelf. In SQL, that's one query shape, run on a schedule: 

SELECT * FROM source_table WHERE updated_at > :last_watermark_value;
-- ...then, only after that batch is successfully written downstream:
UPDATE control_table SET last_watermark_value = MAX(updated_at) FROM this_batch;

Two Requirements for This to Work

Requirement 1 — A Reliable Trigger

The source column must be reliably bumped on every change. GlobalMart's Postgres orders table has a trigger, trg_orders_updated_at, that sets updated_at = now() automatically on every UPDATE — nobody has to remember to do it by hand.

Requirement 2 — Advance Only After Success

The watermark must only move forward after a confirmed successful write. Advance it before confirming the downstream write succeeded, and a failed run silently loses that batch forever.

Point out: orderid, not order_id. Bronze columns from this Postgres source keep the source's own naming (orderid, customerid, orderchannel) — no underscores. Day 5's Silver layer is what renames these. Bronze is raw-as-received, always.

Verification

Verifying an Incremental Run Actually Happened

How do you prove the cursor picked up new changes, rather than just trusting the pipeline UI says "Succeeded"? Three checks, in order.

Three Checks, In Order

CheckWhat It Confirms
Row counts (orders / order_items)A baseline to compare before/after a re-trigger
DESCRIBE HISTORYA new version appears only when the cursor actually found something newer
Top rows by updated_at DESCExactly which rows the most recent run would have picked up

Live Checks 1 & 2 — Row Counts and Delta History

Run against real gbmart — read-only
# Check 1 — note these down; they're what you compare against after a re-trigger.
spark.sql("""
    SELECT 'orders' AS table_name, COUNT(*) AS row_count FROM gbmart.bronze.orders
    UNION ALL
    SELECT 'order_items', COUNT(*) FROM gbmart.bronze.order_items
""").display()
# Check 2 — a new version appears only if the cursor found something newer.
spark.sql("DESCRIBE HISTORY gbmart.bronze.orders") \
    .select("version", "timestamp", "operation") \
    .orderBy("version", ascending=False) \
    .show(5, truncate=False)

Live Check 3 — Most Recently Updated Rows

Run against real gbmart — read-only
spark.sql("""
    SELECT orderid, customerid, orderchannel, updated_at
    FROM gbmart.bronze.orders
    ORDER BY updated_at DESC
    LIMIT 10
""").display()

Since the cursor is updated_at, the rows with the newest values are exactly the rows the most recent run would have picked up.

Proving the Blind Spot (Carried Forward from Day 2)

If a row is hard-deleted from postgres.globalmart.orders right now, the query from a few slides back — WHERE updated_at > last_watermark — would simply never see it. There's no row left to have a newer updated_at.

The row sits in gbmart.bronze.orders forever, undeleted, with no error, no warning, no signal anything is wrong. This is exactly what Day 2's HOL had you prove hands-on, by deleting a test row and watching it not sync.

The fix: CDF — covered in ILT 3, later today — is the one strategy that closes this exact gap. That's exactly why GlobalMart uses CDF, not cursor-based watermarking, for the Bronze → Silver hop.
