Watermark-Based Incremental Loading

A cursor column turns "read everything, every time" into "read only what changed" — and we trace that idea live through GlobalMart's real ingestion pipeline, orders_data_ingestion_cdc, using the exact same six queries the real pipeline's own verification uses.

🔒 Read-only — nothing here writes to gbmart 📋 Follows ILT 1 — Need for Incremental Loading ➡️ Leads into HOL 1 — Build a Watermark Yourself
The Core Idea

The Mechanism, in One Query

Every watermark-based incremental load boils down to the same idea: ask the source "what changed since I last checked?" instead of re-reading everything — like asking a librarian for books returned since Tuesday, instead of re-counting the whole shelf. In SQL, that's one query shape, run on a schedule. 

SELECT * FROM source_table WHERE updated_at > :last_watermark_value;
-- ...then, only after that batch is successfully written downstream:
UPDATE control_table SET last_watermark_value = MAX(updated_at) FROM this_batch;

Requirement 1 — A Reliable Trigger

The source column must be bumped on every change, no exceptions. GlobalMart's Postgres orders table has a trigger, trg_orders_updated_at, that sets updated_at = now() automatically on every UPDATE — nobody has to remember to do it by hand.

Requirement 2 — Advance Only After Success

The watermark must only move forward after a confirmed successful write. Advance it before confirming the downstream write succeeded, and a failed run silently loses that batch forever.

Verification

Verifying an Incremental Run Actually Happened

How do you prove the cursor picked up new changes — instead of just trusting the pipeline UI's green "Succeeded"? You run queries and actually look at the rows. This is the exact six-query pattern used against GlobalMart's own orders_data_ingestion_cdc pipeline, the last time it ran after three real changes landed in the Postgres source.

What Changed in Postgres

  • An UPDATE to order OR-000478
  • Two brand-new INSERTs — orders OR-900001 and OR-900002

Harsh Kumar's Rule of Thumb

Never trust a pipeline run just because the UI says "Succeeded" — go look at the rows it was supposed to bring in. That's all six checks below are: going and looking.

The Real Verification Sequence

Six Checks, In Order

This is the exact sequence GlobalMart's real pipeline verification runs — not generic placeholder examples. Every ID and column name below is real.

  1. Check 1 — Did the update on OR-000478 come through? Heemansh Bhawsar wants to know: did the cursor actually pick that up on the last run, or is Bronze still showing stale data? Expect actualdeliverydate populated, and updated_at bumped to a recent timestamp — proof the row was truly touched, not just proof someone re-ran a query.
  2. Check 2 — Did the 2 new orders land? OR-900001 and OR-900002 were inserted straight into Postgres. Devanand P checks: does the cursor treat a brand-new row the same way it treats an updated one? It should — both show up for the same reason, an updated_at newer than the last watermark. Expect 2 rows back.
  3. Check 3 — Total row count on bronze.orders. The author's own notes said the total should land at 126,036 + 2 = 126,038 at the time this was written. Treat that as a snapshot, not a fact — the real table keeps growing daily. Kumar Pratik always re-runs COUNT(*) live before trusting an older written-down number.
  4. Check 4 — Did matching order_items land? Only relevant if the two new orders also had line items inserted. 2 rows if that optional step ran, 0 rows is a correct result if it didn't — not a failure.
  5. Check 5 — Total row count on bronze.order_items. Same caveat as Check 3: author's notes say 377,866 (unchanged) or 377,868 (if the insert ran) — a baseline at authoring time, not a permanent number. Verify live.
  6. Check 6 — Combined glance. One query, both row counts side by side — the quickest way to eyeball both tables before digging into individual rows.

Checks 1 & 2 — Confirm the Specific IDs

# Check 1
spark.sql("""
    SELECT orderid, customerid, shippingdate, actualdeliverydate, orderchannel, updated_at
    FROM gbmart.bronze.orders
    WHERE orderid = 'OR-000478'
""").display()
# Check 2
spark.sql("""
    SELECT orderid, customerid, orderdate, orderchannel, updated_at
    FROM gbmart.bronze.orders
    WHERE orderid IN ('OR-900001', 'OR-900002')
""").display()

Checks 3 & 5 — Live Counts, Never Hardcoded

# Check 3 — live COUNT(*), not a hardcoded number.
spark.sql("SELECT COUNT(*) AS total_orders FROM gbmart.bronze.orders").display()
# Check 5 — live COUNT(*).
spark.sql("SELECT COUNT(*) AS total_order_items FROM gbmart.bronze.order_items").display()

Check 4 — Matching order_items

# 0 rows is a valid, correct outcome here, not a bug.
spark.sql("""
    SELECT orderitemid, orderid, productid, quantity
    FROM gbmart.bronze.order_items
    WHERE orderid IN ('OR-900001', 'OR-900002')
""").display()

Check 6 — Combined Glance

spark.sql("""
    SELECT 'orders' AS table_name, COUNT(*) AS row_count FROM gbmart.bronze.orders
    UNION ALL
    SELECT 'order_items', COUNT(*) FROM gbmart.bronze.order_items
""").display()

On the row-count checks (3 and 5): the numbers above are the pipeline author's own baseline, written down at one point in time — never a promise about what COUNT(*) returns today. GlobalMart's real orders table grows every day this pipeline runs. Always run the count live and compare it against your own most recent baseline, not a number from an old doc or slide.

Beyond the Real Six

Two Bonus Checks

The six checks above are the exact pattern used against GlobalMart's real pipeline. These two aren't part of that original six, but they answer a slightly different, still-useful question: when did the pipeline last actually change something, and which rows moved most recently?

Bonus A — DESCRIBE HISTORY

A new version appears only when the cursor found something newer than its last watermark. If you re-trigger the pipeline and no new version shows up, that's expected when nothing changed in Postgres since the last run.

spark.sql("DESCRIBE HISTORY gbmart.bronze.orders") \
    .select("version", "timestamp", "operation") \
    .orderBy("version", ascending=False) \
    .show(5, truncate=False)

Bonus B — Most Recently Updated Rows

Since the cursor column is updated_at, the rows with the newest values are exactly the rows the most recent pipeline run would have picked up.

spark.sql("""
    SELECT orderid, customerid, orderchannel, updated_at
    FROM gbmart.bronze.orders
    ORDER BY updated_at DESC
    LIMIT 10
""").display()
Carried Forward From Day 2

Proving the Blind Spot

Every mechanism has a gap. This one's gap is worth knowing precisely, because it's the exact reason the next session exists.

If a row is hard-deleted from postgres.globalmart.orders right now, the query from earlier — WHERE updated_at > last_watermark — would simply never see it. There's no row left to have a newer updated_at.

The row sits in gbmart.bronze.orders forever, undeleted, with no error, no warning, no signal anything is wrong. This is exactly what Day 2's HOL had you prove hands-on, by deleting a test row and watching it not sync.

The fix: CDF — covered in ILT 3, later today — is the one strategy that closes this exact gap. That's exactly why GlobalMart uses CDF, not cursor-based watermarking, for the Bronze → Silver hop.

Reinforce Before HOL 1

Quick-Fire Concept Check

Click to reveal each answer.

Why does Check 1 look specifically at OR-000478 instead of just checking a row count?
A row count only tells you the total moved — it can't tell you whether the specific row you expected to change actually changed correctly. Checking OR-000478 by ID confirms the update itself landed with the right values (actualdeliverydate populated, updated_at bumped), which a count alone could never prove.
Why is 0 rows a correct answer for Check 4, sometimes?
Check 4 only finds rows if the optional order_items insert step was actually run for OR-900001/OR-900002. If it wasn't, order_items genuinely has nothing to bring in for those two orders — 0 rows is the honest, correct result of that state, not a sign anything broke.
Why does this ILT warn against trusting the 126,038 / 377,866 numbers permanently?
Those numbers were the author's own notes at one point in time, and the real orders table keeps growing every day the pipeline runs. A hardcoded number from an old doc goes stale immediately. The only trustworthy number is a live COUNT(*), run right now, compared against your own most recent baseline.
What single event can happen upstream that this watermark loader will never notice?
A hard DELETE in Postgres. Since the cursor only asks for rows with updated_at newer than the last watermark, a deleted row leaves nothing behind to even ask about — it just silently stops existing on the source while sitting forever in Bronze. This is exactly the gap Delta CDF closes, covered next in ILT 3.
