The Manual Pain, Made Concrete

Without an orchestrator, this is what "run the pipeline" actually means, by hand, today:

  1. Confirm the CDC pipeline succeeded for orders/order_items
  2. Kick off the Autoloader ingestion for 5 entities
  3. Wait for all 7 Bronze tables to finish
  4. Run all 7 Silver notebooks, each only once its own Bronze table has landed
  5. Wait for all 7 Silver notebooks to finish
  6. Run 6 dimension builds, then fact_sales last

Nothing here is conceptually hard — it's a lot of ordering rules for a human to hold in their head and babysit, every day, forever.

Section 2

DAG Concepts

Nodes, edges, and why every real orchestrator — Databricks Workflows, Airflow, Dagster — requires the graph to have no cycles.

A DAG Is Just a Recipe With Rules

Some steps must happen in a fixed order (you can't frost a cake before it's baked). Others can happen at the same time (preheating the oven while you mix batter). A DAG (Directed Acyclic Graph) is the data structure every real orchestrator uses to represent exactly that.

TermMeaningGlobalMart Example
NodeOne unit of work — a task"Ingest gbmart.bronze.orders"
EdgeA directed dependency — "B cannot start until A finishes"bronze_orders → silver_orders
DirectedEdges have a direction — order mattersNever the reverse: Silver can't run before Bronze
AcyclicNo path ever loops back to where it startedSee next slide

Why Cycles Are Invalid

Two tasks waiting on each other

If task_a depends on task_b, and task_b depends on task_a, neither can ever start — each is waiting on the other to go first.

Not a performance problem — a logical impossibility. A scheduler must prove a graph has no cycle before it can compute any run order at all.

That proof is exactly what topological sort does (Section 5) — and exactly why it raises an error instead of hanging forever when a cycle exists (Section 6).

Fan-out Independent Work, Free to Run in Parallel

Fan-out is any point in the DAG where multiple tasks become runnable at the same time because none of them depends on any of the others.

GlobalMart's real fan-out: the CDC-driven tasks (bronze_orders, bronze_order_items) and the five Autoloader-driven tasks (bronze_customers, bronze_products, bronze_addresses, bronze_payments, bronze_payment_methods) share zero dependencies on each other. All seven can start at the same moment, with no coordination required between them.

Fan-in A Task That Has to Wait

Fan-in, loosely, is any point where a task cannot start until an upstream task finishes. The stricter, more consequential case is a task with multiple upstream dependencies at once.

GlobalMart's clearest example: gold_fact_sales waits on six upstream tasks simultaneously — five Silver tables (order_items, orders, products, address, payments) plus gold_dim_date. Miss, delay, or fail any one of those six, and fact_sales cannot start.

A design choice, not a law: this session gives every dimension a narrow, single-parent dependency. Plenty of real orchestration jobs instead make every Gold task depend on the entire Silver layer finishing first — coarser and safer, at the cost of avoidable waiting.

Section 3

Workflow Design

How a Databricks Job — the UI now calls this surface "Workflows" — actually models a DAG under the hood.

A Databricks Job Is Just a JSON Document

FieldWhat It Holds
task_keyA short, unique name for this task within the job
depends_onWhich upstream task_key(s) must succeed first
notebook_task.notebook_pathWorkspace path of the notebook this task runs
pipeline_task.pipeline_idUsed instead when the task is a Lakeflow/DLT pipeline run

A task can also be a sql_task, a dbt_task, a python_wheel_task, and others — the shape of the DAG itself never changes.

job = {
  "name": "...",
  "tasks": [ {task}, {task}, ... ],  # every node
  "job_clusters": [ ... ],  # shared compute
  "schedule": {
      "quartz_cron_expression": "...",
      "timezone_id": "..."
  }
}

GlobalMart's real bronze_orders task uses pipeline_task, not notebook_task — it's driven by the orders_data_ingestion_cdc pipeline.

Section 5

Topological Sort

A real algorithm, run for real, over GlobalMart's actual 21-task graph.

Kahn's Algorithm, in Plain Language

  1. Collect every task whose dependencies are all already satisfied
  2. Treat that whole group as one parallel "wave"
  3. Remove them from the graph, and repeat
  4. If tasks remain but none of them ever becomes free, the graph has a cycle

That last rule is exactly how a scheduler detects a cycle without ever running anything — see Section 6.

Section 6 — a Real Error, on Purpose

Live Demo · A Deliberately Broken Graph

The matching notebook wires three real task names into a deliberate cycle: bronze_orders → silver_orders → gold_dim_orders → bronze_orders, then calls topological_sort() on it.

try:
    topological_sort(broken_tasks)
except ValueError as e:
    print(f"ValueError: {e}")
    # -> Cycle detected -- these tasks can never become ready...

Caught cleanly and printed clearly — exactly what a real scheduler should do instead of hanging forever waiting for a task that can never become ready. This is real, executing proof of why DAGs — not arbitrary graphs — are the structure every orchestrator requires.

Sections 7–8

Staying Safe — Nothing Here Is Billable

Everything so far has been plain Python in memory. This section is about what a real Databricks Job would look like — and why this notebook never actually creates one.

What This Would Look Like as a Real Job — Display Only

The matching notebook's to_databricks_job_json() reshapes globalmart_tasks into the nested shape a real Databricks Jobs REST API request expects — depends_on becomes a list of {"task_key": ...} objects, and each task carries either a notebook_task or a pipeline_task block.

Printed as text. Nothing is sent anywhere. That function only builds and returns a plain Python dict — no SDK import, no requests call, no workspace client, and no job-creation or run-triggering call of any kind, in that cell or anywhere else in the notebook. Building this JSON is free; submitting it would create a real, running, billable Databricks Job — precisely the line this session does not cross.

How You'd Actually Submit This — Never From This Notebook

Turning that JSON into a real, running Job is a deliberate action a person takes outside this notebook entirely — for example, pasting it into the Workflows UI's "Create Job" JSON view, or via the Databricks CLI:

# Illustrative only -- shown so you recognize this exact step when Day 11's
# Hands-On walks you through it for real, deliberately, with the instructor
# watching. Do not run this against a shared workspace outside that session.
databricks jobs create --json @globalmart_job.json

Why this notebook never does this, not even once: creating a job costs nothing by itself, but a job is meant to run — and one left attached to a schedule block will trigger real, unattended cluster starts on its own timetable, every day, until a person deletes it. Day 11 creates a real job exactly once, deliberately, paused or manually-triggered rather than scheduled — never as a side effect of opening a notebook.

Safety Checklist — What This Session Never Does

  • ✓ Zero calls that create, start, or trigger a real Databricks Job, Workflow, Pipeline, SQL Warehouse, or cluster
  • ✓ No job-creation or pipeline-creation REST/SDK calls, and no dbutils-based job control, anywhere in the notebook
  • ✓ The one real CLI command shown lives in a markdown cell only — inert text, never a cell that executes in "Run All"
  • ✓ The entire notebook runs top-to-bottom via "Run All" with zero errors — plain Python only, no Spark session required
