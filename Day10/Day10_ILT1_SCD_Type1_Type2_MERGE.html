Why MERGE, Not Separate UPDATE + INSERT

Two separate statements have a race-condition problem — another write between them can turn what should have been an update into a duplicate insert. MERGE INTO ... WHEN MATCHED ... WHEN NOT MATCHED ... does both in one atomic Delta transaction.

Part 1 SCD Type 1 — dim_address

# SCD1 MERGE — one branch, no history columns
(dim_address_tbl.alias("tgt")
    .merge(incoming_change_df.alias("src"), "tgt.address_id = src.address_id")
    .whenMatchedUpdate(set={"address_type": "src.address_type"})
    .execute()
)

One MERGE, one branch (whenMatchedUpdate) — the old value is simply gone afterward. That's correct: nobody needs to ask what an address label used to say.

Part 2 SCD Type 2 — dim_customer (the real pattern)

StepWhat it does
1Read the current full state of Bronze
2Find the version right before the change — CDF reads everything after it
3Take only the changed rows via CDF, not a full re-scan
4Process just those rows (same cleaning logic as the full load, scoped down)
5aMERGE — close out the old version (is_current=false, stamp effective_end_date)
5bAppend the new version (is_current=true, fresh customer_sk)
6Verify — each changed customer now shows exactly 2 rows
# Step 3 — CDF read: only what changed since LAST_PROCESSED_VERSION
cdf_changes_df = (
    spark.read.format("delta")
        .option("readChangeFeed", "true")
        .option("startingVersion", LAST_PROCESSED_VERSION + 1)
        .table(BRONZE_TABLE)
        .filter("_change_type != 'update_preimage'")
)
# Step 5a — close out old versions where email actually changed
(silver_table.alias("tgt")
    .merge(processed_df.alias("src"),
        "tgt.customer_id = src.customer_id AND tgt.is_current = true AND tgt.email <> src.email")
    .whenMatchedUpdate(set={"is_current": "false", "effective_end_date": "current_date()"})
    .execute()
)
Step 5b is a plain append, not a MERGE — every processed row becomes a brand-new Silver row with a fresh customer_sk = sha2(customer_id + effective_start_date). 5a already made sure the old row is closed out, so there's nothing to "match" for the new version.
