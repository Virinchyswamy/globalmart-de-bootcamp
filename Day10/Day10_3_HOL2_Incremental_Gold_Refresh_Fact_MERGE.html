Why Rebuild the Whole Table When Only a Few Rows Changed?

Imagine reprinting an entire book because one page had a typo. That's what a full overwrite does every time it runs — it reprints all ~377K rows even if only a handful actually changed.

What this HOL does instead

Find the one changed page, reprint just that page, and slot it back into the book. The rest of the book never gets touched.

The scale that makes this matter: fact_sales has roughly 377,000 rows today. A handful of new or corrected order_items shouldn't require re-deriving all of them.

This HOL keeps the exact same join logic as Day 7 — it just scopes it to the changed order_items, and writes with MERGE instead of overwrite.

Step 2 — Identify Only the Changed order_items

Hands-On · Your Notebook

The entire point of doing this incrementally — isolate the handful of changed rows instead of re-joining all ~377K rows.

changed_order_items_df = (
    spark.read.format("delta")
        .option("readChangeFeed", "true")
        .option("startingVersion", LAST_PROCESSED_VERSION + 1)
        .table(ORDER_ITEMS_TABLE)
        .filter("_change_type != 'update_preimage'")
)

Step 5 — MERGE INTO fact_sales (Not Overwrite)

Hands-On · Your Notebook

Keyed on fact_sales_sk — a deterministic hash of order_item_id, so re-running this never creates duplicates.

(fact_sales_table.alias("tgt")
    .merge(new_fact_rows_df.alias("src"), "tgt.fact_sales_sk = src.fact_sales_sk")
    .whenMatchedUpdateAll()
    .whenNotMatchedInsertAll()
    .execute()
)
BranchWhen It FiresWhat It Means
whenMatchedUpdateAllfact_sales_sk already existsAn order_item's fact row got recomputed (e.g. late price correction)
whenNotMatchedInsertAllNo existing rowA genuinely new order_item

Full Overwrite vs. Incremental MERGE

Day 7 (overwrite)This HOL (MERGE)
Rows reprocessed per runAll ~377KOnly what changed
Cost at current scaleCheap — fine for training scaleMarginal, but compounds as the table grows
ComplexitySimpler — one join, one writeRequires tracking LAST_PROCESSED_VERSION + CDF

Both are valid choices — MERGE isn't automatically "better." Pick based on table size and how expensive a full rebuild actually is.
