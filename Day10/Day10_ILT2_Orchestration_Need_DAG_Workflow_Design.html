2. DAG Concepts — Nodes, Edges, and Why Cycles Are Invalid

TermMeaningGlobalMart example
NodeOne unit of work — a task"Ingest gbmart.bronze.orders"
EdgeA directed dependency — "B cannot start until A finishes"bronze_orders → silver_orders
DirectedEdges have a direction — order mattersNever the reverse: Silver can't run before Bronze
AcyclicNo path ever loops back to where it startedSee below
Why cycles are invalid: if task_a depends on task_b, and task_b depends on task_a, neither can ever start — each is waiting on the other to go first. Not a performance problem — a logical impossibility. A scheduler must prove a graph has no cycle before it can compute any run order at all; that proof is exactly what topological sort does (Section 5), and exactly why it raises an error instead of hanging forever when a cycle exists (Section 6).

Fan-out Independent Work, Free to Run in Parallel

Fan-out is any point in the DAG where multiple tasks become runnable at the same time because none of them depends on any of the others.

GlobalMart's real fan-out: the CDC-driven tasks (bronze_orders, bronze_order_items) and the five Autoloader-driven tasks (bronze_customers, bronze_products, bronze_addresses, bronze_payments, bronze_payment_methods) share zero dependencies on each other. All seven can start at the same moment, with no coordination required between them.

Fan-in A Task That Has to Wait

Fan-in, loosely, is any point where a task cannot start until an upstream task finishes — even a single dependency is a small fan-in gate in that sense. The stricter, more consequential case is a task with multiple upstream dependencies at once.

GlobalMart's clearest example: gold_fact_sales waits on six upstream tasks simultaneously — five Silver tables (order_items, orders, products, address, payments) plus gold_dim_date. Miss, delay, or fail any one of those six, and fact_sales cannot start.
A design choice, not a law. This session gives every dimension a narrow, single-parent dependency — its own Silver table, nothing else. Plenty of real orchestration jobs instead make every Gold task depend on the entire Silver layer finishing first — coarser and safer against half-finished Silver runs, at the cost of avoidable waiting (dim_payment_method would sit idle waiting on silver_orders, even though it never reads that table). fact_sales already shows the narrower, surgical style for real — see Discussion Question 2 in the matching notebook.

3. Workflow Design — How Databricks Jobs Model a DAG

A Databricks Job (the UI now calls this surface "Workflows") is, underneath the drag-and-drop screen, just a JSON document describing a DAG: a name, a list of tasks, and the compute those tasks run on.

FieldWhat it holdsGlobalMart example
task_keyA short, unique name for this task within the job"silver_orders"
depends_onWhich upstream task_key(s) must succeed first["bronze_orders"]
notebook_task.notebook_pathWorkspace path of the notebook this task runs/Repos/globalmart-prod/silver/build_silver_orders
pipeline_task.pipeline_idUsed instead of notebook_task when the task is really a Lakeflow/DLT pipeline runGlobalMart's real bronze_orders task — driven by orders_data_ingestion_cdc, not a plain notebook

A task can also be a sql_task, a dbt_task, a python_wheel_task, and others — the shape of the DAG itself never changes: every task type still carries a task_key and a depends_on list.

job = {
  "name": "...",
  "tasks": [ {task}, {task}, {task}, ... ],  # every node in the DAG
  "job_clusters": [ ... ],  # shared compute definitions
  "schedule": { "quartz_cron_expression": "...", "timezone_id": "..." }
}

5. Topological Sort — a Real Algorithm, Run For Real

Kahn's algorithm, in plain Python: repeatedly collect every task whose dependencies are all already satisfied, treat that whole group as one parallel "wave," remove them, and repeat. If tasks remain but none of them ever becomes free, the graph has a cycle (Section 6).

Postgres CDC (2 tables) + ADLS Autoloader (5 tables)
                │
                ▼
        Wave 0 -- 7 Bronze tables  (fan-out)
                ▼
        Wave 1 -- 7 Silver tables  (fan-out)
                ▼
        Wave 2 -- 6 Gold dimensions  (fan-out)
                ▼
        Wave 3 -- gold_fact_sales  (fan-in of 6)
# this is the actual, verified output of topological_sort(globalmart_tasks)
WaveTasksCount
0All 7 Bronze tasks7 (fan-out)
1All 7 Silver tasks7 (fan-out)
26 Gold dimensions6 (fan-out)

flat_order, waves = topological_sort(globalmart_tasks)

6. Why DAGs, Not Arbitrary Graphs — a Real Error, on Purpose

The matching notebook wires three real task names into a deliberate cycle: bronze_orders → silver_orders → gold_dim_orders → bronze_orders, then calls topological_sort() on it.

try:
  topological_sort(broken_tasks)
except ValueError as e:
  print(f"ValueError: {e}")
  # -> Cycle detected -- these tasks can never become ready...

Caught cleanly and printed clearly — exactly what a real scheduler should do instead of hanging forever waiting for a task that can never become ready. This is the notebook's proof, with real executing code, of why DAGs (not arbitrary graphs) are the structure every orchestrator requires.
