Part 1

Cost Drivers in Databricks

Before you can be cost-aware, you need to know what actually generates the bill. Three drivers exist — and they are not equally sized.

What Actually Drives the Bill

Think of a running cluster like a taxi meter that keeps ticking whether the taxi is moving or just parked at the curb. Two meters run at the same time for every minute a cluster is up, whether or not it's doing useful work: Databricks' own usage-based DBU fee, and Azure's cloud VM cost for the underlying driver + worker machines.

This is the single biggest lever in this whole session. A cluster sitting idle between two meetings costs exactly the same, minute for minute, as a cluster running a real job.

DriverIn short
1. Cluster uptimeDBU + cloud VM cost, billed every minute the cluster is up
2. Job vs. all-purpose clustersJob clusters auto-terminate; all-purpose can be left running
3. Photon & ServerlessOften less wall-clock time, or no idle time billed at all
4. StorageReal cost, but genuinely small next to compute

Job Clusters vs. All-Purpose Clusters

All-Purpose / Interactive ClusterJob Cluster
CreatedManually, or attached to for notebook workAutomatically, per job run
LifetimeStays up until manually stopped or idle-auto-terminatedTerminates automatically the instant the job finishes
Best forExploration, development, ad-hoc analysis, teachingScheduled / production pipelines
Typical riskLeft running overnight or over a weekend by accidentEssentially none — it cannot outlive the job

Photon often finishes work faster on the same cluster, which can reduce total cost even at a higher per-DBU rate. Serverless compute removes cluster startup/idle time from the equation entirely — you pay for query execution, not for a cluster waiting for the next command.

Part 2

Cost Awareness Practices

Knowing the drivers is step one. Four concrete practices turn "we should be more cost-aware" into things you actually configure.

Four Concrete Practices

  1. Set autotermination_minutes on every interactive cluster — there's rarely a good reason to leave it at 0 (never) outside a short, actively-supervised session
  2. Right-size the cluster to the data — a 32-core cluster reading a 10 GB table isn't "extra safe," it's idle capacity you're paying for
  3. Use spot (preemptible) instances for non-critical batch work — a fraction of on-demand price, with automatic on-demand fallback
  4. Use job clusters, not all-purpose clusters, for scheduled/production pipelines — the single highest-leverage habit in this session

Wasteful vs. Cost-Aware Configs, as Plain Data

These are ordinary Python dictionaries, built and printed for comparison only. Nothing here calls a cluster API — no cluster is created, started, resized, or edited by running this cell.

# WASTEFUL -- all-purpose, left running
wasteful_config = {
    "num_workers": 8,
    "node_type_id": "Standard_DS5_v2",   # oversized for a 10GB table
    "autotermination_minutes": 0,        # 0 = NEVER auto-terminates, not "fast"
}

# COST-AWARE -- job cluster for a scheduled production pipeline
cost_aware_job_config = {
    "num_workers": 4,
    "node_type_id": "Standard_DS4_v2",
    "azure_attributes": {"availability": "SPOT_WITH_FALLBACK_AZURE"},
    # no autotermination_minutes key needed -- ends when the job ends
}

Part 3

Environment Strategy (dev/test/prod)

Every notebook since Day 2 has pointed at one real, shared catalog: gbmart. Right for a training cohort — not how a real production team would run it.

Three Layers of Separation, Not Just One

LayerWhy it matters
Separate catalogs (or catalog + schema) per environmentA bad DROP TABLE or broken MERGE in dev cannot touch a byte of prod — it isn't pointed at prod's catalog at all
Separate external locations / storage credentials per environmentEven if dev code referenced a prod path by mistake, the dev credential has no grant on prod's ADLS container — it fails on a permissions error, not a deleted file
A promotion workflow, not hand-editingCode moves dev → test → prod through Git branches and CI, never by typing directly into the prod notebook

Some teams use a single catalog with environment-tagged schemas instead of three catalogs when catalog-per-environment isn't practical. Either is a legitimate choice — what matters is dev and prod are never the same namespace.

The one catalog that IS real and live all course is gbmart — the prod-like environment. Everything since Day 2 has written directly to it. That's completely fine for a training cohort; a real team inserts dev and test catalogs between a developer's laptop and this one.

Part 4

Promotion Workflow

The rule: prod is only ever changed by a promoted, reviewed change — never by opening a prod notebook and editing it live.

Code Moves, Prod Doesn't Get Hand-Edited

dev branch (Databricks Repos)
  edit + test against gbmart_dev
        |
        v
Pull Request -> CI runs lint / unit tests
        |
        v
Merge to main -> Deploy to TEST
        |         (smoke test vs gbmart_test)
        v
Promote to PROD -> same reviewed code
                   now points at gbmart,
                   deployed by CI/CD

Common failure mode this prevents: someone fixes an urgent bug directly in the prod notebook to "save time." The fix works, but it never gets backported into the dev/Git version — so the next legitimate deployment silently reverts it. Promotion-only changes make this structurally impossible.

Wrap-Up

Key Takeaways

💰 Cost

  • Cluster uptime is the dominant cost driver — DBU + VM cost accrue every minute, working or not
  • Job clusters beat all-purpose for anything scheduled

🗂️ Environment

  • Separation needs separate catalogs AND separate credentials, not just a schema name
  • gbmart is this course's real prod-like environment

🔁 Promotion

  • Prod changes only through Git + CI, never a hand-edit
  • Databricks Repos is what makes promotion possible at all
