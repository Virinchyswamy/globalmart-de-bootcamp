Part 1 Cost Drivers in Databricks

Three drivers generate the bill on Azure Databricks — and they are not equally sized for most data engineering workloads.

1. Cluster uptime — DBU + cloud VM costTwo meters run every minute a cluster is up, working or not: Databricks' own DBU fee (rate varies by compute type) plus Azure's underlying VM cost for the driver + worker nodes. This is the single biggest lever in this session.
2. Job clusters vs. all-purpose clustersJob clusters are created per run and auto-terminate the instant the job ends. All-purpose (interactive) clusters stay up until manually stopped or idle-auto-terminated — that gap is where accidental cost lives.
3. Photon & ServerlessPhoton often finishes work faster at a higher per-DBU rate — less wall-clock time can mean lower total cost. Serverless (SQL warehouses, serverless jobs) removes cluster startup/idle time from the equation entirely.
4. Storage — real, but smallADLS storage bills per GB/month plus transactions, and is genuinely cheap next to compute. For almost every DE workload, compute dominates the bill — this session is entirely about compute for that reason.

Part 2 Cost Awareness Practices

1.Set autotermination_minutes on every interactive cluster — there's rarely a good reason to leave it at 0 (never)
2.Right-size the cluster to the data — a 32-core cluster reading a 10 GB table is idle capacity you're paying for, not "extra safe"
3.Use spot/preemptible instances for non-critical batch jobs — a fraction of on-demand price, with automatic on-demand fallback
4.Use job clusters — not all-purpose clusters — for scheduled/production pipelines, because they terminate automatically

Wasteful vs. cost-aware configs, as plain data

These are ordinary Python dicts, built and printed for comparison — nothing here calls a cluster API or creates, starts, resizes, or edits any real cluster.

# WASTEFUL -- all-purpose, left running
wasteful_config = {
    "num_workers": 8,
    "node_type_id": "Standard_DS5_v2",  # oversized for a 10GB table
    "autotermination_minutes": 0,  # 0 = NEVER auto-terminates, not "fast"
}
# COST-AWARE -- right-sized interactive cluster for dev work
cost_aware_interactive_config = {
    "num_workers": 2,
    "node_type_id": "Standard_DS3_v2",
    "autotermination_minutes": 30,
    "azure_attributes": {"availability": "SPOT_WITH_FALLBACK_AZURE"}
}

# COST-AWARE -- job cluster for a scheduled production pipeline
cost_aware_job_config = {
    "num_workers": 4,
    "node_type_id": "Standard_DS4_v2",
    # no autotermination_minutes key needed -- terminates automatically when the job ends
}

Part 3 Environment Strategy (dev/test/prod)

Every notebook run since Day 2 has pointed at one real, shared Unity Catalog catalog: gbmart — schemas bronze/silver/gold, external location gbmart-ext-loc, storage credential ecomprojectscredentials. That's the right call for a training cohort — everyone needs to see the same real data. A production team would not do this.

EnvironmentCatalogExternal LocationStorage CredentialPurpose
Devgbmart_devgbmart-dev-ext-locecomprojectscredentials_devIndividual development, safe to break
Testgbmart_testgbmart-test-ext-locecomprojectscredentials_testIntegration / smoke testing before promotion
Prodgbmartgbmart-ext-locecomprojectscredentialsReal GlobalMart data — this course's environment, all along
Why three layers, not just a different schema name: separate catalogs mean a bad DROP TABLE or a broken MERGE in dev cannot touch a byte of prod data — it isn't pointed at prod's catalog at all. Separate external locations/storage credentials mean that even if dev code referenced a prod path by mistake, the dev credential has no grant on prod's ADLS container — the mistake fails on a permissions error, not a deleted file. Some teams use a single catalog with environment-tagged schemas instead (e.g. gbmart.dev_bronze) when catalog-per-environment isn't practical — either is legitimate; what matters is dev and prod are never the same namespace.

Part 4 Promotion Workflow — Code Moves, Prod Doesn't Get Hand-Edited

The rule: prod is only ever changed by a promoted, reviewed change — never by opening a prod notebook and editing it live.

dev branch (Databricks Repos) — edit + test against gbmart_dev
    ↓
Pull Request → CI runs lint / unit tests, maybe a dry run against gbmart_test
    ↓
Merge to main
    ↓
Deploy to TEST → smoke test against gbmart_test + its own external location
    ↓
Promote to PROD → same reviewed code now points at gbmart — deployed by CI/CD
not by a person typing into the prod notebook
Common failure mode this prevents: someone fixes an urgent bug directly in the prod notebook to "save time." The fix works, but it never gets backported into the dev/Git version — so the next legitimate deployment silently reverts it. Promotion-only changes make this structurally impossible.

Key Takeaways

✓Cluster uptime is the dominant Databricks cost driver for most DE workloads — DBU + cloud VM cost accrue every minute a cluster runs, working or not
✓Job clusters beat all-purpose clusters for anything scheduled — they cannot be left running by accident
✓autotermination_minutes, right-sizing, and spot instances are configurable habits, not vague advice
✓Environment separation needs separate catalogs AND separate external locations/credentials, not just a different schema name
✓Prod changes only through promotion — Git branches + Databricks Repos + CI, never a hand-edit
✓gbmart is this course's real prod-like environment — right for training, not how a real team would run production traffic
