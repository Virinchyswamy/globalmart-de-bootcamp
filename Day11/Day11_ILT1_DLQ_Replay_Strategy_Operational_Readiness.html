Part 1What a DLQ Is, and Why

Every pipeline eventually meets a row it cannot process: malformed JSON from an API, a schema mismatch after an upstream change, a business-rule violation, a null in a field a downstream step assumes is always populated. Three ways to handle that row:

ApproachWhat happensWhy it's a problem
Crash the batchOne bad row raises an exception; the whole job failsEvery other good row in the batch is blocked too
Silently drop itThe bad row is filtered and never written anywhereDisappears with no record it ever existed
Route it to a DLQWritten as-is to a separate table, tagged with why and whenGood rows keep flowing; the bad row is inspectable and replayable

A Dead-Letter Queue (DLQ) is that third option — a Delta table that exists purely to catch anything that fails processing, for any reason, anywhere in the pipeline. It's called a "queue" because the intent is to drain it: every row that lands there is expected to eventually be replayed or explicitly written off, not to live there forever.

DLQ vs. Day 5's Quarantine Table — Same Mechanism, Different Scope

Day 5 built gbmart.silver.customers_quarantine — structurally identical to a DLQ. What differs is scope:

Day 5's QuarantineThis Session's DLQ

Framing"Is this row valid data?" — a DQ question"Did this row survive processing?" — an operational question
Where it plugs inOne Bronze → Silver transformation, onceAny stage — ingestion, transform, Gold aggregation, an API call
What happens nextMostly stays put for human reviewDesigned to be replayed — draining it is the point
Quarantine is a DLQ used for exactly one purpose (a DQ scan). A DLQ is the general pattern quarantine is one instance of — this session builds the general version, plus the piece Day 5 didn't need: a working replay function.

Part 2Replay Strategy: Getting Rows Back Out Safely

A DLQ that never drains is just an expensive way to lose data slowly. The dangerous part is how you get rows back out: if replay re-runs the transformation and blindly appends the result, running it twice (or retrying after a partial failure) writes the row twice — and a fact_sales-style aggregate downstream quietly becomes wrong.

StepWhat it doesWhy it's safe to re-run
1Read all rows currently in the DLQ tableReading never has side effects
2Apply the fix (default value, corrected business rule)Deterministic — same input, same output, every time
3MERGE the fixed rows into the processed table by natural keyRe-running the same MERGE with the same key can't create a second row
4Remove the replayed rows from the DLQ (MERGE ... WHEN MATCHED THEN DELETE)Once gone from the DLQ, a second replay call finds nothing left to do

Step 3 makes replay safe; step 4 makes it idempotent end-to-end — call the replay function once or ten times in a row, same outcome. This is the exact idempotency principle Day 9/Day 10 already taught for incremental loading, just sourced from a DLQ table instead of a change feed.

Not every DLQ row is auto-replayable. Some failures need a human decision first (is this bad data, or a business rule that needs writing?); some can't be fixed at all (no usable key to write back with). A mature replay strategy separates "safe to replay on a schedule" from "needs a human to look at it" — don't build a replay function that blindly "fixes" everything just because it's sitting in the DLQ.

Part 3Runbooks: Turning Tribal Knowledge Into a Checklist

A runbook is a written, step-by-step "if this breaks, do this" document for a specific pipeline failure — so whoever is on call, not just the person who built the pipeline, can follow it under pressure. Below is a real one for GlobalMart's actual CDC pipeline, orders_data_ingestion_cdc (Lakeflow Connect, query-based on updated_at — Day 2).

Runbook: orders_data_ingestion_cdc failed / didn't run overnight
Symptom: gbmart.bronze.orders/order_items row counts haven't moved, or the pipeline shows a failed/skipped run.
1. Detect Pipeline run history in the Jobs/Pipelines UI; Day 9 HOL 2-style verification (row counts, MAX(updated_at), DESCRIBE HISTORY)
2. Triage Credential/auth expiry (ecomprojectscredentials) → source connectivity → schema drift (Day 3) → cursor (updated_at) nulls/clock-skew → warehouse/cluster startup issue — cheapest checks first
3. Fix Apply the fix for whichever root cause step 2 found; manually trigger a re-run from the Databricks UI (a real click in the workspace — not automated by this notebook)
4. Confirm Re-run step 1's checks; this session's SLA check against the real last-write timestamp should now show MET; check whether any rows need replay as a side effect
5. Close out Log the incident (what broke, root cause, fix, downtime); if it's a new failure mode, add it to step 2 — a runbook that doesn't grow after every incident stops being useful
The pattern generalizes. Every pipeline in this course — Autoloader sources, Silver MERGE jobs, a Gold refresh — deserves the same shape: symptom, detect, triage (cheapest checks first), fix, confirm, close out. Write the shell once; fill in pipeline-specific checks per pipeline.

Part 4SLAs: Defining and Measuring "Fresh Enough"

A pipeline SLA here means one thing: how stale is too stale? GlobalMart's two ingestion patterns justify two different freshness targets:

SourceIngestion patternA reasonable freshness SLAHow you'd measure it
orders / order_itemsQuery-based CDC on updated_at (orders_data_ingestion_cdc)Within 2 hourscurrent_timestamp() vs. MAX(updated_at), or the pipeline's own last-run time
customers, products, addresses, payments, payment_methodsADLS Autoloader — file-drop batch, roughly dailyWithin 24 hoursDESCRIBE HISTORY — timestamp of the most recent Bronze commit
Freshness SLA ≠ "did the pipeline succeed." A pipeline can exit green with nothing to fail on — because no new file arrived at all — and still be a day stale. Measuring freshness directly (as the function below does) catches that; watching only for job failures does not.
The SLA check built in this session is print/log only — no email, Slack webhook, or PagerDuty call. Wiring a real alert on top is an orchestration-layer concern (Databricks Workflows' own notification settings) — out of scope here, and exactly the "don't trigger real systems" boundary this course holds everywhere.

Key Takeaways

→A DLQ is the general-purpose safety net for "this row failed processing" — independent of why. Day 5's quarantine is one specific instance of this same mechanism.
→Route, don't crash or drop. Capture the row, the reason, and a timestamp — inspectable and recoverable beats invisible.
→Replay must be idempotent — a key-based MERGE plus removing the row from the DLQ is what makes "replay twice" match "replay once," the same idempotency principle from Day 9/Day 10.
→Not every DLQ row is auto-replayable — some need a human decision first.
→SLAs measure freshness, not success — a pipeline can exit cleanly and still be stale.
→Runbooks turn tribal on-call knowledge into a checklist anyone can follow under pressure — write them before the first incident, grow them after every real one.
