The Scenario

Business Process

GlobalMart's warehouse operations team wants a Gold-layer star schema for inventory levels. Every night at midnight, an automated job counts how many units of every product currently sit in every warehouse, then writes one snapshot to Silver. GlobalMart runs 4 warehouses — Mumbai, Delhi, Bengaluru, Hyderabad. Each nightly count carries a count_batch_id: an identifier for that night's count run, generated by the warehouse system, with no other attributes attached to it anywhere. Products are the same <your-catalog>.silver.products SCD2 table you already know from this morning. Warehouses have their own attributes (name, city, capacity_units), and — unlike products — GlobalMart has decided not to track warehouse history. If a warehouse's capacity changes, the old value is simply overwritten, no questions asked. The business question that started all of this, first raised by warehouse ops lead P V Ganadeep in a stand-up nobody wanted to be awake for: "How many units of Product X do we have on hand, across all warehouses, right now — and how has that changed over the last quarter?"

Task 1 — Declare the Grain

1In one sentence: what's the grain of this new fact table (we'll call it fact_inventory_snapshot)? This one sentence decides everything downstream, so take your time.

Reveal model answer

One row per product, per warehouse, per nightly count.

Notice what this rules out. "One row per warehouse" or "one row per product" alone would each throw away real information — you'd lose either the per-product breakdown or the per-warehouse breakdown. "One row per count" is just as broken: it would collapse every product and warehouse into a single number per night, which can't answer "how many units of Product X," the actual business question.

Just as important: this is a fundamentally different grain type than fact_sales. fact_sales is a transaction fact table — a row exists because something happened (a purchase). fact_inventory_snapshot is a periodic snapshot fact table — a row exists on a schedule (every midnight), whether or not anything happened, because the business needs to know the state of the world at that moment, not just the events that changed it.

Same as dim_address from this morning's fact_sales build: a fresh key generated in Gold, and no history-tracking columns — the plain, simple pattern, not the exception. If you answered Type 2 out of habit because some dimension in this course is Type 2, that's the exact trap this task was built to catch — reuse-vs-generate and Type-1-vs-Type-2 are independent decisions, made per dimension based on whether the business actually needs history, never by pattern-matching to a different dimension.

Task 3 — Classify the Measures

3fact_inventory_snapshot has one measure: units_on_hand. Classify it — additive, semi-additive, or non-additive — and explain what you can and can't safely SUM().

Reveal model answer

Semi-additive

Safe: SUM(units_on_hand) across product or across warehouse — "total units of Product X across all 4 warehouses tonight" and "total units of everything in the Mumbai warehouse tonight" are both meaningful, correct numbers.

Unsafe: SUM(units_on_hand) across date. Ask Bysani Karthik, who runs the nightly count job — adding "500 units on hand on Monday" to "480 units on hand on Tuesday" does not produce a meaningful "980." It's largely the same physical stock being counted twice. The correct way to answer "how has stock changed over the quarter" is to look at the period-end value or an average across dates, never a running sum.

This is exactly the semi-additive case this morning's ILT 3 said fact_sales does not have — inventory-on-hand was the textbook example used there, and this capstone is where you actually build the fact table it describes. The tell is always the same: if the fact table's grain includes a snapshot-in-time dimension (like a nightly count), any "current state" measure — a balance, a level, a count-on-hand — is semi-additive with respect to that time dimension.

Task 4 — Spot the Degenerate Dimension

4Is there a degenerate dimension candidate in this scenario? If so, what is it, and why does it qualify?

Reveal model answer

count_batch_id. It sits directly on fact_inventory_snapshot as a plain column, with no dimension table built for it at all — matching the textbook definition exactly: an identifier stored on the fact table with no descriptive attributes beyond the ID itself, straight from ILT 3's opening definition.

Notice this is actually a cleaner case than Order_ID was in this morning's ILT 3. GlobalMart built a real dim_orders table anyway, which is what made Order_ID "degenerate from one point of view, a real dimension from another." count_batch_id has no such twist — nobody builds a dim_count_batch table, because there's genuinely nothing to describe about a count batch beyond its own ID. It exists purely so someone like Saket Ranjan, digging into why last night's Hyderabad numbers look off, can group or filter "everything counted in last night's run" and drill straight to the source count job — the same job Order_ID does for fact_sales, just without a second table competing for the label.
