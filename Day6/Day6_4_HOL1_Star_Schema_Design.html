Phase B

dim_date

Generated — no source table.

Why dim_date Is Different

No source table

Every other dimension comes from a Silver table. dim_date doesn't — no source system ships a "list of all dates."

Sized to the data, not an arbitrary range: pull the real bounds straight from silver.orders (earliest order_date, latest actual_delivery_date) and generate exactly that range.

Generate the Date Spine

Hands-On · Phase B
# ─── Generate the date spine, sized to the data — not an arbitrary range ─────
# Pull real bounds from silver.orders so the spine covers every date fact_sales
# will ever need, with no wasted rows either side.
date_bounds = spark.table(f"{SILVER}.orders").select(
    spark_min("order_date").alias("min_date"),
    spark_max("actual_delivery_date").alias("max_date")
).collect()[0]

min_date, max_date = date_bounds["min_date"], date_bounds["max_date"]

date_spine_df = spark.sql(f'''
    SELECT explode(sequence(to_date('{min_date}'), to_date('{max_date}'), interval 1 day)) AS full_date
''')

Derive Calendar Attributes + date_key

Hands-On · Phase B

date_key is the one deliberate exception to the "reuse or hash the natural key" convention used everywhere else in this notebook — Kimball's long-standing convention for date dimensions is an integer YYYYMMDD key. Naming matters: the plain calendar column is named date (not full_date) — that's the exact name Day 7's fact_sales build looks up when it joins order_date against this table.

dim_date_df = (
    date_spine_df
    .withColumn("date_key",    date_format(col("full_date"), "yyyyMMdd").cast("int"))
    .withColumn("date",        col("full_date"))
    .withColumn("day_of_week", date_format(col("full_date"), "EEEE"))
    .withColumn("month",       month(col("full_date")))
    .withColumn("quarter",     quarter(col("full_date")))
    .withColumn("year",        year(col("full_date")))
    .withColumn("is_weekend", dayofweek(col("full_date")).isin([1, 7]))
    .select("date_key", "date", "day_of_week", "month", "quarter", "year", "is_weekend")
)

dim_date_df.write.format("delta").mode("overwrite").saveAsTable(f"{GOLD}.dim_date")
Phase C

The Other 5 Dimensions

Two of these five (dim_customer, dim_product) reuse a surrogate key and SCD2 columns Silver already generated. The other three (dim_address, dim_payment_method, dim_orders) get a fresh sha2() key generated here. Order: smallest/simplest first.

C1 — dim_payment_method

silver.payment_methods · key: payment_method_id
dim_payment_method_df = (
    silver_payment_methods
    .select("payment_method_id", "method_name")
    .withColumn("payment_method_sk",
        sha2(col("payment_method_id").cast("string"), 256))
)
dim_payment_method_df.write.format("delta").mode("overwrite")
    .saveAsTable(f"{GOLD}.dim_payment_method")

Sources from the lookup table payment_methods, not the transactional payments table.

C2 — dim_customer

silver.customers · SCD2 · key: customer_id
# customer_sk / is_current / effective_start_date / effective_end_date
# already exist on silver.customers -- SELECT as-is, don't re-hash.
dim_customer_df = (
    silver_customers
    .select(
        "customer_sk", "customer_id", "full_name",
        "email", "phone_number", "is_current",
        "effective_start_date", "effective_end_date"
    )
)
dim_customer_df.write.format("delta").mode("overwrite")
    .saveAsTable(f"{GOLD}.dim_customer")

Regenerating sha2(customer_id) here would silently collapse SCD2 history back to one row per customer — don't.

C5 — dim_orders — the Sixth Dimension

silver.orders · key: order_id
dim_orders_df = (
    silver_orders
    .select("order_id", "customer_id", "order_date",
            "shipping_tier_id", "supplier_id", "order_channel")
    .withColumn("order_sk", sha2(col("order_id").cast("string"), 256))
)
dim_orders_df.write.format("delta").mode("overwrite")
    .saveAsTable(f"{GOLD}.dim_orders")

Heads-up for Day 7: fact_sales carries Order_ID directly as a natural key — it does not join through dim_orders.order_sk. dim_orders still exists as its own Gold table (built here); it's just not the fact table's chosen join path. ILT 3 revisits this under "degenerate dimensions." Similarly, a customer can have more than one address — that many-to-many is resolved in Day 7's fact build via window-function ranking, not a bridge table.

Phase D

Verify All 6 Dimensions

Row Count = Distinct Surrogate-Key Count

Hands-On · Phase D
dimensions = {
    "dim_customer":        "customer_sk",
    "dim_product":         "product_sk",
    "dim_date":            "date_key",
    "dim_address":         "address_sk",
    "dim_payment_method": "payment_method_sk",
    "dim_orders":          "order_sk",
}

for table, sk_col in dimensions.items():
    df = spark.table(f"{GOLD}.{table}")
    print(table, df.count(), df.select(sk_col).distinct().count())

Row count should equal distinct surrogate-key count for every dimension — that's your uniqueness check.
