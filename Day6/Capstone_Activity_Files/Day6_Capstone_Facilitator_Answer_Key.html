2Why Each Design Decision Was Made

Why periodic snapshot, not transaction grain

The business process is "every night at midnight, count every product in every warehouse." A row is produced on a fixed schedule regardless of whether anything sold, moved, or changed — that is the defining signature of a periodic snapshot fact table. A transaction fact table (like this morning's fact_sales) only produces a row when a discrete business event occurs. There is no "event" here to key off of; there is a recurring measurement. Learners should be able to state this distinction, not just recite the grain.

Why dim_warehouse AND dim_product are both Type 1 here

This morning's dim_customer and dim_product were Type 2 because that scenario's stated business requirement was to preserve history (e.g., track a customer's changed email/phone over time, or a product's price change over time). This capstone's stated requirement is the opposite: GlobalMart does not want warehouse history tracked, and no history requirement is stated for products in this scenario either. (Worth noting: this afternoon's own dim_address, in the real fact_sales build, is Type 1 too — the same "fresh key, no history" pattern as dim_warehouse here, because GlobalMart never stated a need to preserve address version history either.) SCD type is never inherited from a dimension's name or from what a different table did earlier the same day — it is decided fresh, per scenario, from the business requirement in front of you. Treat "Type 2 because dim_product was Type 2 this morning" as a red flag, not a correct answer arrived at by luck.

Why every surrogate key here is freshly generated

This morning's Databricks work inherited natural keys from an upstream Silver layer and could choose to reuse or regenerate a surrogate key against that lineage. This capstone has no upstream system at all — it starts directly from raw, messy source files. There is nothing to inherit from, so the "reuse vs. generate" decision that required real thought this morning is not a decision here at all: every surrogate key (warehouse_sk, product_sk, date_key) must be freshly assigned, and it must be assigned after full deduplication and cleaning, never before (assigning keys before cleaning would burn a surrogate key on a row that gets discarded, or worse, produce two different keys for what is really the same warehouse).

Why count_batch_id is a degenerate dimension

count_batch_id (format BATCH-20260601, one per warehouse/product/night) is an identifier that lives on the fact row but has no attributes of its own worth modeling — there is no dim_batch table, and there shouldn't be one. It is carried through as-is, with no surrogate-key lookup. This is a cleaner example than this morning's Order_ID case, because there is no competing table anyone might mistakenly try to build a lookup against — the "is this a degenerate dimension?" test here is unambiguous: no dimension table exists, full stop.

Why units_on_hand is semi-additive, with a concrete failure example

units_on_hand can be safely summed across product (total stock of all products in a warehouse on a given night) or across warehouse (total stock of a product across all warehouses on a given night). It cannot be meaningfully summed across date. For example: take product P and warehouse W, and suppose the nightly counts across June 1–10 are roughly 500 units each night (stock barely moves). Summing units_on_hand for that single product/warehouse across all 10 nights produces ~5,000 — a number that does not represent 5,000 physical units anywhere; it represents the same ~500 physical units counted ten times. The correct aggregation across date is MAX() or the count from the most recent date, never SUM(). ILT3 taught semi-additivity theoretically using inventory-on-hand as the textbook example of a measure fact_sales does not have — this capstone is where learners build the fact table that actually has one, and prove the failure mode themselves in a PivotTable.

3Data Quality Decisions — Full Rationale

Grade the reasoning, not just the final action. A learner can arrive at the right row count by luck or by copying a classmate's approach without understanding why an action was correct. Listen for the reasoning below in the debrief and in any written justification the submission includes.

Warehouses_Raw: WH01 duplicate (47000 vs 50000 capacity)

Correct action: there is genuinely no way to know which value is correct from the data alone — no timestamp, no second source. The instructions tell learners this explicitly and ask them to make a judgment call and document it, not to find "the" answer. Accept either 47000 or 50000 as full credit, as long as exactly one row survives and the learner's note names which value they kept and why (e.g. "kept the higher value, assuming the lower one was a stale figure from before an expansion" is a fine, defensible guess — so is the reverse). What to listen for: did the learner articulate a reason at all, rather than silently deleting one row with no explanation? Not acceptable at any credit level: averaging or splitting the difference (e.g. 48500) — that invents a number that was never true at any point in time, which is a different and worse failure than picking either real observed value.

Warehouses_Raw: City casing ("bengaluru", "HYDERABAD")

Correct action: normalize with PROPER(). What to listen for: this is a low-stakes mechanical fix, but check the learner didn't simply retype the values by hand (which doesn't scale and won't survive a data refresh) versus using a formula-driven fix.

Warehouses_Raw: WH05 blank Region

Correct action: recover "West" from context (the answer key confirms this is a recoverable blank, not an unresolvable one — the value is knowable, just missing in this row). What to listen for: did the learner treat this differently from the blank Warehouse_Code case in the fact data below? A blank in a 5-row dimension table with an obviously-recoverable, single correct value is not the same category of problem as a blank foreign key in a 1742-row fact table pointing at 5 possible warehouses with no way to determine which one.

Products_Raw: 3 exact duplicate rows

Correct action: Remove Duplicates. What to listen for: nothing subtle here — this should be clean and mechanical. If a learner's dim_product ends up with more than 34 rows, this step or the next one was skipped or done incorrectly.

Products_Raw: 2 near-duplicate rows (inconsistent Category casing per Product_ID)

Correct action: keep the properly-cased version, treating both rows as describing the same product. What to listen for: did the learner notice these were not caught by Remove Duplicates (because the rows aren't byte-for-byte identical) and specifically hunt for near-duplicates keyed on Product_ID? A learner who ends up with 35 or 36 rows in dim_product almost always missed this category-casing issue rather than the exact-duplicate issue.

NightlyCounts_Raw: 12 rows with blank Warehouse_Code

Correct action: exclude/quarantine these rows entirely. The key insight to check for: did the learner recognize this as unresolvable — there is no way to determine, from the data available, which of the 5 warehouses a blank-code count belongs to — and therefore exclude it? This is the same referential-integrity discipline taught in the real Silver-layer pipeline this course is grounded in: rows that cannot be matched to a valid dimension key do not get force-fit into the fact table.

Grade this as a three-way distinction, not pass/fail:

  • Full credit: excluded the rows AND can explain why (unresolvable foreign key, not just "it looked messy").
  • Partial credit: excluded the rows but couldn't articulate why beyond "there was a blank."
  • No credit / flag for debrief: attempted to guess or impute a warehouse code (e.g., filled it with the most common warehouse, or WH01 by default). This is the wrong instinct: silently fabricating which warehouse a count belongs to corrupts inventory totals for whichever warehouse gets guessed, and there is no way to detect the error later — the row will look completely legitimate downstream. This is worse than doing nothing.

NightlyCounts_Raw: 10 rows with negative Units_On_Hand

Correct action: exclude. What to listen for: did the learner identify this as physically impossible (you cannot have negative physical inventory — this is a data-entry error, e.g. a sign flip or a miskeyed adjustment) rather than a legitimate value that should be zeroed out or made positive? Flipping the sign to make a negative count positive is not a valid fix — there's no basis for assuming the magnitude is even correct, only that the record is corrupted.

NightlyCounts_Raw: 20 exact duplicate rows

Correct action: Remove Duplicates. What to listen for: straightforward, but confirm the learner ran this before assigning surrogate keys and building the fact table, not after — running it after can still produce the right final count by coincidence but reflects a workflow that would break on a different dataset.

NightlyCounts_Raw: Count_Date mixed across 3 formats

Real Excel date serials, US-slash text (MM/DD/YYYY), and long text ("Month D, YYYY") are all present in the same column. Correct action: normalize every value to a real date before deriving date_key, using logic equivalent to:

=IF(ISNUMBER(x), x, DATEVALUE(x))

What to listen for: did the learner normalize before building the date_key lookup against dim_date? A learner who tries to derive date_key straight from the raw mixed-format column will get VLOOKUP/XLOOKUP misses on whichever rows weren't real Excel date serials, producing blanks or #N/A in the final fact table — this is the most common silent failure in this exercise because the row count can still look plausible while a subset of dates is simply wrong or missing.

4Common Mistakes to Watch For

Numeric symptoms are the fastest way to diagnose what went wrong in a submission without re-deriving the whole workbook.

fact_inventory_snapshot has 1720 rows
Kept the 20 exact-duplicate rows — Remove Duplicates was skipped or applied to the wrong sheet/range.
fact_inventory_snapshot has 1712 rows
Kept the 12 blank-Warehouse_Code rows instead of excluding them (1742 − 20 − 10 = 1712). Check whether these rows were guessed/imputed rather than dropped — see the Section 4 warning above.
fact_inventory_snapshot has 1710 rows
Kept the 10 negative-Units_On_Hand rows (1742 − 20 − 12 = 1710).
fact_inventory_snapshot has some other odd row count, or blank/#N/A values in warehouse_sk, product_sk, or date_key columns
Almost always a Count_Date normalization failure — the three mixed date formats weren't fully converted before the date_key lookup against dim_date ran, so some rows failed to match and produced errors instead of being cleanly included or excluded.
A large, systematic block of #N/A on date_key — roughly a quarter of the fact table, not a handful of stray rows
This is a locale bug, not a lookup bug — verified empirically: it affects ~23% of rows (391 of 1700) if it triggers. The Count_Date slash-format rows were generated as US-style MM/DD/YYYY text (e.g. "06/10/2026" = June 10). DATEVALUE()'s parsing of that string depends on the learner's own Excel regional date setting, not the string's intended format. On a day-first locale (DD/MM/YYYY — common on Excel installs configured for India, i.e. plausible for a meaningful fraction of this cohort), DATEVALUE("06/10/2026") silently returns 6 October instead of June 10 — no error thrown, just a date that then can't find a match in the 10-row dim_date spine (all June 1–10). The learner-facing instructions doc includes an explicit locale spot-check and a locale-proof fallback formula (=DATE(VALUE(RIGHT(Count_Date,4)), VALUE(LEFT(Count_Date,2)), VALUE(MID(Count_Date,4,2)))) for exactly this reason — if a learner hits this and didn't use the fallback, that's a real, non-obvious Excel gotcha, not a conceptual gap in their star-schema design. Don't dock design-understanding points for it; just point them at the fallback formula.
dim_warehouse has 6 rows instead of 5
Didn't catch the WH01 duplicate (47000/50000 capacity) — both rows were kept as if they were two different warehouses.
dim_product has more than 34 rows (35, 36, or higher)
Missed the Category-casing near-duplicates on top of the exact duplicates — Remove Duplicates alone doesn't catch these because the rows aren't byte-identical.
Learner declares SCD Type 2 for dim_warehouse or dim_product "because that's what we did this morning"
This is the #1 conceptual trap this capstone is designed to catch. It reveals pattern-matching against this morning's dimension names instead of reasoning from this scenario's actual stated business requirement (no history tracking wanted). Flag this explicitly in feedback — the mechanical Excel work (extra effective-date/current-flag columns) is usually done competently by learners who make this mistake, which makes it easy to miss if you're only checking column structure and not the underlying justification.
Learner SUMs units_on_hand across all 10 dates in the PivotTable exercise and reports it as "current stock"
This is the direct, hands-on proof-of-concept failure the semi-additive exercise is built to surface. The resulting number (e.g., ~10x a single night's real count) should have been an obvious red flag to the learner if they sanity-checked it against a single night's value — a written explanation that doesn't catch this should not receive credit on the semi-additive line of the rubric even if the PivotTable itself is mechanically built correctly.

6Suggested Debrief Talking Points

  • Ask the room: who defaulted to SCD Type 2 for a dimension out of habit rather than checking the business requirement stated in this scenario? What does that tell you about the difference between memorizing a pattern and applying a principle?
  • Compare grains directly: put fact_sales's grain (transaction: one row per order line) next to fact_inventory_snapshot's grain (periodic snapshot: one row per product/warehouse/night) on the board. What's the practical tell that distinguishes the two before you've written a single formula — does a row exist because something happened, or because a clock ticked?
  • No upstream Silver layer this time: this exercise had no pre-built system with an existing surrogate key to reuse — every key was generated fresh. Why did that make dim_warehouse/dim_product's reuse-vs-generate decision trivial here, when it required real thought this morning working from Silver-layer data?
  • Same tool, different mechanism, same concept: this morning used sha2(natural_key, 256) in Databricks; this afternoon used a plain sequential integer in Excel. Ask learners to state, in their own words, what stayed constant across both (an ID the table owns, meaningless outside it, a stable join target) versus what changed (the hashing mechanism) — and why the tool changing didn't change the underlying idea.
  • The math-check number: 1742 − 20 − 12 − 10 = 1700, and 1700 = 5 × 34 × 10 exactly. Ask who checked their final row count against this multiplication independently, versus who just trusted whatever number Excel produced. What's the value of having an independent way to verify a row count instead of only trusting the pipeline that produced it?
  • The blank-Warehouse_Code decision: ask who was tempted to guess a warehouse for those 12 rows rather than exclude them, and why that instinct is dangerous specifically in an inventory context — a wrongly-imputed warehouse silently corrupts that warehouse's stock totals with no downstream signal that anything is wrong. Contrast with a context where a wrong guess might be more visibly self-correcting.
