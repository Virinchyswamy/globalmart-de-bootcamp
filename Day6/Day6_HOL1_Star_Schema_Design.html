fact_sales (built Day 7) sits in the middle: one row per order line item, holding Quantity_purchased, Actual_price, Discounted_price, Sales_amount, plus a natural-key reference to each of the 6 points of this star. Today we build the 6 points. The center gets built next.

Phase B dim_date (generated — no source table)

Every other dimension comes from a Silver table. dim_date doesn't — no source system ships a "list of all dates." Generate it once, sized to the data, not an arbitrary range: pull the real bounds straight from silver.orders (earliest order_date, latest actual_delivery_date) and generate exactly that range.

# ─── Generate the date spine, sized to the data — not an arbitrary range ─────
# Pull real bounds from silver.orders so the spine covers every date fact_sales
# will ever need, with no wasted rows either side.
date_bounds = spark.table(f"{SILVER}.orders").select(
    spark_min("order_date").alias("min_date"),
    spark_max("actual_delivery_date").alias("max_date")
).collect()[0]

min_date, max_date = date_bounds["min_date"], date_bounds["max_date"]

date_spine_df = spark.sql(f'''
    SELECT explode(sequence(to_date('{min_date}'), to_date('{max_date}'), interval 1 day)) AS full_date
''')

Derive Calendar Attributes + date_key

date_key is the one deliberate exception to the "reuse or hash the natural key" convention used everywhere else in this notebook — Kimball's long-standing convention for date dimensions is an integer YYYYMMDD key: human-readable and it sorts correctly in plain numeric order, unlike a hash. Naming matters: the plain calendar column is named date (not full_date) — that's the exact name Day 7's fact_sales build looks up when it joins order_date against this table.

dim_date_df = (
    date_spine_df
    .withColumn("date_key",    date_format(col("full_date"), "yyyyMMdd").cast("int"))
    .withColumn("date",        col("full_date"))
    .withColumn("day_of_week", date_format(col("full_date"), "EEEE"))
    .withColumn("month",       month(col("full_date")))
    .withColumn("quarter",    quarter(col("full_date")))
    .withColumn("year",       year(col("full_date")))
    .withColumn("is_weekend", dayofweek(col("full_date")).isin([1, 7]))
    .select("date_key", "date", "day_of_week", "month", "quarter", "year", "is_weekend")
)

dim_date_df.write.format("delta").mode("overwrite").saveAsTable(f"{GOLD}.dim_date")

Phase C The Other 5 Dimensions

For each: inspect the real Silver schema first, then build it. Two of these five (dim_customer, dim_product) reuse a surrogate key and SCD2 tracking columns Silver already generated on Day 5 — Gold's job is to republish Silver's already-versioned rows, not regenerate anything. The other three (dim_address, dim_payment_method, dim_orders) get a fresh sha2()-based surrogate key generated here in Gold. Order: smallest/simplest first, then the bigger ones.

Inspect-First Pattern (repeat for every dimension)

C1 — dim_payment_method (silver.payment_methods, key: payment_method_id)

dim_payment_method_df = (
    silver_payment_methods
    .select("payment_method_id", "method_name")
    .withColumn("payment_method_sk",
        sha2(col("payment_method_id").cast("string"), 256))
)
dim_payment_method_df.write.format("delta").mode("overwrite")
    .saveAsTable(f"{GOLD}.dim_payment_method")

⚠️ Sources from the lookup table payment_methods, not the transactional payments table.

C2 — dim_customer (silver.customers, SCD2 — key: customer_id)

# customer_sk / is_current / effective_start_date / effective_end_date
# already exist on silver.customers -- SELECT as-is, don't re-hash.
dim_customer_df = (
    silver_customers
    .select(
        "customer_sk", "customer_id", "full_name",
        "email", "phone_number", "is_current",
        "effective_start_date", "effective_end_date"
    )
)
dim_customer_df.write.format("delta").mode("overwrite")
    .saveAsTable(f"{GOLD}.dim_customer")

Regenerating sha2(customer_id) here would silently collapse SCD2 history back to one row per customer — don't.

C3 — dim_product (silver.products, SCD2 — key: product_id)

dim_product_df = (
    silver_products
    .select(
        "product_sk", "product_id", "product_name",
        "category", "sub_category", "discounted_price_inr",
        "is_current", "effective_start_date", "effective_end_date"
    )
)
dim_product_df.write.format("delta").mode("overwrite")
    .saveAsTable(f"{GOLD}.dim_product")

Conformed dimension: a future fact_returns would reuse these exact product_sk values.

C4 — dim_address (silver.address, key: address_id)

dim_address_df = (
    silver_address
    .select("address_id", "customer_id", "city",
        "state", "pincode", "address_type")
    .withColumn("address_sk", sha2(col("address_id").cast("string"), 256))
)
dim_address_df.write.format("delta").mode("overwrite")
    .saveAsTable(f"{GOLD}.dim_address")

C5 — dim_orders (silver.orders, key: order_id) — the sixth dimension

dim_orders_df = (
    silver_orders
    .select("order_id", "customer_id", "order_date",
        "shipping_tier_id", "supplier_id", "order_channel")
    .withColumn("order_sk", sha2(col("order_id").cast("string"), 256))
)
dim_orders_df.write.format("delta").mode("overwrite")
    .saveAsTable(f"{GOLD}.dim_orders")
⚠️ Heads-up for Day 7: fact_sales carries Order_ID directly as a natural key — it does not join through dim_orders.order_sk. dim_orders still exists as its own Gold table (built here); it's just not the fact table's chosen join path. ILT 3 revisits this under "degenerate dimensions." Similarly, a customer can have more than one address — that many-to-many is resolved in Day 7's fact build via window-function ranking, not a bridge table.
