Grain Definition

Declaring the Grain

What Is Grain?

Ask this before you touch a single column

Before you build any table, answer one question first: what does a single row actually mean?

If you can't say that in one plain sentence, you're not ready to add a single column yet — you'll end up guessing, and different columns will quietly disagree about what a "row" even is.

That answer has a name

That one-sentence answer is called the grain. Every column you add later has to make sense at that grain — true for exactly one row, no more, no less.

GlobalMart's answer: one row in fact_sales = one product bought within one order. In table terms, one row per (order_id, product_id) combination in order_items.

A Worked Example

Say Bysani Karthik places one order and drops two different products in his cart. Here's how that single order actually shows up in order_items:

Order OR-094494 in order_items:
  order_item_id = OR-J-283399   | product_id = PRD-00410 | quantity = 1
  order_item_id = OR-KSC-283400 | product_id = PRD-00107 | quantity = 5

→ that's exactly 2 rows in fact_sales — one per product. Actual_price/
  Discounted_price are looked up from silver.products; Sales_amount gets
  computed during Day 7's fact build. Each row keeps its own correct
  revenue number — nothing about Bysani's order gets blended together.

What If We'd Picked "One Row Per Order" Instead?

Suppose someone had declared the grain as "one row per order," not "one row per line item." Here's what breaks, using Bysani's same order:

What has to happenWhy that's a problem
Order OR-094494's 2 products have to squeeze into 1 rowWe lose each product's own Quantity_purchased/Sales_amount — we can no longer answer "which product actually sold best?"
product_id would need to hold a list, in one cellEvery dimension expects one clean ID per fact row. A list breaks that everywhere downstream — joins, filters, BI tools

The problem isn't just "less detail" — it's detail you can't get back. Once Silver rows are squashed into one coarser fact row, the per-product numbers are gone. Getting them back means re-running the pipeline from Silver, not a quick fix in Gold. That's why grain gets decided first, before a single column is designed — picking it wrong is expensive to undo.

Could the Grain Be Finer?

Not for GlobalMart's current sources

order_items doesn't track shipment- or unit-level splits. If it ever did, that would justify a new, finer-grained fact table (e.g. fact_shipments), not a change to fact_sales.

A return/refund event is a genuinely different business process — a future fact_returns, at its own grain, not a variant of this one.

A simple test for any column you're tempted to add: does this value stay true for exactly one line item — or could it change depending on which line you're looking at within the same order? If it's the second one, it doesn't belong as a stored column at that grain.

Take Bysani's order again. Quantity_purchased passes the test — each of his two lines has its own correct value. "Total items in this order" fails — that number is only true for both lines together, not for one line by itself. So it doesn't get stored as a column; it gets computed on demand instead, by summing the lines when someone asks.

Consequence for the 4 Measures

Because we picked "one row per line item," two of the four measures behave nicely and two don't — and it matters to know which is which before you build reports on top of them.

Quantity_purchased and Sales_amount are counts and totals — add them up across any number of rows (a customer, a month, all of GlobalMart) and the sum still means something. Actual_price/Discounted_price are rates, not totals — adding two prices together doesn't produce a meaningful number, no matter how correct the grain is.

Full additive/non-additive treatment is next in ILT 3.

Grain Is Settled

Designing the 6 Dimensions

Using GlobalMart's real Silver tables as the source for each one.

1. dim_customer

Source: <your-catalog>.silver.customers  |  Natural key: customer_id  |  Grain: one row per customer version

ColumnWhy it's here
customer_skReused from Silver, not generated in the Gold build — the join target every fact table uses
customer_idNatural/business key — traces back to CustomerID in customers.csv
full_nameWhat the business actually looks at
email, phone_numberContact attributes — also the fields most likely to change over a customer's lifetime
is_currentMarks which version of this customer is true right now
effective_start_date, effective_end_dateThe date range this version of the customer was/is true for

Say Bysani Karthik updates his phone number. If we just overwrote his old number, we'd lose it forever — including on any past order where that old number mattered (like a delivery call that used it). So instead of overwriting, Silver keeps the OLD row untouched and adds a brand NEW row with the new number. Now both are on file: "this was true before," and "this is true now."

This pattern — keep old rows, add new ones instead of overwriting — is called SCD Type 2. Silver already does this for dim_customer's source, as of Day 5: it generates the new customer_sk, closes out the old row, and stamps the effective dates, all automatically.

Gold's job today is simple: just republish those already-correct columns as-is. No re-deciding, no rebuilding.

2. dim_product

Source: <your-catalog>.silver.products  |  Natural key: product_id  |  Grain: one row per product version

ColumnWhy it's here
product_skReused from Silver, same reasoning as dim_customer
product_idNatural/business key (e.g. PRD-00001)
product_nameHuman-readable label for reports and Genie answers
category, sub_categoryWhat "revenue by category" — one of the most common business questions — groups and filters by
discounted_price_inrThe attribute that actually changes — the reason this dimension is SCD Type 2
is_current, effective_start_date, effective_end_dateSCD2 control columns, same role and source (Silver) as in dim_customer

Imagine GlobalMart runs a flash sale next week, cutting a product's price in half for three days. If discounted_price_inr just got overwritten, every past order for that product — including the ones before the sale — would suddenly look like it was sold at the sale price. Revenue reports for last month would silently change today, which makes no sense.

So dim_product keeps history the same way dim_customer does: old price, old row; new price, new row. That's why discounted_price_inr is the column that makes this dimension SCD Type 2.

Like dim_customer, Silver already built this on Day 5. Gold just carries it forward.

3. dim_date

Source: none — generated, not read from Silver  |  Natural key: the calendar date itself  |  Grain: one row per calendar day

No source system ships "a table of dates"

Every other dimension in this deck starts from a real Silver table — data GlobalMart actually collected. Nobody "collects" calendar dates, because we already know every date there is. So instead of reading dim_date from somewhere, we generate it ourselves — one row per day.

How far back and forward should the calendar go? Not an arbitrary guess — pull the real bounds straight from silver.orders (earliest order_date, latest actual_delivery_date) and generate exactly that range. That way there are no wasted rows for dates GlobalMart never did business on, and the table stays correct automatically as more orders come in.

ColumnWhy it's here
date_keySurrogate key — the one deliberate exception to the reuse-or-hash convention
dateThe actual calendar date, for display and date-math in BI tools
year, quarter, monthPre-computed calendar hierarchy — avoids every query recomputing QUARTER(date) itself
day_of_weekDay-of-week name, for weekday/weekend and seasonality analysis
is_weekendCommon business flag — "do we sell more on weekends?" without date-math in every query

Every other freshly-generated surrogate key in this model is a hash — sha2(natural_key, 256), an unreadable jumble of characters. For dim_date, that would turn a perfectly readable date into gibberish for no benefit. So this table breaks the pattern on purpose: date_key is just the date itself, written as a plain integer — 20260703 for July 3rd, 2026.

That choice pays off twice: anyone reading the raw table can tell what date a row is without decoding anything, and because it's a number, it sorts in correct date order automatically — a hash never could.

Worth asking: will GlobalMart ever build a second fact table — say, a future fact_returns? Almost certainly. Should that new fact table get its own separate calendar? No — reusing this exact same dim_date table means "July 3rd" means the identical thing in every report, forever, instead of two tables quietly drifting apart. Reusing one dimension table across every fact table like this has a name: a conformed dimension — more on this later this session.

4. dim_address

Source: <your-catalog>.silver.address (singular)  |  Natural key: address_id  |  Grain: one row per address

ColumnWhy it's here
address_skSurrogate key — generated fresh here in Gold, since Silver never assigned this table one. Even an SCD Type 1 dimension gets one, to keep the join pattern uniform across every dimension
address_idNatural/business key, traces back to source
customer_idFilter "this customer's addresses" without going through the fact table
city, state, pincodeThe entire reason this dimension exists — "revenue by city/state" reporting
address_typeDistinguishes Billing vs. Shipping

dim_address is SCD Type 1, same as dim_payment_method and dim_orders — no is_current, no effective dates, just the current row per address_id. Both silver.address and gold.dim_address agree on this: Silver already overwrites in place, and Gold just republishes that current-state table as-is, adding only the surrogate key Silver never assigned.

That's a deliberate choice, not a gap — GlobalMart isn't tracking "which address a customer had on file at the time of a past order" as a reporting requirement. If that need ever comes up, dim_address would need to move to Type 2 like dim_customer/dim_product — but today it doesn't.

One problem dim_address alone can't solve: Say Prishita Shukla has two addresses on file — one Billing, one Shipping. dim_address can't say by itself which one a specific order actually shipped to.

The fix isn't a bridge table. Day 7's fact_sales build ranks each customer's addresses (Shipping preferred) and picks the top one. dim_address stays a plain, honest dimension — all the resolving happens in the fact build, not here.

5. dim_payment_method

Source: <your-catalog>.silver.payment_methods (the small lookup table)  |  Natural key: payment_method_id  |  Grain: one row per payment method (~5 rows)

ColumnWhy it's here
payment_method_skSurrogate key, generated fresh here in Gold
payment_method_idNatural/business key (e.g. PM-002)
method_nameHuman-readable value ("UPI", "Credit Card") — PM-002 means nothing to a business user on its own

There are two tables with "payment" in the name — easy to grab the wrong one. payment_methods is the small, ~5-row lookup ("UPI", "Credit Card", ...) — that's this dimension's source. payments is something completely different: a transactional table recording every individual payment event on every order. Building dim_payment_method from payments instead would give you thousands of rows, one per transaction, when what you actually want is 5 category rows to group by.

Even though this dimension only has ~5 rows, it still gets a surrogate key generated fresh in Gold, exactly like the bigger dimensions do. Why bother for such a tiny table? Because every fact-to-dimension join in this model should work the same way — same shape, same rules — so nobody building a query has to remember "except for the small ones." The next dimension, dim_orders, is worth a closer look at this same idea.

6. dim_orders — The Sixth Dimension

Source: <your-catalog>.silver.orders  |  Natural key: order_id  |  Grain: one row per order

ColumnWhy it's here
order_skSurrogate key, generated fresh here in Gold — same uniform pattern as dim_address/dim_payment_method
order_idNatural/business key, traces back to source
customer_idFilter "this customer's orders" without going through the fact table
order_dateAlso independently reachable via dim_date through the fact, kept here too as a natural attribute of the order itself
shipping_tier_id, supplier_idCarried as plain IDs — no backing lookup table exists for either yet
order_channelThe one attribute with real reporting value — "Online" vs. "Retail PoS"

It's easy to assume there's no such thing as a "dimension for orders" — surely an order is just the fact table itself? Not quite. Order-level attributes like order_channel ("Online" vs. "Retail PoS") describe the order as a whole, not any one measure — that's exactly what a dimension is for. So dim_orders is real, and today's Hands-On builds it as its own queryable Gold table.

One thing to flag now and come back to: when fact_sales gets built in Day 7, it won't join to dim_orders by a surrogate key the way you'd expect — it carries Order_ID directly instead, the same simplification applied to every dimension in this fact table. dim_orders still exists and is still useful on its own. ILT 3 (next) explains this join pattern in full, under "degenerate dimensions."

Key Design

Surrogate Keys

The Kimball standard — and where GlobalMart deliberately takes a shortcut.

Natural Key vs. Surrogate Key

Imagine GlobalMart's fact table joined to dim_customer using customer_id straight from the source system — no extra key at all. Sounds simpler. Here's why it isn't, once you remember dim_customer is SCD Type 2: a single customer_id like Bysani's now has two rows — his old version and his new version, after his phone number changed. customer_id alone can't distinguish those two rows — they share it. So the join either matches both rows at once (a duplicated fact row, which is worse) or, if forced to pick one, silently falls back to whichever row is marked current — not necessarily the one that was true when the sale actually happened.

Natural key

The identifier the source system assigns (customer_id, PM-002) — means something to the business, but on its own can't tell two versions of the same customer apart.

Surrogate key

A separate identifier Gold creates and owns — meaningless outside the warehouse, but unique per version of a row, not just per customer. That's what makes it a safe, stable join target.

The rule this leads to (Kimball-standard, and cert material): dimension tables get a surrogate key, and fact tables join to dimensions on that key — never the natural key. GlobalMart's own fact_sales is a deliberate, documented exception to this rule — covered a few slides ahead, with its real cost spelled out.

Reuse from Silver, or Generate Fresh in Gold?

Reuse from SilverGenerate fresh in Gold
Applies todim_customer, dim_productdim_address, dim_payment_method, dim_orders
WhySilver already built these as SCD2 tables and generated the key thereSilver never assigned these one, so Gold generates sha2(natural_key, 256)
MethodSELECT the existing customer_sk/product_sk as-isaddress_sk = sha2(address_id, 256), payment_method_sk = sha2(payment_method_id, 256), order_sk = sha2(order_id, 256) — same single-column hash pattern for all three

Two different questions, two different answers — don't mix them up. Question 1: where does the surrogate key come from — reused from Silver, or made fresh in Gold? Question 2: do we keep history when something changes — Type 1 or Type 2? These are independent; the answer to one doesn't determine the other.

In GlobalMart's model today, the two answers happen to move together: dim_customer/dim_product reuse Silver's key and keep Type 2 history; dim_address/dim_payment_method/dim_orders all generate a fresh key in Gold and stay Type 1. That's a coincidence of this particular dataset, not a rule — nothing stops a future dimension from reusing a key while staying Type 1, or generating a fresh key while tracking Type 2 history. Don't assume the two questions are linked just because they align here.

dim_date.date_key is the one further exception to both paths — a plain YYYYMMDD integer, as covered above.

Why a Single-Column Hash Is Enough for These Three

All three freshly-generated keys — address_sk, payment_method_sk, order_sk — hash just one column: the natural key alone. That only works because of something all three dimensions have in common.

All three are Type 1

dim_address, dim_payment_method, and dim_orders are all SCD Type 1 — exactly one row per natural key, forever, no version history. Prishita Shukla has exactly one row in dim_address for her address_id, today and always.

One row per key means the natural key is already unique

Since there's never more than one row per natural key, sha2(natural_key, 256) is guaranteed to produce a unique _sk value per row. Nothing extra needs to go into the hash.

Contrast with dim_customer/dim_product: those two are Type 2 — the same customer_id can legitimately appear on more than one row (one per version), so a hash of the natural key alone wouldn't be unique per row. That's exactly why they don't hash anything at all — they reuse the surrogate key Silver already generated when it built the SCD2 version history, which is what actually makes each version's row identifiable.

Why a Hash-Based Surrogate Key at All?

Why not just make up a simple counter — 1, 2, 3... — for each new dimension row, instead of a hash? It would work at first, but it breaks down for a few concrete reasons:

ReasonExplanation
IdempotentRe-running the Gold build produces the exact same key for the same natural key, every time. A counter wouldn't — re-run the pipeline twice and row order could shift, silently handing out different numbers to the same customer
Decouples from source-system key changesIf Supabase or an ADLS file drop changes its ID format, fact_sales doesn't care — Gold's keys are Gold-owned, not borrowed from a system that might change its mind
Stable under SCD Type 2The fact must point at the exact dimension row version true at the moment of the sale — only a Gold/Silver-controlled key supports that
Join performanceA fixed-length hash joins faster than long string natural keys at fact_sales's scale

GlobalMart's Shortcut

Everything so far has been building toward one rule: dimensions get a surrogate key, and facts join on it. So here's a surprise — when fact_sales actually gets built (Day 7), it doesn't follow that rule at all. It carries Customer_ID, Product_ID, Order_ID, Address_ID, Payment_ID, and Time_ID straight from the source — natural keys, not the surrogate keys we just spent this whole section designing.

Five of the six join their dimension directly this way, using the natural key. (Time_ID is a special case — it is dim_date.date_key, so natural and surrogate happen to be the same column there, no shortcut needed.)

Payment_ID Is the Exception to the Exception

The other five natural keys, even used this shortcut way, still successfully find their matching row in the dimension. Payment_ID doesn't — it comes from silver.payments, a completely different ID space than dim_payment_method.payment_method_id. They're not the same kind of number at all, so there's no row to match.

So unlike the other five, fact_sales doesn't resolve to dim_payment_method at all. ILT 3 goes deeper on this.

The Cost of the Shortcut

Why does this matter, concretely? Recall from a few slides back: a natural key like customer_id can't tell two versions of the same customer apart, so a join on it falls back to whichever row is marked current. Say a customer's email changes next month. Every one of that customer's past fact_sales rows, when joined today, now resolves to their current dim_customer row — not the version that was actually true back when each sale happened. A report asking "what was true at the time of the sale" quietly gets today's answer instead.

That's a real cost, and GlobalMart is accepting it on purpose — this is a deliberate, documented simplification, not an oversight, made in exchange for every dimension joining the same simple way.

The rule to internalize regardless

Don't walk away thinking "surrogate keys are optional." The surrogate-key discipline taught in this section is still the correct default for any dimensional model. fact_sales is the documented exception GlobalMart chose — not the pattern to copy elsewhere.

Reuse Discipline

Conformed Dimensions

The Problem This Solves

Imagine two different teams at GlobalMart, working independently. One builds fact_sales and needs a "product" dimension, so they build one. Later, another team builds a returns-analysis fact table and also needs a "product" dimension — but instead of reusing the first team's table, they build their own from scratch, with slightly different category groupings.

Now "revenue by category" (from team one) and "return rate by category" (from team two) silently disagree — not because the numbers are wrong, but because "category" doesn't mean the same thing in both reports anymore. Nobody notices until a leadership meeting where the two numbers don't add up, and nobody can say why.

The fix: build it once, share it everywhere

The fix is simple to state: build each dimension exactly once, with one agreed definition, and have every fact table reuse that exact same table — never rebuild a slightly-different copy. A dimension used this way has a name: a conformed dimension.

GlobalMart's Conformed Dimensions

dim_product and dim_customer, built today, are designed to be reused this way. If GlobalMart later builds a fact_returns (from returns.csv, which already exists in the raw data), it would join to the exact same dim_product/dim_customer rows built today — not a fresh copy. That means "revenue by category" and "return rate by category" automatically agree, because both queries filter through the identical category values, from the identical table.

dim_date is the cleanest example of all — any future fact table joins to today's exact table, not a re-derived one.

This is the exact trust problem GlobalMart started this course to solve (Day 1, Problems #1 and #5) — one number, one source of truth, agreed across every team.

SCD Strategy

SCD Type 1 vs. Type 2

A conceptual preview of the decision framework.

The MERGE-based mechanics are taught in a later session. Today's Hands-On builds every dimension as a simple current-state table, except where Silver already built SCD2 in (dim_customer, dim_product).

The Decision Framework

SCD Type 1SCD Type 2
BehaviorOverwrite the old value in placeKeep the old row, insert a new row, mark which is current
History preserved?NoYes — full version history
Extra columnsNoneis_current, effective_start_date, effective_end_date
GlobalMart exampleFixing a typo'd city; a payment method's display name changingA customer's email/city changes but past orders must still show what was true then; a product's price changes but past revenue must reflect the price paid at the time

One question settles it every time: "If this value changes, does anyone need to know what it used to be?" If no — just overwrite it, Type 1, done. If yes — keep the old row and add a new one, Type 2. Every dimension decision in this course comes down to answering that one question honestly.

Round 1 — Grain & Reuse-vs-Generate

Why is fact_sales's grain "one row per order line item," not "one row per order"?
order_items.csv already shows the real shape: OrderItemID, OrderID, ProductID, Quantity — one order can have many rows, one per product bought. Graining at "one order" would force you to squash multiple products into one row (arrays, string-concat, or dropped detail) — you'd lose the ability to ask "which products sold" at all. Grain follows what the source data actually records, not a convenient guess.
dim_customer and dim_product reuse Silver's surrogate key. dim_address, dim_payment_method, and dim_orders don't. Why the split?
Silver already built customers/products as full SCD2 tables on Day 5 — it generated customer_sk/product_sk and stamped is_current/effective dates there. Gold just republishes that decision. Silver never did any of that for address/payment_methods/orders — those three have no surrogate key upstream, so Gold has to generate one from scratch.
Is dim_address SCD Type 1 or Type 2?
Type 1, at both layers — and they agree, not by coincidence. silver.address is Type 1 (overwrite-in-place, a deliberate choice made at that layer). gold.dim_address just republishes that current-state table, adding only the surrogate key Silver never assigned. No is_current, no effective dates — same plain pattern as dim_payment_method/dim_orders. Unlike dim_customer/dim_product, there's no version history being preserved at either layer.
dim_address, dim_payment_method, and dim_orders all hash just their natural key for a fresh surrogate key. Why is a single-column hash safe for all three?
Because all three are SCD Type 1 — exactly one row per natural key, forever, no version history. That means sha2(natural_key, 256) is already guaranteed unique per row; there's never a second row sharing the same natural key that the hash would need to disambiguate. Contrast dim_customer/dim_product: those are Type 2, so the same natural key legitimately appears on multiple rows (one per version) — which is exactly why they don't hash the natural key at all, and instead reuse the surrogate key Silver already generated when it built the SCD2 history.

Round 2 — Sources, Conformance & SCD

payment_methods vs payments — which one is the dimension?
payment_methods — the small ~5-row lookup table (Credit Card, UPI, Debit Card, Net Banking, COD). payments is transactional detail: when Devanand P pays for an order via UPI, that specific payment event — gift-card amount, coupon usage, everything about that one transaction — lands in payments, not payment_methods. It describes what happened, not a stable category to filter/group by, so it's fact-adjacent, not a dimension.
What makes dim_customer and dim_product "conformed" dimensions specifically?
They're built once, with a stable set of surrogate keys, with the explicit intent that a future fact table (like fact_returns) will join to the exact same customer_sk/product_sk values — not rebuild its own copy. That shared vocabulary is what "conformed" means: two different fact tables agreeing on what "the same customer" or "the same product" means.
Every surrogate key in this star is a sha2() hash except one. Which, and why?
date_key, on dim_date — a plain YYYYMMDD integer, per Kimball's long-standing convention for date dimensions. It's human-readable in ad-hoc SQL, and being numeric, it sorts correctly in plain ascending order — a hash can't do that.
Bysani Karthik updates his phone number. In dim_customer, does that produce a new row or update the existing one?
New row — that's the whole point of Type 2. Silver closes out Bysani's old row (effective_end_date set, is_current flipped to false) and inserts a new one with his new phone number and a fresh customer_sk. Any fact_sales row from before the change still points at his old customer_sk, preserving what was true at the time of that order — his order history doesn't quietly rewrite itself.

Round 3 — Don't Mix These Two Decisions Up

"Reuse from Silver vs. generate fresh in Gold" and "SCD Type 1 vs Type 2" — are those the same decision?
No — conceptually, they're two independent decisions. It just happens that, across GlobalMart's current 6 dimensions, the answers move together: dim_customer/dim_product reuse Silver's key and track Type 2 history; dim_address/dim_payment_method/dim_orders all generate a fresh key and stay Type 1. That's a coincidence of this dataset, not a rule — a dimension could in principle reuse a key and still be Type 1, or generate a fresh key and be Type 2.
How many dimensions does fact_sales actually have a foreign key to?
6 dimension tables get built today: dim_customer, dim_product, dim_date, dim_address, dim_payment_method, dim_orders. The whiteboard sketch shows 8 boxes total, but order_items and returns aren't among the 6 — they're reference-only, not dimensions fact_sales connects to. Exactly how fact_sales connects to each of the 6 — and one key that doesn't resolve the way you'd expect — is ILT 3's topic this afternoon.
