1. What Is Grain?

Grain is the single, unambiguous statement of what one row in a fact table represents. Kimball's rule: declare the grain in one sentence, before designing a single column. Every measure and dimension added afterward must be true at that grain.

GlobalMart's declared grain: one row in fact_sales = one line item within one order — one row per (order_id, product_id) combination in order_items.

A worked example

Order OR-094494 in order_items:
  order_item_id = OR-J-283399  | product_id = PRD-00410 | quantity = 1
  order_item_id = OR-KSC-283400 | product_id = PRD-00107 | quantity = 5

→ contributes exactly 2 rows to fact_sales — one per product. Actual_price/
Discounted_price looked up from silver.products; Sales_amount computed
during Day 7's fact build. Each row carries its own correct revenue number.
If grain were "one row per order"...Problem
Order OR-094494's 2 products collapse into 1 rowLose per-product Quantity_purchased/Sales_amount — can't answer "which product sold best?"
product_id would need to be a list in one cellBreaks the star schema pattern — dimensions expect one clean FK per fact row
Coarser grain always loses information you cannot get back later without re-processing Silver. This is the single biggest reason to get grain right the first time.

Finer than a line item? Not for GlobalMart's current sources — order_items doesn't track shipment- or unit-level splits. If it ever did, that would justify a new, finer-grained fact table (e.g. fact_shipments), not a change to fact_sales. A return/refund event is a genuinely different business process — a future fact_returns, at its own grain, not a variant of this one.

The grain test: before adding any column, ask "is this value true for exactly one line item, or could it vary within the order?" Quantity_purchased and Discounted_price pass. "Total items in this order" fails — that's an order-level aggregate. It doesn't belong as a stored column in fact_sales at all; compute it on demand with SUM(Quantity_purchased) GROUP BY Order_ID.
Consequence for the 4 measures: at this grain, Quantity_purchased and Sales_amount always SUM correctly at any rollup level. Actual_price/Discounted_price do not — summing a rate is never meaningful, even at the right grain. Full additive/non-additive treatment is ILT 3.

3. Designing dim_product

Source: gbmart.silver.products  |  Natural key: product_id  |  Grain: one row per product version

ColumnWhy it's here
product_skReused from Silver, same reasoning as dim_customer
product_idNatural/business key (e.g. PRD-00001)
product_nameHuman-readable label for reports and Genie answers
category, sub_categoryWhat "revenue by category" — one of the most common business questions — groups and filters by
discounted_price_inrThe attribute that actually changes — the reason this dimension is SCD Type 2

discounted_price_inr is exactly the kind of attribute that makes dim_product a realistic SCD Type 2 candidate — if GlobalMart runs a flash sale and drops a price, historical sales should keep reporting against the price that was true at the time of the sale. Like dim_customer, this was already decided and built in Day 5's Silver layer — Gold just carries it forward. is_current matters here: Day 7's Gold reporting views filter on it directly (WHERE p.is_current = true) whenever they join dim_product.

4. Designing dim_date

Source: none — generated, not read from Silver  |  Natural key: the calendar date itself  |  Grain: one row per calendar day

Every other dimension has a Silver source table. dim_date never does, in any dimensional model — no source system ships a "table of dates." Sized to the data, not an arbitrary range: pull the real bounds straight from silver.orders (earliest order_date, latest actual_delivery_date) and generate exactly that range — no wasted rows either side, and it stays correct automatically as GlobalMart's order history grows.

ColumnWhy it's here
date_keySurrogate key — see the callout below, the one deliberate exception to the reuse-or-hash convention
dateThe actual calendar date, for display and date-math in BI tools
year, quarter, monthPre-computed calendar hierarchy — avoids every query recomputing QUARTER(date) itself
day_of_weekDay-of-week name, for weekday/weekend and seasonality analysis
is_weekendCommon business flag — "do we sell more on weekends?" without date-math in every query
Why date_key is an integer YYYYMMDD, not a hash: every other freshly-generated surrogate key in this model is sha2(natural_key, 256) (Section 7). dim_date breaks that pattern on purpose — e.g. 20260703. Long-standing Kimball convention: human-readable, sorts correctly as a number, partitions Delta tables cleanly.
dim_date is the textbook example of a conformed dimension (Section 8) — every fact table GlobalMart ever builds joins to this exact same table. Built once, reused forever.

dim_address

ColumnWhy it's here

The many-to-many problem — and how it's actually resolved. One customer can have multiple addresses — a plain dimension table can't say by itself "which address did this specific order line ship to." That's real, but it is not solved with a bridge table. Day 7's fact_sales build resolves it with a window-function ranking: rank each customer's addresses (prefer Shipping), keep the top-ranked one, join on customer_id. dim_address itself stays a plain, honest dimension — the resolution logic lives entirely in the fact build. (Day 7 HOL 1 does build one illustrative bridge table, for a hypothetical products↔campaigns relationship, purely to teach the bridge-table pattern in general — unrelated to addresses.)

dim_payment_method

Source: gbmart.silver.payment_methods (the small lookup table)  |  Natural key: payment_method_id  |  Grain: one row per payment method (~5 rows)

ColumnWhy it's here
payment_method_skSurrogate key, generated fresh here in Gold
payment_method_idNatural/business key (e.g. PM-002)
method_nameHuman-readable value ("UPI", "Credit Card") — PM-002 means nothing to a business user on its own
Common mistake — don't confuse the two payment tables. dim_payment_method sources from payment_methods (the 5-row lookup), not from payments (the transactional table recording every individual payment event per order). A tiny reference table like this is sometimes called a mini-dimension.

Both dimensions get a surrogate key generated fresh in Gold, even though they're small — keeping every dimension's join shape identical (a rule Section 6's dim_orders shows the one case worth a closer look at).

This is the sixth dimension — it's easy to assume order_id has no dimension at all. It does: dim_orders is real, and today's Hands-On builds it. What's still true is that fact_sales (Day 7) doesn't join to it by surrogate key — it carries Order_ID directly as a natural key instead, the same simplification the fact table applies to every dimension. dim_orders exists as its own queryable Gold table regardless — ILT 3 (next) revisits this exact point under "degenerate dimensions."

7. Surrogate Keys — the Kimball Standard, and Where GlobalMart Takes a Shortcut

Natural key: the identifier the source system assigns (customer_id, PM-002) — means something to the business. Surrogate key: an identifier Gold owns, meaningless outside the warehouse, whose only job is a stable, efficient join target. The Kimball-standard rule, and cert material: dimension tables get a surrogate key, and fact tables join to dimensions on that key — never the natural key.

Reuse from SilverGenerate fresh in Gold
Applies todim_customer, dim_productdim_address, dim_payment_method, dim_orders
WhySilver already built these as SCD2 tables and generated the key thereSilver never assigned these one, so Gold generates sha2(natural_key, 256)
MethodSELECT the existing customer_sk/product_sk as-isaddress_sk = sha2(address_id, 256), same pattern for the other two

dim_date.date_key is the one further exception to both paths — a plain YYYYMMDD integer (Section 4).

Reason for a hash-based surrogate keyExplanation
IdempotentRe-running the Gold build produces the exact same key for the same natural key, every time — an auto-increment counter would not
Decouples from source-system key changesIf Supabase or an ADLS file drop changes its ID format, fact_sales doesn't care — Gold's keys are Gold-owned
Stable under SCD Type 2The fact must point at the exact dimension row version true at the moment of the sale — only a Gold/Silver-controlled key supports that
Join performanceA fixed-length hash joins faster than long string natural keys at fact_sales's scale
The shortcut GlobalMart's real fact_sales actually takes: even though every dimension above has a proper surrogate key, fact_sales itself (Day 7) does not use any of them. It carries Customer_ID, Product_ID, Order_ID, Address_ID, Payment_ID, and Time_ID. Five of these six join their dimension directly by natural key (Time_ID is dim_date.date_key — natural and surrogate collapse into the same column for that one dimension). Payment_ID is the exception to the exception: it comes from silver.payments, a completely different ID space from dim_payment_method.payment_method_id — so fact_sales doesn't resolve to dim_payment_method at all (ILT 3 Section 4). This is a deliberate, documented simplification, not an oversight — cost: no point-in-time SCD2 accuracy. If a customer's email changes, every one of their past fact_sales rows now resolves to the current dim_customer row when joined, not the version true when each sale happened. The surrogate-key discipline above is still the correct default to teach — this fact table is the documented exception, not the pattern.

8. Conformed Dimensions

A conformed dimension is built once, with one definition, and reused unchanged by every fact table in the warehouse.

GlobalMart's example: dim_product and dim_customer, built today, are designed to be reused. A future fact_returns (from returns.csv, which already exists in the raw data) would join to the exact same dim_product/dim_customer rows — so "revenue by category" and "return rate by category" automatically agree, because both queries filter through the identical category values. dim_date is the cleanest example of all — any future fact table joins to today's exact table, not a re-derived one.
Without conformance, two teams building two fact tables might each build their own "product dimension" with slightly different category groupings — now "revenue by category" and "return rate by category" silently disagree. This is the exact trust problem GlobalMart started this course to solve (Day 1, Problems #1 and #5).

Scope note: this is a decision framework, not an implementation lesson — the MERGE-based mechanics are taught in a later session. Today's Hands-On builds every dimension as a simple current-state table, except where Silver already built SCD2 in (dim_customer, dim_product).
SCD Type 1SCD Type 2
BehaviorOverwrite the old value in placeKeep the old row, insert a new row, mark which is current
