Fact Table Types

Three Types of Fact Tables

The difference is about when a row is written and whether it ever changes afterward.

The Three Types

Transactional Fact — fact_sales is this type

One row per business event, captured the moment it happens. Grain = the event. Inserted once, essentially never updated.

GlobalMart: one row per order line item, inserted when placed. Append-only — same discipline as Bronze/Silver.

Periodic Snapshot Fact — not used today

One row per entity per fixed time period — daily, weekly, monthly — whether or not anything happened.

Hypothetical GlobalMart example (not built): fact_inventory_daily — one row per product per day.

Accumulating Snapshot Fact — not used today

One row per process instance, updated in place as it moves through milestones. The one type that breaks append-only.

Hypothetical: order lifecycle fact — order_placed_date → shipped_date → actual_delivery_date, same row, updated repeatedly.

Why fact_sales is transactional: its grain (one order line item) is an event grain, not a time-period or process-instance grain. Inserted once when Bronze/Silver capture the line; Gold never edits Quantity_purchased or Discounted_price afterward.

Measures

Additive, Semi-Additive, Non-Additive

fact_sales carries exactly 4 measures. Rule of thumb: before writing SUM() on any of them, ask — does adding these two numbers together produce something a business person would recognize as meaningful?

fact_sales's 4 Measures

Additive — Quantity_purchased · Sales_amount

Safe to SUM across any dimension — product, customer, date, category, region, any combination.

SUM(Sales_amount) by category this month, by customer this year — always correct. This is "revenue."

Non-Additive — Actual_price · Discounted_price

Never SUM either. Summing a rate/price across different line items produces a meaningless number.

Wrong: AVG(Discounted_price) across many products. Right: avg. selling price = SUM(Sales_amount)/SUM(Quantity_purchased).

Semi-Additive — not in fact_sales

Summable across most dimensions, but not across time. Classic example: inventory on-hand, account balance.

3 warehouses × 100 units today = 300, valid. One warehouse's 100 units summed over 7 idle days = 700, meaningless (same stock counted 7×).

The one legitimate exception: Day 7 HOL 2's real vw_monthly_category_sales view runs ROUND(AVG(Actual_price - Discounted_price), 2) AS avg_discount_given — that's averaging the difference of two rates (itself a rate), not averaging a raw price across unrelated products. Discount-gap analysis is meaningful; averaging raw prices across different products still isn't.

GlobalMart's Twist on the Textbook Case

Degenerate Dimensions

By the textbook definition: an identifier stored in the fact table with no corresponding dimension table of its own — usually because it has no descriptive attributes beyond the ID itself.

Order_ID Looks Like a Classic Candidate

By that definition...

Order_ID looks like a classic degenerate-dimension candidate — just an ID, sitting in the fact table.

But GlobalMart built dim_orders anyway — this afternoon's Hands-On constructs it from gbmart.silver.orders, complete with its own surrogate key (order_sk) and order_channel/shipping_tier_id/supplier_id/order_date.

So which is it — degenerate, or a real dimension? Both, depending which table you're looking from.

Looking From Which Table?

Looking from...What Order_ID is
dim_orders itselfA real, standalone Gold dimension — one row per order, its own surrogate key, independently queryable ("orders by channel") without ever touching fact_sales
fact_salesOrder_ID sits as a plain natural-key column — fact_sales does not join through dim_orders.order_sk at all

From fact_sales's Point of View, Order_ID Still Does the Degenerate-Dimension Job

  1. COUNT(DISTINCT Order_ID) answers "how many orders?" — different from "how many line items?" (Day 7 HOL 2's real vw_regional_sales view uses exactly this)
  2. It groups line items back into their parent order
  3. It supports drill-through back to the source order record

The Actual Lesson

Having a real dimension table for something doesn't force every fact table to join to it by surrogate key. GlobalMart's fact_sales treats Order_ID as if it were degenerate — it still joins dim_orders fine on the natural key, it just never goes through order_sk, purely because the natural-key simplification (next section) applies uniformly to all six dimensions. dim_orders isn't wasted — it just serves order-level analysis on its own, not through the fact table.

Payment_ID is a stricter case, not "the same story": it doesn't merely skip a surrogate key, it doesn't resolve to dim_payment_method through any column at all — the two aren't even in the same ID space.

Key Design

Why fact_sales Uses Natural Keys

Not the surrogate keys its dimensions already have.

Every Dimension Already Has a Proper Surrogate Key

customer_sk/product_sk (reused from Silver's SCD2 build), address_sk/payment_method_sk/order_sk (generated fresh in Gold), and dim_date.date_key (the YYYYMMDD exception).

The Kimball-standard rule — and cert material — says a fact table should join to its dimensions on exactly those surrogate keys, never the natural key.

fact_sales Does Not Follow That Rule

It carries Customer_ID, Product_ID, Order_ID, Address_ID, Payment_ID, and Time_ID — six natural/business keys.

Five join their dimension directly: Customer_ID→dim_customer, Product_ID→dim_product, Order_ID→dim_orders, Address_ID→dim_address, Time_ID→dim_date (Time_ID is literally dim_date.date_key).

Payment_ID is the odd one out — it doesn't resolve to dim_payment_method at all, since the two live in different ID spaces.

The only surrogate key fact_sales actually generates is its own row identity: fact_sales_sk = sha2(order_item_id, 256) — a key for the fact row itself, not a foreign key to anything.

Why This Is a Real Cost

ReasonExplanation
Point-in-time accuracy, lostIf a customer's email changes, dim_customer (Type 2) keeps both rows with different customer_sk values. Joining on the bare Customer_ID instead means every join — including against last year's sales — resolves to whichever row currently has that ID, not the version true at sale time.
Uniformity (why GlobalMart accepts the cost)All 6 dimensions get identical natural-key treatment — no special-case join logic to remember per dimension, even for dim_orders, the newest and most obviously dimension-shaped table.
Documented, not hiddenDay 7 HOL 2's own Key Takeaways state it directly: "Natural-key joins were a deliberate choice, not a shortcut — you now know exactly what it costs and why it was still the right call for this program."

Rule to internalize regardless: the Kimball-standard, cert-tested default is still join facts to dimensions on the surrogate key. GlobalMart's fact_sales is the documented exception you now understand the cost of — not the pattern to reach for by default in your own designs.
