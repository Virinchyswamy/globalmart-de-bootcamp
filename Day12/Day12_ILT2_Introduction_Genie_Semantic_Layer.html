1. What Is Databricks Genie?

Genie is a Databricks AI/BI feature that lets a business user type a plain-English question — "What was our revenue by category last month?" — against a curated Genie Space, and get back a generated SQL query plus a tabular/plotted answer. No SQL is written by the person asking.

1. Ask A business user types a natural-language question into the Genie chat UI. No SQL, no join logic — plain English.
2. Genie interprets Genie's LLM reads the Genie Space's metadata — table/column names, comments, sample questions — to work out which tables, columns, and joins answer it.
3. SQL + answer Genie generates SQL, runs it against a warehouse, and returns the result — usually alongside the SQL itself, so it can be checked.

A Genie Space is a scoped, curated subset of a catalog — specific tables/views, instructions, sample questions, example SQL — deliberately narrower than "the whole catalog," so the LLM is not guessing across hundreds of unrelated tables.

Be honest about the boundary: a Genie Space is set up entirely by clicking through the Databricks workspace UI — Catalog Explorer → Genie → New Space, selecting tables, writing instructions, adding sample questions — not by running code in a notebook. The matching hands-on, "Set Up Genie on Gold Layer — Descriptions + Natural Language Queries," is a separate, later session done live in the workspace UI against the real gbmart Gold layer. Nothing in this session's notebook creates a Genie Space.

2. What a Semantic Layer Is, and Why Genie Needs One

Two raw facts about gbmart.gold.fact_sales: a column named Sales_amount (type decimal), and a column named Actual_price (type decimal). To an LLM — or a brand-new analyst — those names alone answer none of the questions that matter.

Without a semantic layerWith a semantic layer
Sales_amountJust a decimal column. Safe to SUM? Pre- or post-discount? Unknown."Revenue in INR for this order line item — quantity times discounted price. Safe to SUM."
Actual_priceJust a decimal column. Looks summable like any other number."Original list price per unit, in INR. Non-additive — never SUM directly across products."

A semantic layer is the metadata that answers these questions before anyone has to ask — table comments, column comments, certified views with business-friendly names, unambiguous column names, and sample questions registered against a Genie Space. None of it changes what the data is. All of it changes whether the schema is usable by something that has never seen your business before.

GlobalMart already has two semantic-layer artifacts — built before Genie ever entered the conversation. Day 7 HOL 2's gbmart.gold.vw_monthly_category_sales (year/month/category revenue, quantity, orders, avg. discount) and gbmart.gold.vw_regional_sales (state/city revenue, orders, customers, avg. order value) exist because category managers and regional ops leads needed one agreed-upon number to report against — not because Genie needed them. That is precisely what a semantic layer is. A Genie Space built on gbmart.gold would point straight at these two views for exactly the questions they already answer.

4. The Part We CAN Script: Preparing Semantic-Layer Metadata

Genie Space setup is UI-only (Section 1). The semantic layer underneath it — table/column comments, and verifying they landed — is real, scriptable Databricks SQL. The matching notebook does this against a safe practice copy, never the real gbmart.gold.fact_sales table.

Step A Seed a Practice Copy, Look at the Raw Schema

# The ONLY touch against the real table anywhere in this notebook -- read-only.
YOUR_SCHEMA = "main.YOUR_SCHEMA"
spark.sql(f"CREATE SCHEMA IF NOT EXISTS {YOUR_SCHEMA}")
PRACTICE_TABLE = f"{YOUR_SCHEMA}.fact_sales_practice"

# CREATE OR REPLACE -- idempotent, safe to re-run
spark.sql(f"CREATE OR REPLACE TABLE {PRACTICE_TABLE} AS SELECT * FROM gbmart.gold.fact_sales LIMIT 100")

# "Before" -- names and types only, exactly what an LLM sees with no semantic layer
for col_name, col_type in spark.table(PRACTICE_TABLE).dtypes:
    print(col_name, col_type)

Step B Add Real Table + Column Comments

# Table comment -- on the PRACTICE copy only, never the real gbmart.gold table
spark.sql(f"COMMENT ON TABLE {PRACTICE_TABLE} IS '...'")

# Column comments -- additivity-correct, matching Day 6 ILT 3 exactly
column_comments = {
    "Quantity_purchased": "...Additive -- safe to SUM across any dimension.",
    "Sales_amount":      "Revenue in INR ... Additive and safe to SUM.",
    "Actual_price":      "...Non-additive -- never SUM/AVG directly across products.",
    "Discounted_price": "...Non-additive -- derive avg. selling price as SUM(Sales_amount)/SUM(Quantity_purchased).",
    # ... plus fact_sales_sk, Payment_ID, Customer_ID, Product_ID, Order_ID, Address_ID, Time_ID
}
for column_name, comment_text in column_comments.items():
    spark.sql(f"ALTER TABLE {PRACTICE_TABLE} ALTER COLUMN {column_name} COMMENT '{comment_text}'")

Step C Verify the Comments Landed

spark.sql(f"DESCRIBE TABLE {PRACTICE_TABLE}").show(truncate=False)
spark.sql(f"DESCRIBE TABLE EXTENDED {PRACTICE_TABLE}").show(truncate=False)
What this session's notebook will NOT do: call any Genie API/SDK, or otherwise attempt to create a Genie Space from code. As of this course's design that setup is UI-only — faking it with code that would not actually work would teach the wrong lesson.
Before (Step A)After (Step C)
What a column name tells youActual_price, decimal — nothing elseSame column, plus: "non-additive, never SUM directly across products"
Can Genie safely answer "total sales"?Has to guess which of 3 decimal columns is the revenue measureKnows Sales_amount is the additive revenue measure — stated directly

Nothing about the underlying data changes between Step A and Step C — same 100 rows, same values. The only thing that changes is whether the schema can explain itself. That is the entire value of a semantic layer, and exactly what Genie's natural-language-to-SQL translation leans on.

5. Sample Questions: Bootstrapping Genie's Natural-Language Matching

A Genie Space lets you register sample questions paired with the SQL that correctly answers them, so Genie has worked examples to pattern-match against. Illustrative only — not executed in this session.

Sample questionMaps to
"What was our revenue by category last month?"SELECT category, SUM(total_revenue) FROM gbmart.gold.vw_monthly_category_sales ... GROUP BY category
"Which states generate the most revenue?"SELECT state, SUM(total_revenue) FROM gbmart.gold.vw_regional_sales GROUP BY state ORDER BY total_revenue DESC
"What is our average discount by category?"SELECT category, AVG(avg_discount_given) FROM gbmart.gold.vw_monthly_category_sales GROUP BY category
"How many orders came from each region?"SELECT state, city, total_orders FROM gbmart.gold.vw_regional_sales
Every sample question maps to one of the two already-built Gold views from Day 7 HOL 2 — not a fresh query against raw fact_sales. Genie's easiest, most reliable answers come from certified views someone already got right, not from re-deriving join and aggregation logic live, per question.

Key Takeaways

1. Genie translates natural language to SQL against a curated Genie Space.
2. Genie Spaces are set up entirely through the Databricks workspace UI — no SDK/API call creates one.
3. A semantic layer is what makes raw tables usable by something that has never seen your business before.
4. vw_monthly_category_sales and vw_regional_sales (Day 7 HOL 2) are already real semantic-layer artifacts.
5. Comments must be additivity-correct, or they actively mislead — a wrong comment is worse than no comment.
6. Every COMMENT / ALTER TABLE statement ran against a 100-row practice copy — the real gbmart.gold.fact_sales was only ever read, once, via LIMIT 100.
