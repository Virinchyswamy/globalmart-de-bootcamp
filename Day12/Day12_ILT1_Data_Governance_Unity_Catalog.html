1 The Permissions Model — One Hierarchy, Four Levels

Unity Catalog secures exactly one hierarchy, top to bottom. Every privilege sits at one of these four levels — functions (including the row-filter/masking functions below) and views sit at the same level as tables.

metastore # one per region/account -- you don't manage this
  └── gbmart CATALOG
       ├── bronze SCHEMA
       │    └── customers, orders, ... TABLE
       ├── silver SCHEMA
       │    └── customers, orders, ... TABLE
       └── gold SCHEMA
           ├── dim_customer TABLE
           ├── dim_product TABLE
           └── fact_sales TABLE

USE CATALOG/USE SCHEMA trip people up: being able to "step into" gbmart.gold doesn't let you read anything inside it — you also need SELECT on the schema or the table itself.

GRANT / REVOKE Syntax, and Inheritance

-- Give a group read access to an entire schema -- present AND future tables in it
GRANT USE CATALOG ON CATALOG main              TO `analysts`;
GRANT USE SCHEMA  ON SCHEMA  main.YOUR_SCHEMA    TO `analysts`;
GRANT SELECT      ON SCHEMA  main.YOUR_SCHEMA    TO `analysts`;

-- Narrower: only one specific table, nothing else in the schema
GRANT SELECT ON TABLE main.YOUR_SCHEMA.practice_customers TO `analysts`;

-- Take it away again -- same shape, opposite direction
REVOKE SELECT ON SCHEMA main.YOUR_SCHEMA FROM `analysts`;
Granting SELECT at this level......covers
CATALOG gbmartEvery schema and table in the whole catalog, now and later
SCHEMA gbmart.goldEvery table in gold today — and any table added next month, no new grant needed
TABLE gbmart.gold.fact_salesOnly that one table
Inheritance is the point to memorize: a grant at the schema level isn't a one-time snapshot of today's tables — it's a standing rule for whatever exists in that schema at query time, including tables nobody has built yet. The GRANT/REVOKE examples above are illustrative syntax only, shown against the practice-schema naming pattern — nothing in this notebook executes a GRANT/REVOKE against anything. The only thing actually executed against real grants is reading them, next.

Real, Read-Only: the Actual gbmart Grants

SHOW GRANTS is itself just a read. Wrapped in try/except because this demo account may not own gbmart — a permission error is a normal Unity Catalog boundary, not a bug.

CATALOG = "gbmart"

grant_checks = [
    ("CATALOG gbmart",                f"SHOW GRANTS ON CATALOG {CATALOG}"),
    ("SCHEMA gbmart.gold",           f"SHOW GRANTS ON SCHEMA {CATALOG}.gold"),
    ("TABLE gbmart.gold.fact_sales", f"SHOW GRANTS ON TABLE {CATALOG}.gold.fact_sales"),
]

for label, stmt in grant_checks:
    print(f"--- SHOW GRANTS ON {label} ---")
    try:
        spark.sql(stmt).display()
    except Exception as e:
        print(f"Could not read grants on {label} -- normal Unity Catalog boundary, not a bug. ({str(e)[:120]})")

2 Row-Level Security — Row Filters

A row filter is a SQL function returning BOOLEAN — a row is visible only if the function returns true for it. Attach it once with ALTER TABLE ... SET ROW FILTER, and every reader of that table — any tool, any notebook, any dashboard — is filtered automatically, with zero application-side filtering code.

-- Define: returns true only for rows this filter should let through
CREATE OR REPLACE FUNCTION your_catalog.your_schema.region_filter(region STRING)
RETURNS BOOLEAN
RETURN region = 'US';

-- Attach: from now on, EVERY reader of this table only sees region = 'US' rows
ALTER TABLE your_catalog.your_schema.your_table
SET ROW FILTER your_catalog.your_schema.region_filter ON (region);

Production versions are usually role-aware, so different groups see different slices of the same table:

-- Illustrative only -- what a role-aware version looks like in production
CREATE OR REPLACE FUNCTION your_catalog.your_schema.region_filter(region STRING)
RETURNS BOOLEAN
RETURN CASE
    WHEN is_account_group_member('global_admins') THEN true      -- see everything
    WHEN is_account_group_member('us_sales_team') THEN region = 'US'
    ELSE false
END;
The hands-on demo below uses the simpler fixed-literal version (region = 'US') on purpose — deterministic no matter which account runs it, exactly what a repeatable classroom demo needs.

3 Column-Level Security — Masking

A masking function is the column equivalent: instead of true/false per row, it returns a transformed value of the same type for one column. Attach with ALTER TABLE ... ALTER COLUMN ... SET MASK.

-- Define: returns a transformed value, same type as the column (STRING here)
CREATE OR REPLACE FUNCTION your_catalog.your_schema.email_mask(email STRING)
RETURNS STRING
RETURN CONCAT('***', SUBSTRING(email, INSTR(email, '@'), LENGTH(email)));

-- Attach to one column
ALTER TABLE your_catalog.your_schema.your_table
ALTER COLUMN email SET MASK your_catalog.your_schema.email_mask;

And, again, realistic production masks are role-aware — full value for one role, redacted for everyone else, same column, same table:

-- Illustrative only -- full email for one role, masked for everyone else
RETURN CASE
    WHEN is_account_group_member('customer_support') THEN email        -- full value
    ELSE CONCAT('***', SUBSTRING(email, INSTR(email,'@'), LENGTH(email))) -- redacted
END;
The hands-on demo runs the simpler unconditional version — masked for absolutely everyone, including you — for the same determinism reason as the row filter. Swapping in the CASE/is_account_group_member(...) shape is the only change needed to make it role-aware in production.

Why a Practice Table, Not gbmart

Every function we actually create and every table alteration we actually run targets a table we create ourselves in main.YOUR_SCHEMA — never anything already in the shared Gold layer. Two concrete reasons:

1. It's disruptive to everyone else, immediately. The instant a row filter/mask is attached to a shared table, every other student's and the instructor's next query is filtered/masked too — mid-class, with no warning.
2. It isn't a quiet, reversible change. Unlike a SELECT, attaching a row filter or mask is a standing metadata change. Undoing it needs another explicit statement — it doesn't expire on its own.
Compute note: row filters and column masks are enforced on supported compute only — a SQL warehouse, a shared-access-mode cluster, or a sufficiently recent single-user runtime. If your cluster doesn't support them, the demo's ALTER/SELECT cells print a clear fallback message instead of failing — an expected compute limitation, not a bug.

Hands-On: Build It on a Practice Table

# --- setup: isolates this demo from the real gbmart catalog ----------------
YOUR_SCHEMA = "main.YOUR_SCHEMA"  # replace with e.g. main.governance_lab if reusing later
spark.sql(f"CREATE SCHEMA IF NOT EXISTS {YOUR_SCHEMA}")

PRACTICE_TABLE  = f"{YOUR_SCHEMA}.practice_customers"
ROW_FILTER_FUNC = f"{YOUR_SCHEMA}.us_region_filter"
MASK_FUNC        = f"{YOUR_SCHEMA}.email_mask"

# --- clean slate first -- makes Run All safe more than once ----------------
for stmt in [f"ALTER TABLE {PRACTICE_TABLE} DROP ROW FILTER",
         f"ALTER TABLE {PRACTICE_TABLE} ALTER COLUMN email DROP MASK",
         f"DROP TABLE IF EXISTS {PRACTICE_TABLE}",
         f"DROP FUNCTION IF EXISTS {ROW_FILTER_FUNC}",
         f"DROP FUNCTION IF EXISTS {MASK_FUNC}"]:
    try: spark.sql(stmt)
    except Exception: pass  # expected on the first run

# --- build: 6 rows, 3 regions, one email column -----------------------------
spark.sql(f"CREATE TABLE {PRACTICE_TABLE} (customer_id INT, customer_name STRING, region STRING, email STRING) USING DELTA")
spark.sql(f"INSERT INTO {PRACTICE_TABLE} VALUES (1,'Asha Rao','US','asha.rao@example.com'), ... ")
spark.table(PRACTICE_TABLE).orderBy("customer_id").display()  # baseline: all 6 rows, full emails
# --- Step 1: attach the row filter (region = 'US') --------------------------
try:
    spark.sql(f"CREATE OR REPLACE FUNCTION {ROW_FILTER_FUNC}(region STRING) RETURNS BOOLEAN RETURN region = 'US'")
    spark.sql(f"ALTER TABLE {PRACTICE_TABLE} SET ROW FILTER {ROW_FILTER_FUNC} ON (region)")
except Exception as e: print(f"Could not attach -- check compute access mode. ({str(e)[:120]})")

spark.table(PRACTICE_TABLE).orderBy("customer_id").display()  # now: only the 3 region='US' rows
# --- Step 2: attach the email mask ('***' before '@') -----------------------
try:
    spark.sql(f"CREATE OR REPLACE FUNCTION {MASK_FUNC}(email STRING) RETURNS STRING RETURN CONCAT('***', SUBSTRING(email, INSTR(email,'@'), LENGTH(email)))")
    spark.sql(f"ALTER TABLE {PRACTICE_TABLE} ALTER COLUMN email SET MASK {MASK_FUNC}")
except Exception as e: print(f"Could not attach -- same compute requirement. ({str(e)[:120]})")

spark.table(PRACTICE_TABLE).orderBy("customer_id").display()  # now: 3 rows, email masked too

4 Lineage — Two Different (Related) Things

"Lineage" gets used loosely, but this session means two specific, different things — a common trip-up:

DESCRIBE HISTORYUnity Catalog Lineage (Catalog Explorer)
ScopeOne table's own version timelineCross-object graph: tables, notebooks, jobs, dashboards
Answers"What changed in this table, and when?""What fed this table, and what consumes it downstream?"
Captured byThe Delta transaction log — every commitUnity Catalog observing every query that reads/writes across tables
GranularityTable + versionTable-level and column-level
How you see itSQL: DESCRIBE HISTORY <table>Catalog Explorer's Lineage tab, or system.access.table_lineage/column_lineage
Both are automatic — neither needs manual tagging — but they are not the same feature. DESCRIBE HISTORY is queryable right here in a notebook; the cross-table lineage graph is primarily a Catalog Explorer UI experience.

Real, Read-Only: Version History on gbmart.gold.dim_customer

dim_customer is SCD2 (Day 6/10) — genuinely interesting history, since Day 10's SCD2 MERGE demo added versions on top of Day 6's initial build.

HISTORY_TABLE = f"{CATALOG}.gold.dim_customer"  # SCD2 -- has real version history

try:
    (spark.sql(f"DESCRIBE HISTORY {HISTORY_TABLE}")
        .select("version", "timestamp", "operation", "userName")
        .orderBy("version", ascending=False).limit(10).display())
except Exception as e:
    print(f"Could not read history -- lacks SELECT, or table not present. ({str(e)[:120]})")

Bonus (Optional) — Lineage as a Queryable System Table

If an account admin has enabled the system schema, system.access.table_lineage/column_lineage expose lineage as queryable metadata — 100% read-only. Wrapped in try/except since this is an account-level setting the demo account may not have; Catalog Explorer's Lineage tab always works regardless.

try:
    (spark.table("system.access.table_lineage")
        .filter("source_table_full_name LIKE 'gbmart.%' OR target_table_full_name LIKE 'gbmart.%'")
        .limit(10).display())
except Exception as e:
    print(f"Not enabled / no permission -- Catalog Explorer's Lineage tab works regardless. ({str(e)[:100]})")

Key Takeaways

✓One hierarchy — metastore → catalog → schema → table/view/function — and grants at a higher level are inherited by everything below, including objects created later.
✓GRANT/REVOKE syntax is identical for users, groups, and service principals.
✓A row filter (BOOLEAN function + SET ROW FILTER) and a mask (transform function + SET MASK) apply to every reader automatically — no application-side filtering code.
✓DESCRIBE HISTORY (one table's version timeline) and Catalog Explorer lineage (the cross-table/notebook/job graph) are both automatic, but answer different questions.
✓Never attach a row filter/mask or change a grant on a real shared table you don't own outright — practice on your own schema first.
