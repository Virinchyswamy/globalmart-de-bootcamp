Why Storage Format Matters

Looking for one fact in a stack of loose paper means reading every page. Looking it up in a book with an index means turning straight to the right page. The file format is the difference between the stack and the index.

Format Determines

  • How much data is read (column pruning, row skipping)
  • How fast it reads (compression, encoding)
  • What guarantees you get (ACID, schema enforcement)
  • How much storage you use (compression ratio)
Bronze orders: 1.4M rows, 9 columns
Query: WHERE OrderDate = '2026-06-15'

CSV (no pruning, no stats):
  → reads ALL 9 columns, ALL 1.4M rows
  → 100% of data scanned

Parquet (columnar, compressed):
  → reads only OrderDate column
  → ~11% of data scanned

Delta + partitioning (partition pruning):
  → reads ONLY the matching partition
  → maybe 0.1% of data scanned

Format choice is a multiplier on every query cost.

Use Delta for ALL Bronze, Silver, and Gold tables. No exceptions. Delta = Parquet performance + ACID + time travel + schema evolution.

CSV Is an Ingestion Format, Not a Storage Format

✅ CSV Is Good For

Receiving files from external systems — suppliers, APIs, one-off exports.

❌ CSV Is Bad For

  • No schema enforcement — OrderID could be "ORDER-001", "001", or 1
  • Every query reads every column
  • No statistics — Spark can't skip rows
  • No transactions — partial writes leave corrupt data

Parquet — the Columnar Standard

  • ✅ Great for read-heavy analytics; column pruning; compressed by default
  • ❌ No ACID — two concurrent writes can corrupt data
  • ❌ No time travel, no easy schema evolution
  • ❌ Updates require rewriting entire files

Delta Lake — Parquet + a Transaction Log

Delta = Parquet files + _delta_log/ folder

_delta_log/:
  00000000000000000000.json  ← Version 0: initial table creation
  00000000000000000001.json  ← Version 1: first write
  00000000000000000002.json  ← Version 2: OPTIMIZE run
  ...
  00000000000000000010.checkpoint.parquet  ← periodic checkpoint

Each log entry records:
  - Which files were added / removed
  - Min/max statistics per column per file
  - Schema at this version
  - Who made the change and when

Delta = Parquet performance + ACID + time travel + schema evolution. That log is what makes every guarantee in this session possible.

Why Delta Is Right for Bronze — ACID & Time Travel

1. ACID Guarantees

Scenario: Auto Loader is mid-write when the cluster dies.

Without ACID: a partial file is written — 50,000 rows half-written, no way to know which made it. With Delta: the uncommitted transaction is treated as if it never happened; the next run restarts cleanly from checkpoint.

2. Time Travel

SELECT COUNT(*) FROM gbmart.bronze.orders
VERSION AS OF 5;

SELECT * FROM gbmart.bronze.orders
TIMESTAMP AS OF '2026-06-10 12:00:00';

Why Delta Is Right for Bronze — Schema Evolution & Data Skipping

3. Schema Evolution

df.write.format("delta").mode("append") \
    .option("mergeSchema", "true") \
    .saveAsTable("gbmart.bronze.products")
# New source column? Bronze table gains it automatically.

4. File Statistics — Data Skipping

WHERE order_date = '2026-06-15'

File A: min=06-01, max=06-14 → SKIP
File B: min=06-15, max=06-20 → READ
File C: min=06-21, max=06-30 → SKIP

Only File B is read — automatic with Delta, no configuration needed.

Section 2 — Layout

Partitioning & Partition Pruning

How you physically lay data out on disk so queries can skip what they don't need.

What Is Partitioning?

Like filing paper invoices into monthly folders instead of one giant pile — if someone asks for June's invoices, you grab one folder instead of searching everything.

Partitioning physically splits a table into sub-folders based on a column's value.

Without partitioning:
  part-00000.parquet  ← all 1.4M rows, one folder
  part-00001.parquet

With partitioning by ingestion_date:
  _ingested_at=2026-06-13/
    part-00000.parquet
  _ingested_at=2026-06-14/
    part-00000.parquet
  _ingested_at=2026-06-15/
    part-00000.parquet

Partition Pruning in Action

Query: WHERE ingestion_date = '2026-06-15'

With partitioning:
  Spark finds ingestion_date=2026-06-15/
  → reads ONLY that folder
  → skips every other date folder

Result: 30 days of data → reads 1/30 = 3.3%
from pyspark.sql.functions import to_date, current_timestamp

df = df.withColumn("ingestion_date", to_date(current_timestamp()))

df.write \
    .format("delta") \
    .mode("append") \
    .partitionBy("ingestion_date") \
    .saveAsTable("gbmart.bronze.orders")

Choosing Partition Columns — 3 Criteria

  1. High query filter frequency — it's in your WHERE clause almost every time
  2. Low-to-medium cardinality — not too many unique values
  3. Evenly distributed — data spread roughly equally across partitions
ColumnGood?Reason
ingestion_dateYesMost queries filter by date; natural daily partition
order_channelYes3–5 values, low cardinality
customer_idNoTens of thousands of values — tiny partitions
order_idNoNever partition on a primary key

The Over-Partitioning Trap

Partitioning by OrderID on 1.4 million orders creates 1.4 million folders, each holding one file with one row. That's not organisation — that's a filing cabinet with one sheet of paper per drawer.

Problems

  • Delta transaction log tracks 1.4M files → slow to open table
  • 1 Spark task per partition → 1.4M tasks for a simple COUNT
  • Listing 1.4M folders on ADLS takes minutes

Rule of thumb: minimum ~1 GB of data per partition value to justify partitioning at all.

For GlobalMart's ~200 MB orders dataset, partitioning by date across 365 days = ~550 KB per partition — too small. Better: no partitioning + Z-ORDER instead.

Z-ORDER BY — Clustering Without Partitioning

BEFORE OPTIMIZE ... ZORDER BY (customer_id):
  File A: customer_id = C001, C045, C200, C999 (random mix)
  File B: customer_id = C002, C100, C500, C700 (random mix)
  Query WHERE customer_id = 'C001' → must scan both files

AFTER OPTIMIZE ... ZORDER BY (customer_id):
  File A: customer_id = C001 – C250  (low range)
  File B: customer_id = C251 – C500  (mid range)
  Query WHERE customer_id = 'C001' → only File A read

Z-ORDER co-locates related rows within files — no sub-folders, works with high-cardinality columns like customer_id or order_id.

Z-ORDER vs Partitioning

PartitioningZ-ORDER
Creates sub-foldersYesNo

OPTIMIZE gbmart.bronze.orders
ZORDER BY (customer_id, order_date);

Liquid Clustering (Delta 3.0+)

You partitioned by order_channel. Six months later the business starts filtering by category instead — changing partition columns on a 10 TB table means hours of rewrite.

Liquid Clustering replaces both partitioning and Z-ORDER with a unified, adaptive approach — no full rewrite needed to change clustering columns.

CREATE TABLE gbmart.bronze.orders
CLUSTER BY (customer_id, order_date);

-- Change any time, no rewrite:
ALTER TABLE gbmart.bronze.orders
CLUSTER BY (order_channel, order_date);

-- Same OPTIMIZE command, no ZORDER needed:
OPTIMIZE gbmart.bronze.orders;

Liquid Clustering vs Z-ORDER vs Partitioning

PartitioningZ-ORDERLiquid Clustering
Column changeFull rewriteEasyEasy
Small file riskHighLowLow
IncrementalNoNoYes
Best forSimple date splits, large tablesMedium cardinality columnsMost new tables in Databricks

Recommendation: use Liquid Clustering for new tables. For older tables or simple date splits on very large tables, partitioning still works well.

Layout Decision Framework

What is my daily data volume per partition?
      │
      ├── < 1 GB per day
      │       → DO NOT partition
      │       → Use Z-ORDER or Liquid Clustering on query columns
      │
      └── > 1 GB per day
              │
              ├── Date-based, low cardinality query pattern
              │       → Partition by date + Z-ORDER secondary columns
              │
              └── Multi-dimensional / evolving query pattern
                      → Use Liquid Clustering
Section 3 — Keeping It Fast

Performance Levers

Small files, caching, joins, and safe cleanup — the levers you pull once data is already laid out.

The Small File Problem

Streaming writes every 30 seconds create one small file per trigger. After 24 hours: 1,440 files × 50 KB = 72 MB total — but 1,440 storage opens and 1,440 Spark tasks just to read it.

Why Cloud Storage Hates Small Files

  • ADLS is optimised for large sequential reads (128 MB – 1 GB)
  • Each small-file open() has network round-trip latency
  • Listing thousands of files is an expensive metadata operation
SymptomWhat You See
Slow queries, small dataA 100 MB table takes 30 seconds to scan
High task count1,000+ tasks for a simple COUNT
Slow table openspark.table(...) takes a long time to start
Delta log bloat_delta_log/ has thousands of JSON files

OPTIMIZE — Manual Compaction

BEFORE: 1,440 files × 50 KB = 72 MB
AFTER:  1 file × 72 MB
OPTIMIZE gbmart.bronze.orders;

OPTIMIZE gbmart.bronze.orders
ZORDER BY (customer_id, order_date);

What OPTIMIZE Does NOT Do

  • ❌ Does not delete the old small files — they're marked removed in the log, not deleted
  • ❌ Does not free up storage — that's VACUUM's job
  • ❌ Does not change the data — same rows, reorganised into larger files

AUTO OPTIMIZE — Automatic Compaction

SettingWhat It Does
optimizeWriteBefore writing, shuffles data to target ~128 MB per output file — prevents small files at write time
autoCompactAfter a write completes, runs a background OPTIMIZE — asynchronous, doesn't slow the write
ALTER TABLE gbmart.bronze.orders SET TBLPROPERTIES (
    'delta.autoOptimize.optimizeWrite' = 'true',
    'delta.autoOptimize.autoCompact'   = 'true'
);

Recommendation for Bronze streaming tables: enable both. For Z-ORDER, still schedule a daily manual job — AUTO OPTIMIZE never Z-ORDERs.

Caching — When It Helps, When It Doesn't

bronze_df = spark.table("gbmart.bronze.orders")
bronze_df.cache()
bronze_df.count()          # triggers caching
bronze_df.count()          # reads from memory — fast
bronze_df.unpersist()      # always free memory when done

Databricks Disk Cache is a second, automatic layer — caches raw Parquet data on local SSDs, transparent, survives across jobs on the same cluster.

ScenarioCache?
Small reference table, joined repeatedlyYes
Large Bronze table, single scanNo
Dimension table across many Gold queriesYes
Streaming sourceNo

Broadcast Joins

Large: gbmart.bronze.orders (1.4M rows)
Small: gbmart.gold.dim_payment_method (5 rows)

Default sort-merge join:
  1. Shuffle ALL of orders across network
  2. Shuffle the small table too
  3. Sort both sides, then merge
  → expensive for no reason
from pyspark.sql.functions import broadcast

result = orders_df.join(
    broadcast(dim_payment_method_df),
    on="payment_method_id", how="left"
)
# Small table shipped to every worker once;
# orders_df never shuffles. 100x+ faster.

Use broadcast when one table is under ~100 MB and reused repeatedly — lookup tables like dim_payment_method, dim_date, dim_product.

VACUUM — Cleaning Up Old Files

OPTIMIZE marks old files "removed" in the log but doesn't delete them. VACUUM physically deletes them to free storage.

VACUUM gbmart.bronze.orders RETAIN 168 HOURS;  -- 7 days
VACUUM gbmart.bronze.orders RETAIN 168 HOURS DRY RUN;

Never run RETAIN 0 HOURS — it deletes all previous version files immediately and permanently disables time travel. 7 days is the safe minimum: Delta time travel reads old file versions, and VACUUM-ing files still referenced by recent versions breaks it.

Typical schedule: daily OPTIMIZE (compaction + Z-ORDER), weekly VACUUM RETAIN 168 HOURS.

Unified Decision Framework

PERFORMANCE PROBLEM?
      │
      ├── Query slow on a large table
      │     ├── Many small files?      → OPTIMIZE + AUTO OPTIMIZE
      │     ├── Filtering by a column? → ZORDER BY, or Liquid Clustering
      │     ├── Joining a small table? → broadcast()
      │     └── Repeated scans?        → .cache()
      │
      ├── Storage cost too high → VACUUM RETAIN 168 HOURS
      │
      └── New table layout
            ├── < 1 GB/day               → Z-ORDER or Liquid Clustering
            ├── > 1 GB/day, date-filtered → partition + ZORDER
            └── Multi-dimensional         → Liquid Clustering
Recap

Key Takeaways

Always Delta

For Bronze, Silver, and Gold — no exceptions. Partitioning helps date columns on large tables; over-partitioning causes small files.

Z-ORDER / Liquid Clustering

File-level skipping for high-cardinality columns without folder explosion. Liquid Clustering is the modern default.

Cache, Broadcast, VACUUM

Cache small reused tables. Broadcast joins under ~100 MB. VACUUM weekly — never below 7-day retention.
