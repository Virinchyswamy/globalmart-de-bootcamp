Section 1

What Problem Are We Trying to Solve?

Before learning any tool, it helps to understand exactly what problem that tool exists to solve. Here's the problem.

📦 A small dataset is easy

A spreadsheet with 500 rows opens instantly, no matter how you query it. Excel just loads the whole thing into memory and you're done. Nobody thinks about "storage strategy" for 500 rows.

🏔️ A huge dataset is a different world

Now imagine 5 million rows, spread across a year of daily files, several gigabytes total. Opening "the whole thing" every time you ask a question stops being instant — it can take minutes, and you're paying for that compute every single time.

Analogy: Finding a name in a 1-page contact list is instant — just glance at it. Finding a name in a 50-volume phone book by reading every page front to back is a completely different problem, even though it's "the same task." At scale, how the data is organized starts to matter more than the task itself.

A very brief word on Spark

Apache Spark is the engine that reads, transforms, and writes large datasets by splitting the work across many machines at once, in parallel. We won't go deep into Spark's internals here — just know that everything in this page (storage formats, partitioning, performance levers) exists specifically to make Spark's job faster and cheaper when the data gets big.

Section 2

Storage Formats

The very first lever: how is the data physically written to disk? Click each format below to expand it.

📄

CSV Comma-Separated Values

▾
What it is

Plain text, one row per line, values separated by commas. No types, no compression, no structure beyond that.

How it stores data
OrderID,Category,Sales
ORD-001,Electronics,199.99
ORD-002,Furniture,89.50
Analogy: A CSV is a handwritten shopping list — readable by anyone, but there's no way to quickly find "just the prices" without reading every line.
Advantages
  • Universally readable — Excel, any language, any system
  • Simple to produce and inspect by eye
Disadvantages
  • No compression — every character takes full space
  • No schema — every read has to guess or be told types
  • Row-based — can't skip columns you don't need
Real-world use case

Landing raw exports from a source system into Bronze — never a working format after that.

Not for storageGood for exchange

🧾

JSON JavaScript Object Notation

▾
What it is

Text format where every record carries its own field names — self-describing, and able to represent nested/variable structure that CSV can't.

How it stores data
{"OrderID":"ORD-001","Category":"Electronics","Sales":199.99}
{"OrderID":"ORD-002","Category":"Furniture","Sales":89.50}
Analogy: JSON is like a shopping list where you re-write "Item:" and "Price:" next to every single entry — clearer, but a lot more paper used for the same information.
Advantages
  • Self-describing — field names travel with every record
  • Handles nested/variable-shape data CSV can't
Disadvantages
  • Repeats field names on every record — usually larger than the equivalent CSV
  • Still row-based, still no compression by default
Real-world use case

API responses, event/webhook payloads — anything semi-structured landing in Bronze.

Not for storageGood for semi-structured exchange

🗄️

Parquet Columnar binary format

▾
What it is

A binary, columnar format — instead of storing complete rows one after another, it stores every column's values together, then compresses each column separately.

Why Parquet is columnar

If a query only needs 2 of your 25 columns, a columnar file lets Spark read only those 2 columns off disk and skip the other 23 entirely. A row-based format has to read every column of every row regardless.

Analogy: Row-based storage is a stack of index cards, one person per card, every field written on it. Columnar storage is a spreadsheet with one long column per field — if you only want everyone's "City," you read one column top to bottom instead of flipping through every card.
Advantages
  • Column pruning — skip irrelevant columns entirely
  • Compresses far better (similar values sit together)
  • Stores its own schema/types — no guessing on read
Disadvantages
  • Not human-readable (binary)
  • No transaction log — no ACID guarantees, no time travel, no safe concurrent writes
Real-world use case

Any analytical dataset where you don't need Delta's transactional guarantees.

Fast readsSmall on disk

🔺

Delta Lake Parquet + transaction log

▾
What it is

The same Parquet files as above, plus a folder called _delta_log/ that records every write as a numbered, atomic commit.

Why Delta = Parquet + transaction log

Parquet alone has no memory of its own history — if two writers touch it at once, or a write fails halfway, there's no safety net. The transaction log gives Delta ACID transactions (all-or-nothing writes), time travel (query any past version), and reliable concurrent reads/writes — none of which plain Parquet can do.

Analogy: Parquet is the filing cabinet. Delta is the same filing cabinet plus a logbook by the door recording every single time a folder was added, changed, or removed — so you can always reconstruct exactly what the cabinet looked like at any point in time.
Advantages
  • Everything Parquet has, plus:
  • ACID transactions — safe concurrent writes
  • Time travel — query/restore any past version
  • UPDATE/DELETE/MERGE support
  • Schema enforcement + safe schema evolution
Disadvantages
  • Slightly more overhead than raw Parquet for the log itself
  • Best supported inside Databricks/Spark ecosystems
Real-world use case

Bronze, Silver, and Gold — the default table format for essentially everything in a modern lakehouse.

Quick Check

Storage Formats Quiz

1. Why is Parquet usually faster to query than CSV, even for a query that only needs 2 out of 25 columns?

Parquet files are always stored on faster disks
Parquet automatically deletes unused columns
Parquet is columnar, so Spark can read only the 2 needed columns and skip the rest

2. What does Delta add on top of plain Parquet?

A completely different file format for the actual data
A transaction log (_delta_log/) giving ACID transactions and time travel
Automatic translation into CSV for BI tools

3. Why is JSON often larger on disk than the equivalent CSV, despite being "more structured"?

Every record repeats its field names, with no compression to offset it
JSON always stores data twice for safety
JSON requires a schema file stored separately
Section 3

Partitioning Strategy

Storage format controls how each file is encoded. Partitioning controls which files exist in the first place — and where.

What partitioning means

Partitioning physically splits a table's data into separate folders based on the value of one or more columns. All rows where Year=2024 live in a folder literally named Year=2024/ — not just logically grouped, actually separate folders on disk.

Folder structure

📁 sales_partitioned/
  ├── Year=2022/
  │    ├── Month=1/ part-00000.parquet
  │    └── Month=2/ part-00000.parquet
  ├── Year=2023/ ... 12 Month= folders
  ├── Year=2024/
  │    ├── Month=1/ ... Month=12/
  ├── Year=2025/ ... 12 Month= folders
  └── Year=2026/ ... 12 Month= folders

✅ Good partition columns

  • Low-to-moderate cardinality — tens to low hundreds of distinct values
  • Year, Month — a handful of values, queries filter on them constantly
  • Country — only 6 distinct values in our dataset

❌ Bad partition columns

  • High cardinality — thousands+ distinct values
  • CustomerID, OrderID — one tiny folder per value, recreates the small-files problem
  • Anything rarely used in a WHERE clause — no pruning benefit to justify the folder overhead

Common patterns

📅 Date partitioning

partitionBy("Year", "Month") — the most common pattern. Most BI queries filter on a recent date range, so this is almost always a safe default for fact tables.

🌍 Country partitioning

partitionBy("Country") — useful when queries are commonly scoped to one region/market at a time, and the column has few distinct values.

🧱 Multi-level partitioning

partitionBy("Country", "Year") creates Country=.../Year=.../ nested folders — powerful, but multiply the distinct-value counts together; too many levels recreates the small-files problem fast.

Quick Check

Partitioning Quiz

1. Why is CustomerID usually a bad partition column?

Customer IDs are usually stored as text, and text can't be used for partitioning
It has extremely high cardinality — one folder per customer creates huge numbers of tiny folders/files
Spark doesn't allow partitioning on ID columns

2. A query filters WHERE Year = 2024 AND Month = 6 on a table partitioned by Year and Month. What happens?

Spark reads every folder, then filters the rows afterward
Spark can't use partition folders for multi-column filters
Spark lists only the Year=2024/Month=6/ folder and skips every other folder entirely
Section 4

Performance Levers

Storage format and partitioning get you most of the way. These three levers tune the rest.

File Sizing

Every file Spark touches has fixed overhead — listing it, opening it, scheduling a task for it. Too many small files means paying that overhead over and over for very little actual data each time. Too few, huge files means poor parallelism — not enough pieces of work to spread across all your machine's cores. The sweet spot is roughly 128MB – 1GB per file.

❌ Small Files Problem

200 tiny files — huge per-file overhead relative to the actual data in each one

✅ Right-Sized Files

A handful of ~128MB–1GB files — good parallelism, low overhead

Caching

Spark is lazy — nothing actually runs until an action like .count() forces it. Every action normally recomputes from scratch, including re-reading from storage. .cache() tells Spark: the first time this DataFrame is computed, keep the result in memory so any later action reuses it instead of recomputing.

Without cache

Query 1 → read from disk
Query 2 → read from disk again
Query 3 → read from disk again

With .cache()

Query 1 → read from disk, store in memory
Query 2 → read from memory (fast)
Query 3 → read from memory (fast)

Clustering

Clustering (ZORDER, or Liquid Clustering) co-locates related rows within files, instead of splitting them into separate folders like partitioning does.

Partitioning

Creates physical folders. Coarse-grained — use for low-cardinality columns you always filter on (Year, Month).

Clustering

Reorders data within existing files. Fine-grained — use for higher-cardinality columns you often filter on but that would make terrible partition folders (CustomerID, Category).

Quick Check

Performance Levers Quiz

1. What's the main downside of having thousands of tiny files instead of a handful of right-sized ones?

Fixed per-file overhead (listing/opening/scheduling) ends up dominating the actual work
Small files take up more disk space than large ones for the same data
Spark can only read files larger than 100MB

2. When is caching a DataFrame the right call?

Always — cache every DataFrame you create, just in case
When the same DataFrame will be queried/reused multiple times in one session
Only when the DataFrame is smaller than 1MB

3. What's the key difference between partitioning and clustering?

They're the same thing with different names
Clustering is always faster, so partitioning is never needed
Partitioning creates separate folders (coarse); clustering reorders data within files (fine-grained), without exploding folder count

1️⃣ Get the format right first

Columnar Parquet/Delta beats row-based CSV/JSON before you've touched partitioning at all — column pruning alone changes everything.

2️⃣ Then organize it

Partition by what you always filter on. Cluster/Z-ORDER what you often filter on but shouldn't be a folder.

3️⃣ Then tune performance

Keep files ~128MB–1GB. Cache what gets reused. Every lever compounds with the others.
