Partitioning & Partition Pruning

Partitioning physically splits a table into sub-folders by column value. A query filtering on that column reads only the matching folder — partition pruning.

ColumnGood Partition Column?Reason
ingestion_dateYesLow cardinality, filtered often
order_channelYes3–5 values, low cardinality
customer_idNoTens of thousands of values — tiny partitions
order_idNoNever partition on a primary key
The over-partitioning trap: minimum ~1 GB of data per partition value to justify it. Below that, use Z-ORDER or Liquid Clustering instead — no folders, no small-file explosion.

The Small File Problem

Streaming writes create many tiny files over time — each one costs a storage-layer open() call and a Spark task, regardless of how little data it holds.

OPTIMIZECompacts many small files into few large ones. Does NOT free storage — old files are marked removed, not deleted.
AUTO OPTIMIZEoptimizeWrite prevents small files at write time; autoCompact compacts after writing, in the background.
VACUUMPhysically deletes the files OPTIMIZE marked as removed. Never run RETAIN 0 HOURS — permanently kills time travel.

Unified Decision Framework

Small files? → OPTIMIZE (fix) + AUTO OPTIMIZE (prevent) Filtering by column? → ZORDER BY, or Liquid Clustering Joining small table? → broadcast() Repeated scans? → .cache() Storage cost high? → VACUUM RETAIN 168 HOURS New table, <1GB/day? → Liquid Clustering, no partitioning New table, >1GB/day, date-filtered? → partition + ZORDER secondary columns
