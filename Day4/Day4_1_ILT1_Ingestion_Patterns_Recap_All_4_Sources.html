Wait — Is It 2 Sources or 4?

You'll hear this session nicknamed "all 4 sources." Here's a simple way to think about why that's not the same as "4 systems."

The Supplier-Crate Analogy

A restaurant has one supplier who delivers everything in 4 separate crates: produce, meat, dairy, dry goods. You wouldn't say the restaurant has "4 suppliers" — it has one supplier, delivering across four crates.

That's GlobalMart's ADLS side: one delivery mechanism (Auto Loader watching one external location), four flat files landing in it — products, customers, addresses, payments. Four files, one pathway.

The confirmed architecture: exactly two real systems feed GlobalMart's Bronze layer — Postgres (Supabase) and ADLS. "4" only ever refers to file count, never to system count.

GlobalMart's Two Real Pathways

Pathway 1 — Postgres (Supabase) via Lakeflow Connect

  • Tables: orders, order_items
  • Mechanism: query/cursor-based capture (cursor: updated_at)
  • Captures deletes: No — the one gap of this mode
  • Built: Day 2 HOL 1

Pathway 2 — ADLS File Drops via Auto Loader

  • Tables: products, customers, addresses, payments
  • Mechanism: cloudFiles streaming source
  • Exactly-once via: checkpoint
  • Built today — Day 4 HOL 1

Why only two? GlobalMart's production footprint is simple on purpose: one OLTP database for transactional data, and flat files for everything suppliers/ops teams hand off in bulk.

Pathway 1

Postgres (Supabase) via Lakeflow Connect CDC

The transactional core — every order and order line item is written here first, and changes must be captured continuously.

The Ingestion Challenge: Why Not Just Query Postgres?

Imagine tracking changes to a 500-page diary by re-reading the entire diary every hour just to find what's new. Slow — and if a page gets torn out (a delete), you'd never notice.

That's a Plain Query Against Postgres

  • Postgres is OLTP — optimised for fast writes, not bulk reads
  • Querying millions of rows every hour kills performance
  • We need changes only — not the whole table, every time
  • WHERE updated_at > last_run also misses deletes entirely

The fix: a managed pipeline that re-queries just the cursor column on a schedule instead of you hand-rolling the watermark script. That's what Lakeflow Connect automates for GlobalMart's real orders/order_items pipeline — still cursor-based under the hood, just managed for you (Lakeflow Connect can also read the WAL directly in a different mode — Day 2 HOL 2 teaches that mode by hand — but it's not what GlobalMart's real pipeline runs).

The Mechanism — Query/Cursor-Based Capture

Supabase PostgreSQL
      │
      ▼  Lakeflow Connect queries WHERE updated_at > last_seen_value
Lakeflow Connect (managed, production) — orders_data_ingestion_cdc
      │
      ▼  INSERT / UPDATE upserted (history tracking: Off / SCD1)
<your-catalog>.bronze.orders , <your-catalog>.bronze.order_items

Key Concepts (Recap from Day 2)

  • Cursor column — the column re-queried each run to find what changed; GlobalMart's real pipeline uses updated_at
  • Lakeflow Connect re-queries the source table and lands upserted rows straight into Bronze — no manual scheduling
  • Lakeflow Connect can also run log-based (reads the WAL directly, does catch deletes) — but GlobalMart's real pipeline is cursor-based, so it cannot detect hard deletes
  • Each row lands upserted (SCD1, latest state) — no discrete change-event log, unlike log-based CDC

Pathway 2

ADLS File Drops via Auto Loader

Reference and enrichment data — not live transactions — landing periodically as flat files.

The Ingestion Challenge: Files, Not a Live Feed

Four flat files land in raw-data/ at unpredictable times: products.csv, customers.csv, addresses.csv, payments.csv.

What Makes This Hard

  • Files land at unpredictable times
  • Must process each file exactly once — no duplicates
  • Schema can evolve (a supplier adds a column)
  • Volume varies wildly file to file
raw_stream = (
    spark.readStream
    .format("cloudFiles")
    .option("cloudFiles.format", "csv")
    .option("cloudFiles.schemaEvolutionMode", "addNewColumns")
    .load(f"{EXTERNAL_LOCATION}/products/")
    .withColumn("_ingested_at", current_timestamp())
)

What Makes Auto Loader Special

Without Auto Loader (plain read loop)

  • Run 1: reads products.csv → 12,000 rows
  • Run 2: reads products.csv again → 12,000 duplicate rows
  • Every run re-processes every file

With Auto Loader (cloudFiles)

  • Run 1: reads products.csv → checkpoint records it
  • Run 2: sees it in checkpoint → skip; new file → process only that
  • Zero duplicates, exactly-once delivery

Trigger modes: availableNow=True processes pending files then stops (what GlobalMart uses for periodic drops); processingTime="30 seconds" runs continuously.

Why Not APIs or Neo4j? (Day 3 Side-Explorations)

If you've heard GlobalMart described as having "4 source systems" — Postgres, a REST API, Neo4j, and ADLS — that was an earlier design. The confirmed architecture only has two.

PatternWhat You LearnedWhy Not in This Pipeline
REST API ingestionPagination, rate limiting, scheduled pullsNo enrichment API in scope for fact_sales — but a real pattern for other projects
Neo4j / CypherNodes, edges, graph traversalProduct/customer relationships live in flat reference tables, not a graph DB

The takeaway: knowing more patterns than your current project needs is normal and valuable. For GlobalMart, only Lakeflow Connect + Autoloader touch Bronze.

Bronze Rules

  1. Never transform — land raw data as close to source shape as possible
  2. Autoloader tables always add audit columns: _ingested_at, _source_file
  3. Autoloader Bronze is append-only; Lakeflow Connect Bronze is the exception — it's upserted, and can't see a source DELETE
  4. All 6 tables are Delta format, regardless of pathway

Recap

Key Takeaways

Two Pathways

Postgres Lakeflow Connect + ADLS Autoloader — not four. Lakeflow Connect beats hand-rolled watermark JDBC on cost/complexity, but doesn't catch hard deletes; Auto Loader beats a plain read loop.

Different Write Patterns

Autoloader Bronze is append-only with audit columns. Lakeflow Connect Bronze is upserted — latest state only, no delete capture.

Six Tables

orders, order_items (Lakeflow Connect) + products, customers, addresses, payments (Autoloader) — all feeding fact_sales.
