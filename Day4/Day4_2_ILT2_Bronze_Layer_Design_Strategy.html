Bronze in the Medallion Architecture

Think of a restaurant kitchen: raw ingredients arrive at the receiving dock exactly as the supplier sent them. Nobody chops or seasons anything there — that happens later, in prep.

The Three Stations

  • Receiving dock (Bronze) — land it raw, ask questions later
  • Prep station (Silver) — wash, chop, standardise — "make it trustworthy"
  • Plated dish (Gold) — ready to serve — "make it useful"; this is where fact_sales lives
Sources → BRONZE → SILVER → GOLD → Consumers

BRONZE  = Raw ingestion layer
          "Land first, ask questions later"

SILVER  = Cleaned, conformed, enriched
          "Make it trustworthy"

GOLD    = Business-ready aggregates
          "Make it useful"

Bronze Is NOT a Staging Area

Common misconception: Bronze is a temporary holding area you delete once Silver is built. Wrong — Bronze is permanent.

Staging Area (wrong mental model)Bronze Layer (correct)
Temporary — deleted after processingPermanent — kept forever
No audit trailFull audit trail (when + from where)
No time travelDelta time travel across all historical loads
Can't reprocessCan always reprocess Silver from Bronze

Bronze is your insurance policy. If Silver has a bug, you don't go back to the source — you reprocess from Bronze. Faster, cheaper, and the source may have already changed.

Why Keep Bronze Forever? A Real Example

❌ Without Bronze

Silver job has a timezone bug → orders from 11 PM to 1 AM get the wrong date. Fix requires re-extracting from Postgres and re-requesting ADLS file history — painful, and the files may no longer be there.

✅ With Bronze

Correct the transformation, rerun Silver from Bronze. Problem solved — no re-extraction, no missing files, no dependency on the source system still having the data.

This is why every GlobalMart Bronze table is kept forever, regardless of pathway.

The 3 Golden Rules of Bronze

Every table GlobalMart writes to Bronze — CDC or Autoloader — follows the exact same three rules.

Rule 1 — Land Raw, Transform Never

✅ Bronze DOES

  • Append incoming data
  • Add audit columns
  • Store CDC events as-is
  • Preserve source column names
  • Handle schema evolution

❌ Bronze DOES NOT

  • Rename columns
  • Cast data types
  • Join with other tables
  • Filter rows
  • Aggregate or apply business rules

The only columns Bronze adds are audit columns — everything from the source lands exactly as it arrived.

Rule 2 — Idempotent Writes

Idempotent means running the ingestion multiple times produces the same result — no duplicates, no matter how many times a job reruns.

Run 1: products.csv → 12,000 rows in Bronze
Run 2: products.csv → same 12,000 rows (not re-processed)
Run 3: products_v2.csv → 12,040 rows (only 40 new rows added)

ADLS Autoloader

Achieved via checkpoint — tracks every file already processed.

Postgres CDC

Achieved via WAL offset — Lakeflow Connect tracks the last consumed event via the replication slot.

Rule 3 — Never Delete, Only Append

Both Pathways Are Append-Only in Bronze

  • Never delete rows from Bronze
  • If Postgres deletes an order → Bronze stores the DELETE event (a new row with _cdc_op = 'DELETE')
  • If a corrected products.csv is dropped → Bronze appends the new file's rows alongside the old ones
  • Silver handles MERGE / dedup to reflect the true current state

Neither pathway ever overwrites Bronze wholesale. There is no "full snapshot, overwrite daily" source in GlobalMart's real pipeline — every table here is naturally append-only.

Audit Columns — The Bronze Standard

Every Bronze table adds these during ingestion — deliberately minimal, not a kitchen-sink of "just in case" columns.

ColumnTypeValueWhich Pathway
_ingested_attimestampcurrent_timestamp()Both
_source_filestringcol("_metadata.file_path")Autoloader only
_cdc_opstringINSERT / UPDATE / DELETECDC only
from pyspark.sql.functions import current_timestamp, col

# Autoloader sources:
df = (df.withColumn("_ingested_at", current_timestamp())
        .withColumn("_source_file", col("_metadata.file_path")))

# CDC sources — _cdc_op comes from the CDC event itself:
df = df.withColumn("_ingested_at", current_timestamp())

Why Keep Audit Columns This Minimal?

A common instinct is to add _source_system, _batch_id, _load_type, and similar "just in case" columns to every table. GlobalMart's real build doesn't.

Every extra column is one more thing to keep correct across every ingestion script, forever. Add a column only when a real query will filter or group by it.

Why Each "Obvious" Extra Column Is Redundant Here

  • _source_file already answers "which pathway, which file, when" for Autoloader — the path itself encodes the source folder
  • _cdc_op already answers "what kind of change" for CDC — there's only one CDC source, so _source_system would be the same literal value on every row: zero information content

Table Naming — the Real, Live Unity Catalog Pattern

-- Fully qualified: CATALOG.SCHEMA.TABLE
gbmart.bronze.orders
gbmart.bronze.products
gbmart.silver.orders    -- cleaned
gbmart.gold.fact_sales  -- business-ready

Why No Source Prefix?

A common instinct coming from path-based storage is to encode layer and source into the table name itself (bronze_adls_products). In Unity Catalog, don't — the three-level namespace already carries that information.

gbmart.bronze.bronze_adls_products is redundant. Just gbmart.bronze.products — the schema already says "bronze," the catalog already says "GlobalMart."

Write Modes — Append vs Overwrite

Append — GlobalMart's Default, Every Table

Use append when the source produces an ordered stream of events or a new batch of rows. Postgres CDC events append; Auto Loader file rows append.

Overwrite would only apply to a full-state snapshot source with no event log — GlobalMart has none today. Know the pattern anyway; you'll meet it on other projects.

❌ Wrong: overwriting Bronze orders daily
   Day 1: 1,400,000 rows → Bronze = 1,400,000
   Day 2: 1,500,000 rows → Bronze overwritten
   Day 3: Day 1 bug found → CANNOT go back

✅ Correct: appending every day
   Day 1: 1,400,000 rows appended
   Day 2: 100,000 new rows appended
   Day 3: time travel back to Day 1 state
Section 6

CDC Bronze Design

CDC produces an event log — not the current state of the table. Bronze stores every event; Silver decides what "current" means.

What CDC Events Look Like in Bronze

_cdc_op  | _ingested_at          | order_id  | customer_id | ...
---------|------------------------|-----------|-------------|----
INSERT   | 2026-06-15 09:00:00   | ORD-001   | CUST-001    | ...
UPDATE   | 2026-06-15 10:15:00   | ORD-001   | CUST-001    | ...  ← status changed
DELETE   | 2026-06-15 12:30:00   | ORD-002   | CUST-002    | ...  ← cancelled

Bronze stores ALL events — it does not apply MERGE. For ORD-001, Bronze has 2 rows (INSERT + UPDATE); Silver's MERGE takes the latest event per order_id, so gbmart.silver.orders ends up with exactly 1 row for it.

Why Store Every Event? And What _cdc_op Means

Why Keep the Full Event Log

  1. Audit trail — see every change ever made to any order
  2. Replayability — Silver can be rebuilt with any version of the transformation logic
  3. Debugging — trace wrong Silver data back to the exact CDC event
  4. Compliance — financial regulations often require full event logs
_cdc_opMeaningSilver Action
INSERTNew rowINSERT into Silver
UPDATERow was modifiedMERGE (update) into Silver
DELETERow deleted at sourceMERGE (delete) or soft-delete flag

GlobalMart's 6 Bronze Table Designs

gbmart.bronze.orders:
  _cdc_op          STRING
  _ingested_at     TIMESTAMP
  order_id         STRING
  customer_id      STRING
  order_date       STRING  ← kept STRING, Silver casts
  ... (all source columns)
gbmart.bronze.products:
  _ingested_at     TIMESTAMP
  _source_file     STRING
  product_id       STRING
  product_name     STRING
  category         STRING
  ... (all CSV columns)

CDC pathway (orders, order_items) carries _cdc_op + _ingested_at. Autoloader pathway (products, customers, addresses, payments) carries _source_file + _ingested_at. Everything else is the entity's own source columns, untouched.

Recap

Key Takeaways

Permanent, Not Staging

Bronze is kept forever — your insurance policy if Silver ever needs to be rebuilt.

3 Golden Rules

Land raw, idempotent writes, never delete — every GlobalMart Bronze table is append-only.

Minimal Audit Columns

_ingested_at always, plus _source_file (Autoloader) or _cdc_op (CDC) — nothing without a real downstream use.
