1. The Core Idea

The Goal

Walk into class, explain the concept using the .html file, then run the matching .ipynb notebook live, top to bottom, with zero errors. Learners then replicate the same steps in their own Databricks accounts — that replication is the actual point of the bootcamp, not just watching you run it.

Every notebook is pre-built and working against the real GlobalMart data already sitting in the shared gbmart catalog. You are not building pipelines live in front of the class — you are demonstrating pipelines that already work, so class time goes to explaining why, not debugging why not.

2. How Files Are Organized — Naming Convention

One folder per day. Every topic inside a day is a matched pair — same base filename, two extensions — plus an optional .md for topics that also exist as a graded hands-on in the LMS.

Day{N}/
  Day{N}_{order}_ILT{x}_Topic_Name.ipynb    # the notebook you run live
  Day{N}_{order}_ILT{x}_Topic_Name.html     # the slide-deck explainer you present first
  Day{N}_{order}_HOL{x}_Topic_Name.ipynb    # hands-on lab (learners rebuild this themselves)
  Day{N}_{order}_HOL{x}_Topic_Name.html     # HOL instructions, same visual style
  Day{N}_{order}_HOL_Topic_Name.md          # only where an LMS-graded hands-on exists
  Day{N}_{order}_REF_Topic_Name.html/.ipynb # cert-prep content — concept only
  Day{N}_{order}_DEMO_Topic_Name.ipynb/.html # instructor demo, not a graded lab

2. File Organization — Sort-Order Fix & Standalone Modules

New as of 2026-07-04: every file in every day folder now leads with an {order} digit — its position in that day's teaching sequence. All ~50 HTML files across Day 1–12 (and their matching notebooks) were restyled to this slide-deck format and renamed with this prefix on this date.

Why: plain alphabetical sort puts DEMO and HOL before ILT (D, H < I) and REF after (R > I) — so a file browser used to list a hands-on or reference file before the concept session that introduces it. The numeric prefix forces file-browser sort order to match teaching order, every time.

Two different numbers — don't confuse them

The leading {order} sequences everything in the day. The trailing {x} in ILT{x}/HOL{x} still sequences within that type only — always teach ILT1 before ILT2, etc., since later ones often depend on earlier ones. When a day has only one of a type, {x} is dropped (e.g. Day 1's HOL, Day 3's DEMO and REF).

Not every ILT is pipeline-flow content. A handful of sessions are deliberately standalone modules — real Databricks/DE knowledge in GlobalMart flavor, but not wired into the Bronze→Silver→Gold narrative and not required for later days. Day 2 ILT/HOL 3 (Code Versioning) was the first; Day 10 ILT 2/3 (orchestration) and the Day 11/Day 12 ILT sessions (Section 6) follow the same pattern. Teach these in a different order, or skip one under time pressure, without breaking the main pipeline story.

3. Running One Teaching Session, Step by Step

  1. Open the .html file first in a browser (double-click it, no server needed) and present it like a slide deck — it already contains the concept, the diagrams, and the real table/column names you'll see in the notebook, so there are no surprises.
  2. Open the matching .ipynb in your Databricks workspace and attach it to a running cluster.
  3. Run every cell top to bottom, live. Every notebook in Day 1–Day 12 has been verified to run clean — the pipeline-accurate ones against the real gbmart catalog, the standalone concept ones in plain Python/read-only SQL — if a cell errors, that's a workspace/permissions issue to fix, not an expected part of the demo.
  4. Narrate the comments, not the syntax — every cell has a comment explaining why that step exists, so read that aloud before running the cell rather than explaining PySpark mechanics line by line.
  5. For HOLs, hand off to learners after your walkthrough — they rebuild the same steps in their own catalog/schema. Where a notebook says main.YOUR_SCHEMA or similar, that's the one line each learner edits to point at their own workspace.
  6. Never re-run a "build" HOL twice against the same shared table expecting the same result unless its markdown explicitly says it's idempotent (MERGE-on-key or overwrite) — a few labs use SHALLOW CLONE specifically so they're safe to rehearse repeatedly (see Section 5).

4. fact_sales — Grain, Measures & Dimensions

Grain & Measures

Grain: one row per order_item; joins dimensions by natural key, not surrogate key — a deliberate simplification in the real build, taught as-is. The only surrogate key fact_sales generates is its own row identity, fact_sales_sk.

Measures: Quantity_purchased, Sales_amount (additive); Actual_price, Discounted_price (non-additive — never SUM/AVG directly).

Dimensions (6)

dim_customer, dim_product, dim_date, dim_address, dim_payment_method, dim_orders — all 6 have a proper surrogate key, but fact_sales doesn't use any of them (natural-key joins instead).

Note on naming: globalmart_problem_statement_architecture (1).html (the original brief) uses more generic table/column names than the real workspace does. Where the two disagree, every notebook follows the real gbmart workspace, since that's what learners will actually see when they explore the catalog — the architecture doc is the concept story, gbmart is the ground truth.

5. Safety Rules Already Built Into These Notebooks

🔁 SHALLOW CLONE / practice schema for repeatable HOLs. Any HOL centered on MERGE/SCD/CDF/OPTIMIZE against a table other cohorts also touch (e.g. Day 9 HOL 2, Day 10 both HOLs) first runs CREATE TABLE ... SHALLOW CLONE or builds in a personal main.YOUR_SCHEMA. Real data and mechanics, but a version history that's entirely yours.

🚫 No live pipeline/cluster/job spend. Nothing in this repo starts, triggers, or schedules a real Databricks pipeline, job, or SQL warehouse. Day 9 HOL 2 Part 2 only verifies the real orders_data_ingestion_cdc pipeline — it never re-triggers it. Day 10/11's orchestration and cost sessions teach job/cluster config as inspectable Python dicts, never submitted to a real API.

👀 Sayli's account — read-only, one-time port. A colleague's already-working implementation of this pipeline was exported read-only once and used as the accuracy reference for real-pipeline notebooks. Nothing in this project writes to or triggers anything in her account — her code was copied statically, then commented for teaching, not called live.

✅ Idempotent by default elsewhere. Builds that aren't clone-based (e.g. Day 4/5 Bronze/Silver builds) use overwrite or key-based MERGE, so re-running them in rehearsal reproduces the same end state rather than duplicating rows.

🔒 Governance demos never touch real gbmart security. Day 12 ILT 1's row-filter/masking demo creates its own practice table and functions in main.YOUR_SCHEMA — it never attaches a filter, mask, or grant to a real gbmart.* object. That would silently change what every other student and the instructor sees, mid-class.

📊 Metadata reads only, for cost/system-table checks. Day 11 ILT 2's cost-awareness session reads real, live SHOW CATALOGS output and attempts system.billing.usage/system.compute.clusters (wrapped in try/except, since those usually need admin access) — always read-only, never a cluster-creation or resize call.

7. Lessons From This Build — Worth Knowing Before You Extend It

Day 6 incident: resolved. Earlier in this build, a background subagent thought to have failed instead silently auto-resumed hours later with a stale, pre-verification mental model and overwrote 3 of Day 6's 4 files (wrong catalog name, only 5 dimensions, wrong measure names). It has since been fully rebuilt from Day 7's real, untouched dependency contract plus the original teammate's verified real pipeline code, and independently re-verified cell by cell — zero stale references remain, all 6 dimensions are present and correctly named, and every cross-file reference between Day 6 and Day 7 checks out.

Never trust a subagent's self-report alone

A "failed" or "completed" status from a background agent isn't proof of what actually landed on disk. The Day 6 incident was only caught because the content itself looked wrong on a direct read — not because of any failure signal. Independently re-open and check any file an automated process touched: JSON/HTML validity, a safety-pattern search, and at least a skim of the actual content, every time — especially before teaching from it.

"4 sources" is a trap — GlobalMart really has 2. An earlier design draft described 4 ingestion source systems (Postgres, a REST API, Neo4j, ADLS). The confirmed architecture has only 2 real ones (Postgres CDC + ADLS Autoloader) — Day 3's API/GraphDB content is an intentional side-exploration that never reaches Bronze. This mistake resurfaced once already while building Day 10/12's standalone modules and had to be corrected across two files — if you ever see "4 sources" stated as architectural fact anywhere in future material, treat it as a bug to fix, not a fact to repeat.

A different-looking style exists in reference for making the hands/ — but that folder is LMS export output, not the import format, and using it will fail import.

Confirmed by an actual failed→fixed import test: resetting numbers per scenario or omitting frontmatter both throw real import errors ("Duplicate input number", "'name' is required"). Copy Day1_5_HOL_PySpark_SparkSQL_ADLS.md's structure exactly for any new one.
